### Plugin: `git-harness`

| Skill | Command | Description |
|-------|---------|-------------|
| Commit-PR | `/commit-pr` | 커밋·push·PR 생성·PR 리뷰 단일 파이프라인. §0.1 상태 파악(조용히) → §0.2 진입점 질문(commit/push/pr에 상태 근거 (추천) 표시, pr은 기존 PR 지정/새 PR 생성으로 분기) → §0.3 모드별 전제 조건 검사(보호 브랜치·대상 존재·secret·gh 인증, **기존 PR 리뷰엔 보호 브랜치 검사 미적용**) → §9 커밋 전 리뷰 레인(9.1 /simplify 문의 → 9.2 `code-simplifier` 서브에이전트+재스테이징(폴백 2단) → 9.3 코드리뷰 문의 → 9.4 코드리뷰 서브에이전트(correctness·security·performance·readability, verdict CONFIRMED/PLAUSIBLE)) → **커밋 게이트**(치명=correctness&CONFIRMED, 중요=correctness&PLAUSIBLE 또는 그 외&CONFIRMED → 차단 / 경미=그 외&PLAUSIBLE → 통과. 요약: correctness이거나 CONFIRMED면 차단, 수정→재스테이징→재리뷰) → §1~§4 커밋 메시지(`이슈번호 type: 제목`·한국어 명령형·본문 기본 생략·`Co-Authored-By` 금지) → §5 프리뷰 승인 후 `git commit --cleanup=whitespace -F -`(stdin, 고정 경로 금지) → §6 push(통보만) → §7 PR 생성(타겟 추천·프리뷰는 "이 제목·본문으로 맞나요?") → §8 PR 리뷰 여부 문의(진입점 승인의 명시적 예외, 내장 `/review` Skill 명시 호출) → 종료 요약. **진입점 선택 = 이후 단계 승인**(예외 ① 되돌리기 어려운 행위 직전 *내용* 확인 ② §8) |

> **(2026-08-02 v0.3.0)** 기존 `commit`·`review-to-pr` 두 스킬을 `commit-pr` 하나로 통합했다. 커밋~PR은 원래 한 줄기 작업인데 스킬이 쪼개져 있어 사용자가 매번 다음 스킬을 다시 불러야 했다. 핵심 변경 — ① **상태 기반 진입점 추천**(질문 전에 `git status`/`branch`/`log`/`log @{u}..HEAD`/`gh pr view`를 조용히 실행하고 **명령 실패도 판단 근거**로 읽어 각 항목에 (추천)+이유 한 줄) ② **진입점 선택 = 이후 단계 승인**(중간에 "push할까요?"·"PR 만들까요?"를 되묻지 않음 — 흐름만 끊고 정보를 더하지 않으므로. 예외는 되돌리기 어려운 행위 직전의 *내용* 확인과 §8 PR 리뷰 실행 여부뿐) ③ **커밋 차단 게이트**(리뷰어에겐 흔들리는 5단계 severity 대신 답할 수 있는 2값 verdict만 요구하고, severity 환산은 결정론 표가 맡는다. correctness이거나 CONFIRMED면 차단 → 수정·재스테이징 후 **재리뷰**로만 통과 판정, 자기보고 불신) ④ **게이트는 경고이지 거부권이 아님**(사용자가 의도된 것이라며 진행을 택하면 무엇을 안고 가는지 남기고 따른다) ⑤ 모드별 전제 조건만 검사(기존 PR 리뷰엔 보호 브랜치 검사 미적용 — 쓰기가 아니므로) ⑥ 커밋은 `--cleanup=whitespace -F -`(본문 `# 요약` 헤딩이 주석으로 삭제되는 것과 고정 경로 임시파일의 병렬 세션 충돌 방지). 스킬 본문은 흐름·게이트만 담고 상세는 references 3종(`commit-message.md`·`review-lane.md`·`pr-creation.md`)에 둔다. **경계** — 저장소 상태를 바꾸지 않는 상류 산출물 검수(`review-harness`)·완성 코드 정적 리뷰(`frontend-harness` `/review`)·하네스 자체 진단(`meta-harness`)은 범위가 아니다.

> `meta-harness`는 "Meta-Harness: End-to-End Optimization of Model Harnesses"(arXiv 2603.28052v1)를 토대로, **압축 요약이 아닌 full-trace experience store**(repo-wide 기본 `.claude/experience-store/`, plugin opt-in `.claude/plugin-store/{target}/`)를 proposer가 직접 `grep`/`cat`으로 조회하는 것을 핵심으로 한다(논문 Table 3: full-trace가 요약 기반보다 우월). 4명의 에이전트(`trace-capturer`, `failure-diagnostician`, `pareto-refiner`, `experience-historian`)를 서브에이전트로 spawn한다(모두 `model: "opus"`). 모든 패치는 **사용자 승인 게이트** 후에만 적용한다. 추가로 **self-heal 캡처 훅(`UserPromptSubmit`)** 이 사용자의 '수정/보강/방향전환' 발화를 세션 중 `signals/*.jsonl`에 원형 적재하고(캡처 전용·비차단·요약 금지), 추후 회차의 healer가 Phase 1 warm-start로 누적 신호를 끌어와 진단·패치에 쓴다(적용은 승인 게이트 후). **(2026-06 v0.3.0)** 데이터 적재(신호 캡처)와 지침 보강(patch 설계)이 자족 reference `references/data-capture-criteria.md`(C1~C9 적재 기준 + CLAUDE.md/Skill/hook/rule 메커니즘 선택, 1차 출처 인라인)를 operative하게 따르도록 additive 배선했다 — 묶음 캡처·요약 금지·그 순간 기록·프로젝트 최상단 모음·strong/weak 신호 등급·고칠 곳(전역 메모리 포함)+이름 통일·검증 후 재사용, 반복 무시 규칙→hook 전환(③ 장치화). 훅은 흔한 한국어 교정어 포착 확장·신호 등급·git-root 모음·status를 더했고(캡처 전용·exit 0 불변), 승인 게이트·Pareto 비후퇴·full-trace 보존은 그대로다. 1차 출처(Anthropic context-engineering·best-practices·hooks·steering blog)는 deep-research가 3-0 확인을 보고(과정 보고; arXiv 2606.13174/2505.16067/2603.07670은 기준 문서 근거 인용, 재검증 안 함). **(2026-06-28 v0.4.0)** 결정론 근거를 hook/permission으로 **1급 라우팅**하도록 additive 배선 — 진단이 enforcement 성격을 먼저 분류(`enforcement_class`: deterministic-enforce/record/judgment)해 매번 반드시 일어나야/막혀야 하는 근거는 advisory 본문(CLAUDE.md/Skill)이 아니라 hook/permission으로 **첫 발생부터** 보내고, hook이면 신규 자족 reference `references/hook-lifecycle.md`(공식 hooks 라이프사이클 distill: 전체 event·상황→event 선택·record(exit0)/enforce(exit2·deny)·config·matcher)로 상황에 맞는 event를 고른다. 배치는 경계 유지(플러그인 hook=plugin 모드 in-boundary·repo-wide면 hook_spec 동봉 scope-escalation; `.claude/settings.json`은 직접 수정 않고 `update-config` 핸드오프). 자체 라이프사이클 훅으로 SessionStart `warm-start-nudge`(미소비 strong 신호 표면화, 주입 전용·근사치·env 비활성) 추가. **정직성 정정**: `.claude/rules`는 결정론이 아니라 advisory(결정론 강제는 hook·permission뿐). 안전 불변(승인 게이트·Pareto 비후퇴·full-trace·exit 0·settings.json 직접수정 금지) 그대로. 1차 출처(code.claude.com hooks·hooks-guide·memory·skills·settings + steering blog)는 등급(VERBATIM/요약/추론)과 함께 플러그인 내 `references/hooks-grounding.md`(provenance)에 보존, 지침 .md는 URL 인라인.

| Skill | Command | Description |

| Product Spec | `/product-spec` | 기획자(PM)용 **기획문서(PRD) + 사용자 스토리 + 인수조건** 작성·검증 + **기획 완성도 점검(DoR)(생성 전 선행)** 진입 오케스트레이터. 개발 착수 *전* 단계, 도메인 무관 인터랙티브. 7 Phase 구성 (입력 모드 R 재갱신 재진입 / A 기획안 / B 인터뷰 — R을 먼저 판별):

- **Phase 0 요구/문제 정의(Discovery)** — `requirements-analyst`. 기획안이 있으면(모드 A) 전문에서 **문제 정의 카드**(고정필드: problem / target_users / goals(비즈니스·사용자) / constraints / success_metrics(관찰형))를 **추출**하고 모호 필드만 한 번에 1질문 보강. 없으면(모드 B) 한 번에 한 질문 인터뷰. 승인 게이트.
- **Phase 1 기획 완성도 점검(DoR)(모드 A 진입질문 필수·생성 전 선행)** — `dor-evaluator`. PRD·스토리 생성 *전*, 모드 A에선 **진입 질문을 반드시 제시**하고(생략·자동 스킵 금지) 사용자 동의(예/모호한 긍정) 시 **원본 기획안**을 기획 완성도 점검(DoR)으로 평가 — 기획 완성도 게이트(DoR 게이트) · 좋은 스토리 6가지 기준 점수표(INVEST 스코어카드; Testable·Independent=0이면 차단) · 조건·행동·결과(Given-When-Then) 완결성(정상/경계/에러/빈/권한) · 모호성 점검 · 의존성/계약 참조. `# 기획 완성도 점검 결과(DoR Review)` + **보완할 점 점검표(보강 체크리스트)**(충족=`[O]` / 미충족=`[ ]`+보강 예시)를 **채팅으로 제시**하고 그 보강점을 이후 PRD·스토리에 반영. 방법론은 `references/dor-review-rubric.md`에 **내재화**(외부 플러그인 참조·의존 없음 — 단독 설치로 독립 동작). 파일 저장은 사용자가 선택할 때만(`.claude/_docs/<슬러그>/product-spec-review.md`) — **보완 문답에서 건너뛴 항목이 1건 이상이면 Phase 1 직후, 0건이면 마무리**에 묻고 한 번 답한 질문은 반복하지 않는다. ([references/dor-review-rubric.md])
- **Phase 1.1 기획안 보완 문답(생성 전 · 오케스트레이터 소유)** — 점검표 제시 직후 **PRD·스토리·인수조건 중 어느 것도 만들기 전에** 보완 여부를 3지선다로 묻는다(기존 Phase 1 종료 게이트를 **대체** — 게이트 총량 불변). (1)이면 미충족 항목을 **하나씩**(묶음 질문 금지) 묻고 **매 질문에 `건너뛰기`·`전부 건너뛰기`** 선택지를 준다. 답변 처리는 닫힌 5종(응답 / 건너뜀+사유 / 일괄 건너뜀 / 모호는 1회 재질문 후 건너뜀 / 게이트 (3) '나중에 보완' → `건너뜀(나중에 보완)` 일괄). **건너뜀을 '보완됨'으로 승격 금지**, 진척은 `응답 n건·건너뜀 n건` 계수뿐, 보완 대장은 반영 대장 4열에 흡수(원문은 각주 · **대장에 Given-When-Then 문장 금지**), **보완 후 `dor-evaluator` 재호출·INVEST 총점·3단 판정 재산출 금지**. 모드 B는 Phase 0 카드 게이트 문장이, 평가 거절 경로는 §1.1-N 게이트가 대신한다.
- **Phase 2 기획문서(PRD) 작성·확정 (계획 → 설계 → 비평 루프)** — `prd-planner` → `prd-designer` → `prd-critic`을 한 회차로 순차 호출한 뒤 사용자가 확정을 선택할 때 기록한다. **섹션 소유권 분리** — 계획이 §1 배경·문제 / §2 목표·성공지표(관찰형) / §3 범위(In·Out 명시), 설계가 §4 핵심 요구사항(`FR-n`/`NFR-n`) / §5 가정·리스크 / §6 마일스톤을 소유하고, 비평은 **쓰기 권한 0**(읽기 전용 지적만). **본문 단일 소유권** — PRD 문자열은 오케스트레이터가 보유하고 에이전트는 섹션 패치만 반환한다. **게이트 총량 불변식** — Phase 2가 추가하는 승인 게이트는 회차당 정확히 1개(① 확정 / ② 한 번 더 / ③ 지정 항목만)이고 그 앞에 확인 질문이 최대 1개 붙을 수 있으며(질문은 게이트가 아니다), 하위 단계 사이에는 게이트가 없다. **루프 중 파일 생성 금지**(기록은 확정 후 미리보기 승인 1회). 설계는 **기획 설계**(D1~D12: 요구 원자성·ID / 기능·비기능 분리 / 범위↔요구 쌍방 매핑 / 여정 단계 / 상황·전이 / 예외 5종 제품 규칙 / 업무 규칙 / 정보 항목 / 권한 / 의존 / 가정↔요구 연결 / 마일스톤 완료 판정)이며 **기술 아키텍처(API·데이터 모델·컴포넌트·상태관리·캐싱)와 스토리 문장은 산출 금지**. 비평은 렌즈 **C-1~C-7**(문제–목표 정합 / 범위 경계 / 지표 관찰성 / 요구 완결성·원자성 / 예외 공백 / **근거 추적·발명 감사** / 보강점 반영 감사(점검표가 있을 때만))에 **원문 인용 필수**, **차단 사유 닫힌 4종**(Out 공백·판정불가 지표·요구 ID 누락중복 또는 In 미전개·출처 없는 수치), **처리분류 A/B/C**(B=사용자만 아는 사실 → 고치지 말고 `[확인필요]`; B를 A로 처리하면 발명), **정체 가드 G1~G3**, 회차당 12건 상한(절단 시 건수 표기). **비평에 확정 거부권 없음** — 사용자가 확정을 고르면 잔존 지적을 부록 B `[미해소 지적]`으로 기록만 하고 즉시 따른다. 확정 후 쓰기 전 미리보기 승인. ([references/prd-template.md] · [references/prd-design-checklist.md] · [references/prd-critique-lenses.md])
- **Phase 3 사용자 스토리 도출** — `story-writer`. Phase 2.2 설계가 남긴 여정·상황·예외 제품 규칙·권한 표가 시나리오의 1차 재료(설계는 목록까지, 문장화는 여기서). PRD 요구사항(`FR-n`/`NFR-n`)→스토리("…로서 …하고 싶다, 왜냐하면 …") + 좋은 스토리 6가지 기준(INVEST) 자가점검 + `[인수조건 인계]` 메모. **조건·행동·결과 문장은 쓰지 않는다**(Phase 5 단독 소유·단일 원본). Phase 1 보강점(예외 흐름 등) 반영. ([references/user-story-guide.md])
- **Phase 4 1차 적대적 검증(PRD↔스토리)** — `spec-reviewer`. 대상은 **PRD와 스토리 *사이***이며 Phase 2에서 **사용자에게 제시된 항목**(비평 지적 목록·반영 대장·부록 B)을 **스토리 증거 없이 재지적하지 않되, 제시된 적 없는 §1~§6 문장(절단·미점검분)은 정당한 대상**이다. **칭찬형 금지**: 요구↔스토리 추적 매트릭스(완전성) · 좋은 스토리 6가지 기준(INVEST) 통과 · 목표↔요구↔스토리 일관성 · 모호/판정불가 문장 색출. **인수조건 관찰성·흐름 커버리지는 이 단계 축이 아니다**(그 시점엔 대상이 없다 — Phase 6 소유). **리포트는 채팅 제시만**(파일 없음), 결함은 additive-first로 PRD·스토리에 반영.
- **Phase 5 인수조건 작성** — `acceptance-writer`. 확정 스토리를 **조건·행동·결과(Given-When-Then)** 시나리오로 전개해 **`acceptance-criteria.md`(최종 산출물)** 를 만든다. **인수조건 1개 = 단일 관심사 1개**(서로 다른 관심사·트리거는 시나리오를 쪼갠다; 같은 관심사의 분리 불가한 다중 관찰점은 한 Then 허용). 스토리마다 **정상 + 해당 예외 흐름 5종**(경계·에러·빈 상태·권한·상태 전이)을 덮고 묶음 끝에 `(흐름 커버: …)` 1줄, 해당 없으면 `해당 없음 — (사유)`로 **누락과 의도된 제외를 구분**. Then은 관찰 가능해야 하고(판정 체크: 두 사람이 같은 화면·로그로 동일 결론) `AC-<스토리번호>.<일련번호>` ID에 출처 `US-n`을 연결해 **스토리↔인수조건 추적 표**를 만든다. **예외 흐름 정책·수치를 발명하지 않는다** — 입력에 없으면 `[확인필요]`(빈 곳 지적은 하네스 일, 정책 결정은 기획자 일). **단일 원본** — 조건·행동·결과 문장은 이 파일에만 두고 `user-stories.md`에 중복하지 않는다. 쓰기 전 미리보기 승인. ([references/acceptance-criteria-guide.md])
- **Phase 6 2차 적대적 검증(스토리↔인수조건)** — `spec-reviewer` 2차 호출. 스토리↔인수조건 추적(빠짐·고아) · 인수조건 관찰성 · 단일 관심사 위반 · 흐름 커버리지 · **누락 시나리오 마이닝**(5흐름 축, 정책 발명 없이 빈 곳만 지적). 1차에서 제시된 PRD↔스토리 항목을 **인수조건 증거 없이 재지적하지 않는다**. **채팅 제시만**(파일 없음) — 결함은 `acceptance-criteria.md`에 흡수.
- **마무리 §1 재갱신 경로(조건부)** — 문서 생성 후 기획안이 보완되면 Phase를 새로 만들지 않고 **기존 Phase 2·3·5를 지정 범위로 재호출**한다. R0 진입(자발 발화는 세션당 1회) → R1 델타 수집(§1.1과 같은 규약 — 하나씩·건너뛰기) → R2 영향 범위 **닫힌 4라벨**(R-A 요구/범위/스토리 집합 · R-B 예외 흐름 정책·마커 · R-C 문구만 · R-0 문서에 자리 없음, 경계 모호 시 상위 승격) → R3 **상류→하류 고정**(PRD→스토리→인수조건) + **델타 모드 계약**(전체 재생성 금지·변경 블록만·`story-writer` 재조립은 `[재조립 제안]` 후 승인 시에만) + **ID 동결**(`FR-n`/`NFR-n`/`US-n`/`AC-n.m`은 주소 — 스토리가 갈려도 AC ID 불변, 현재 출처는 `출처: US-n`이 정본) → R4 **참조 대조(ID 기계 대조·자기보고 — Phase 4·6을 대체하지 않음)** + **쌍 규칙 재검증**(PRD·스토리 중 한쪽이라도 갱신되면 1차 / 스토리·인수조건 중 한쪽이라도면 2차, 전수 전환은 닫힌 3종) → R5 이력(PRD 부록 A 정본) → R6 종료 조건 T1~T6 → R7 종료 보고. **재갱신 비평은 지정 항목 + C-2·C-4·C-6**(발명 감사 강제 ON — 새 값이 처음 들어오는 유일한 통로).
- **마무리 §2 저장(opt-in)·§3 산출물 요약** — 산출물은 `.claude/_docs/<기획서 슬러그>/`(기획서별 폴더)에 모은다. Phase 1 기획 완성도 점검(DoR) 결과 + **§9 보완 문답 기록**은 사용자가 저장을 선택할 때만 `product-spec-review.md`로 저장(즉시 저장 안 함 · **건너뜀 1건 이상이면 Phase 1 직후에 묻고 마무리에서 반복하지 않음**). **이 하네스가 만드는 파일은 `PRD.md`·`user-stories.md`·`acceptance-criteria.md`·`product-spec-review.md` 넷뿐**이며, 1차·2차 적대적 검증 리포트는 채팅으로만 제시하고 파일로 남기지 않는다.

> `product-spec-harness`는 **개발 전 제품 기획 산출물(PRD·사용자 스토리·인수조건) 작성 + 생성 전 기획안의 기획 완성도 점검(DoR)**에 특화한 도메인 무관 인터랙티브 하네스다. 8명의 에이전트(`requirements-analyst`, `dor-evaluator`, `prd-planner`, `prd-designer`, `prd-critic`, `story-writer`, `acceptance-writer`, `spec-reviewer`)를 서브에이전트로 spawn한다(모두 `model: "opus"`; Phase 순차, Phase 2는 계획→설계→비평 한 회차, `spec-reviewer`는 Phase 4·6 **2회** 호출로 대상이 다르다). 내재화 원칙 — 승인 게이트(미리보기 후 쓰기) · 관찰형 인수조건(조건·행동·결과(Given/When/Then)) · 요구↔스토리 완전성 추적 · 적대적 검증 2회(채팅 제시만·파일 없음) · 기획 완성도 점검(DoR) 내재화(생성 전 선행, 저장 opt-in, Honesty Guardrail·2025+ 근거) · **PRD 확정 루프(계획→설계→비평, 섹션 소유권·회차당 게이트 1개·비평 거부권 없음)** · **인수조건 단일 원본**(조건·행동·결과 문장은 `acceptance-criteria.md`에만) · additive-first · 한 번에 한 질문. **네 점검의 대상·축 분리(중복 금지)** — Phase 1은 *사용자가 준 원본 기획안*(착수 준비도), Phase 2.3은 *이번 회차 PRD 초안 §1~§6*(계획의 내적 강건성, 스토리 없음 → 스토리·INVEST·커버리지 축 금지), Phase 4(1차)는 *PRD + 스토리 사이*(요구↔스토리 추적·정합; 인수조건이 아직 없으므로 완료 판정 축은 다루지 않음), Phase 6(2차)은 *스토리 + 인수조건 사이*(빠짐·고아·관찰성·단일 관심사·흐름 커버리지)이며, Phase 4는 Phase 2에서 **사용자에게 제시된 항목**(비평 지적 목록·반영 대장·부록 B)을 스토리 증거 없이 재지적하지 않되, **제시된 적 없는 §1~§6 문장(절단·미점검분)은 정당한 대상이다**. **정직성** — 루프의 품질 개선 효과를 측정하지 않으므로 주장은 '지적과 그 처리 결과가 문서에 남는다'까지로 한정하고(루프 이력=변화의 기록이지 개선의 증거 아님), 점수·백분율·성숙도 등급을 산출하지 않으며(`n건` 카운트만 — 유일 예외는 Phase 1의 INVEST 점수표와 그 총점에서 나오는 3단 착수 판정(착수가능/보완 후/보류)으로, 입력 기획안 준비도 신호이지 산출물 품질 등급이 아니다. 금지 대상은 하네스가 산출물에 매기는 평가 점수·등급이지 PRD 본문의 성공지표 수치가 아니다. Phase 4 게이트의 백분율도 `전체 요구 {t}건 중 미커버 {k}건` 건수 표기로 교체), 닫힌 차단 목록의 트레이드오프(종료 보장 ↔ 주관적 중대 결함 미차단)를 숨기지 않는다. **보완·재갱신의 정직성** — 보완 문답과 재갱신이 산출물 품질을 얼마나 높이는지 측정하지 않으므로 주장은 '무엇이 채워지고 무엇이 `[확인필요]`로 남았는지가 문서에 남는다'까지로 한정한다. `기준 입력 v{N}`은 **식별자이지 등급·점수가 아니고**, 보완 후 INVEST 총점·3단 판정을 **재산출하지 않는다**(재채점하면 점수 차이가 성숙도 등급처럼 읽힌다). **알려진 한계** — `product-spec-review.md`가 opt-in이라 저장을 거절하면 항목 단위 이력(§8 3값·§9)이 사라지고 배치 단위 비교(PRD 부록 A)만 남으며, ID 동결의 대가로 `AC-n.m` 접두 숫자가 현재 출처 스토리와 달라질 수 있다(니모닉을 주소 안정성과 맞바꿨고, 종료 보고에 매번 표기한다). 산출물은 `.claude/_docs/<기획서 슬러그>/`에 모은다. **독립성** — 단독 설치로 동작하며 다른 마켓플레이스 플러그인을 참조·의존하지 않는다(기획 완성도 점검(DoR) 평가 방법론 + PRD 확정 루프의 기획 설계 점검표·비평 렌즈를 모두 플러그인 내부 references에 내재화). **경계** — 프론트엔드 화면 구현·기술 설계용 PRD·구현 요구사항·코드 작성, 코드/하네스/커밋 작업, *이미 완성된* 상류 산출물을 핸드오프 게이트로 검수만 하는 작업은 범위가 아니다(트리거 충돌 방지를 위해 description·trigger-eval에 명시).

| Loop Engineering | `/loop-engineering` | 검증 가능한 목표를 향해 한 작업을 **자율 반복(loop)으로 완성**하는 진입 오케스트레이터. 실행 루프(① 목표 → ② 실행 → ③ 검증 → ④ 실패시 수정 → ⑤ 통과시 종료)와 지속학습 루프(실패 → 조사 → 검증 → 정립 → 참조)를 결합한다. Phase 0 목표 설계(Goal Card 승인 게이트, auto/gated 확정) → Phase 1 자율 반복(Execute→Verify→(FAIL)Diagnose→Distill). 중단조건(통과·최대 반복·무진전·예산)으로 무한 루프를 막는다 |

5개 에이전트 구성 (모두 `model: "opus"`):

- **Goal** — `goal-setter`. 모호한 요청을 **검증 가능한 목표(Goal Card)** 로 변환 — 관찰형 성공기준 + *실행 가능한* 검증 방법 + 중단조건(최대 반복·무진전·예산) + 범위(In/Out). "루프는 검증기만큼만 좋다"가 제1원칙.
- **Execute** — `loop-executor`. 목표를 향한 **1회 반복**. 2회차+엔 메모리의 관련 교훈을 consult하고 직전 개선안을 적용해 검증기를 통과시킬 **최소 변경 1개**(confound 격리)를 시도.
- **Verify** — `loop-verifier`. 검증 방법을 **실제로 실행**해 기준별 **엄격 PASS/FAIL + 증거**. 적대적(먼저 실패할 이유를 찾음), 증거 없는 PASS 금지.
- **Investigate** — `failure-analyst`. FAIL 시 **재시도 전에 root cause**를 진단(증상 ≠ 원인) → trace 증거로 **사실로 전환** → **다음 반복의 접근을 직접 작성**(사람이 아니라 에이전트가 개선 프롬프트를 씀). 같은 원인 M회면 무진전 → 구조 변경 권고.
- **Distill/Consult** — `memory-curator`. *검증된* 교훈만 **distill**해 `lessons.md`에 쌓고, 다음 반복에 관련 규칙만 **surface(consult)**. raw 반복 trace(`iterations.jsonl`)는 보존(요약 금지).

> `loop-engineering`은 **주어진 작업을 검증 루프로 완성**하는 데 특화한 도메인 무관 멀티 에이전트 하네스다. 5명의 에이전트를 서브에이전트로 spawn한다(모두 `model: "opus"`). 루프 메모리는 `.claude/loop-memory/{goal-slug}/`(goal.md / iterations.jsonl / lessons.md)에 누적되어 회차·세션을 넘어 학습한다(continual learning). **경계** — 하네스 자체 진단·개선(meta-harness)·새 하네스 생성(harness-generator)·기획문서(product-spec/frontend)·커밋/PR 리뷰(git-harness)·native `/loop`(시간 간격 폴링)은 범위가 아니다. native `/goal` 위에 검증기 설계·재시도 전 진단·지속학습 메모리·무진전 감지를 구조화해 얹은 버전으로 위치한다. **(2026-06 심화)** Osmani "Loop Engineering" 원전을 additive 반영 — 여섯 빌딩블록(factory model: automations·worktrees·skills·plugins/connectors·sub-agents·external memory) 중 skills(하네스 자체)·sub-agents·external memory를 *기본 구현*으로(sub-agents는 실제 검증을 실행하는 강한 verifier로), 나머지를 코어 흐름 불변의 *opt-in 레인*으로 framing하고, 기계 검증이 막지 못하는 사람-쪽 결함(comprehension rot·cognitive surrender·orchestration tax)에 stay-the-engineer 가드(merge 전 diff 이해 게이트 green CI≠구현·병렬 review-bandwidth 상한·loop-verifier reward-hacking 경계)를 더했다(현재 기능 전부 보존, principles §8 / research dossier §9).

4개 에이전트 구성 (모두 `model: "opus"`):

- **Scope** — `context-scoper`. 작업이 모델에 *반드시 도달해야 할 정보*와 *토큰 예산*을 정의. retrieval need를 must/nice/out으로 분류하고 각 need에 '왜 필요한가'를 붙임(컨텍스트는 많을수록 좋은 게 아니다).
- **Retrieve/Generate** — `context-retriever`. retrieval need(특히 must-have)를 충족하는 후보 컨텍스트를 RAG식으로 수집·생성. 출처·relevance·토큰·충돌을 표기하고 must-have 미충족은 생성으로 메우지 않고 보고.
- **Process** — `context-processor`. 예산 안으로 압축·정렬·중복제거. 전면 재작성 금지(디테일 보존 구조적 증분), 가장 중요한 컨텍스트를 앞·뒤 배치(lost-in-the-middle 대응), 충돌은 둘 다 보존·표시.
- **Manage** — `context-curator`. 진화하는 playbook으로 큐레이션(generation/reflection/curation), context-collapse 가드, (멀티 에이전트면) REGISTRY(≤200토큰 상태요약)/FOCUS(a_i) 격리, 최종 페이로드 검증(예산·must-have·출처·위치) 후 출하.

> `context-engineering`은 **모델에 들어갈 정보 페이로드의 조립·최적화**에 특화한 도메인 무관 하네스다. 4개 에이전트를 서브에이전트로 spawn한다(모두 `model: "opus"`; Scope→Retrieve→Process→Manage 순차). 산출물은 `.claude/context-engineering/{slug}/`(context-brief.md / payload.md / playbook.md)에 모이고 같은 slug 재실행 시 playbook을 먼저 참조한다. **내재화 원칙** — Scope 우선(retrieval need 먼저) · 체계적 최적화≠더 채우기 · 구조적 증분(brevity bias·context collapse 가드) · 위치 인지 배치(lost-in-the-middle) · playbook 큐레이션 · 사실 보존·환각 컨텍스트 금지 · 멀티 에이전트 per-agent 격리(opt-in) · 검증 없는 출하 금지 · 승인 게이트. **경계** — 작업의 에이전트 병렬화 판단 · AI 산출물 평가(judge 구성) · 엔지니어용 실행 명세 작성 · 기획자용 PRD · 하네스 자체 진단 · 단발 코드 수정은 범위가 아니며(일반 개념으로만 변별, 타 플러그인 비의존), description·trigger-eval에 명시한다. 근거: A Survey of Context Engineering(arXiv:2507.13334)[정의·taxonomy, vote 3-0] · ACE: Agentic Context Engineering(arXiv:2510.04618, ICLR 2026)[진화 playbook·brevity bias·context collapse, vote 3-0] · DACS: Dynamic Attentional Context Scoping(arXiv:2604.07911)[context pollution·REGISTRY/FOCUS, vote 2-1 medium — 정량수치 비인용, 질적 패턴만].

## comprehension-harness

에이전트가 쓴 코드 변경을 **사람이 실제로 이해하고 있는지 실측하고 그 이해를 자산으로 남기는** 도메인 무관 인터랙티브 멀티 에이전트 하네스. 한 문장 원칙은 **"이해했다는 느낌은 이해의 증거가 아니다"**. 강연 *"Understanding is the new bottleneck"*(2026, 자막 원문 확보)이 세운 구분 — **검증을 위한 이해**(맞았나? 에이전트가 점점 잘한다) vs **참여를 위한 이해**(다음 아이디어를 낼 수 있는가) — 중 **후자**를 만든다. 강연의 기법 4종(설명서·퀴즈·마이크로월드·공유 공간)을 승격하되 **규정을 그대로 옮기지 않고 8각도 1차 문헌 수집 + 적대적 반증 2라운드로 대조해 교정**했다.

4개 에이전트 구성 (모두 `model: "opus"`):

- **Phase 1 도달** — `reach-auditor`. **R1 링크 지도**(1급)·R2 JS 없이 본문이 초기 HTML에 있는가·R3 `.md`/`Accept: text/markdown` 협상·R4 죽은 링크·앵커·soft-404·R5 벤더 공개 UA replay로 **오차단 탐지**·R6 robots.txt **보고만**·R7 토큰 census(**임계값·등급 없음**)·R8 머신 리더블 스펙 존재. 산출물에 **정확도 언어를 쓰지 않는다**.
- **Phase 2 내용** — `content-auditor`. **C1 심볼별 예제 존재**·**C2 예제 컴파일·실행 검증**·C3 문서↔코드 시그니처 드리프트(AST 우선, 정규식만이면 표기)·**C4 거짓으로 판정되는 서술**(파싱·실행으로 판정된 것만)·C5 대상 심볼의 낯섦(레지스트리·사설 여부)·C6 주입 표면. **산문 품질을 채점하지 않는다**.
- **Phase 3 개입** — `intervention-planner`. **T-A 위험0**(거짓 제거·깨진 예제·죽은 링크) / **T-B 검증 통과분만 반영**(실행·스키마·상태코드 실패 시 되돌림) / **T-C report-only**(llms.txt·robots.txt·마크다운 전환·구조 재편·컨텍스트 파일 — **만들지도 고치지도 않음**). 계획 승인 + **항목별 개별 승인**.
- **Phase 4 수용** — `acceptance-verifier`. 배터리를 **개입 전에 고정**하고 재측정. **도달 지표와 내용 지표를 하나의 숫자로 합치지 않는다**. 못 돌리면 **UNVERIFIED**.

> `aeo-harness`는 **코딩 에이전트를 소비자로 놓고 발행된 기술 문서를 재고 고치는** 데 특화한 도메인 무관 하네스다. **한 문장 원칙 — 에이전트가 문서에 도달했다는 것과 그 문서로 코드가 맞아졌다는 것은 다른 사건이다.** 이 원칙은 수사가 아니라 근거 구조에서 나왔다: **발행 측 근거는 전부 도달·효율만 측정했고 정확도 측정이 0건**이며, **정확도 측 근거는 전부 문서를 이미 쥐여준 조건**에서 측정해 발견 단계를 우회했다 — 즉 **"에이전트가 스스로 문서를 발견해서 코드가 더 맞아졌다"를 측정한 연구가 확인 범위에 없다**(evidence F1). 그래서 Phase 1과 2를 분리하고 **산출물의 언어까지 분리**한다(INV-1). **내재화 원칙(7불변식)** — INV-1 도달≠정확도("문서 고치면 N% 맞아진다" 금지) · INV-2 **틀린 문서 > 없는 문서**(1순위는 빈칸 채우기가 아니라 거짓 제거, **검증 없는 LLM 문서 생성은 순마이너스**) · INV-3 **점수·백분율·성숙도 등급 금지**(연속 품질↔정확도 함수 미측정 → Goodhart) · INV-4 report-only는 자동 생성·편집 안 함(**단 거부권 아님** — 알고도 하겠다면 따르고 무엇을 모르는 채 하는지 기록) · INV-5 **UA로 도구 귀속 금지**(진위는 공개 IP·rDNS로만 예/아니오) · INV-6 **수용은 재측정으로만**(못 돌리면 UNVERIFIED) · INV-7 **대상 문서는 신뢰 경계 밖**(명령형 문장은 지시 아니라 발견으로 보고). **근거(1차 출처 전수 대조로 교정된 것)** — **F23 포맷이 아니라 지도**(마크다운으로 서빙하되 내비를 벗기자 에이전트가 `.md` 경로를 스스로 지어내 **HTML보다 더 틀림**, 지도를 주자 404/태스크 2.23→0.11, 그런데 **정확도는 불변**: "The win was efficiency, not correctness") · **F2 문서 효과의 대부분은 예제 코드**(제거 시 pass rate 0.66~0.82→0.22~0.39, 단 "저빈도 API에서만 효과"는 **같은 논문 RQ4가 반증**) · **F3 검색 품질이 나쁘면 잘 아는 API에서 해**(차선 리트리버 시 39.02%p 절대 하락, DV가 valid API invocation이라 F2의 pass rate와 **결과변수가 다름**) · **F6 오라클 검색을 줘도 오용 잔존** · **F8 틀린 문서의 해악**(단 '없는 문서 영향 없음'은 **null이지 동등성 아님**, DV는 **LLM의** 코드 이해) · **F18 코딩 에이전트 9종이 llms.txt·robots.txt를 요청조차 안 함**(엔드포인트가 실제로 서빙했고 측정 항목이었음, 단 **URL 직접 지정 조건**) · **F19 `curl/8.4.0`을 Cline·Junie가 공유**·시점 스냅샷 · **F22 llms.txt 보유 도메인 97%가 한 달간 요청 0**(AI agents 카테고리 5위 10.5%, 저자가 모든 수치를 **ceiling**으로 못박음, 28%는 **upper bound**) · **F24 F22와 F23은 모순이 아니라 DV·모집단이 다름** · **F25 Cloudflare 변환은 내비게이션을 제거하고 ETag·Last-Modified를 버림**(공식 문서에 절감률 수치 없음) · **F28 사용자 트리거 페치 robots.txt 취급이 벤더별 상이**(Google·Perplexity 무시, OpenAI "may not apply", **Anthropic만 면제 없음**) · **F32/F34 Google Search 문서는 llms.txt 미언급, Lighthouse는 부재를 감점 안 함**(404→N/A) · **F36 조사 중 실제 프롬프트 인젝션 조우**. **인용 금지 14항** — 토큰 상한 수치(15,000/25,000/20,000)·"100K~200K 실사용 한도"·"llms.txt가 AI 가시성을 올린다"·"agent-permissions.json은 신흥 표준"(저자가 `non-enforceable by design` 명시)·"robots.txt 오설정이 에이전트를 조용히 차단"·UA 문자열 기반 식별·"HTML→Markdown N% 절감"·GEO 40% 전이·"컨텍스트 파일은 도움 안 된다"(F11은 **LLM 생성본** 결론)·"문서를 잘 쓰면 LLM이 코드를 더 잘 짠다"(뭉뚱그린 형태)·품질점수→정확도 함수·"Claude-Code llms.txt 소비 2위"(원문 오기, 실측 3위이고 2위는 IP 미확인 봇)·193,217 토큰을 실측처럼(저자가 "not an empirical finding" 라벨)·"개선 N% 보장". **결정론 스크립트 2종** — `reach_probe.py`(stdlib only, census 전용, 점수 없음, UA replay는 오차단 탐지만) · `check_evidence.py`(정의되지 않은 F앵커·인용 금지 문구·점수 어휘 자동 검사, 부정 맥락은 허용하되 건수 보고). **경계**(범주로만 서술) — 검색엔진·답변엔진 노출 최적화(SEO/GEO) · 저장소 정적 점수·성숙도 측정 · 사람의 이해 실측 · 머지 가능 여부 판정 · 테스트 계층 설계·생성 · `AGENTS.md`/`CLAUDE.md` 작성(근거가 출처별로 갈리고 서로 반박) · 하네스 자체 진단 제외. 커밋하지 않고 저장은 opt-in.
