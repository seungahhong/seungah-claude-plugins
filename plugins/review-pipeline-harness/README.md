# review-pipeline-harness

**AI가 코드를 많이 쓰는 팀의 코드 리뷰 *시스템*을 설계하는 하네스.** PR 한 건이 아니라, 변경이 머지되기까지 거치는 층·승인 정책·AI 리뷰어 구성·루프 수렴·측정을 설계한다.

> "사람이 코드를 읽었나"가 아니라 **"이 변경에서 무엇이 잘못될 수 있고, 어떤 검사가 그것을 잡기에 맞는가"** 를 묻는다.
> 목표는 **변경당 사람 시간은 줄이고 revert는 늘지 않게**. 둘 중 하나만 보면 비용은 사라진 게 아니라 옮겨진 것이다.

사례 근거는 Anthropic이 공개한 자사 리뷰 운영(2026-10 블로그)과 Code Review 제품 문서다. `/deep-research`로 주장 25개를 3표 적대 검증해 21개를 확인하고 4개를 기각했다.

## 이 하네스가 하는 일 / 하지 않는 일

| 한다 | 하지 않는다 |
|------|-------------|
| 저장소의 리뷰 경로를 7개 층으로 지도화한다 | PR 한 건의 머지 여부를 판정하지 않는다 |
| 변경 기반 위험 등급·승인 규칙을 설계한다 | 브랜치 보호·ruleset·CODEOWNERS를 **바꾸지 않는다** |
| REVIEW.md 초안과 깊이·차단 게이트 선택지를 낸다 | REVIEW.md·CLAUDE.md·CI 워크플로를 **쓰지 않는다** |
| 리뷰-수정 루프 수렴 장치와 노이즈 측정을 설계한다 | 효과를 약속하지 않는다("revert N% 감소") |
| 사람 시간 지표를 revert·인시던트 가드레일과 짝짓고 circuit breaker를 설계한다 | 점수·성숙도 등급을 만들지 않는다 |
| 정책을 공격 시나리오로 깨 본다 | 커밋하지 않는다 |

특정 Phase만 고를 수도 있다(예: "REVIEW.md만"). 이때 앞 Phase가 없어 생기는 공백을 알려 준다.

## 7 Phase

| Phase | 에이전트 | 하는 일 | 게이트 |
|-------|----------|---------|--------|
| **0** 인테이크·기준선 | (오케스트레이터) | 대상·아픈 곳·AI 리뷰어 종류·작성자 구성·관측 수단을 **한 번에 한 질문**으로. 선택 시 `gh` 읽기 전용 + `pr_baseline.py`로 사람 시간 기준선 | A |
| **1** 방어 계층 지도 | `layer-auditor` | L1 PR 전 검증 ~ L7 탐지·롤백을 `있음/약함/없음/미확인`으로 + 실패 유형→잡았어야 할 층 | B |
| **2** 위험 등급 승인 정책 | `risk-policy-designer` | 결정론 바닥 + 판단 상향 분류 규칙, 승인 규칙 R1~R7, CODEOWNERS·브랜치 보호 **제안** | C |
| **3** AI 리뷰어 구성 | `review-config-author` | REVIEW.md 초안, 등급↔Quick/Standard/Deep, 정책 파일 신뢰 경계, 차단 게이트 선택지 | D |
| **4** 수렴·노이즈 정책 | `review-config-author` | 라운드 상한·diff-only 재리뷰·반복 금지·부류 지목, 원천 수정, 응답 4분류 측정 | E |
| **5** 지표·eval·가드레일 | `metrics-guardrail-designer` | 사람 시간 H ↔ 가드레일 G 짝, 인시던트 eval 세트, **circuit breaker** | F |
| **6** 적대 검증 | `policy-red-teamer` | 공격 시나리오 A1~A12로 `막힘/부분/뚫림` + 보완안 + 정직성 감사 | G |

모든 Agent 호출은 `model: "opus"`.

## 7 불변식

| # | 불변식 | 왜 |
|---|--------|-----|
| **INV-1** | **설계만 한다, 적용은 사람** | 설정·정책 파일·CI를 바꾸지 않는다. `gh api`는 GET만 |
| **INV-2** | **사람 시간 절감은 가드레일과 짝** | revert·인시던트가 오르면 사람 시간은 절약이 아니라 이동이다 |
| **INV-3** | **등급은 변경이 정한다** | 에이전트 승인은 사람 슬롯을 채우지 못하고, 지휘한 사람이 필수 리뷰어이며, 승인은 특정 커밋에만 유효 |
| **INV-4** | **정책은 신뢰 경계 안에서** | REVIEW.md 등 정책 파일은 보호된 base에서만 읽히고, 그 변경은 항상 사람이 본다 |
| **INV-5** | **노이즈가 비용이다** | 에이전트 작성자에게 nit 하나는 커밋 하나와 다음 라운드다. 단 진짜 버그가 먼저 |
| **INV-6** | **근거 정직성** | 사내 운영·호스티드 제품·오픈소스 플러그인을 섞지 않는다. 벤더 수치를 목표값으로 쓰지 않는다 |
| **INV-7** | **경고이지 거부권이 아니다** | 더 느슨한 정책을 고르면 경고·기록 후 따른다 |

## 근거에서 교정한 것

- **"에이전트 5개(또는 4개)가 관점별로 본다"** 는 기각됐다(0-3). 오픈소스 플러그인 설명을 제품 구조로 옮긴 오류다. 제품은 finder 여러 개 + **별도 verifier 그룹 투표**이며, 수와 정족수는 공개되지 않았다.
- **"Anthropic은 항상 사람이 승인한다"** 도 기각됐다(1-2). 사내 Low 등급은 사람 0명으로 머지되고, 제품은 승인도 차단도 하지 않는다.
- **"검증을 주면 2~3배 좋아진다"** 는 측정이 아니라 추정이다.
- 16%→54%, 65%→78%, 8.9%→1.5% 같은 수치는 모두 **미감사 자체 보고**다. 이 하네스는 목표값으로 쓰지 않는다.

## 경계

- **특정 PR·diff 한 건의 머지 판정** — 범위 밖. 이 하네스는 판정이 *어떻게* 내려지게 할지를 설계한다.
- **코드 착수 *전* 상류 산출물 검수**, **CI 파이프라인·IaC·릴리스 설계**, **LLM 채점기 설계**, **사람↔에이전트 협업 일반의 위임 설계**, **커밋·PR 작성**, **장애 대응**, **하네스 자체 진단** — 범위 밖.

경계는 범주로만 서술하며 **다른 플러그인을 이름으로 참조하거나 의존하지 않는다** — references 6종과 기준선 스크립트를 내재화한 독립 플러그인이다.
