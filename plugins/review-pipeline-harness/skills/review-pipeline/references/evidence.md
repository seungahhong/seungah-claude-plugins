# 근거 대장 (Evidence) — 이 하네스가 사실로 말해도 되는 것

이 문서는 `review-pipeline` 하네스의 **사실 정본**이다. 다른 참조 문서(`layer-model.md`·`risk-tier-policy.md`·`review-md-template.md`·`convergence-and-noise.md`·`metrics-guardrails.md`)와 5개 에이전트 산출물은 수치·효과·사례를 말할 때 **여기에 있는 것만** 쓴다.

- 여기에 **없는** 수치·효과는 **쓰지 않는다.** 모르면 안 쓰는 것이 정답이다.
- **인용 금지 목록(§7)** 에 있는 주장은 하네스 출력 어디에서도 사실로 말하지 않는다.
- 확인 시점: **2026-11-14.** 제품 동작(트리거·깊이 수준·보호 브랜치 규칙)은 계속 바뀐다. 구현 시점에 §8 절차로 재확인한다.
- 수집 방법: `/deep-research`(5각도 검색 → 17개 출처 fetch → 주장 25개 3표 적대 검증 → 21개 확인·4개 기각) + 1차 원문 직접 읽기.

## 1. 등급 정의

이 하네스의 근거는 대부분 **한 회사가 자기 운영과 제품을 설명한 1차 자료**다. 그래서 등급은 "누가 말했는가"보다 **"무엇에 대한 설명인가"** 로 나눈다. 세 가지를 섞어 인용하는 것이 이 도메인의 가장 흔한 오류다(§6).

| 등급 | 정의 | 사용 규칙 |
|------|------|-----------|
| `[VENDOR-OPS]` | Anthropic이 **사내 운영**(Claude Code 저장소·사내 모노레포)을 설명한 1차 자료 | 설계 **사례**로 서술 가능. 수치는 "벤더 자체 보고·미감사·정의와 대조군 미공개"를 병기. **효과 근거로 전용 금지** |
| `[VENDOR-PRODUCT]` | 호스티드 **Code Review 제품** 문서·출시 글 | 제품이 *어떻게 동작하는지*의 근거로만. 사내 운영 사실과 섞지 않는다 |
| `[VENDOR-OSS]` | 오픈소스 **`/code-review` 플러그인** 리스팅·소스 | 위 두 가지와 **별개 구현**이다 |
| `[SECONDARY]` | 1차 자료를 되풀이한 보도 | 1차 자료에 없는 내용은 쓰지 않는다. 과장·오기가 확인된 것은 §7 |
| `[HARNESS]` | 출처가 주장하지 않은 **이 하네스의 설계 선택**(위 사실에서의 추론) | "하네스 설계 선택이다"라고 **명시**한다. 출처의 주장처럼 쓰지 않는다 |

> 등급 없는 사실 주장은 이 하네스에서 결함이다. Phase 6 `policy-red-teamer`의 정직성 감사 대상이다.

## 2. 문제 정의 — 왜 리뷰를 *시스템*으로 다시 짜는가

| E6 | 코드 리뷰의 두 가지 일: (1) 출시 전 문제 발견·수정 (2) 코드베이스에 대한 **공유된 이해** 형성. 글은 주로 (1)을 다룬다 | VENDOR-OPS | (2)는 이 하네스 범위 밖임을 경계에 적는 근거 |

## 5. 사람 승인·수렴·측정 — Phase 2·4·5의 근거

| ID | 사실 | 등급 | 주의 |
|----|------|------|------|
| E25 | **등급은 작성자가 아니라 변경이 정한다.** 분류기가 변경을 읽고 위험 등급을 고른다. Low(문서·카피·내부 전용 기능·플래그 뒤 추가형 변경) = 자동·보안 검사가 green이면 사람 승인 0명 / Medium(일반 제품 변경, 캐싱·자동 업데이터·시스템 프롬프트 같은 민감 영역) = 1명 / High(최고 위험 코드 + 항상 2명이 필요한 경로) = 2명 | VENDOR-OPS | **0/1/2는 한 회사의 선택이지 업계 표준이 아니다**(§7 X8). 이 하네스는 사람 수를 사용자가 정하게 한다 |
| E26 | 두 번째 분류기가 **등급과 무관하게 사람이 필요한지**를 따로 판단한다. 소유자가 민감하다고 지정한 경로와 **CI 워크플로 파일은 항상 사람**이 본다 | VENDOR-OPS | |
| E27 | 가벼운 경로는 **신뢰 작성자**(주로 소유 팀)에게만. 그 외 작성자는 두 번째 사람이 필요하다 | VENDOR-OPS | 작성자는 *등급*이 아니라 *가벼운 경로 자격*에만 영향 |
| E28 | **에이전트의 승인은 사람의 승인으로 치지 않는다** — 사람을 요구하는 자리를 채울 수 없다. 에이전트가 쓴 PR에서는 **에이전트를 지휘한 사람이 필수 리뷰어 1명으로 계산**된다 | VENDOR-OPS | |
| E29 | **승인은 특정 커밋 하나에만 유효하다.** 시스템이 보증할 수 없는 새 커밋(에이전트 push, 손으로 해결한 merge)이 오면 다시 승인해야 한다 | VENDOR-OPS | 채택 체크리스트: "새 커밋에서 승인을 dismiss" |
| E30 | **모든 발견에는 응답해야 한다** — 고치거나, 사유를 달아 스레드를 resolve한다 | VENDOR-OPS | |
| E31 | 사람이 책임지는 것: 무엇을 만들지(방향·취향·범위), 위험한 코드 리뷰(결제·자동 업데이터·CI 워크플로), **패턴을 정하는 아키텍처**, 증거 읽기(테스트 출력·명령·스크린샷·발견), 결과 소유 | VENDOR-OPS | |
| E32 | 수렴 작업 전→후: 1회 리뷰·수정으로 통과 **65%→78%**, 5라운드 이상 필요 **8.9%→1.5%**, 통과까지 평균 리뷰 횟수 **2.08→1.32** | VENDOR-OPS | 미감사 자체 보고. 어떤 조치가 얼마나 기여했는지 분리되지 않음 |
| E33 | 수렴 장치: **라운드 상한**(3라운드 후 리뷰어가 작성자에게 접근 방식 재고를 요청), 처음 몇 차례 이후 **diff만 재리뷰**, **결함 부류를 지목**해 모든 인스턴스를 고치게 함, **이미 게시한 발견은 반복하지 않음** | VENDOR-OPS | |
| E34 | git blame 결과, 리뷰어가 계속 지적한 것의 약 **59%** 는 첫 패스부터 있던 코드였다 — 매 라운드가 새 버그가 아니라 오래된 버그를 조금씩 더 꺼냈다. 극단 사례로 CLI PR 하나가 밤새 **50회 넘게** 리뷰·수정을 돈 뒤 작성자가 멈췄다 | VENDOR-OPS | 반복 리뷰의 함정 사례 |
| E35 | **기본으로 여러 라운드를 도는 것은 함정이다** — 매번 새로운 것을 찾지만 그 비용은 위험한 변경에서만 값어치가 있다. **에이전트 작성자에게는 노이즈가 더 비싸다** — 사람은 nit을 몇 초 만에 넘기지만 에이전트는 커밋을 하나 더 만들고 다음 라운드를 촉발한다 | VENDOR-OPS | INV-5의 출처 |
| E36 | 노이즈 측정: 모든 리뷰어 코멘트를 **응답으로 분류**(fixed / wrong / intentional / didn't matter). **깨끗한 것으로 알려진 PR**에도 리뷰어를 돌려 해로운 변경으로 이어질 오경보를 센다. 명시된 우선순위: **진짜 버그 잡기가 먼저, 리뷰 라운드 줄이기가 두 번째** | VENDOR-OPS | |
| E37 | **인시던트를 eval로**: 과거 인시던트·revert PR(전문가가 확인한 버그 포함)로 eval 세트를 만들어 **매일** 돌린다. 리뷰어의 모든 변경(프롬프트·도구·모델)을 이것으로 채점하고 **점수를 올리지 못한 변경은 버린다** | VENDOR-OPS | |
| E38 | 기존 코드에 대한 **야간 리뷰**가 오래된 버그를 다른 곳에서 드러나기 전에 잡는 데 도움이 된다 | VENDOR-OPS | PR 루프와 분리 |
| E39 | "고친 사람이 소유한다" — 변경은 작고 되돌릴 수 있게, **blast radius가 리뷰 기준을 정한다**, 회귀는 텔레메트리·사내 사용으로 드러나고, 인시던트 리뷰는 개인이 아니라 시스템을 본다. 방향 전환은 **일찍**, 완성된 PR에 차단 코멘트가 아니라 스레드에서 | VENDOR-OPS | |

## 6. 섞으면 안 되는 세 가지

| 대상 | 승인 | 차단 | 정책 파일 | 필터 |
|------|------|------|-----------|------|
| **Anthropic 사내 운영** `[VENDOR-OPS]` | 위험 등급별 사람 0/1/2명, 에이전트 승인 불인정 | **열린 발견이 머지 차단**(E9) | REVIEW.md·CLAUDE.md | verifier 투표 + 스타일·정리 제외 |
| **호스티드 Code Review 제품** `[VENDOR-PRODUCT]` | **하지 않음** | **하지 않음**(neutral check, E24) | REVIEW.md(base/보호 브랜치만, E18) | verifier 투표 + 정확성 범위 |
| **오픈소스 `/code-review`** `[VENDOR-OSS]` | 하지 않음 | 하지 않음 | CLAUDE.md | confidence ≥ 80(E23) |

"Anthropic은 AI 리뷰로 사람 승인을 없앴다"(사내 Low 등급만 해당)도, "제품은 항상 사람 승인을 유지한다"(제품은 승인 정책을 정하지 않는다)도 **둘 다 틀린 일반화**다(§7 X2).

## 7. 인용 금지 목록

하네스 산출물 어디에서도 아래를 사실로 말하지 않는다.

| ID | 금지 주장 | 이유 |
|----|-----------|------|
| X1 | "Code Review는 에이전트 5개(또는 4개)가 각각 CLAUDE.md 준수·버그·git 이력·이전 코멘트·코드 주석을 본다" | 적대 검증 **0-3 기각**. 오픈소스 플러그인 설명을 제품 구조로 옮긴 오류 |
| X2 | "Anthropic은 모든 PR에 사람 승인을 유지한다" / "AI 리뷰가 사람 승인을 대체했다" | **1-2 기각** / 범위 오류. 사내 Low 등급은 사람 0명, 제품은 승인 정책이 없다(§6) |
| X3 | "이 정책(또는 이 하네스)을 도입하면 revert가 N% 준다 / 1회 통과율이 N%가 된다" | E2·E22·E32는 한 회사 미감사 자체 보고이며 조치별 기여가 분리되지 않았다. **효과 약속 금지** |
| X4 | "finder가 자기 발견을 스스로 검증한다" | 2차 보도의 과장. 검증은 **별도 verifier 그룹**의 투표다(E12) |
| X5 | verifier 정족수·에이전트 수·위험 분류기 정확도의 구체 숫자 | **미공개**. 숫자를 지어내지 않는다. 하네스 설계에서 숫자가 필요하면 `[HARNESS]` 기본값으로 밝힌다 |
| X6 | "리뷰 코멘트는 사람 리뷰어가 단 것" | 2차 보도의 오기 |

## 8. 재검증 절차

제품 동작은 바뀐다. 사용자의 실제 도입 대상이 호스티드 제품이면, 정책 확정 전에 아래를 **현재 문서**로 다시 확인하라고 안내한다(하네스가 대신 단정하지 않는다).

1. REVIEW.md를 어느 브랜치에서 읽는지, 보호 브랜치 조건(E18)
2. 깊이 수준·트리거 옵션(E20)
3. check run 결론과 차단 게이트 구성 방법(E24)
4. 로컬 `/code-review`가 읽는 정책 파일(E23)
