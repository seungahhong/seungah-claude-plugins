# 위험 등급 승인 정책 (Risk-Tier Policy) — Phase 2

**등급은 변경이 정한다, 작성자가 아니라**(evidence E25). 이 문서는 등급 규칙·승인 규칙·분류 방법을 설계하는 틀이다. 숫자(등급별 사람 수)는 **사용자가 정한다** — Anthropic의 0/1/2는 한 회사의 선택이다(E25, X8).

## 1. 등급 정의 틀

| 등급 | 변경의 성격(출발점, E25) | 사람 승인 수 | 전제 조건 |
|------|--------------------------|--------------|-----------|
| `Low` | 문서·카피, 내부 전용 기능, **플래그 뒤의 추가형 변경** | 사용자가 정함(사례: 0) | 자동 검사·보안 검사 green · **신뢰 작성자만**(E27) · 가드레일 지표와 circuit breaker가 있어야 0명 허용(INV-2) |
| `Medium` | 일반 제품 변경, 민감 영역(사례: 캐싱·자동 업데이터·시스템 프롬프트) | 사용자가 정함(사례: 1) | |
| `High` | 최고 위험 코드, 항상 2명이 필요한 경로 | 사용자가 정함(사례: 2) | |

등급 표는 **이 저장소의 실제 경로·변경 유형**으로 채운다. 예시를 그대로 복사하지 않는다.

### "플래그 뒤"의 함정

"플래그 뒤 추가형"이 Low가 되려면 **플래그 기본값이 꺼짐**이고 **켜는 변경이 별도 PR**이어야 한다. 기본값이 켜진 플래그는 플래그가 아니다. 이 조건을 등급 규칙에 명시한다(`[HARNESS]` 설계 선택).

## 2. 승인 규칙 (모든 등급 공통)

| 규칙 | 근거 | 강제 수단(제안) |
|------|------|-----------------|
| R1 **에이전트 승인은 사람 슬롯을 채우지 못한다** | E28 | 봇 계정은 CODEOWNERS·required reviewers에서 제외, 봇 승인을 세지 않는 규칙 |
| R2 **에이전트가 쓴 PR에서는 에이전트를 지휘한 사람이 필수 리뷰어 1명** | E28 | PR 템플릿에 "지휘한 사람" 필드 · 해당 사람의 승인 요구 |
| R3 **승인은 특정 커밋에만 유효** — 시스템이 보증할 수 없는 새 커밋(에이전트 push·손으로 해결한 merge)은 재승인 | E29 | dismiss stale approvals on new commits |
| R4 **always-human 경로** — 소유자가 지정한 민감 경로, **CI 워크플로 파일**, 그리고 **리뷰 정책 파일 자체**(REVIEW.md·CLAUDE.md·CODEOWNERS·등급 규칙 정의) | E26 + `[HARNESS]`(정책 파일 추가) | CODEOWNERS로 해당 경로에 사람 소유자 지정 + code owner review 요구 |
| R5 **가벼운 경로는 신뢰 작성자만** — 그 외 작성자는 한 명 더 | E27 | 신뢰 작성자 목록(팀) · 목록 변경도 always-human |
| R6 **모든 발견에 응답** — 고치거나 사유를 달아 resolve | E30 | require conversation resolution before merging |
| R7 **등급과 무관한 사람 요구(escape hatch)** — 분류기·작성자·리뷰어 누구든 "사람 필요"를 올릴 수 있고 내릴 수는 없다 | E26 | 라벨(예: `needs-human`)이 붙으면 required review +1 |

## 3. 분류 방법 — 결정론 바닥 + 판단 상향

출처는 "분류기가 변경을 읽고 등급을 고른다"고만 하고 기준·정확도는 공개하지 않았다(X5). 이 하네스는 다음 구조를 **설계 선택**으로 제안한다(`[HARNESS]`).

1. **결정론 바닥(floor)** — 경로 패턴·파일 유형·변경 유형 규칙으로 **최소 등급**을 정한다. CODEOWNERS·라벨러 같은 기존 도구로 표현할 수 있어야 한다. 규칙은 저장소에 있고 always-human 경로(R4)다.
2. **판단 상향(LLM 분류기 등)** — 바닥보다 **올릴 수만 있고 내릴 수 없다.** 분류기가 Low라고 해도 바닥이 Medium이면 Medium.
3. **불확실하면 위로** — 분류 근거를 쓸 수 없으면 한 단계 위.
4. **분할 우회 감시** — 큰 변경을 Low 조각 여러 개로 쪼개는 패턴은 Phase 6 공격 시나리오 A4로 점검한다.

분류 규칙의 출력 형식:

```markdown
| 규칙 ID | 조건(경로·유형) | 최소 등급 | 근거(이 저장소의 사례·소유자 지정) |
|---------|-----------------|-----------|-------------------------------------|
| T-01 | `docs/**`, `*.md`(정책 파일 제외) | Low | 문서 변경, 런타임 영향 없음 |
| T-02 | `src/cache/**` | Medium | 소유자 지정 민감 영역 |
| T-03 | `.github/workflows/**`, `CODEOWNERS`, `REVIEW.md`, `CLAUDE.md` | High + always-human | R4 |
```

## 4. 산출 제안물 (적용하지 않는다)

- **tier-policy.md** — 등급 표 + 승인 규칙 R1~R7 + 분류 규칙 표 + 사용자가 정한 숫자와 그 이유
- **CODEOWNERS 제안** — 추가·변경할 줄만 diff 형태로. 파일을 쓰지 않는다
- **브랜치 보호·ruleset 제안** — 체크리스트: required status checks · required approving reviews(등급별 수를 표현할 수 없으면 그 한계를 적는다) · require review from code owners · dismiss stale approvals · require conversation resolution · merge queue · 봇의 bypass 금지
- **표현 불가 목록** — 플랫폼 기본 기능으로 표현할 수 없는 규칙(예: 등급별 다른 승인 수, 지휘한 사람 요구)은 **"별도 체크(Action 등)가 필요함"** 으로 따로 적는다. 표현된 것처럼 쓰지 않는다

## 5. 사용자가 더 느슨한 정책을 고를 때

경고하고 기록한 뒤 **따른다**(INV-7). 경고는 한 줄로 "이 선택으로 어떤 실패가 어느 층에서도 잡히지 않게 되는가"를 쓴다. 조용히 보류하거나 더 엄격한 안으로 바꿔치기하지 않는다.
