# test-layering-harness

> 인수조건(AC)을 **방법론 × 계층 택소노미**로 계층별 테스트 스위트로 계획하고, **사람이 하나씩 승인**하며 순차 적용하는 독립 플러그인.

## 무엇을 하나

인수조건(Acceptance Criteria, Given-When-Then)을 입력받아:

1. **저장소를 감지**해 테스트 구성 프리셋을 추천하고(Trophy-lean / Google-pipeline / Contract-honeycomb),
2. 각 AC를 **방법론 카드 4개 + 계층 카드 3개(7개 축 카드)**를 조합해 **명확한 포함/제외 기준**으로 라우팅해 나누고(12개 셀로 미리 만들지 않고 상황에 맞게 조합; 기준은 2025+ 공식표준·논문에 연결) CI 단계에 배치한 **계획표**를 만들되 — **테스트는 사용자가 선택한 방법론·계층 안에서만** 추가하고(스코프 가드), 밖으로 필요하면 임의 추가 없이 확장을 묻고,
3. **계획 전체를 먼저 승인**받은 뒤, **개별 테스트를 하나씩 승인**받으며 순차로 생성·적용·실행하고(unit/integration은 대상 파일 폴더에 `__test__/`를 **무조건 만들어** 그 안에 두고 — 저장소에 다른 배치 관습이 있어도 예외 없이 `__test__/` 강제·작성 전후 경로 검사 —, E2E는 선택 시 테스트 경로를 초기에 문의),
4. 마지막에 **다시 확인받아** 확정("반영")한다.

### API 경계 — unit/integration은 mock, E2E는 모드 태그

- **unit·integration은 실제 API를 호출하지 않는다**(예외 없음 — live로 나가면 그 계층 정의 자체를 벗어난다). 네트워크 경계 인터셉터(MSW/nock 등)를 우선 쓰고, 없으면 모듈 double로 폴백하며 "무엇이 검증 범위 밖인지"를 계획에 적는다. fixture는 **① 저장소 기존 재사용 → ② 사용자가 준 실제 응답 → ③ 스키마 유도(`[실측 캡처 아님]` 표기)** 순으로 확보한다(스킬이 fixture를 만들려고 실제 API를 부르지 않는다).
- **E2E는 스펙 한 벌에 모드 태그**로 분기한다 — **`@e2e-mock`(기본)** 은 CI에서 캡처 fixture로 결정론 실행, **`@e2e-live`** 는 실제 API 연동 검증용으로 **지목한 시나리오에만** 붙고 **고정 CI 스테이지 없이 수동으로만** 돈다.
- ⚠️ **mock 통과 = 연동 정상이 아니다.** fixture는 캡처 시점 스냅샷이라 실제 API가 바뀌어도 초록이다 — 연동 확인 장치는 `@e2e-live` 수동 실행뿐임을 산출물에 병기한다.

### E2E smoke — 실제 API 연동이 필수 (live 전용)

위 기본값의 **유일한 예외**다. **`@smoke`가 붙은 E2E 스펙은 요청 없이도 `@e2e-live`만 갖는다** — `@e2e-mock`을 붙이지 않고 mock 주입·fixture도 만들지 않는다. 대신 **CI 고정 스테이지에 넣지 않고**(PR-gate·post-deploy·nightly 전부 제외) 수동 레시피 `test:e2e:smoke:live`로만 돌린다. `test:smoke`는 비-E2E smoke(주로 integration)만 뽑는다.

**하네스가 실제로 돌리는 조건**: 게이트 B에서 ① 대상 환경(base URL) ② 테스트 계정·시드 데이터(또는 "불필요") ③ **그 자리 실행 승인** 이 셋이 모두 있을 때만 — 계획을 승인했다고 실행까지 승인된 것이 아니다. 프로덕션이면 한 번 더 확인하고, 부작용이 있는 여정(결제·발송·삭제·과금)은 개별로 묻고, 비밀 값은 대화에 받지 않는다(env·secret 키 이름만). 못 돌리면 레시피를 **UNVERIFIED**로 남긴다.

⚠️ **대가를 감추지 않는다**: 고정 스테이지가 없으므로 **E2E smoke는 자동 배포 게이트가 아니라 승격 전 사람이 돌리는 수동 체크포인트**다. 그리고 이 규칙은 "배포 게이트는 결정론적이고 외부 의존이 0이어야 한다"는 통상 권고(MinimumCD·Fowler)와 **상충하는 운영 결정**이다 — 근거로 정당화하지 않고 상충 사실을 산출물에 적는다. live 통과도 **실행 시각·그 환경에 한정된 관측**이지 항구적 연동 보증이 아니다.

### Sanity — 변경 관련 페이지/컴포넌트를 PR 전에

sanity는 새 테스트를 만드는 축이 아니라 **이미 있는 테스트를 골라 돌리는 선택 레인**이다. **변경 파일 → 그 파일을 import하는 상위 페이지/컴포넌트 → 관련 페이지의 `@e2e-mock`** 까지 넓혀 **PR job**에서 돌린다(unit/integration은 **차단**, mock E2E는 **비차단 리포트**). 매핑이 불확실하면 좁히지 않고 전체로 폴백하며, 변경 관련 대상에 테스트가 **아예 없을 때만** 선택 스코프 안에서 새로 만든다. 산출물은 선택 스크립트 2종 + **CI job 스니펫 제안**(yaml은 직접 고치지 않는다).

세 번의 승인 게이트(계획 → 개별 → 최종)를 건너뛰지 않는다. 승인 없이는 파일을 쓰지 않는다.

## 왜 이렇게

AI가 테스트를 자동 생성할수록 위험은 "작성 속도"가 아니라 **"무엇을, 어느 층에, 어떤 오라클로 검증하는가"**로 옮겨간다. 2025+ 근거([research dossier](skills/test-layering-harness/references/research/test-strategy-research.md))가 반복해 지목하는 최대 리스크는 **오라클 강도** — LLM은 명세(기대)가 아니라 구현(실제 동작)을 그대로 굳혀, 버그를 "초록(통과)"으로 은폐한다. 그래서 이 스킬은 오라클을 **기대(AC) 기준으로 오검증**하고, 적용한 테스트를 **실제로 실행**하며, **기존 flaky를 먼저** 정리한다.

## 어떻게 쓰나

스킬을 부르고(예: "이 인수조건으로 계층별 테스트 계획 세우고 하나씩 승인받으며 추가해줘"), 초기 문의에 답한다:

- **인수조건(AC)** — 붙여넣기·파일 경로. **스킵 가능** — 스킵 시 저장소에서 후보(스토리·PRD·기존 테스트 제목)를 찾아 제안한다.
- **개발 환경(경로)** — **스킵 가능** — 미입력 시 **현재 프로젝트 경로**를 기준으로 테스트 러너·디렉토리 관습을 감지한다.

이후 스킬이 프리셋을 추천하면 확정/변경하고, 계획을 승인하고, 테스트를 하나씩 승인하면 된다.

## 정직성 원칙

- **비율%(70/20/10)를 하드코딩하지 않는다** — 원저자(Fowler)도 상대화한 folklore. 무게중심만 프리셋으로 제안한다.
- **smoke = sanity 는 ISTQB상 동의어** — "smoke=넓고얕음 / sanity=좁고깊음" 구분은 실무 컨벤션이지 표준이 아님을 병기한다.
- **근거 없는 효과 수치를 약속하지 않는다**("버그 80% 조기 포착"·"mock 전환으로 flaky N% 감소" 등은 folklore).
- **mock 통과를 연동 검증으로 보고하지 않는다** — fixture는 캡처 시점 스냅샷이라 계약 변화(drift)를 구조적으로 못 잡는다.
- **정적 live-호출 검사의 한계를 감추지 않는다** — 통과는 "네트워크로 안 나간다"의 증명이 아니다(우회 가능).
- **sanity의 PR job 배치·차단성은 표준이 아니라 운영 결정**임을 병기한다(ISTQB/ISO에 sanity 스테이지 규정 없음).
- **E2E smoke의 live 전용 규칙도 근거가 아니라 운영 결정**임을 병기한다 — 게이트 결정론 권고와 상충하며, 그 대가(자동 차단 상실)를 함께 적는다. "live smoke로 장애 N% 조기 포착" 류 효과 수치는 인용하지 않는다.
- **미실행을 통과로 옮기지 않는다** — live 레시피를 만들었다는 것은 검증이 아니라 `UNVERIFIED`다. live 실패도 테스트 결함 / 코드 결함 / **환경·외부계** 3분류로 구분한다.
- 모든 결론에 신뢰도(HIGH/MED/LOW)와 출처, 모순·folklore 표기를 계승한다.

## 도구 경계 (다른 플러그인과의 구분)

이 플러그인의 축은 **"AC → 방법론×계층 택소노미 계획 → 3게이트 순차 적용"**이다. 다음은 범위 밖:

| 이건 저기서 | 플러그인 |
|---|---|
| 리스크 기반 오라클·자가치유 실행·flaky 트리아지 end-to-end 에이전틱 QA | `qa-agent-harness` |
| 백엔드 코드의 generate→compile→execute→repair 수리 루프 | `backend-harness` / test-generator |
| AC↔테스트 커버리지 **읽기전용** 핸드오프 게이트 검수 | `review-harness` / test-coverage-review |
| FE 개발 워크플로우 내부의 TDD | `frontend-harness` |
| 에이전트가 코드 생성할 실행 가능 명세(spec) 작성 | `spec-driven-development` |
| 커밋 메시지·PR | `git-harness` |
