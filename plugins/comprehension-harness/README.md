# comprehension-harness

**에이전트가 쓴 코드 변경을 내가 실제로 이해하고 있는지 실측하고, 그 이해를 자산으로 남기는 하네스.**

> 이해했다는 **느낌**은 이해의 증거가 아니다.
> 그래서 이 하네스는 설명을 읽히기 **전에** 예측을 받아내고, 답한 것과 못 답한 것을 실측하며, **무엇을 모르는 채로 가는지**를 적는다.

출발점은 Geoffrey Litt(Notion)의 강연 *"Understanding is the new bottleneck"*(2026)이 세운 구분이다 — **검증을 위한 이해**(맞았나? 에이전트가 점점 잘한다)와 **참여를 위한 이해**(다음 아이디어를 낼 수 있는가? 대체되지 않는다). 이 하네스는 **후자**를 만든다.

## 이 하네스가 하는 일 / 하지 않는 일

| 한다 | 하지 않는다 |
|------|-------------|
| 이해 부채를 지도로 그린다 | 결함을 찾거나 **머지 가능 여부를 판정하지 않는다** |
| **설명서를 보기 전에** 예측을 받는다 | 코드를 **수정하지 않고 커밋하지 않는다** |
| 검증 훅이 붙은 설명서를 낸다 | "이 변경은 안전합니다"라고 **보증하지 않는다** |
| 자유서술 회상 + 교정 피드백으로 실측한다 | **점수·백분율·성숙도 등급을 만들지 않는다** |
| **모르는 채로 가는 것**을 명시한다 | 못 맞혔다고 **진행을 막지 않는다**(경고이지 거부권이 아니다) |
| 마이크로월드는 근거 상태를 알리고 **사용자가 정한다** | **"이해도가 향상됩니다"라고 약속하지 않는다** |

## 사용법

```
/comprehension-loop
```

또는 자연어로 — "에이전트가 쓴 이 코드 내가 이해 못 하고 있는 것 같아", "이 변경 설명서 만들어줘", "내가 이거 진짜 이해했는지 퀴즈 내줘", "vibe coding 하다 보니 뭐가 뭔지 모르겠어", "이 로직 감 잡게 만져볼 시뮬레이터 만들어줘", "이 변경에서 나만 아는 게 뭔지 정리해줘".

첫 행동은 **대상 변경과 "다음에 이 영역에서 무엇을 할 것인지"를 묻는 것**이다. 참여 목적이 없으면 "전부 이해"라는 달성 불가능한 목표로 흘러간다.

## 6 Phase

| Phase | 에이전트 | 하는 일 | 게이트 |
|-------|----------|---------|--------|
| **0** 이해 인테이크 | (오케스트레이터) | 대상·**참여 목적**·사전지식·에이전트 역할·예산·동시대기 — **한 번에 한 질문** | A |
| **1** 이해 부채 지도 | `debt-cartographer` | 6표면 관측 + 참여 목적 스코프 + **설명서 공개 전 예측 문항** | B |
| **2** 설명서 공개 | `explainer-architect` | 배경 → 직관 → **검증 훅** → `[확인]`/`[추론]` → 순서 안내 + **예측 채점 동시 공개** | C |
| **3** 이해 검증 게이트 | `comprehension-examiner` | 자유서술 회상 + **교정 피드백(diff 좌표)** + 격차 + **묻지 않은 범위 열거** | D |
| **4** 마이크로월드 *(조건부)* | `microworld-builder` | **값싼 대안 먼저** → 조건 **관측·고지** → 만들지 말지는 **사용자 결정**(기본값은 안 만듦) | E |
| **5** 공유 이해 *(조건부)* | `shared-context-curator` | 산출물에서 **복원되지 않는 것만** 펌프 + 열린 질문 | F |

모든 Agent 호출은 `model: "opus"`.

> **에이전트가 5개인 이유** — 설명을 **쓰는** 역할과 이해를 **캐묻는** 역할을 의도적으로 분리한다. 같은 에이전트가 자기 설명서를 근거로 문항을 내면 문항이 설명서의 요약이 되고, 측정되는 것은 이해가 아니라 *그 문서를 읽었는지*가 된다.

## 강연과 갈라진 지점 (근거가 바꾼 것)

| 강연 원안 | 이 하네스 | 왜 |
|---|---|---|
| 설명서를 읽고 그다음 퀴즈 | **예측을 먼저 받고(답을 산출하게), 직후에 설명서 + 채점 동시 공개, 불일치 항목을 앞에** | AI 설명은 이해를 검증하기 전에 체감 이해부터 올린다. 표준 단일 에이전트 설명은 실측상 "체감 이해 최고·객관 학습 최저"를 만들었다. **문항을 보여주기만 하면 효과가 사라지고**(산출 g=0.65 vs 읽힘 g=0.22), **이득은 예측이 빗나간 항목에만** 있다 |
| "5문항, 중간 난이도, 함정 아님" | **개수 규정 없음. 실측 초기 성공률 70~80% + 자유서술 + 교정 피드백 필수 + 문항 A/B/C 분류** | "5문항·중간 난이도"는 1차 출처가 없다. 그리고 효과는 재료 복잡도가 아니라 **문항이 요구하는 지식 유형**에 따라 갈린다 — 적혀 있는 것의 회상(A)은 지지되지만 **적혀 있지 않은 구조 도출(B)은 이득 없음~해로움(d=−0.37)** 이다 |
| 인터랙티브 도해를 설명서에 | **설명서에는 넣지 않음. Phase 4가 조건 검사 후에만** | 보는 것만으로는 참여가 아니고, **학습자 통제를 붙일수록 이점이 단조 소멸해 완전 통제에서 −0.120** 이 된다 |
| 마이크로월드를 실천으로 제시 | **opt-in · 조건 관측·고지 · 기본값은 안 만듦 · 결정은 사용자** | 우리 도메인은 측정된 적이 없고, **인접한 네 하위군 전부에서 추정치가 0 또는 음수**다(추상 표상 g=0.006 n.s. · 정보학 g=0.108 n.s. · 완전 학습자 통제 −0.120 · 이해/전이 결과변수가 가장 작음). 구조·배치는 **정적 1장이 이긴다**(d=1.30) |
| "코드 변경을 산문 순서로 재배치" | **REPORT-ONLY 유지 + "직접 시험되었고 결론 미달"로 정직성 상향. "위험한 것 먼저"만 근거 있음** | 이 기법은 실제로 시험됐다(n=50, 검정력 부족, 저자들이 결론을 못 내렸다). 근거가 있는 것은 **위험한 부분을 앞에 놓는 것**뿐이고 그마저 **결과변수가 결함 탐지이지 이해가 아니다** |
| 공유 공간이 팀 이해를 만든다 | **"나만 아는 것"을 뽑아내는 펌프로만** | 커뮤니케이션 매체는 고유정보 풀링에 영향이 없었다(3,189집단 메타분석) |
| "퀴즈를 통과 못 하면 리뷰를 요청하지 않는다" | **경고이지 거부권이 아니다** | 개인 규칙이며 측정된 게이트가 아니다. "퀴즈 = 속도 조절기"는 인용 금지 항목이다 |

## 7 불변식

| # | 불변식 | 왜 |
|---|--------|-----|
| **INV-1** | **검증이 아니라 참여를 위한 이해** | 결함·리스크·머지 가능 여부를 판정하지 않는다. 이상한 점은 **열린 질문**으로. 코드를 고치지 않고 커밋하지 않는다 |
| **INV-2** | **자기보고는 센서가 아니다** | 자가평가의 판별력 상한은 우연 50% 대비 54.5%, R²≈5.9%. 확신은 **격차 계산의 한쪽 항**으로만 |
| **INV-3** | **설명은 예측 뒤에 공개된다** | AI 설명은 이해 도구이기 전에 **과확신 장치**다. 대조 불가능한 것을 단언하지 않고, 그 자체로는 어떤 게이트도 통과시키지 못한다 |
| **INV-4** | **퀴즈 통과는 이해의 증명이 아니다** | 통과 = "물어본 것에 답했다". 점수화 금지. **묻지 않은 범위를 반드시 열거** |
| **INV-5** | **마이크로월드는 기본값이 아니라 명시된 가설** | 우리 도메인은 미측정이고 **인접한 네 하위군 전부에서 추정치가 0 또는 음수**다. 기본값은 안 만들고 근거를 알린다 — **단 조건은 게이트가 아니라 권고이고, 명시 요청을 기각하지 않는다** |
| **INV-6** | **게이트는 경고이지 거부권이 아니다** | 못 맞혀도 사용자가 진행을 선택하면 따르고, **무엇을 모르는 채로 가는지** 알린다 |
| **INV-7** | **효과를 약속하지 않는다** | 정직하게 주장 가능한 것은 둘뿐 — 리뷰되지 않던 변경을 읽고 답한 변경으로 바꾼다 / 과확신을 낮추고 빈틈을 드러낸다 |

## 정직성

이 하네스가 인용하는 정량치는 대부분 **학부생·레지던트·크라우드워커가 산문·단어쌍·조종석 과제**를 다룬 데서 나왔다. **전문 소프트웨어 엔지니어가 diff를 읽고 이해했는지를 측정한 연구는 이 조사에서 0건이었다.** 그리고 40년 95개 코드 이해 실험 중 *이해가 무엇을 낳는가*를 조사한 연구도 **0건**이다 — 강연의 핵심 주장("축적된 이해가 다음 아이디어를 낳는다")은 근거가 약한 것이 아니라 **분야가 한 번도 실험적으로 묻지 않은 질문**이며, 이 하네스는 그것을 **설계 가설**로만 쓴다.

검증은 2라운드로 했다. 1라운드는 8각도 수집(F1~F55) + 4개 적대적 fact-check, 2라운드는 **1라운드가 "아무도 1차를 열지 못했다"고 표시한 항목을 실제로 개봉**(F56~F76)했다. 2라운드에서 **애니메이션 vs 정적 판정이 뒤집혔고**, **literate diff는 "미확인"에서 "직접 시험되었고 결론 미달"로 정정**되었으며, **예측 커밋의 근거가 새로 확보**되었다. **2라운드의 감사 레인(설계 규칙 재감사·인용 금지 재검증·완전성 비평)은 세션 한도로 실행되지 못했다** — 그 사실도 정본에 적혀 있다.

근거 등급·사실표·**인용 금지 목록**·남은 미지는 [skills/comprehension-loop/references/evidence.md](skills/comprehension-loop/references/evidence.md)가 정본이다.

## 범위 밖

변경을 읽고 결함을 찾아 **머지 판정**하기 · 코드 착수 *전* 상류 산출물 준비도 검수 · **명세**를 작성해 그대로 구현·검증시키기 · 테스트를 새로 계획·계층화해 생성하기 · 저장소 전체를 **정적 점수**로 측정하기 · 사람과 에이전트의 **분업·자율 수준·감독 체계** 설계 · 프로덕션 장애 대응 · 하네스 자체의 진단·개선.

**독립 플러그인이다** — references 6종을 전부 내재화했고 다른 플러그인을 참조하거나 의존하지 않는다. 단독 설치로 동작한다.
