# 설명서 구조 (Phase 2)

목적 — 사람이 **예측을 제출한 뒤에** 읽는, **스스로 검증 가능한** 설명서를 만든다.

> **성공 기준은 "명료함"이 아니라 "검증 가능성"이다.** 설명이 과의존을 줄인 유일한 조건은 **검증 비용을 낮춘 경우**였고([evidence.md](./evidence.md) F10), 설명이 도움이 된 유일한 메커니즘은 **검증 가능성**이었다(F11). 내용이 비어 있는 설명도 진짜와 비슷한 신뢰를 만든다(F12). 그래서 잘 읽히는 설명서는 목표가 아니다 — **틀렸을 때 사용자가 5분 안에 알아챌 수 있는 설명서**가 목표다.

---

## 1. 공개 규약 (불변식)

1. **Phase 1의 예측이 제출되기 전에는 이 문서를 보여주지 않는다.**
2. 공개 후 **정답 채점 결과를 함께 보여준다.** 시험을 치르는 것만으로는 과확신이 안 꺼진다 — 꺼뜨린 것은 **채점 결과를 본 단계**였다(F8: 예측 시험 단계는 양쪽 모두 비유의, 채점 결과 열람은 양쪽 모두 유의).
3. **이 문서 자체는 어떤 게이트도 통과시키지 못한다.** 읽었다는 사실은 상태 변화가 아니다.

---

## 2. 다섯 블록

### B1. 배경 — 사전지식에 맞춰 잘라낸다

- **Phase 0에서 받은 사전지식 수준으로 분량을 정한다.** 숙련자에게 배경을 강제하지 않는다 — 초보자에게 도움이 되는 지원은 숙련이 쌓이면 불필요해지고 이어서 **해롭게** 된다(F15 전문성 역전). 원문: *"Without such tailoring, the effectiveness of instructional designs is likely to be random."*
- 이 블록은 **명시적으로 접을 수 있어야** 한다.
- 배경은 **이 변경을 읽는 데 필요한 것만**. 시스템 전반 투어가 아니다.

### B2. 직관 — 본질 먼저, 구체 예로

- 한 문단 안에 **이 변경이 무엇을 하기로 되어 있는지**가 들어간다.
- **장난감 입력 하나와 그 결과**를 붙인다. 추상 서술만 있으면 검증할 수 없다.
- **길이는 보상이 아니라 감점 대상이다** — LLM 답변은 77% 더 장황했고, 사용자의 35%가 **포괄성과 문체 때문에** 그것을 선호했다(F14).

### B3. 검증 훅 — 이 문서의 핵심 블록

**설명서가 주장하는 것마다, 사용자가 그것을 값싸게 확인할 방법을 붙인다.** 이 블록이 없으면 이 설명서는 신뢰만 만들고 이해는 만들지 않는다(F12).

| 훅 유형 | 형태 | 언제 |
|---|---|---|
| **입출력 쌍** | "`f({a:1})` → `[1]`, `f({})` → `[]`" — 붙여넣어 돌릴 수 있게 | 순수 함수·변환 |
| **실행 명령** | 돌려볼 수 있는 정확한 명령 한 줄과 **기대 출력** | 테스트·스크립트 |
| **grep 좌표** | `파일:라인` 또는 검색 문자열 — 주장이 참인지 30초 안에 확인 | 불변식·호출자 |
| **반증 좌표** | "이 문장이 틀렸다면 `X`에 `Y`가 있을 것이다" | 추론한 주장 |

**대조 불가능한 것은 단언하지 않는다.** 확인 못 한 주장은 `[미확인]`으로 남긴다.

### B4. 확인/추론 분리

모든 문장은 둘 중 하나다.

- **`[확인]`** — diff에서 직접 읽었거나 명령을 돌려 출력을 봤다.
- **`[추론]`** — 코드에서 유도했으나 실행으로 확인하지 않았다.

**두 번째 유형이 절반을 넘으면 그 사실을 문서 맨 위에 적는다.** 프로그래밍 Q&A에서 LLM 답변의 52%가 오정보였고 사용자는 39%를 지나쳤다(F14) — 가장 가까운 측정치이며, 낙관할 근거가 아니다.

### B5. 변경 순서 안내 (literate diff)

파일 목록 순서가 아니라 **이해 순서**로 재배치하고, 각 덩어리 앞에 한 줄 안내를 붙인다.

> **정직성 표기(필수 · 2차 검증에서 정정)** — 이 기법은 **직접 시험되었고 결과는 통계적으로 결론에 도달하지 못했다**(F71: n=50, 검정력 부족, 3쌍 중 1쌍만 방향 부합, 1쌍은 역방향, 저자들이 스스로 신뢰할 만한 결론을 내릴 수 없다고 적었다). 등급은 **REPORT-ONLY**이고 **효과를 주장하지 않는다.** 강연 저자 본인의 유보("인터랙티브 요소는 crutch가 될 수 있고 slop이 될 수 있다")가 그의 제안 자체보다 근거가 낫다.
>
> **두 주장을 분리한다.**
> - **(a) "관련 부분을 묶어 산문 순서로 재배치하면 이해가 는다"** → REPORT-ONLY, 직접 시험 **결론 미달**(F71).
> - **(b) "가장 위험한 부분을 맨 앞에 놓아라"** → 이것만 근거가 있다(F72: 통제 실험 n=106 + 산업 관측 재현). **단서 둘을 반드시 병기한다** — **결과변수는 결함 탐지이지 이해가 아니고**, **두 결함 유형 중 하나에서만 나타났다**(다른 하나 p=0.346).
>
> **순서 개입의 상한**(F76) — 리뷰 세션의 53%만 첫 파일에서 시작하고, 파일 간 이동의 **37%만 도구 순서를 추종**하며, **55%가 변경 범위 밖 파일을 방문**한다. 경험 많은 리뷰어일수록 순서를 덜 따른다. **이 개입은 정의상 절반 남짓에만 닿는다.**
>
> Baum 외 (2017)의 6원칙(관련 부분 인접·필요 전 정보 제공·충돌 시 묶기·청크·동시 가시성·설명 가능한 규칙)은 체크리스트로 쓰되 라벨한다: **"12명 인터뷰 + 201명 설문에서 귀납된 중범위 이론이며, 저자들 자신의 확인 실험이 유의성에 도달하지 못했다."**

### B6. 순서보다 크기가 먼저다

같은 실험 안에서 **순서 효과 d=0.13(n.s.)** 인데 **크기 효과는 동일 결함 탐지율 76%→36%** 였다(F75, McNemar p≤0.0117). 설명서를 어떻게 배열할지 고민하기 전에 **"이 변경이 한 번에 읽히는 크기인가"** 를 문서 상단에 관측값으로 적는다.

**반대 단서를 병기한다** — **큰 변경을 두 PR로 쪼개는 것은 결함 탐지도 근거 이해도 개선하지 않았다**(n=28, 둘 다 null). 측정된 이득은 **오탐 감소뿐**(d=0.36). 즉 **"작게 만들어라"는 지지되고 "쪼개서 보여줘라"는 지지되지 않는다.** 하네스는 크기를 **관측해 적을 뿐 분할을 처방하지 않는다.**

### B7. "인지부하를 낮춘다"로 정당화하지 않는다

전문 개발자 **n=67** 등록보고서에서 **인지부하가 높을수록 성과가 좋았다**(F73). 이 축에서 부하 감소는 검증된 메커니즘이 아니다. 설명서의 가치는 리뷰어의 노동을 **덜어주는** 데 있지 않고 **어디에 쓸지 재배치**하는 데 있다.

## 3. 하지 않는 것

| 금지 | 왜 |
|---|---|
| **설득력 있는 서사로 쓴다** | 설명은 정오와 무관하게 수용률을 올린다(F9). 잘 읽히는 틀린 설명이 최악이다 |
| **인터랙티브 도해를 기본으로 넣는다** | 참여 위계에서 "보는 것"은 최하단이다([microworld-patterns.md](./microworld-patterns.md) 참조). 필요하면 Phase 4가 조건 검사를 거쳐 만든다 |
| **결함·리스크·머지 판정을 쓴다** | 이 하네스는 판정하지 않는다. 이상한 점은 **열린 질문**으로 적는다 |
| **"이 변경은 안전합니다"** | 보증하지 않는다 |
| **점수·등급·성숙도** | 어떤 형태로도 만들지 않는다 |
| **저자의 자기보고를 확인으로 옮긴다** | "테스트 통과했습니다"는 근거가 아니다. 직접 돌린 것만 `[확인]` |
| **길게 쓴다** | 장황함은 선호를 만들고 검증을 어렵게 한다(F14) |
| **"이 설명이 명료했는가"·"이 순서가 이해를 도왔는가"를 지표로 받는다** | **코드 리뷰 도메인 안에서 반증됐다**(F74) — 리뷰어의 **76%가 "위치는 나에게 영향 없다"고 답했으나 실제 오즈는 64% 달라졌고**, 순서 복잡도 지각은 **이해 지각으로도 객관 점수로도 이어지지 않았다**. 받더라도 **격차의 한쪽 항**으로만 |
| **분할을 처방한다** | "작게 만들어라"는 지지되고 **"쪼개서 보여줘라"는 지지되지 않는다**(F75) |

## 4. 산출 형식

기본은 **마크다운**이다. 사용자가 요청하면 **자체완결 HTML** 한 파일로 낸다(외부 CDN·폰트·이미지 참조 금지, CSS·JS 인라인).

HTML로 낼 때:
- 코드 블록은 `<pre>` 또는 `white-space: pre-wrap`이 있는 요소에만 넣는다(그렇지 않으면 줄바꿈이 뭉개진다).
- 파일명은 날짜 프리픽스(`YYYY-MM-DD-`)로 시작해 시간순 정렬되게 한다.
- **저장 위치는 사용자에게 묻는다.** 기본은 저장소 밖(스크래치 경로)이며, 저장소 안에 둘 때는 버전 관리 대상인지 확인한다.

## 5. 자체 점검 (문서를 내기 전)

- [ ] Phase 1 예측이 제출된 뒤에 공개하는가
- [ ] 채점 결과를 함께 보여주는가
- [ ] 모든 주장에 검증 훅이 붙었는가 — 없으면 그 주장을 지운다
- [ ] `[확인]`/`[추론]`이 문장마다 구분되는가
- [ ] `[추론]` 비율을 문서 맨 위에 적었는가
- [ ] 배경이 사전지식 수준에 맞게 잘렸고 접을 수 있는가
- [ ] 결함 판정·안전 보증·점수가 없는가
- [ ] 강연 유래 기법(literate diff·도해)에 **효과 주장이 붙지 않았는가**
