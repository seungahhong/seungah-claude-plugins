# 커밋 전 리뷰 레인 상세 (§9)

`commit` 모드에서 커밋 메시지 작성(§1) 이전에 실행하는 리뷰 레인의 상세 절차.

리뷰를 커밋 **전에** 두는 이유는 단순하다 — 커밋 후에 고치면 히스토리에 "리뷰 지적 반영" 커밋이 하나 더 붙고, 원래 커밋의 의도가 두 개로 쪼개진다.

---

## 대상 diff

| 상황 | 대상 |
| ---- | ---- |
| 스테이징된 변경이 있음 | `git diff --staged` |
| 스테이징된 변경이 없음 | `git diff` (작업트리 전체) |

`git diff --name-only`로 파일 목록을 함께 뽑아 서브에이전트에 전달한다.

---

## §9.1 /simplify 진행 여부 문의

```
[commit-pr] 커밋 전에 /simplify(code-simplifier)를 돌릴까요?

  1. 진행     — 명확성·중복·가독성 정리 후 코드리뷰 문의로
  2. 건너뛰기 — 바로 코드리뷰 문의로 (→ §9.3)

선택 (1 / 2):
```

## §9.2 code-simplifier 서브에이전트

Agent 도구로 `code-simplifier` 서브에이전트를 spawn한다(`model: "opus"`).

전달할 것:

- 대상 파일 목록과 diff
- **기능 변경 금지** — 동작 동일성을 유지한 채 명확성·중복·가독성만 개선한다
- 제안이 아니라 **직접 적용**한다
- 산출물: 적용한 변경 요약, 적용하지 않은 제안 목록

후처리:

- 파일이 바뀌었으면 `git add`로 **재스테이징**한다. 빠뜨리면 방금 다듬은 코드가 커밋에서 빠진 채 원본만 들어간다.
- 적용 내역을 사용자에게 간략히 보고한다.
- 끝나면 §9.3으로 간다.

폴백 순서:

1. `code-simplifier` 서브에이전트 spawn
2. 실패 시 내장 `/simplify` 호출
3. 그것도 불가하면 사용자에게 알리고 **건너뛴다** — 리뷰 도구 부재로 파이프라인 전체를 세우지 않는다

## §9.3 /code-review 진행 여부 문의

```
[commit-pr] 커밋 전에 코드리뷰를 돌릴까요?

  1. 진행     — correctness/security/performance/readability 리뷰
  2. 건너뛰기 — 바로 커밋 메시지 작성으로 (→ §1)

선택 (1 / 2):
```

## §9.4 코드리뷰 서브에이전트

내장 `/code-review`는 `disable-model-invocation`이라 Skill 도구로 호출할 수 없다. Agent 도구로 리뷰 서브에이전트를 spawn한다(`model: "opus"`).

전달할 것:

- 대상 diff와 파일 목록
- 관점 4종: **correctness · security · performance · readability**
- 각 발견에 반드시 **verdict**를 매길 것:
  - `CONFIRMED` — 코드를 읽어 **어떤 조건에서 어떻게 잘못되는지**까지 특정됨
  - `PLAUSIBLE` — 의심스럽지만 확정하지 못함(주변 코드 미확인, 호출부 불명 등)
- 발견 형식: `파일:라인 · 관점 · verdict · 무엇이 · 어떤 조건에서 잘못되는지`
- 못 본 영역(읽지 않은 파일, 확인 못 한 호출부)을 함께 보고할 것

verdict를 두 값으로만 두는 이유: 리뷰어에게 5단계 severity를 매기게 하면 등급이 흔들려 게이트 기준이 무의미해진다. **"확정했는가"**는 리뷰어가 실제로 답할 수 있는 질문이고, 심각도 환산은 아래 표가 결정론적으로 맡는다.

---

## 커밋 게이트 — severity 3등급 환산

| severity | 조건 | 처리 |
| -------- | ---- | ---- |
| 치명 | correctness & CONFIRMED | **차단** |
| 중요 | correctness & PLAUSIBLE, 또는 그 외 관점 & CONFIRMED | **차단** |
| 경미 | 그 외 관점 & PLAUSIBLE | 통과 |

**한 줄 요약: correctness이거나 CONFIRMED면 차단한다.**

### 차단 시

```
[gate] 커밋을 보류합니다. 치명 1건 · 중요 2건

| # | severity | 관점 | verdict | 파일:라인 | 내용 |
|---|----------|------|---------|-----------|------|
| 1 | 치명 | correctness | CONFIRMED | src/cart.ts:42 | ... |
```

- 수정 → `git add` 재스테이징 → **§9.4 재리뷰**로 돌아간다.
- 고쳤다는 자기보고를 통과 근거로 쓰지 않는다. 재리뷰 결과로만 판정한다.
- 사용자가 "이건 의도한 것"이라며 명시적으로 진행을 요청하면 그 판단을 따르되, **무엇을 안고 커밋하는지 한 줄로 남긴다**. 게이트는 경고이지 거부권이 아니다.

### 통과 시

경미만 남으면 목록을 한 번 보고하고 §1(커밋 메시지 작성)으로 진행한다. 경미까지 차단하면 게이트 자체가 무시당하기 시작한다.

---

## 안티패턴

- ❌ §9.2와 §9.4를 한 번에 spawn하고 결과를 합치기 — simplifier가 파일을 고치는 중에 리뷰어가 옛 코드를 읽는다. 이 레인은 순차다.
- ❌ 리뷰 결과의 로직 변경 제안을 확인 없이 자동 적용 — 동작이 달라지는 수정은 사용자 확인 대상이다.
- ❌ 스타일·미사용 import 같은 자명한 수정을 하나씩 확인받기 — simplifier가 적용하고 내역만 보고한다.
- ❌ 재스테이징 없이 커밋 — 리뷰 반영분이 커밋에서 누락된다.
