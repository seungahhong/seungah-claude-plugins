# PR 생성 상세 (§7)

`새 PR 생성` 경로에서 사용하는 상세 절차. push(§6)는 이미 끝난 상태로 들어온다.

---

## 타겟(base) 브랜치 결정

### 후보 제시

```bash
git branch -r
```

원격 브랜치 중 `origin/HEAD`(심볼릭 참조)와 현재 브랜치를 제외한 목록을 후보로 보여준다.
통합 브랜치(`rc`, `rc2`, `dev` 등)로 올리는 팀이 많아 `main`·`master`는 기본 추천에서 빼되, 사용자가 지목하면 그대로 쓴다.

### 유효성 검증

```bash
git ls-remote --heads origin <target-branch>
```

원격에 없으면 다시 입력을 요청한다.

### 현재 브랜치 확인

```bash
git branch --show-current
```

보호 브랜치에서는 PR을 만들지 않는다(§0.3에서 이미 걸러졌어야 한다). feature 브랜치로 전환을 안내한다.

### push 상태 확인

```bash
git log 'origin/<현재-브랜치>..HEAD' --oneline 2>/dev/null
```

미push 커밋이 남아 있으면 PR 생성 전에 push가 필요함을 알린다.

## 변경 사항 분석

`references/commit-message.md`의 **본문 작성 판단 프로세스(§1.4)** 를 PR 수준으로 확장 적용한다. 대상 diff는 타겟 브랜치 대비 전체 변경이다.

```bash
git fetch origin <target-branch> --quiet
git diff 'origin/<target-branch>...HEAD' --stat
git diff 'origin/<target-branch>...HEAD'
```

1. **변경 범위 파악** — 수정 파일 수, 변경 라인 수, 영향 모듈/레이어
2. **의도 추론** — 단순 버그 픽스인지, 구조 변경인지, 새 요구사항인지
3. **숨겨진 영향 탐색** — 인터페이스 변경, 동작 차이, 하위 호환성, 성능
4. **테스트 변경 확인** — 테스트 파일 추가/수정 여부, 커버 케이스

## PR 메시지 포맷

### 제목

```
이슈번호 type: 한국어 제목
```

- 브랜치명에서 `[A-Z]{2,}-\d+` 패턴으로 이슈 번호 추출(없으면 생략, 가짜 ID 금지)
- Type은 커밋과 동일 (feat/fix/docs/style/refactor/test/chore)
- 한국어 명령형, 70자 이내

### 본문

```markdown
## 요약
- 변경 내용의 핵심을 1~2문장으로 설명

## 배경 (선택)
- 왜 이 변경이 필요했는가
- diff만 봐서는 알 수 없는 비즈니스 맥락이나 기술 부채 배경

## 설계 (선택)
- 왜 이 방식인가. 대안이 있었다면 왜 이걸 골랐는지

## 영향
- 이전 동작과 달라진 점
- API 시그니처 변경, 기본값 변경, 삭제된 기능 등
- 영향이 없으면 "없음"으로 명시

## 테스트 시나리오
- 서비스 로직 관점에서 수동 검증이 필요한 항목
- 정상 동작, 엣지 케이스, 회귀 가능성 시나리오
```

**필수 섹션**: 요약, 영향, 테스트 시나리오
**선택 섹션**: 배경, 설계 — 내용이 있을 때만 포함. 억지로 채우지 않는다.

커밋 본문과 달리 PR 본문은 기본적으로 작성한다. 리뷰어는 커밋 히스토리를 모르는 상태로 들어오기 때문이다.

### 본문에 쓰지 않는 것

- 파일 단위 수정 사항 나열 (diff가 보여준다)
- 구현 단계 설명 (diff가 보여준다)
- diff에서 바로 읽히는 내용의 반복
- 출처 표기 문구 (예: `Co-Authored-By: ...`)

## 프리뷰 및 생성

프리뷰에서 묻는 것은 **"PR 만들까요?"가 아니라 "이 제목·본문으로 맞나요?"** 다. 생성 여부는 진입점 선택에서 이미 승인됐다.

```
[PR] 이 제목·본문으로 맞나요?

제목: <PR 제목>
Base: <target-branch>  ←  Head: <현재 브랜치>

--- 본문 ---
<PR 본문 프리뷰>
--- 본문 끝 ---

  1. 승인 — PR 생성
  2. 수정 — 제목/본문 수정 후 재프리뷰
```

승인 시:

```bash
gh pr create --base <target-branch> --title "<제목>" --body "$(cat <<'BODY'
<본문>
BODY
)"
```

생성된 PR URL을 출력하고 §8(PR 리뷰 여부 문의)로 간다.

## 예시

### 제목

```
FRONTEND-1234 feat: 커밋·PR 파이프라인 스킬 추가
```

### 본문 (필수 섹션만)

```markdown
## 요약
- 커밋·push·PR 생성·PR 리뷰를 하나의 진입점에서 이어서 처리하도록 통합

## 영향
- 기존 /commit, /review-to-pr 스킬을 대체한다
- 진입점 선택 이후에는 push·PR 생성 여부를 다시 묻지 않는다

## 테스트 시나리오
- 변경만 있는 상태에서 실행 시 commit이 추천되는지 확인
- push 완료 상태에서 실행 시 pr이 추천되는지 확인
- gh 미인증 상태에서 pr 모드 선택 시 안내 후 중단되는지 확인
```

### 본문 (선택 섹션 포함)

```markdown
## 요약
- 인증 미들웨어를 공통 모듈로 분리하여 라우트 핸들러의 중복 세션 검증 로직 제거

## 배경
- 각 라우트 핸들러에 중복돼 있던 세션 검증 로직을 한 곳에서 관리하기 위함
- 신규 라우트 추가 시 인증 로직 누락 사고가 2건 발생한 이력 있음

## 설계
- 미들웨어 패턴으로 추출. HOC 방식 대비 라우트 설정에서 의존성이 명확하게 드러남
- 인증이 필요 없는 공개 라우트는 `skipAuth` 옵션으로 명시적 제외

## 영향
- 기존 핸들러에서 직접 호출하던 `verifySession()`이 제거됨
- 토큰 갱신 정책 변경 시 수정 지점이 한 곳으로 집중

## 테스트 시나리오
- 미들웨어 적용된 라우트에서 유효한 세션으로 정상 접근 가능한지 확인
- 만료된 토큰으로 요청 시 401 응답 반환 확인
- 미들웨어 미적용 공개 라우트가 기존과 동일하게 동작하는지 확인
```
