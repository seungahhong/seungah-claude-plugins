# commit-pr — 커밋 · push · PR 생성 · PR 리뷰 파이프라인

커밋부터 PR 리뷰까지는 원래 한 줄기 작업인데, 스킬이 쪼개져 있으면 사용자가 매번 다음 스킬을 다시 불러야 한다.
이 스킬은 **저장소의 현재 상태를 먼저 읽어 어디서 시작할지 추천**하고, 사용자가 고른 지점부터 끝까지 한 흐름으로 진행한다.

## 흐름 지도

```
§0.1 상태 파악(조용히) → §0.2 진입점 질문 → §0.3 모드별 전제 조건 검사
        │
   ┌────┼──────────────┬───────────────────────────┐
   │ commit            │ push                      │ pr ─┬─ 기존 PR 지정 ──→ §8
   ▼                   ▼                           ▼     └─ 새 PR 생성 ───→ §7
 §9.1 /simplify 문의   §6 Push                    §7
 §9.2 code-simplifier  (§9~§5 건너뜀)
 §9.3 코드리뷰 문의
 §9.4 코드리뷰 + 커밋 게이트(차단)
 §1~§4 커밋 메시지 작성 + Validation
 §5 프리뷰 → 승인 → 커밋
   │
   └──→ §6 Push ──→ §7 PR 생성 ──→ §8 PR 리뷰 여부 문의 ──→ 종료 요약
```

섹션 번호(§1~§9)는 문서상의 사양 번호이고, **실행 순서는 위 지도**를 따른다(리뷰 레인 §9가 커밋 §1보다 먼저 실행된다).

## 설계 원칙 — 진입점 선택 = 이후 단계 승인

사용자가 §0.2에서 진입점을 고르는 순간, **그 지점부터 파이프라인 끝까지 진행하는 데 동의한 것**으로 본다.
진행 중에 "push할까요?", "PR 만들까요?"를 다시 묻지 않는다. 흐름만 끊고 정보를 더해주지 않는 질문이기 때문이다.

예외는 둘뿐이다:

1. **되돌리기 어려운 행위 직전의 *내용* 확인** — §5 커밋 메시지 프리뷰, §7 PR 제목·본문 프리뷰.
   여부를 묻는 게 아니라 "이 내용이 맞나"를 묻는 것이라 흐름을 끊을 값어치가 있다.
2. **§8 PR 리뷰 실행 여부** — 팀원이 보는 인라인 코멘트가 GitHub에 남는 행위라 모드와 무관하게 따로 묻는다.

§0.2에서 사용자에게 "중간에서 멈추고 싶으면 그 지점에서 말씀해 주세요"라고 미리 알려, 되묻지 않는 대신 언제든 멈출 수 있게 한다.

## §0.1 상태 파악 — 질문하기 전에 조용히 수행

진입점을 추천하려면 저장소가 지금 어떤 상태인지 알아야 한다. 사용자에게 묻기 **전에** 다음을 실행한다(출력을 그대로 쏟지 말고 판단에만 쓴다):

```bash
git status --porcelain          # 작업트리·스테이징 변경
git branch --show-current       # 현재 브랜치
git log --oneline -10           # 최근 커밋
git log '@{u}..HEAD' --oneline  # 미push 커밋 (upstream 없으면 실패)
gh pr view --json number,url,title,state 2>/dev/null   # 현재 브랜치의 열린 PR
```

**실패도 판단 근거다.** `@{u}` 조회 실패는 "upstream 미설정 = 아직 한 번도 push 안 됨", `gh pr view` 실패는 "열린 PR 없음 또는 gh 미인증"을 뜻한다. 실패했다고 중단하지 말고 신호로 읽는다.

## §0.2 진입점 질문 — 사용자가 보는 첫 상호작용

§0.1의 상태를 근거로 **각 항목에 (추천) 표시와 왜 추천인지 한 줄**을 붙여 제시한다. 상태를 읽지 않고 세 개를 나열만 하면 사용자가 대신 판단해야 한다.

```
[commit-pr] 어디서부터 시작할까요?

  1. commit — 변경 3개 파일이 스테이징돼 있습니다 (추천)
  2. push   — 미push 커밋 없음
  3. pr     — push된 커밋이 없어 아직 PR을 만들 수 없습니다

중간에서 멈추고 싶으면 그 지점에서 말씀해 주세요.
선택 (1 / 2 / 3):
```

추천 기준:

| 상태 | 추천 |
| ---- | ---- |
| 작업트리·스테이징에 변경 있음 | 1. commit |
| 미push 커밋 있음 | 2. push |
| push 완료 / 열린 PR 있음 | 3. pr |

### PR 단계 하위 분기 질문

`3. pr`을 선택하면 한 번 더 묻는다:

```
  1. 기존 PR 지정 — 이미 열려 있는 PR을 대상으로 합니다
  2. 새 PR 생성   — 현재 브랜치로 새 PR을 만듭니다
```

- **기존 PR 지정** — PR 번호나 URL을 입력받고 `gh pr view <번호|URL>`로 대상을 확정한다. → **§8로 직행**(§1~§7 전부 건너뜀)
- **새 PR 생성** — 타겟(base) 브랜치를 확인하고 → **§7로**

## §0.3 모드별 전제 조건 검사

선택된 모드에만 해당하는 검사를 수행한다. 관련 없는 검사로 사용자를 붙잡지 않는다.

| 검사 | 적용 모드 | 내용 |
| ---- | -------- | ---- |
| 보호 브랜치 | commit · push · 새 PR | 현재 브랜치가 `main`/`master`/`dev`/`cdev`/`develop`/`release`/`rc`·`rc2`·`rc3`·`rc4` 인지 |
| 커밋 대상 존재 | commit | 스테이징 또는 작업트리에 변경이 있는지 |
| 미push 커밋 존재 | push | push할 커밋이 실제로 있는지 |
| 미push 커밋 부재 | 새 PR | 남아 있으면 PR 전에 push가 필요하다고 안내 |
| secret 의심 문자열 | commit · push | 대상 diff에 `API_KEY=` · `SECRET=` · `TOKEN=` · `Bearer ` · `-----BEGIN` |
| gh 사용 가능 | pr | `which gh && gh auth status` |

**기존 PR 리뷰에는 보호 브랜치 검사를 적용하지 않는다** — 리뷰는 저장소에 쓰는 행위가 아니라서 보호 브랜치 여부가 위험 요소가 아니다.

보호 브랜치 목록은 팀마다 다르다. 위 목록에 없는 통합 브랜치를 쓰는 저장소라면 사용자가 알려준 이름을 그 세션 동안 보호 브랜치로 취급한다.

**불충족 시 중단한다.** 무엇이 불충족인지 사용자에게 알리고, 명시적 승인이나 진입점 재선택을 받기 전까지 다음 단계로 진행하지 않는다. 여기서 조용히 넘어가면 보호 브랜치 직접 커밋·secret 커밋처럼 되돌리기 비싼 사고가 난다.

## §9 커밋 전 리뷰 레인 (commit 모드 전용)

상세 절차·서브에이전트 프롬프트 규격·게이트 판정표는 [`references/review-lane.md`](references/review-lane.md)를 따른다.

### §9.1 /simplify 진행 여부 문의

```
  1. 진행     — code-simplifier로 명확성·중복·가독성 정리
  2. 건너뛰기 — 바로 코드리뷰 문의로 (→ §9.3)
```

### §9.2 code-simplifier 서브에이전트

Agent 도구로 `code-simplifier` 서브에이전트를 spawn한다(`model: "opus"`).

- 기능 변경 없이 명확성·중복·가독성 개선을 **직접 적용**한다.
- 파일이 바뀌었으면 재스테이징(`git add`)한 뒤 §9.3으로 간다. 재스테이징을 빠뜨리면 방금 다듬은 코드가 커밋에서 빠진다.
- spawn 실패 → 내장 `/simplify` 폴백 → 그것도 불가하면 사용자에게 알리고 건너뛴다. 리뷰 도구 부재로 파이프라인 전체를 세우지 않는다.

### §9.3 /code-review 진행 여부 문의

```
  1. 진행     — 코드리뷰 서브에이전트 실행
  2. 건너뛰기 — 바로 커밋 메시지 작성으로 (→ §1)
```

### §9.4 코드리뷰 서브에이전트

내장 `/code-review`는 `disable-model-invocation`이라 Skill 도구로 호출할 수 없다. 대신 Agent 도구로 리뷰 서브에이전트를 spawn한다(`model: "opus"`).

- 관점: **correctness · security · performance · readability**
- 각 발견에 **verdict**를 매긴다 — `CONFIRMED`(코드를 읽어 재현 조건까지 특정됨) / `PLAUSIBLE`(의심되지만 확정 못 함)
- 발견 형식: `파일:라인 · 관점 · verdict · 무엇이 · 어떤 조건에서 잘못되는지`

### 커밋 게이트 — severity 3등급 환산

verdict 두 값과 관점을 severity 3등급으로 환산해 커밋을 통과시킬지 정한다:

| severity | 조건 | 처리 |
| -------- | ---- | ---- |
| 치명 | correctness & CONFIRMED | **차단** |
| 중요 | correctness & PLAUSIBLE, 또는 그 외 관점 & CONFIRMED | **차단** |
| 경미 | 그 외 관점 & PLAUSIBLE | 통과 |

**한 줄 요약: correctness이거나 CONFIRMED면 차단한다.**

- 치명·중요가 하나라도 있으면 커밋하지 않는다. 수정 → 재스테이징 → **§9.4 재리뷰**로 돌아간다. 고쳤다는 자기보고가 아니라 재리뷰 결과로 통과를 판정한다.
- 경미만 남으면 목록을 보고하고 §1로 통과시킨다. 경미까지 차단하면 게이트가 무시당하기 시작한다.

## §1~§4 커밋 메시지 작성 + Validation

형식 사양·type 표·본문 작성 판단 프로세스·예시·검증 체크리스트는 [`references/commit-message.md`](references/commit-message.md)를 따른다. 핵심만:

- 형식 `이슈번호 type: 제목`. 이슈번호는 브랜치명에서 `[A-Z]{2,}-\d+`로 추출하고, **없으면 생략한다(가짜 ID 금지)**.
- type 7종: `feat` `fix` `docs` `style` `refactor` `test` `chore`
- 제목은 한국어 명령형.
- **본문은 기본 생략.** 제목만으로 의도가 전달되지 않을 때만 요약/배경/설계/영향/테스트 시나리오를 붙인다.
- 출처 표기(`Co-Authored-By: ...` 등) 금지.
- 커밋 직전 체크리스트로 검증한다.

## §5 커밋 메시지 프리뷰 → 승인

메시지 전문을 보여주고 두 선택지를 제시한다. 직접 `git commit`을 먼저 실행하지 않는다.

```
  1. 승인 — 이 메시지로 커밋
  2. 거절 — 피드백을 반영해 메시지 수정 후 재프리뷰
```

승인 시 **stdin으로** 커밋한다:

```bash
git commit --cleanup=whitespace -F - <<'MSG'
FRONTEND-1234 feat: 결제 수단 선택 UI 추가
MSG
```

- `--cleanup=whitespace` — 본문이 `# 요약` 같은 헤딩을 쓰는데, 기본 cleanup 모드는 `#`로 시작하는 줄을 주석으로 보고 지워버린다. 이 옵션이 없으면 본문이 통째로 사라진다.
- `-F -` (stdin) — `/tmp/commit-message.txt` 같은 **고정 경로를 쓰지 않는다**. 병렬 세션에서 서로의 메시지를 덮어쓰고, 실패 시 남은 파일이 다음 커밋에 섞인다.

거절 시 피드백을 반영해 메시지를 고치고 다시 프리뷰한다. 커밋이 끝나면 §6으로 간다.

## §6 Push — 여부를 다시 묻지 않음

진입점 선택이 이미 승인이다. 대신 **무엇을 어디로 보내는지 한 줄로 통보**하고 실행한다.

```
[push] <현재 브랜치> → origin/<현재 브랜치> (커밋 2개)
```

```bash
git push -u origin <현재 브랜치>
```

- 실패하면 **원문 에러를 그대로 출력하고 중단**한다. `non-fast-forward`는 사용자가 봐야 할 정보다.
- `--force` / `--force-with-lease` / `--no-verify` 류는 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.
- 보호 브랜치로의 push는 §0.3에서 이미 걸러졌어야 한다. 여기까지 왔다면 재확인 없이 push하지 않는다.

## §7 PR 생성 — 여부를 다시 묻지 않음

상세 절차(브랜치·타겟 검증, 변경 분석, 제목·본문 포맷)는 [`references/pr-creation.md`](references/pr-creation.md)를 따른다.

1. **타겟(base) 추천** — `git branch -r`의 원격 브랜치 중 `HEAD`(심볼릭 참조)와 현재 브랜치를 제외한 목록을 후보로 보여준다. 통합 브랜치(`rc`, `dev` 등)로 올리는 팀이 많아 `main`·`master`는 기본 추천에서 빼되, 사용자가 지목하면 그대로 쓴다.
2. `references/pr-creation.md` 절차로 브랜치·타겟 유효성을 검증하고, 변경을 분석해 제목·본문을 작성한다.
3. **프리뷰 승인** — "PR 만들까요?"가 아니라 **"이 제목·본문으로 맞나요?"**를 묻는다. 여부는 이미 승인됐고, 확인할 값어치가 있는 건 내용이다.
4. 생성 후 PR URL을 출력한다.

```bash
gh pr create --base <target> --title "<제목>" --body "$(cat <<'BODY'
<본문>
BODY
)"
```

## §8 PR 리뷰 여부 문의 — 진입점 승인의 명시적 예외

**모드와 무관하게 반드시 따로 묻고, 승인된 경우에만 리뷰한다.** GitHub PR에 팀원이 보는 인라인 코멘트가 남는 행위라, 다른 단계와 달리 되돌리기가 사회적으로도 비싸다.

```
[review] 방금 만든 PR(<URL>)을 리뷰할까요?

  1. 리뷰 진행
  2. 종료
```

- **1. 리뷰 진행** — 내장 `/review`를 **명시 호출**한다. Skill 도구에 PR URL을 인자로 넘긴다.
  다른 플러그인에도 `review`라는 동명 커맨드가 있을 수 있어 자연어 트리거에 의존하면 엉뚱한 스킬이 뜬다. 항상 Skill 도구로 이름을 지정해 호출한다.
- **2. 종료** — 리뷰 없이 끝낸다. PR은 그대로 열려 있으니 나중에 언제든 리뷰할 수 있다고 한 줄 알린다.

## 종료 요약

어느 지점에서 끝났든 마지막에 한 줄로 요약한다 — **커밋 해시 · push 여부 · PR URL**.

```
[완료] a1b2c3d 커밋 · origin/FE-851 push 완료 · PR https://github.com/org/repo/pull/123
```

## 사용자 소통 원칙

- 단계 전환 시 지금 무엇을 하는지 한 줄로 알린다(질문이 아니라 통보).
- 에러는 원문을 그대로 전달하고 임의로 재시도하지 않는다.
- 서브에이전트가 자동 적용한 수정은 내역을 간략히 보고한다.
- 사용자가 중간에 멈추자고 하면 그 지점에서 멈추고, 어디까지 됐는지 요약한다.
