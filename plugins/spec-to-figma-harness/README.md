# spec-to-figma-harness

기획(유저스토리·인수조건)을 **디자인에 어떻게 반영해야 FE가 되묻지 않고 개발할 수 있는지**로 옮겨 주는 하네스.

> **한 문장 원칙** — 기획서의 **시나리오**는 *상태 프레임*으로, 기획서의 **규칙**은 *레이어 어노테이션*으로.

## 무엇을 하나

FE가 개발하다 멈추는 지점은 기획 문서와 Figma 사이에 남은 **추측해야 하는 틈**이다. 이 하네스는 그 틈을 **착수 전에 목록으로 드러내는** 절차를 4단계로 돌린다(틈을 메우는 것은 사람의 답변이지 AI의 추측이 아니다).

1. **AC 분해 · 상태 전수 도출** — AC 한 줄마다 "화면이 바뀌는가(→프레임) / 값·조건인가(→어노테이션)"를 판정하고, 상태 카탈로그 6축(데이터 · 진행/전이 · 입력/검증 · 권한/세션 · 콘텐츠 경계 · 반응형)을 **역방향으로 호명**해 AC에 없는 상태를 드러낸다.
2. **Figma 반영 설계도** — 페이지=에픽 / 섹션=유저스토리 / 프레임=상태로 이름을 확정하고, 프레임 목록·프로토타입 flow·Variables·컴포넌트·Auto Layout 요구·Ready for dev 계획을 낸다. 기존 파일이 있으면 **있는 것 / 없는 것 / 이름이 다른 것**을 읽기 전용으로 대조한다.
3. **어노테이션 스펙** — 디자인만 봐서는 알 수 없는 규칙을 레이어별 핀 문안으로 쓴다(인터랙션 · 데이터 바인딩 · 검증 규칙 · 모션 · 트래킹 · 참조/예외). **확정은 어노테이션, 논의 중은 댓글**로 분리해 제안한다.
4. **FE 자율개발 적대 검증** — "이 문서만 들고 개발을 시작하면 어디서 멈추는가"를 FE 1인칭으로 캐고, 준비도를 기획·디자이너·FE owner별로 판정한 뒤 **남은 질문 목록**을 남긴다.

## 어떻게 쓰나

```
/spec-to-figma
```

또는 그냥 이렇게 말해도 된다.

- "이 유저스토리랑 인수조건을 피그마 화면 구조로 번역해줘"
- "AC별로 어떤 프레임·상태가 필요한지 뽑고 어노테이션 문안까지 만들어줘"
- "기획을 디자이너용 반영 지시서로 바꾸고, 빠진 상태가 뭔지도 캐줘"

시작하면 **한 번에 하나씩** 묻는다 — 스토리·AC 원문 → 범위 → 티켓 ID 체계 → 기존 Figma 파일 → 디자인 시스템/플랜 → 반응형 → 산출물 위치. 매 단계 끝에 산출물을 보여주고 **승인을 받은 뒤에만** 다음으로 넘어간다.

저장을 선택하면 `.claude/_docs/<슬러그>/` 아래에 남는다(기본은 채팅 제시).

| 파일 | 내용 |
|------|------|
| `state-map.md` | AC↔상태 커버리지 매트릭스 · 역방향 호명 결과 · 되물음 목록 |
| `blueprint.md` | 명명 규칙 · 프레임 목록 · 레이어 지목 · flow · 토큰 요구 · 기존 파일 델타 |

| `readiness-report.md` | FE가 멈추는 지점 · 상충 · owner별 준비도 · 남은 질문 |

## 정직성 (은탄환 없음)

- **모르는 값을 지어내지 않는다.** 에러 문구·버튼 라벨·API 필드·트래킹 이벤트명·글자 수 제한·임계값은 **당신이 준 것만** 쓴다. 없으면 `[기획 확인 필요]`로 남기고 되물음에 올린다. 그럴듯한 마이크로카피를 채우면 디자이너가 그리고 FE가 구현해 **틀린 값이 스펙이 된다**.
- **커버리지는 품질이 아니다.** "AC 전수 매핑하면 FE 질문이 0이 된다"·"재작업 N% 감소" 같은 주장은 **측정 근거가 없어 인용하지 않는다**. 준비도를 점수·백분율로 환산하지도 않는다.
- **디자인을 대신 결정하지 않는다.** 무엇이 필요한지까지가 산출이고, 어떻게 보일지는 디자이너의 결정이다. **Figma 파일을 만들거나 고치지 않는다** — 기존 파일은 읽기만 한다.
- **팀이 못 쓰는 기능을 전제하지 않는다.** Code Connect(Organization/Enterprise + Dev/Full seat), 어노테이션 생성(Full seat + 편집 권한), `Ready for dev` view·`Completed`(Org/Enterprise)는 플랜 조건이 있다. 못 쓰면 대체 경로를 함께 준다.
- **관행은 관행이라 말한다.** 티켓 ID 명명, 어노테이션 vs 댓글 분기는 Figma 공식 근거가 없는 실무 관행이다. 왜 유용한지는 설명하되 효과 수치는 붙이지 않는다.
- **커밋하지 않는다.** 파일 저장은 미리보기 후 승인할 때만.

## 경계

다음은 이 하네스가 하지 않는다.

- 이미 있는 디자인의 누락·사각지대를 **읽기 전용으로 검수해 게이트 판정**하기
- Figma 링크에서 **디자인 컨텍스트를 추출해 코드 작업용 파일로** 내리기
- 기획안에서 **PRD·유저스토리를 처음부터 작성**하기 (스토리·AC는 이 하네스의 **입력**이다)
- 인수조건을 **테스트 계층·QA 시나리오로 전개**하기
- 화면을 **코드로 구현·리뷰·커밋**하기

이 하네스의 자리는 하나다 — **요구는 있는데 디자인이 무엇이어야 하는가**.

## 구성

- 스킬 1개: `spec-to-figma` (오케스트레이터)
- 에이전트 4개: `state-cartographer` / `figma-blueprinter` / `annotation-writer` / `handoff-critic` (모두 opus)
- 참조 5종: AC 분해 매트릭스 · 어노테이션 템플릿 · Figma 설계 규약 · 준비도 체크리스트 · **근거 대장**
- 다른 플러그인에 의존하지 않는 **독립 플러그인**이다.
