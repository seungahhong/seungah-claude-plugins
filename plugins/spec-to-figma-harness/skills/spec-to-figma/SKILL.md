# Spec to Figma — 기획 → 디자인 반영 → FE 자율개발 핸드오프 오케스트레이터

유저스토리와 인수조건(AC)을 입력으로 받아, **FE가 추측하지 않고 개발할 수 있는 Figma 반영 설계도**를 만든다. 특정 제품·도메인에 종속되지 않은 공통 절차다.

> **한 문장 원칙** — 기획서의 **시나리오**는 *상태 프레임*으로, 기획서의 **규칙**은 *레이어 어노테이션*으로.
>
> "~하면 ~화면이 보인다"는 눈에 보이는 프레임으로 그리고, "20자 제한", "스크롤 100px에서 고정"은 해당 레이어에 붙는 어노테이션으로 남긴다. 이 둘이 빠짐없이 채워지면 개발자가 추측할 것이 줄어든다.

4 Phase로 진행한다: **AC 분해·상태 도출(Phase 1) → Figma 반영 설계도(Phase 2) → 어노테이션 스펙(Phase 3) → FE 자율개발 적대 검증(Phase 4)**. 그 앞에 **Phase 0 스펙 인테이크**가 있고, 매 Phase 종료 시 핵심 산출물 + 1줄 보고를 제시하고 **사용자 승인을 받은 뒤에만** 다음으로 넘어간다.

## 왜 '스토리에서 출발·발명 금지·검증 가능한 틈'인가

1. **화면이 아니라 스토리에서 출발한다** — 화면 목록부터 그리면 "왜 이 화면이 필요한가"가 사라지고, 티켓↔디자인↔코드의 추적이 끊긴다. AC를 먼저 분해해야 *빠진 상태*가 드러난다.
2. **모르는 값을 지어내지 않는다** — 이 하네스의 가장 큰 실패 모드는 LLM이 그럴듯한 에러 문구·API 필드명·글자 수 제한을 **채워 넣는 것**이다. 그 추측은 디자이너가 그대로 그리고 FE가 그대로 구현해 **틀린 값이 스펙이 된다**. 확인되지 않은 값은 `[기획 확인 필요]`로 남기고 되물음 목록에 올린다.
3. **커버리지는 품질의 증거가 아니다** — "AC 4개 = 프레임 4개"는 누락 점검 장치이지 품질 보증이 아니다. "전수 매핑하면 개발자 질문이 0이 된다"는 종류의 정량 주장은 **측정된 근거가 없다**([references/evidence.md](./references/evidence.md)). 이 하네스는 커버리지를 세되 그것으로 품질을 약속하지 않는다.

## 경계 (먼저 읽고 발동 여부를 판단하라)

이 하네스의 고유 판별자는 **요구(스토리·AC)는 있는데 디자인이 무엇이어야 하는가를 *생성*** 하는 것이다. 방향은 **기획 → 디자인 → FE**이며, 다음은 명시적으로 범위 밖이다.

- **이미 있는 디자인의 검수·게이트 판정** — *디자인이 있고 그것이 충분한가*를 읽기 전용으로 판정해 디자인팀에 되돌리는 작업은 범위 밖이다. 이 하네스는 *아직 없는* 화면·상태·규칙을 설계한다.
- **Figma 링크의 디자인 컨텍스트 추출·파일화** — 노드 맵·토큰·스크린샷을 뽑아 코드 작업용 컨텍스트 파일로 내리는 작업은 범위 밖이다.
- **PRD·유저스토리 작성** — 스토리·AC는 이 하네스의 **입력**이다. 문제 정의에서 스토리를 만들어내는 작업은 범위 밖이다(입력이 없으면 만들지 말고 **되묻는다**).
- **인수조건의 테스트 계층 전개·QA 시나리오 설계·실행** — AC를 unit/통합/E2E나 테스트 시나리오로 전개하는 작업은 범위 밖이다.
- **화면의 코드 구현·컴포넌트 작성·리뷰·커밋** — 산출물은 디자인 반영 설계와 핸드오프 문서이지 코드가 아니다.
- **Figma 파일을 대신 만들거나 수정하는 것** — 아래 INV-3 참조. 기존 파일은 **읽기 전용**으로만 참조한다.

경계가 모호하면 한 질문으로 확인한다 — "*스토리·AC로 디자인에 무엇을 반영해야 할지 설계* 하려는 건가요, 아니면 *이미 있는 디자인 검수 / 컨텍스트 추출 / 스토리 작성 / 테스트 전개 / 코드 구현*을 하려는 건가요?" **후자면 이 하네스의 범위 밖임을 한 줄로 알리고 종료한다**(다른 도구를 지목하거나 대신 수행하지 않는다).

## 내재화 원칙 (모든 Phase가 따른다)

- **승인 게이트** — 매 Phase 종료 시 핵심 산출물 + 1줄 보고를 제시하고 사용자 승인을 받는다. 형식: `[Phase N] {핵심결정} — 다음: {다음}. 진행할까요?`
- **한 번에 한 질문(짧게)** — 인테이크·되물음은 한 번에 하나만. 번호 선택지를 제시하고, 직전 답이 다음 질문을 결정한다. 질문을 목록으로 쏟아붓지 않는다. 어려운 용어(어노테이션·Variables·Code Connect·Auto Layout)는 처음 등장 시 쉬운 말 1줄 정의를 곁들인다.
- **INV-1 · 발명 금지(가장 강한 불변식)** — 사용자에게 노출되는 **문구 원문**, **API 필드·파라미터**, **트래킹 이벤트명**, **수치 경계**(글자 수·임계값·재시도 횟수), **권한 정의**는 사용자가 준 것만 쓴다. 없으면 `[기획 확인 필요: 무엇이 필요한지]` 플레이스홀더 + 되물음 목록. **그럴듯한 마이크로카피를 채우지 않는다.** — *예외*: 카탈로그의 **표준 상태명**(로딩·빈 상태·에러 등)을 상태·프레임 이름으로 쓰는 것은 발명이 아니다(금지 대상은 *사용자에게 노출되는 값*이지 분류 어휘가 아니다). 화면의 **업무 명칭**은 예외가 아니다.
- **INV-2 · 커버리지 ≠ 품질** — AC↔프레임 매핑 수를 세되 "질문 0", "재작업 N% 감소" 같은 효과를 약속하지 않는다. 정량 수치는 [references/evidence.md](./references/evidence.md)의 등급·출처와 함께만 인용하고, 그 문서의 **인용 금지 목록**은 사실로 말하지 않는다.
- **INV-3 · 디자인 결정을 대신하지 않는다** — 이 하네스는 *무엇이 필요한가*(어떤 상태·어떤 규칙·어떤 구조·어떤 이름)를 명세한다. *어떻게 보일까*(레이아웃·비주얼·톤)는 디자이너의 결정이다. **Figma 파일을 생성·수정하지 않는다.** 기존 파일은 델타 진단을 위한 읽기 전용 참조만 허용한다.
- **INV-4 · 도구 제약 정직** — Figma의 일부 기능은 특정 시트·플랜에서만 쓸 수 있다(Code Connect = Dev/Full seat + Organization/Enterprise, 어노테이션 *생성* = Full seat + 편집 권한, `Ready for dev` view·`Completed` 상태 = Org/Enterprise). 팀이 쓸 수 없는 기능을 전제한 체크 항목을 강요하지 않고 **대체 경로**를 함께 제시한다. 상세·출처는 [references/figma-blueprint.md](./references/figma-blueprint.md).
- **INV-5 · 되물음은 산출물이다** — 확인 못 한 항목을 숨기고 매끈한 문서를 내지 않는다. 되물음 목록(누구에게·무엇을·왜 필요한지)은 1급 산출물이며, 빈칸이 있는 정직한 문서가 채워진 추측보다 낫다.
- **커밋하지 않는다** — 파일 저장은 opt-in(`.claude/_docs/<슬러그>/`), 저장 전 미리보기 후 승인.

## 산출물 배치

별도 지정이 없으면 최종 산출물은 **채팅으로 제시**한다. 사용자가 저장을 원하면 **`.claude/_docs/<슬러그>/`** 에 기록한다(슬러그는 스토리/에픽 이름에서, 시작 시 한 번 확인). 모든 언어는 **한국어**. **모든 파일은 사용자가 저장을 선택할 때만 기록한다.**

```
.claude/_docs/<슬러그>/
  state-map.md          # Phase 1 AC↔상태 커버리지 매트릭스 + 되물음 목록 — 저장 선택 시
  blueprint.md          # Phase 2 구조·프레임 목록·레이어 지목·flow·토큰 요구 — 저장 선택 시
  annotations.md        # Phase 3 레이어별 어노테이션 스펙(복붙용) — 저장 선택 시
  readiness-report.md   # Phase 4 적대 검증 + 준비도 판정 + 남은 질문 — 저장 선택 시
```

> 산출물 파일명은 `references/`의 방법론 문서 이름과 겹치지 않게 둔다(같은 이름이면 어느 쪽이 산출물인지 혼동된다).

# 인터랙티브 플로우

## Phase 0 — 스펙 인테이크 (**가장 먼저**)

> **첫 행동 규약(불변식)** — 사용자가 "화면 목록 뽑아줘"처럼 결과물만 지목하더라도, **먼저 유저스토리·AC 원문을 확보한다.** 스토리 없이 화면부터 설계하면 이 하네스는 추측 생성기가 된다. AC가 아예 없으면 그 사실을 말하고, ⓐ 가진 만큼만으로 진행(누락은 전부 되물음으로) 또는 ⓑ 스토리·AC부터 정리하고 돌아오기를 **사용자가 고르게** 한다.

**한 번에 한 질문**으로 아래를 채운다. 이미 답이 주어진 항목은 묻지 않고 확인만 한다.

1. **스토리·AC 원문** — 붙여넣기 / 파일 경로 / 티켓 링크 중 무엇으로 줄지. (없으면 위 규약대로 분기)
2. **범위** — 이번에 다룰 스토리 개수(1개인지 에픽 전체인지). 많으면 우선순위 상위 N개부터.
3. **티켓 ID 체계** — `US-123`·`PROJ-456` 등 실제로 쓰는 표기. 없으면 임시 ID를 쓰되 임시임을 표시.
4. **기존 Figma 파일 유무** — 있으면 링크(델타 진단용 **읽기 전용**), 없으면 신규 설계.
5. **디자인 시스템·토큰** — 공용 라이브러리 컴포넌트와 Variables(색·간격 토큰)를 쓰고 있는지.
6. **코드 컴포넌트 매핑** — 코드베이스 컴포넌트와 Figma 컴포넌트가 연결(Code Connect)돼 있는지. *모른다*도 유효한 답이다.
7. **팀 플랜·시트** — Organization/Enterprise인지, 편집 가능한 Full seat이 있는지(INV-4의 대체 경로 판단에 쓴다). 모르면 "미확인"으로 두고 해당 항목을 '해당없음'으로 처리한다.
8. **반응형 대상** — 브레이크포인트가 필요한지, 필요하면 어떤 폭인지.
9. **산출물 위치** — 채팅만 / 파일 저장(저장이면 슬러그도 함께 확인). **여기서 정한 값을 마무리에서 다시 묻지 않는다.**

**게이트 A** — 인테이크 카드를 표로 보여주고 승인받는다.
`[Phase 0] 스토리 {N}개·티켓체계 {X}·기존파일 {유/무} 확보 — 다음: AC 분해·상태 도출. 진행할까요?`

## Phase 1 — AC 분해 · 상태 전수 도출

`state-cartographer`를 `model: "opus"`로 호출한다. 입력: Phase 0 카드 + 스토리·AC 원문. 참조: [references/ac-to-state-matrix.md](./references/ac-to-state-matrix.md).

수행 내용:
1. **이분 분류** — AC 한 줄마다 시나리오(→프레임) / 규칙(→핀) / 둘 다 / 판정 불가를 판정한다. 한 AC가 상태 여러 개를 만들 수 있음을 전제한다.
2. **역방향 호명** — 상태 카탈로그(데이터·진행·입력검증·권한세션·콘텐츠 경계·반응형)를 하나씩 호명해 "해당하는가 / AC가 있는가"를 판정한다. 해당하는데 AC가 없으면 **되물음**이다(결함 단정 금지).
3. **커버리지 매트릭스** — AC↔상태↔프레임(예정)↔핀(예정)을 양방향으로 채운다.
4. **되물음 목록** — INV-1에 걸리는 미확인 값을 "누구에게 / 무엇을 / 왜 필요한지"로 적는다.

**게이트 B** — 매트릭스 + 되물음 목록을 제시한다. 되물음이 있으면 **여기서 사용자가 답할 기회를 준다**(한 번에 하나씩, 최대 5개까지 묻고 나머지는 목록으로 남긴다). 답변은 그대로 반영하고, 답 못 한 항목은 `[기획 확인 필요]`로 유지한다.
`[Phase 1] AC {N}개 → 상태 {M}개(신규 발견 {K}개)·되물음 {Q}개 — 다음: Figma 반영 설계. 진행할까요?`

## Phase 2 — Figma 반영 설계도

`figma-blueprinter`를 `model: "opus"`로 호출한다. 입력: Phase 1 매트릭스. 참조: [references/figma-blueprint.md](./references/figma-blueprint.md).

수행 내용:
1. **구조·명명** — 페이지=에픽 / 섹션=유저스토리 / 프레임명=`{티켓ID} / {화면} · {상태}` 규칙으로 전체 이름을 확정한다(명명 규칙 자체는 실무 관행이며 공식 근거가 아님을 표기 — evidence.md).
2. **프레임 목록** — Phase 1의 상태마다 프레임 1행. 각 행에 대응 AC 번호·필요 이유·"이미 있음/신규" 표시.
3. **기존 파일 델타(있을 때)** — Figma MCP 읽기 도구로 현재 프레임 이름을 받아 **있는 것 / 없는 것 / 이름이 다른 것**을 대조한다. **읽기 전용**(INV-3).
4. **프로토타입 연결** — 어느 프레임에서 어느 프레임으로 가는지 flow 표. 흐름은 텍스트 설명보다 연결로 표현한다.
5. **토큰·컴포넌트 요구** — Variables/라이브러리 컴포넌트/Auto Layout 사용 요구와, 그것이 Inspect 정확도에 왜 필요한지. Code Connect는 **플랜 조건과 함께** 제안한다(INV-4).
6. **Ready for dev 계획** — 어떤 섹션/프레임을 언제 마킹할지. 플랜 제약과 대체 경로 병기.

**게이트 C** — 설계도를 제시하고 승인받는다.
`[Phase 2] 프레임 {N}개(신규 {K})·flow {F}개·토큰 요구 {T}건 — 다음: 어노테이션 스펙. 진행할까요?`

## Phase 3 — 어노테이션 스펙

`annotation-writer`를 `model: "opus"`로 호출한다. 입력: Phase 1 규칙 목록(`R#`) + **Phase 2 레이어 지목 표**. 참조: [references/annotation-templates.md](./references/annotation-templates.md).

수행 내용:
1. **핀 작성** — Phase 2가 지목한 레이어마다 6분류(인터랙션/조건 · 데이터 바인딩 · 검증 규칙 · 모션 · 트래킹 · 참조/예외) 중 해당 항목만 채운다. **디자인만 봐서 알 수 있는 것은 쓰지 않는다**(색·크기·간격은 Inspect에 이미 있다). **Phase 2 표에 없는 레이어 이름을 새로 만들지 않는다**(INV-1).
2. **복붙 가능한 문안** — 디자이너가 Figma에 그대로 붙여 넣을 수 있는 5필드 블록(`[대상]`·`[분류]`·`[본문]`·`[근거]`·`[확정]`)으로 낸다. 확정도는 **확정 / 잠정 / 미확정** 3값.
3. **확정/미확정 분기** — 확정된 스펙은 **어노테이션**, 아직 논의 중인 것은 **댓글**로 분리해 제안한다. 이 구분은 실무 관행이며 공식 문서상 비교 서술은 없다(evidence.md).
4. **AC 역참조** — 각 핀에 근거 AC 번호를 붙여 양방향 추적이 되게 한다.
5. **미확인 표시** — INV-1에 걸리는 값은 `[기획 확인 필요]`로 남기고, 핀 자체를 지어내지 않는다.

**게이트 D** — 어노테이션 스펙을 제시하고 승인받는다.
`[Phase 3] 핀 {P}개(미확인 {U}개) — 다음: FE 자율개발 적대 검증. 진행할까요?`

## Phase 4 — FE 자율개발 적대 검증

`handoff-critic`을 `model: "opus"`로 호출한다. 입력: Phase 1~3 산출물 전부. 참조: [references/handoff-readiness.md](./references/handoff-readiness.md).

수행 내용:
1. **FE 1인칭 시뮬레이션** — "이 문서만 들고 개발을 시작한다"고 가정하고, 화면별로 **어디서 멈춰 되묻게 되는지**를 구체적으로 짚는다. 칭찬 금지.
2. **틈 유형 점검** — 상태 누락 / 규칙 누락 / 문구 미정 / 데이터 계약 미정 / 흐름 미정 / 재사용 판단 불가 / **상충**(AC↔AC · AC↔프레임 · AC↔핀 · 프레임↔핀 · 핀↔핀 5쌍).
3. **준비도 판정** — 체크리스트를 owner별(기획·디자이너·FE·**하네스 자체**) 4그룹 모두 통과/미통과/해당없음 판정. **점수화하지 않는다.** 개수 임계로 착수 가부를 만들지 않는다(착수 결정은 팀의 권한).
4. **남은 질문 목록** — 누구에게 무엇을 물어야 하는지, 답이 없으면 어떤 개발이 막히는지.
5. **정직성 점검** — 산출물에 지어낸 값·근거 없는 수치 주장이 섞이지 않았는지 자체 감사한다.

**게이트 E** — 검증 리포트를 제시한다. 미통과 항목이 있으면 ⓐ 지금 보완(해당 Phase로 되돌아감) ⓑ 목록으로 남기고 마무리 중 선택하게 한다.
`[Phase 4] 멈춤 {N}건·상충 {C}건·미통과 {Y}건 — 다음: 마무리(저장·요약). 진행할까요?`

# 마무리

## 1. 산출물 저장 (opt-in)

저장 여부를 묻고, 동의 시 파일마다 **미리보기 → 승인 → 기록** 순으로 진행한다. 승인 없이 파일을 만들지 않는다. **커밋하지 않는다.**

## 2. 요약 보고

```
[Spec→Figma] 스토리 {N} · AC {A} → 프레임 {F}(신규 {K}) · 핀 {P} · 되물음 {Q}
준비도: 통과 {X} / 미통과 {Y} / 해당없음 {Z}  (점수 아님)
지금 막는 것: {가장 크리티컬한 미확인 항목 1~3개}
다음 행동: {누구에게 무엇을 확인 → 그다음 무엇}
```

## Common pitfalls

- **모르는 문구를 채워 넣는다** — 최대 실패 모드. `[기획 확인 필요]`가 정답이다(INV-1).
- **AC 1개 = 프레임 1개로 기계 매핑** — 한 AC가 상태 2~3개를 만드는 경우가 흔하다.
- **커버리지를 품질로 보고한다** — "전수 매핑 완료 = 질문 0"은 근거 없는 주장이다(INV-2).
- **디자인을 대신 결정한다** — 레이아웃·비주얼·톤은 디자이너 몫이다(INV-3).
- **Inspect에 이미 있는 것을 어노테이션에 쓴다** — 색·크기·간격 반복은 노이즈이고 드리프트 원인이다.
- **팀이 못 쓰는 기능을 전제한다** — Code Connect·`Ready for dev` view 등은 플랜 조건이 있다(INV-4).
- **되물음을 숨기고 매끈한 문서를 낸다** — 빈칸이 정직한 산출물이다(INV-5).
- **기존 Figma 파일을 수정한다** — 읽기 전용이다. 반영은 디자이너가 한다.
- **질문을 한꺼번에 쏟아붓는다** — 한 번에 하나씩.
