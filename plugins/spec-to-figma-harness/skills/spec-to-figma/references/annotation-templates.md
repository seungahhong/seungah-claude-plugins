# 어노테이션 템플릿 (정본)

레이어에 붙는 어노테이션 핀을 작성할 때 따르는 참조. Phase 3(`annotation-writer`)이 따른다.

> **기획서의 "규칙"은 레이어 어노테이션으로.** 시나리오(화면 구성 변화)는 상태 프레임 몫이다 — [ac-to-state-matrix.md](./ac-to-state-matrix.md).

## 0. 판별 기준 — 무엇을 쓰고 무엇을 쓰지 않는가

**단일 기준: 디자인(Inspect)만 봐서 알 수 없는 것만 쓴다.** Inspect에 이미 있는 값을 어노테이션에 옮겨 적으면 노이즈이자 드리프트 원인이다(디자인이 바뀌면 텍스트만 낡는다).

| 대상 | 쓴다? | 이유 |
|------|-------|------|
| 색·크기·간격·폰트·radius·그림자, 디자인 변수(토큰)명 | ❌ | Inspect에 이미 있다. Dev Mode Inspect는 **변수명 + 해석된 값**을 함께 보여준다 `[GOLD]` |
| 정렬 방향·사이징 등 Figma가 속성으로 제공하는 값 | △ 속성으로만 | Annotations는 자유 텍스트 + **정해진 목록에서 고르는 속성**이고, 속성값은 디자인이 바뀌면 자동 갱신된다 `[GOLD]`. 같은 값을 자유 텍스트로 또 쓰면 드리프트 |
| 트리거·조건 분기 (언제 이 화면/요소가 나오나) | ✅ | 정지된 프레임에서 관찰 불가 |
| 데이터 출처·포맷·정렬·말줄임 기준 | ✅ | 목업의 더미 텍스트로는 알 수 없다 |
| 검증 경계·에러 문구 원문·검증 시점 | ✅ | 화면에 보이는 1개 사례로 규칙을 역추론할 수 없다 |
| 모션 값 | △ 보조 | Motion/프로토타입이 1차 수단(§2-④) |
| 트래킹 이벤트명·파라미터 | ✅ | 디자인에 흔적이 전혀 없다 |
| 예외·재사용 출처·미결정 사항 | ✅ | 되물음을 없애는 실질 항목 |
| 코드 구현 지시(props·CSS·클래스명) / 레이아웃·비주얼·톤 지시 | ❌ | 리포 매핑은 Code Connect의 일 `[GOLD]`(§4)이고, 어떻게 보일지는 디자이너 몫 — **INV-3** |

> 어노테이션 본문이 Figma MCP 응답에 어떤 형태로 실리는지는 확인된 공식 서술이 없다. **"MCP로 그대로 전달된다"를 전제하지 말 것**(근거 없음).

## 1. 핀 1개의 표준 형식

핀 하나 = **1레이어 · 1분류 · 1관심사**. 5줄 헤더를 고정한다.

| 필드 | 규칙 |
|------|------|
| `[대상]` | 레이어 경로 `프레임명 > 그룹 > 레이어`. 핀은 레이어에 붙으므로 Figma 안에서는 생략 가능하지만, **핸드오프 문서·대체 경로(§4)에서는 필수** |
| `[분류]` | 6분류 중 하나 + 괄호로 Figma 카테고리(Development / Interaction / Accessibility / Content) `[GOLD]` |
| `[본문]` | 분류별 문안 템플릿(§2)을 그대로 채운다. 확인 안 된 값은 `[기획 확인 필요: 무엇]` |
| `[근거]` | AC 번호. AC가 없는 규칙이면 `AC 없음(되물음 Q-n)` |
| `[확정]` | `확정` / `잠정` / `미확정 n건` (§3) |

### 복붙 예시 4개

```
[대상] US-123 / 주문내역 · 기본 > ItemCard > 작성일
[분류] 데이터 바인딩 (Development)
[본문] [표시값] 작성일 ← [기획 확인 필요: API 필드 경로]
       [포맷] YYYY.MM.DD (AC-5 원문)
       [정렬] 목록 전체 최신순 내림차순 (AC-5)
       [없을 때] [기획 확인 필요: 행 숨김인지 '-' 표기인지]
[근거] AC-5
[확정] 미확정 2건
```

```
[대상] US-123 / 주문내역 · 빈상태 > EmptyBlock > 전체보기버튼
[분류] 인터랙션/조건 (Interaction)
[본문] [언제] 버튼 클릭
       [조건] 필터가 1개 이상 적용된 상태에서만 이 블록이 렌더된다
       [결과] 적용 필터 전부 해제 → `US-123 / 주문내역 · 기본`(S-DEFAULT)로 전이
       [예외] 최초 진입부터 0건이면 이 버튼 없음 → `US-123 / 주문내역 · 최초 0건`
[근거] AC-3, AC-7
[확정] 확정
```

```
[대상] US-456 / 폼 · 기본 > EmailField
[분류] 검증 규칙 (Content)
[본문] [제약] [기획 확인 필요: 허용 형식·최대 길이]
       [검증 시점] 포커스 아웃 시 1차, 제출 시 재검증 (AC-11)
       [에러 문구] "[기획 확인 필요: 원문 그대로]"
       [표시 위치] 필드 하단 → `US-456 / 폼 · 검증실패`(S-INVALID) 참조
[근거] AC-11
[확정] 미확정 2건
```

```
[대상] US-456 / 폼 · 성공 > Toast
[분류] 모션/트랜지션 (Interaction)
[본문] [표현 수단] Figma Motion(이 프레임의 전이에 적용됨) — 값은 Dev Mode Inspect에서 확인
       [전이] S-SUBMITTING → S-SUCCESS, 토스트 진입/퇴장
       [노출 시간] [기획 확인 필요: 자동 사라짐 초]
       [중단·재진입] 연속 제출 시 토스트를 [기획 확인 필요: 교체/누적]
[근거] AC-14
[확정] 미확정 2건
```

## 2. 6분류 템플릿

### ① 인터랙션/조건 — Figma 카테고리 `Interaction`

- **잡는 것**: 트리거(클릭·스크롤·포커스·진입), 조건 분기, 표시/숨김·비활성 조건, 전이 대상 프레임.
- **문안**

  ```
  [언제] <트리거>
  [조건] <참일 때 / 거짓일 때>
  [결과] <상태 코드 또는 프레임명>으로 전이
  [예외] <조건 밖 처리>
  ```
- **좋은 예**: `[언제] 목록 하단 [기획 확인 필요: 스크롤 임계값] 도달 [조건] 다음 페이지 존재 [결과] S-PAGING [예외] 마지막 페이지면 요청 없음 + 안내 문구 [기획 확인 필요: 원문]` — **확인 안 된 임계값은 그럴듯한 수치로 채우지 말고 플레이스홀더로 남기는 것이 정답 형태다.**
- **나쁜 예**: `클릭하면 자연스럽게 목록이 갱신됩니다` — 무엇을 클릭하는지·어느 프레임으로 가는지 없고 "자연스럽게"는 관찰 불가.
- **INV-1 함정**: 버튼 라벨 원문, 스크롤 임계값(200px 같은 수치), 연타·재시도 횟수, 디바운스 시간.

### ② 데이터 바인딩 — `Development`

- **잡는 것**: 값의 출처(API 필드), 포맷(날짜·통화·단위), 정렬 기준, 말줄임 기준, 빈 값 대체.
- **문안**

  ```
  [표시값] <레이어> ← <필드 경로>
  [포맷] <규칙>
  [정렬] <기준·방향>
  [없을 때] <대체 표현 / 레이어 숨김>
  ```
- **좋은 예**: §1 첫 번째 복붙 예시(확인된 것은 AC 인용, 나머지는 플레이스홀더).
- **나쁜 예**: `createdAt을 표시` — 필드명 출처 불명(지어낸 값일 가능성), 포맷·정렬·빈 값 규칙 없음.
- **INV-1 함정**: 필드명·엔드포인트·쿼리 파라미터, 페이지 크기, 기본 정렬, 말줄임 글자 수.

### ③ 검증 규칙 — `Content`(문구) + `Development`(경계)

- **잡는 것**: 입력 제약·허용 문자·길이 경계, 검증 트리거 시점, **에러 문구 원문**, 에러 표시 위치.
- **카테고리 분할**: 핀 1개 = 1카테고리이므로 **문구는 `Content`, 경계·검증 로직은 `Development`로 핀을 나눈다**(한 핀에 두 카테고리를 함께 적지 않는다).
- **문안**

  ```
  [대상 입력] <필드>
  [제약] <경계·허용 규칙>
  [검증 시점] 입력 중 / 포커스 아웃 / 제출 시
  [에러 문구] "<원문 그대로>"        ← 원문 없으면 [기획 확인 필요]
  [표시 위치] 필드 하단 / 상단 배너 / 토스트 → <S-INVALID 프레임>
  ```
- **좋은 예**: §1 세 번째 복붙 예시.
- **나쁜 예**: `[에러 문구] "올바른 이메일 형식을 입력해주세요"` — 기획서에 없는 문구를 그럴듯하게 생성한 경우. 디자이너가 그대로 그리고 FE가 그대로 박아 **틀린 값이 스펙이 된다**.
- **⚠️ 에러 문구는 원문 그대로.** 번역·존댓말 통일·줄임 등 **다듬기 금지**(문구는 기획/UX writer 소관). 원문이 없으면 문구 칸은 비우고 되물음으로 올린다 — **INV-5**.
- **INV-1 함정**: 문구 전체, 최소/최대 길이, 정규식, 허용 확장자·용량.

### ④ 모션/트랜지션 — `Interaction`

- **1차 수단은 어노테이션이 아니다.** `Figma Motion`은 GA이며 키프레임/이징이 Dev Mode에서 그대로 inspect되고 CSS/JSON/React로 export된다 `[SILVER]`(Config 2026 recap). 값이 정해졌다면 Motion/프로토타입으로 표현하고, **어노테이션은 도구를 못 쓰거나 "왜 이 전이인가"를 설명할 때의 보조 수단**이다.
- **문안**

  ```
  [표현 수단] Figma Motion / 프로토타입 / (미사용 시) 텍스트
  [전이] <출발 상태> → <도착 상태>
  [값] duration <ms> / easing <이름>   ← 입력에 없으면 [기획 확인 필요]
  [중단·재진입] <연타·되돌림·중도 이탈 시>
  ```
- **좋은 예**: §1 네 번째 복붙 예시(값은 Motion에, 규칙만 텍스트로).
- **나쁜 예**: `부드럽게 페이드 인 (300ms, ease-out)` — 300ms/ease-out의 출처가 없고(지어낸 값), 값이 정해졌다면 Motion과 텍스트를 이중 관리하게 된다.
- **INV-1 함정**: duration·easing 수치, 토스트 자동 사라짐 초, 반복 횟수.

### ⑤ 트래킹 이벤트 — `Development` (또는 파일 커스텀 카테고리, §4)

- **잡는 것**: 이벤트명, 발생 시점(노출/클릭/성공 응답 후), 파라미터와 값 출처, 중복 발생 방지.
- **문안**

  ```
  [이벤트명] <원문 그대로>          ← 없으면 [기획 확인 필요]
  [발생 시점] 노출 / 클릭 / 서버 성공 응답 후
  [파라미터] <key>=<값 출처>
  [중복 방지] 세션 1회 / 매번
  ```
- **좋은 예**: `[이벤트명] [기획 확인 필요: 이벤트명] [발생 시점] 저장 API 200 응답 후 1회 (AC-16) [파라미터] item_id=목록 항목 식별자(필드명 [기획 확인 필요]) [중복 방지] [기획 확인 필요: 세션 1회인지 매번인지]` — AC로 확인된 것만 단정하고, 이벤트명·필드명·중복 규칙은 플레이스홀더로 남긴다.
- **나쁜 예**: `click_filter_apply 발생` — 팀 컨벤션을 추측해 만든 이벤트명. 분석 대시보드가 통째로 어긋난다.
- **INV-1 함정**: 이벤트명·파라미터 키·값 enum, "노출 3초 이상" 류 임계값.

### ⑥ 참조/예외 — `Development`

- **잡는 것**: 재사용 출처, 다른 화면과 동일 규칙임의 명시, 예외 케이스, 미결정 사항, 근거 AC 번호.
- **문안**

  ```
  [동일] <다른 프레임/화면>과 동일 규칙 — 차이점: <없음 / 명시>
  [예외] <케이스> → <처리>
  [미결정] [기획 확인 필요] <질문>
  [근거] AC-n, AC-m
  ```
- **좋은 예**: `[동일] US-100 / 주문내역 · 에러와 동일 — 차이점: 재시도 버튼 없음 [예외] 부분 실패(S-PARTIAL) 시 실패 섹션만 에러 [근거] AC-9`
- **나쁜 예**: `기존이랑 똑같이` — 무엇과 같은지, 다른 점이 정말 없는지 확인 불가.
- **INV-1 함정**: "동일하다"는 단정 자체(확인 안 됐으면 `[기획 확인 필요]`), 예외 처리 방식 임의 결정.

## 3. 확정 핀(Annotation) vs 논의 스레드(Comment)

> 여기서 나누는 것은 **수단(핀이냐 댓글이냐)** 이고, 핀의 확정도 어휘는 `[확정]` 필드의 **`확정` / `잠정` / `미확정`** 3값뿐이다(다른 어휘를 만들지 않는다).

| 성격 | 수단 | 작성 주체 | FE의 취급 |
|------|------|-----------|-----------|
| 확정된 스펙 | **Annotation 핀** | 디자이너/기획 합의 후 | **이것만 믿고 개발 착수** |
| 논의·질문·제안 | **Comment** | 누구나 | 개발 근거로 쓰지 않음 |
| 확인 대기 | Annotation 안의 `[기획 확인 필요]` + Comment 스레드 | 작성자 | **착수 보류 대상**으로 목록화 |

- 이 분기는 **`[관행]`이다.** Figma 공식 문서에는 Annotations와 Comments를 비교 서술한 대목이 **없다**(3자 블로그만 존재 `[BRONZE]`). "댓글은 해결되면 사라지고 주석은 남는다"는 실무 운용 규약으로만 말하고, 공식 기능 차이로 단정하지 않는다.
- **왜 유용한가**: FE가 캔버스의 모든 텍스트를 판독하지 않고 "확정 핀"만 읽고 개발할 수 있다. 논의는 스레드에서 끝나고 결론만 핀으로 승격된다.
- **한계(정직하게)**: 어노테이션도 낡는다. Figma는 마킹 후 디자인이 수정되면 dev status를 자동 `Changed`로 바꾸고 `[GOLD]`, 목록에서 고른 **속성값**은 자동 갱신되지만 `[GOLD]`, **자유 텍스트 본문이 낡았는지는 아무도 알려주지 않는다.** 그래서 규약이 필요하다:
  - `Changed`가 뜬 Section/Frame/Component는 **그 안의 핀 전수 재검토** 후 다시 `Ready for dev`. `[확정]`이 `잠정`인 핀은 착수 전 재확인.
  - **INV-2**: "핀을 다 붙였으니 질문이 없다"고 말하지 않는다. 질문 감소를 측정한 연구는 확인되지 않았고, 어떤 "질문 N% 감소" 수치도 인용하지 않는다.

## 4. Figma Annotations 기능 제약과 대체 경로

| 항목 | 사실 | 등급 |
|------|------|------|
| 정식 기능명·단축키 | `Annotations`(⇧T), `Measurements`(⇧M) | `[GOLD]` |
| 내용 구성 | 자유 텍스트 + **정해진 목록에서 고르는 속성**(정렬 방향·사이징 등), 속성은 디자인 변경 시 자동 갱신 | `[GOLD]` |
| "CSS 속성이 자동으로 붙는다" | **공식 문서에 없다** — 속성 선택형이다. 전제 금지 | 근거 없음 |
| 기본 카테고리 | Development / Interaction / Accessibility / Content | `[GOLD]` |
| 커스텀 카테고리 | 가능하되 **파일 단위 한정**(다른 파일로 자동 전파되지 않음) | `[GOLD]` |
| 생성 권한 | **Full seat + can edit(유료 플랜)** / 열람은 Full 또는 Dev seat + can view | `[GOLD]` |
| Dev status | `Ready for dev`(전 유료 플랜), `Completed`(**Organization/Enterprise 전용**), 수정 시 자동 `Changed`. 대상은 Section/Frame/Component | `[GOLD]` |
| `Ready for dev` view / focus view | **Organization·Enterprise 전용** | `[GOLD]` |
| Code Connect | 리포 컴포넌트 ↔ Figma 컴포넌트 매핑. **Dev 또는 Full seat + Organization/Enterprise 필요** | `[GOLD]` |
| Design mode에서도 주석이 보임 | 2차 보도만, 공식 원문 확보 실패 | `[BRONZE]` |

> **`Accessibility` 카테고리는 이 하네스가 산출하지 않는다** — 접근성 스펙은 이 하네스의 표적이 아니다. §2의 6분류는 `Development` / `Interaction` / `Content` 3종에만 매핑된다.

**INV-4 — 팀이 못 쓰는 기능을 전제한 요구를 강요하지 않는다.** 인테이크에서 플랜/시트를 확인하고 아래 대체 경로를 병기한다.

| 못 쓰는 것 | 대체 경로 |
|------------|-----------|
| Annotations 생성(무료/시트 없음) | 프레임 우측에 **고정 폭 텍스트 레이어 규약**: 1블록 = 1핀, 첫 줄 `ANNO | <분류> | <레이어 경로>`, 이하 §1 형식 그대로. 페이지 최상단에 범례 프레임 1개 `[관행]` |
| 커스텀 카테고리(파일 단위 한정) | 기본 4종만 쓰고 본문 첫 토큰에 접두어 — `[TRACK]`, `[BIND]`, `[VALID]` `[관행]` |
| `Completed` 상태 / Ready-for-dev view (Org·Ent 전용) | 프레임명 접미어 `[READY]` / 별도 체크리스트 표로 대체 `[관행]` |
| Code Connect (Org·Ent 필요) | ⑥ 참조 핀에 **컴포넌트 이름만** 한 줄. props·CSS 지시는 금지(§5-6) |
| 어노테이션 자체를 안 쓰는 팀 | 별도 스펙 문서 + **1 프레임 ↔ 1 앵커 ID** 링크. 프레임/섹션명에 티켓 ID를 넣는 방식은 **`[관행]`**(Figma 공식 문서는 sections를 협업 영역 지정·파일 탐색 정리 용도로만 기술하며 티켓 연계 서술이 없다) |

## 5. 안티패턴

| # | 안티패턴 | 왜 나쁜가 | 대신 |
|---|----------|-----------|------|
| 1 | 캔버스에 설명 텍스트 흩뿌리기 | 레이어와의 결속이 없어 어느 요소 얘기인지 모르고, 프레임 복제 시 유실·중복 | 핀으로 레이어에 결속. 불가하면 §4 텍스트 레이어 **규약**(위치·형식 고정) |
| 2 | Inspect 값 재기술(색·간격·폰트·토큰명) | 이미 Inspect·변수에 있다 `[GOLD]`. 디자인이 바뀌면 텍스트만 낡아 **드리프트** | §0 판별표. 속성으로 고를 수 있는 건 속성으로(자동 갱신) |
| 3 | 문구·필드명·이벤트명 지어내기 | 디자이너가 그리고 FE가 구현해 **틀린 값이 스펙이 된다** — INV-1 | `[기획 확인 필요: 무엇]` + 되물음 목록 (INV-5) |
| 4 | 한 핀에 5가지 섞어 쓰기 | 어느 줄이 확정인지 구분 불가, 부분 변경 시 통째로 낡음 | **1핀 1분류 1관심사**, 6분류로 쪼갠다 |
| 5 | 낡은 핀 방치 | 자유 텍스트는 자동 갱신되지 않는다 — FE가 틀린 스펙을 믿는다 | `Changed` 발생 시 핀 전수 재검토 후 재마킹(§3) |
| 6 | 코드로 지시하기 (`<Button variant="primary">`, 클래스명, CSS) | 어노테이션은 구현 명세가 아니고, 리포 매핑은 Code Connect의 일 `[GOLD]`. 리포가 바뀌면 즉시 거짓말이 된다 | 컴포넌트 **이름**까지만. 매핑은 Code Connect |
| 7 | 디자인 결정 대행 ("여기는 2단 그리드로", "톤을 부드럽게") | **INV-3** — 무엇이 필요한가만 명세하고 어떻게 보일지는 디자이너 몫 | 필요한 상태·규칙·데이터만 기술 |
| 8 | 커버리지를 성과로 주장 ("전수 매핑 → 질문 0", "재작업 N% 감소") | **INV-2** — 측정 연구가 확인되지 않았다 | 산출물은 커버리지 표와 **미확정 목록**으로만 말한다 |
| 9 | 못 쓰는 기능 전제 (Org 전용 상태·Code Connect 요구) | 실행 불가한 스펙은 무시되고 규약 전체의 신뢰를 깎는다 — **INV-4** | §4 대체 경로 병기 |
| 10 | 미확정을 그럴듯하게 봉합해 `[확정]`으로 표기 | 되물음이 사라져 FE가 잘못된 확신으로 착수 | `잠정`/`미확정 n건` 표기 유지 — **빈칸이 있는 정직한 문서 > 채워진 추측** |
