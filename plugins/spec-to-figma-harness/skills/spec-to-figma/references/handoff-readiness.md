# 핸드오프 준비도 — 체크리스트 · 적대 검증 절차

Phase 4(`handoff-critic`)가 **"FE가 이 패키지만 들고 되묻지 않고 개발을 시작할 수 있는가"**를 판정할 때 쓰는 문서. 판정 대상은 Phase 1~3 산출물(상태 매핑표 · Figma 반영 설계도 · 어노테이션 스펙)과 실제 Figma 파일(있다면, **읽기 전용**).

---

## 0. 판정 규약

| 값 | 의미 | 조건 |
|----|------|------|
| **통과** | 관찰 가능한 증거가 실제로 존재한다 | "있을 것 같다"가 아니라 프레임명·핀 문안·표의 행을 **지목할 수 있어야** 한다 |
| **미통과** | 증거가 없거나, 있으나 값이 `[기획 확인 필요]`다 | 미통과는 결함 단정이 아니라 **막히는 지점의 표시**다 |
| **해당없음** | 이 스토리 범위에 그 축이 존재하지 않는다 | 이유를 1줄로 적는다. 판정을 피하는 도피처로 쓰지 않는다 |

**집계는 개수까지만.** `통과 12 / 미통과 3 / 해당없음 1`은 쓰되 **백분율·점수·등급(A/B/C, "준비도 80%")으로 환산하지 않는다.**

- 항목 가중치에 대한 측정 근거가 없다 — 임의 가중은 근거 없는 수치를 만들어낸다(INV-2).
- 점수는 Goodhart 표적이 된다. "점수를 올리려고" 항목을 해당없음으로 밀거나 빈칸을 추측으로 채우는 순간 이 하네스의 최대 실패 모드(INV-1)가 발동한다.

**미통과 1개도 그 자체로 블로커가 아니다.** 아래 §4 표의 *임시 진행 가능 여부*로 갈린다.

**준비도 판정 보고는 기획·디자이너·FE·하네스 자체 4그룹을 모두 포함한다.** 3그룹(기획·디자이너·FE)만 보고하면 §1-D 하네스 자체(HN) 항목이 리포트에서 증발한다. 해당 그룹에 판정할 항목이 없더라도 그룹 자체를 생략하지 않고 **해당없음 + 이유**로 남긴다.

### 판정 순서 (이 순서로 돌린다)

1. **§2 FE 1인칭 시뮬레이션을 먼저 돌린다** — 체크리스트를 먼저 보면 항목에 끌려가 "문서에 쓰여 있으니 통과"가 된다. 실제로 막히는 지점을 먼저 캔 뒤 체크리스트로 분류한다.
2. 멈춤 지점을 **§3 틈 유형**으로 분류한다.
3. §1 체크리스트를 owner별로 **통과/미통과/해당없음** 판정한다(멈춤 지점이 걸리는 항목은 자동으로 미통과).
4. 미통과·멈춤을 **§4 남은 질문 표**로 합친다(중복 질문은 병합).
5. 제출 전 **§5 자체 정직성 감사 5문항**을 통과시킨다.

> **읽기 전용 원칙** — 검증 중 Figma 파일을 열더라도 **수정하지 않는다**(INV-3). 판정 근거로 쓰는 파일 관찰은 MCP 읽기 도구(`get_metadata`로 노드·이름 맵, `get_screenshot`으로 실제 화면, `get_variable_defs`로 토큰, `get_code_connect_map`으로 코드 매핑) 범위 안에서만 한다. selection 기반 호출은 데스크톱 서버에서만 되고 remote는 프레임 링크가 필요하다 **[SILVER]**. 도구가 없으면 사용자가 제시한 산출물만으로 판정하고 **"파일 미확인"을 리포트에 명시**한다.

## 1. owner별 체크리스트

각 항목: **확인 문장 / 관찰 가능한 증거 / 미통과 시 FE가 추측하게 되는 것**. 증거를 지목하지 못하면 통과로 적지 않는다.

세 번째 칼럼은 **결과 예측이 아니라 "무엇이 정의되지 않아 FE가 무엇을 추측하게 되는가"** 만 적는다. 재작업·지연·급조·비용 같은 결과어는 측정 근거가 없는 인과 주장이므로 쓰지 않는다(evidence.md §4 인용 금지).

### 1-A. 기획(PO) — 값과 규칙의 원본 소유자

| ID | 확인 문장 | 관찰 가능한 증거 | 미통과 시 FE가 추측하게 되는 것 |
|----|-----------|------------------|---------------------------------|
| PO-1 | 모든 AC가 최소 1개의 상태 프레임 또는 핀에 연결됐다 | 커버리지 매트릭스 정방향 열에 빈칸이 없다 | 그 AC가 어느 화면·어느 상태에 반영되는지 정의되지 않음 → FE가 반영 위치를 스스로 지목하게 됨 |
| PO-2 | 사용자에게 노출되는 **문구가 원문 그대로** 있다(에러·빈 상태·토스트·버튼 라벨) | 핀 본문에 따옴표로 감싼 실제 문장이 있다. `[기획 확인 필요]`면 미통과 | 노출 문구 원문이 정의되지 않음 → FE가 안내 문구를 임의로 정하게 됨 |
| PO-3 | **수치 경계**가 명시됐다(글자 수·임계값·재시도 횟수·페이지 크기) | 핀에 숫자와 단위가 있다("20자", "100px", "1회") | 말줄임 기준·페이지 크기·재시도 횟수가 정의되지 않음 → FE가 숫자를 임의로 정하게 됨 |
| PO-4 | **권한·상태별 접근 규칙**이 정의됐다(비로그인·권한 없음·세션 만료) | `S-UNAUTH`/`S-FORBIDDEN`/`S-EXPIRED` 행이 채워졌거나 "해당없음+이유" | 비로그인·권한 없음·세션 만료에서 무엇이 보이는지 정의되지 않음 → FE가 라우팅 가드와 리다이렉트 대상을 임의로 정하게 됨 |
| PO-5 | **트래킹 이벤트명·파라미터**가 확정됐거나 "이번 범위 아님"으로 명시됐다 | 핀에 이벤트명 문자열이 있거나 범위 제외 표기 | 이벤트명·파라미터 키가 정의되지 않음 → FE가 계측 키 이름을 임의로 정하게 됨 |
| PO-6 | AC끼리 서로 모순되지 않는다 | 동일 조건에 다른 결과를 지시하는 AC 쌍이 없다(§3 상충 참조) | 같은 조건에 두 개의 결과가 남아 있음 → FE가 어느 AC가 유효한지 임의로 고르게 됨 |

### 1-B. 디자이너 — 화면·구조·인스펙트 가능성의 소유자

| ID | 확인 문장 | 관찰 가능한 증거 | 미통과 시 FE가 추측하게 되는 것 |
|----|-----------|------------------|---------------------------------|
| DS-1 | Phase 1에서 도출된 **상태마다 프레임이 존재**한다(빈/로딩/에러/오버플로 포함) | 프레임 목록의 각 행에 대응 프레임명이 있다 | 정상 외 상태의 화면 구성이 정의되지 않음 → FE가 로딩·빈·에러 화면의 구성 요소를 임의로 정하게 됨 |
| DS-2 | 프레임 이름이 **티켓 ID + 화면 + 상태** 규칙을 따른다 | `US-123 / 필터 · 빈상태` 형태의 실제 이름 | 프레임과 AC의 대응이 이름에 드러나지 않음 → FE가 어느 프레임이 어느 AC의 결과인지 추측하게 됨 (명명 규칙 = **[관행]**, Figma 공식 문서에 티켓 연계 서술 없음) |
| DS-3 | 화면 간 **이동이 프로토타입 연결로 표현**됐다(텍스트 설명 대체 아님) | flow 표의 각 행에 대응하는 실제 연결 | 진입점·되돌아가기 경로가 정의되지 않음 → FE가 화면 간 이동 경로를 추측하게 됨 |
| DS-4 | 색·간격·타이포가 **Variables/스타일로 바인딩**됐다(하드코딩 아님) | Dev Mode Inspect에 변수명 + 해석된 값이 함께 뜬다 **[GOLD]**. MCP `get_variable_defs`는 실제 변수를 쓸 때만 토큰을 반환하고 하드코딩이면 hex 그대로 나온다 **[SILVER]** | 그 값이 토큰인지 이 화면 전용 값인지 구분되지 않음 → FE가 색·간격을 하드코딩할지 토큰으로 쓸지 추측하게 됨 |
| DS-5 | 반복 요소가 **컴포넌트/인스턴스**로 되어 있다 | 동일 UI가 프레임마다 복제 도형이 아니라 인스턴스다 | 공통 여부가 파일에 표시되지 않음 → FE가 이 UI가 공통 컴포넌트인지 화면 전용인지 추측하게 됨(§3 재사용 판단 불가) |
| DS-6 | **모션은 어노테이션 텍스트가 아니라 프로토타입/Motion으로** 표현됐다 | 인터랙션/모션이 파일에 실재. Figma Motion은 GA이며 키프레임·이징이 Dev Mode에서 inspect되고 CSS/JSON/React로 export, MCP로도 전달된다 **[SILVER, Config 2026 recap]** | duration·easing의 실제 값이 파일에 없음 → FE가 모션 값을 추측하게 됨 |
| DS-7 | 개발 대상 범위가 **`Ready for dev`로 마킹**됐다 | Section/Frame/Component에 상태 표시. 대상 3종·`Mark as ready for dev` 라벨·수정 시 자동 `Changed` **[GOLD]** | 어느 프레임이 확정본인지 표시되지 않음 → FE가 어떤 버전이 최신인지 추측하게 됨 |
| DS-8 | 확정 스펙은 **어노테이션**, 논의 중인 건 **댓글**로 분리됐다 | 핀과 댓글이 섞여 있지 않다 (이 분리는 **[관행]** — Figma 공식 문서에 둘의 비교 서술 없음) | 확정 스펙과 논의 중 의견이 구분되지 않음 → FE가 어느 문장이 유효한 스펙인지 추측하게 됨 |

### 1-C. FE — 코드로 옮길 수 있는가의 판정자

| ID | 확인 문장 | 관찰 가능한 증거 | 미통과 시 FE가 추측하게 되는 것 |
|----|-----------|------------------|---------------------------------|
| FE-1 | 화면의 각 값이 **어떤 데이터에서 오는지** 적혀 있다 | 데이터 바인딩 핀에 필드/응답 위치가 명시(`[기획 확인 필요]`면 미통과) | 값의 출처 필드가 정의되지 않음 → FE가 응답 구조와 필드명을 추측하게 됨 |
| FE-2 | 로딩·실패의 **범위**(전체 화면 / 섹션 / 인라인)가 지정됐다 | `S-LOADING`·`S-ERROR`·`S-PARTIAL` 프레임이 범위를 보여준다 | 로딩·실패가 화면 전체인지 일부인지 정의되지 않음 → FE가 상태를 전역으로 둘지 지역으로 둘지 추측하게 됨 |
| FE-3 | 사용자 조작마다 **직후 상태**가 지정됐다(제출 중·성공·중복 방지) | `S-SUBMITTING`/`S-SUCCESS` 프레임 또는 인터랙션 핀 | 조작 직후 화면이 정의되지 않음 → FE가 제출 중 표시·성공 처리·중복 실행 차단 방식을 추측하게 됨 |
| FE-4 | **콘텐츠 경계**가 지정됐다(긴 텍스트 줄 수·최대/최소 건수·선택 필드 누락) | `S-OVERFLOW`/`S-MAX`/`S-MISSING-FIELD` 행 | 경계 상황의 표시 방식이 정의되지 않음 → FE가 줄 수·최대 건수·누락 필드 대체 표시를 추측하게 됨 |
| FE-5 | 코드 컴포넌트와의 매핑 여부가 **플랜 조건과 함께** 판정됐다 | Code Connect 사용/미사용 결정 + 근거. Code Connect는 **Dev 또는 Full seat + Organization/Enterprise 플랜** 필요 **[GOLD]** | 팀이 실제로 쓸 수 있는 기능 범위가 확정되지 않음 → FE가 코드 매핑이 제공되는지 여부를 추측하게 됨(INV-4) |

### 1-D. 하네스 자체 — 이 패키지가 정직한가 (owner: 전원)

| ID | 확인 문장 | 관찰 가능한 증거 | 미통과 시 FE가 추측하게 되는 것 |
|----|-----------|------------------|---------------------------------|
| HN-1 | **지어낸 값이 없다** — 문구·API 필드·이벤트명·수치·권한 정의는 전부 사용자 입력 출처다 | 각 값에 출처 AC 번호 또는 사용자 답변이 대응된다 | 어떤 값이 입력 출처이고 어떤 값이 하네스가 채운 것인지 구분되지 않음 → FE가 그 값이 기획 확정인지 추측하게 됨(INV-1 최대 실패 모드) |
| HN-2 | 미확인 값이 **`[기획 확인 필요]`로 가시화**됐고 §4 질문 목록에 올라 있다 | 플레이스홀더 개수 = 질문 목록 행 수와 대응 | 미확인 표시가 없어 빈칸과 확정값이 같은 모양으로 보임 → FE가 무엇이 아직 안 정해졌는지 추측하게 됨(INV-5) |
| HN-3 | 팀이 **쓸 수 없는 기능을 전제하지 않았다**, 전제했다면 대체 경로가 병기됐다 | 플랜/시트 제약이 걸리는 항목에 대체안 1줄이 붙어 있다 | 팀이 실제로 쓸 수 있는 대체 경로가 적히지 않음 → FE가 그 정보를 어디서 받을지 추측하게 됨(INV-4) |
| HN-4 | **디자인 결정을 대신하지 않았다** | 레이아웃·비주얼·톤 지시가 아니라 "무엇이 필요한가"만 적혀 있다 | 하네스가 적은 비주얼 지시와 디자이너 확정본이 구분되지 않음 → FE가 어느 쪽이 실제 디자인인지 추측하게 됨(INV-3) |

> **플랜·시트 제약 요약 [GOLD]** — 어노테이션 *생성* = Full seat + can edit(유료 플랜), *열람* = Full 또는 Dev seat + can view / dev status 변경 = Full 또는 Dev seat, `Ready for dev`는 전 유료 플랜이나 **`Completed` 상태와 `Ready for dev` view/focus view는 Organization·Enterprise 전용** / Code Connect = Dev 또는 Full seat + Organization·Enterprise. 제약에 걸리면 해당 항목을 **해당없음**으로 두고 대체 경로(예: 프레임명 접미사·별도 표 관리)를 적는다.

## 2. FE 1인칭 시뮬레이션 절차

**"이 문서와 이 파일만 들고 지금 개발을 시작한다"**고 가정하고 화면마다 아래 순서로 훑는다. **칭찬 금지** — 잘된 점은 적지 않는다. 출력은 "어디서 멈추는가"만이다.

각 단계에서 답을 **문서에서 지목하지 못하면 즉시 멈춤으로 기록**한다("아마 이럴 것이다"로 넘어가지 않는다).

| # | 단계 | 캐는 질문 | 멈춤 신호 |
|---|------|-----------|-----------|
| 1 | **진입** | 이 화면에 어떻게 들어오나? 진입 경로가 여러 개면 각각 초기 상태가 같나? URL 파라미터·딥링크가 있나? | 프로토타입 연결이 없다 / 진입 경로가 프레임에 안 보인다 |
| 2 | **데이터 요청** | 진입 즉시 무엇을 요청하나? 요청 중 화면은? 어떤 필드가 어느 텍스트로 가나? 캐시·재요청 조건은? | 데이터 바인딩 핀이 없다 / `[기획 확인 필요]` |
| 3 | **렌더 분기** | 정상·0건·에러·부분 실패·권한 없음에서 각각 무엇이 보이나? 0건이 **최초 0건**인지 **필터 결과 0건**인지 구분되나? 문구 원문은? | 분기 중 프레임이 없는 것이 있다 / 문구가 비어 있다 |
| 4 | **사용자 조작** | 각 버튼·입력의 트리거 시점(입력 중/포커스 아웃/제출)과 직후 상태는? 비활성 조건은? 중복 실행은 어떻게 막나? 검증 실패 메시지의 **위치**는? | 조작은 있는데 직후 상태 프레임이 없다 |
| 5 | **실패 경로** | 요청이 실패하면? 재시도가 있나, 몇 번인가? 반복 실패 시 문구가 바뀌나? 실패 시 사용자가 입력한 값은 보존되나? 타임아웃·오프라인은? | 실패가 "에러 화면 1장"으로만 뭉뚱그려져 있다 |
| 6 | **경계값** | 텍스트가 아주 길면? 목록이 1건/최대치면? 선택 필드가 비면 무엇이 대신 보이나? | `S-OVERFLOW`/`S-MAX`/`S-MISSING-FIELD` 미지정 |
| 7 | **재사용 판단** | 이 UI는 공통 컴포넌트인가 이 화면 전용인가? 이미 코드에 있는 것인가? 있다면 어떤 것인가? | 인스턴스가 아니라 복제 도형 / 매핑 정보 없음 |

**실행 규칙**

- **화면 단위로 완주한다** — 단계 1~7을 한 화면에서 끝내고 다음 화면으로 간다. 단계별로 전 화면을 훑으면 화면 안의 연쇄(진입→요청→분기)가 끊긴다.
- **"디자이너에게 물어보면 되지"로 넘기지 않는다** — 물어봐야 한다는 사실 자체가 멈춤이다. 기록한다.
- **문서에 있는 문장을 그대로 옮겨 확인한다** — 기억이나 맥락으로 메우지 않는다. 지목할 수 없으면 없는 것이다.
- **잘된 항목은 쓰지 않는다** — 리포트 분량이 검증 강도로 오인되면 안 된다. 출력은 멈춤 목록과 판정표뿐이다.
- **모든 상태 프레임을 대상으로 한다** — 정상 화면만 훑으면 이 절차가 무의미해진다. 빈·에러·권한 없음 프레임에서도 단계 1~7을 돌린다.

**기록 형식** — 멈춤 1건 = 1행: `[화면/상태] 단계 N — 내가 답할 수 없는 것: … → 필요한 것: … → 물을 사람: …`

```
[필터 결과 / S-EMPTY] 단계 3 — 답할 수 없음: 0건 안내 문구 원문
  → 필요: 문구 원문 1문장(최초 0건 / 필터 0건 각각) → 물을 사람: 기획(PO)
[필터 결과 / S-ERROR] 단계 5 — 답할 수 없음: 재시도 버튼 클릭 후 재실패 시 화면
  → 필요: 반복 실패 시 문구·횟수 → 물을 사람: 기획(PO)
```

멈춤이 여러 건인 화면은 남은 질문 표 상단에 올린다. 개수 임계로 등급이나 착수 가부를 만들지 않는다(착수 결정은 팀의 권한이다).

## 3. 틈(gap) 유형 분류

| 유형 | 탐지 질문 2개 | 대표 증상 |
|------|---------------|-----------|
| **상태 누락** | ① 상태 카탈로그 축 중 "해당함"인데 프레임이 없는 것은? ② 한 AC가 상태를 2개 이상 만드는데 프레임이 1개뿐인 곳은? | 정상 화면만 여러 장 있고 로딩·빈·에러가 없다 |
| **규칙 누락** | ① 디자인만 봐서는 알 수 없는데 핀이 없는 요소는? ② 조건부 표시/숨김 요소인데 조건이 안 적힌 것은? | "이건 언제 보이나요?"가 나오는 요소 |
| **문구 미정** | ① 사용자 노출 텍스트 중 원문 대신 예시("~같은 안내")로 적힌 곳은? ② 프레임의 텍스트와 핀의 문구가 다른 곳은? | 로렘입숨·"에러 메시지" 같은 자리표시자 |
| **데이터 계약 미정** | ① 화면 값 중 출처 필드가 안 적힌 것은? ② 포맷·정렬·단위·시간대가 안 정해진 값은? | 날짜·금액·정렬 순서를 FE가 임의 결정 |
| **흐름 미정** | ① 진입/이탈 경로가 프로토타입에 없는 프레임은? ② 성공 후 어디로 가는지 안 적힌 조작은? | 만들어졌지만 아무 데서도 도달할 수 없는 프레임 |
| **재사용 판단 불가** | ① 여러 화면에 같은 UI가 복제 도형으로 있는 곳은? ② 코드에 이미 있는 컴포넌트인지 표시가 없는 곳은? | 같은 카드가 화면마다 미묘하게 다르다 |
| **상충** | ① 같은 조건에 다른 결과를 지시하는 **AC↔AC** 쌍은? ② **AC↔프레임 · 프레임↔핀 · 핀↔핀 · AC↔핀** 중 서로 다른 값을 말하는 곳은? | AC는 "20자", 핀은 "30자", 프레임은 2줄 말줄임 |

**누락 vs 해당없음을 구분한다** — "빈 상태 프레임이 없다"는 *누락*일 수도, *이 화면은 0건이 발생하지 않는다*는 **해당없음**일 수도 있다. 둘을 스스로 판정하지 말고 해당 여부를 되묻는다. 발생 가능성을 추론해 누락으로 단정하면 불필요한 프레임을 디자이너에게 요구하게 되고(볼륨 가점 금지), 반대로 임의로 해당없음 처리하면 실데이터에서 터진다.

**상충은 미통과 중에서도 우선 처리한다** — 누락은 물어보면 되지만, 상충은 **양쪽 다 이미 스펙처럼 보이기 때문에** FE가 모르고 한쪽을 구현한다. 상충 발견 시 어느 쪽이 맞는지 **추론해서 고르지 말고** 두 출처를 나란히 인용해 질문으로 올린다.

## 4. 남은 질문 목록 형식

| # | 질문 | 대상 | 답이 없으면 막히는 것 | 임시 진행 |
|---|------|------|----------------------|-----------|
| Q1 | 필터 결과 0건일 때 안내 문구 원문은? | 기획(PO) | 빈 상태 화면 구현 전체 | **블로킹** — 노출 문구는 임시값이 릴리스에 남는다 |
| Q2 | 조회 실패 시 재시도 횟수는? | 기획(PO) | 에러 처리 분기 | 가정 진행 — "재시도 1회" 가정 명시 후 진행, 확정 시 상수만 교체 |
| Q3 | 목록 카드가 공통 컴포넌트인가? | 디자이너 | 컴포넌트 구조 결정 | 가정 진행 — 화면 전용으로 만들고 필요 시 승격 |

**임시 진행 판정 규칙**

- **블로킹** — 사용자 노출 문구, 권한/보안 분기, 트래킹 이벤트명, 데이터 계약(필드·포맷). 잘못된 값이 그대로 배포되거나 나중 교체 비용이 국소적이지 않다.
- **가정 진행** — 값 하나만 바꾸면 흡수되는 것(임계 수치·애니메이션 시간·내부 상수). 반드시 **가정 문장을 산출물에 남기고** 확정 시 되돌릴 지점을 지목한다.
- 판단이 애매하면 **블로킹으로 올린다.** 추측을 진행시키는 쪽이 이 하네스에서 더 비싼 실수다.

**작성 규칙**

- 질문은 **답할 수 있는 형태**로 쓴다 — "빈 상태 어떻게 하나요?"(X) → "필터 결과 0건일 때 화면에 보일 안내 문구 원문 1문장과 버튼 유무"(O).
- 같은 값을 요구하는 멈춤 여러 건은 **한 질문으로 병합**하고 막히는 것 칸에 화면을 나열한다.
- **블로킹을 위에, 대상별로 묶어** 정렬한다(PO 질문끼리, 디자이너 질문끼리) — 받는 사람이 한 번에 답할 수 있게.
- 답이 오면 해당 행을 지우지 말고 **답변과 반영 위치(프레임/핀)를 같은 행에 기록**한다. 추적이 남아야 나중에 값이 바뀔 때 어디를 고칠지 안다.

## 5. 자체 정직성 감사 (리포트 제출 전 5문항)

1. **지어낸 것이 없는가** — 이 리포트에 등장하는 모든 문구·API 필드·이벤트명·수치·권한 정의가 사용자 입력이나 AC로 역추적되는가? 하나라도 "그럴듯해서 썼다"면 지우고 `[기획 확인 필요]`로 바꾼다.
2. **근거 없는 효과 주장이 없는가** — "이렇게 하면 질문이 없어진다 / 재작업이 준다 / N% 개선" 류 문장이 있는가? 있으면 삭제한다. 수치는 등급·출처와 함께만 쓴다.
3. **미확인이 가시화됐는가** — 모든 미확인 값이 `[기획 확인 필요]`로 표시되고 §4 표에 대응 행이 있는가? 표시 없이 넘어간 빈칸이 있는가?
4. **못 쓰는 기능을 전제하지 않았는가** — 팀의 플랜·시트로 실행 불가한 항목을 "미통과"로 찍지 않았는가? 제약이 있으면 **해당없음 + 대체 경로**로 바꿨는가?
5. **디자인 결정을 대신하거나 Figma 파일을 수정하지 않았는가** — 리포트에 레이아웃·비주얼·톤을 *결정한* 문장이 있는가? 검증 중 Figma 쓰기 MCP 도구를 호출하거나 파일을 편집하지 않았는가? 파일 관찰은 읽기 도구 범위 안에서만 했는가?(INV-3)

5문항 중 하나라도 걸리면 **리포트를 고친 뒤 제출한다.** 감사 결과 자체도 리포트 말미에 1줄로 남긴다.

## 6. 정직성 — 이 체크리스트가 보장하지 않는 것

**이 체크리스트를 전부 통과해도 FE 질문이 0이 된다는 보장은 없다.** "AC를 전수 상태 프레임으로 그리면 개발자 질문이 사라진다", "happy path만 그린 디자인이 재작업을 유발한다" 같은 주장은 **측정 연구가 확인되지 않았다.** 어떤 형태의 "질문 N% 감소", "재작업 N% 절감" 수치도 이 하네스에서 **인용하지 않는다.**

인용 가능한 유일한 근접 수치는 다음 하나뿐이다.

> Telerik/Progress, *Workflows in the Age of AI* (2025-09-29~12-05, **n=225 자기선택 표본**) — "구현이 매우 효율적"이라고 답한 비율 21%. 협업이 나쁘다고 답한 팀 중 재작업 비용 증가 33%·출시 지연 42%. **[SILVER — 벤더 공개 리포트]** 출처: https://www.telerik.com/ai-design-development-workflows-report-2025

이 수치는 **상관관계이며 인과가 아니다.** "핸드오프를 잘하면 재작업이 33% 준다"로 바꿔 말하는 순간 원문에 없는 주장이 된다. 이 문서에서 이 수치는 *협업 품질과 재작업이 함께 관측된다*는 방향성까지만 지지한다.

이 체크리스트가 실제로 하는 일은 **"FE가 추측해야 하는 지점을 개발 착수 전에 목록으로 만든다"** 뿐이다. 그 목록을 누가 언제 채울지는 사람의 결정이며, 채우지 않은 채 착수하는 선택도 팀의 권한이다. 통과 개수는 세되 **품질을 약속하지 않는다.**
