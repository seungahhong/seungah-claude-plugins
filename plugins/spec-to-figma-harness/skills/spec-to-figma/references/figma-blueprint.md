# Figma 반영 설계도 — 구조·명명·연결·플랜 제약

Phase 2(`figma-blueprinter`)의 정본. **"이 스토리를 Figma에 어떻게 반영해야 하는가"를 설계**하는 규약이며, 디자인 자체를 만들지 않는다.

> **이 문서 전체의 3대 전제**
> - **읽기 전용(INV-3)** — Figma 파일을 생성·수정하지 않는다. 기존 파일은 델타 진단을 위한 조회만.
> - **발명 금지(INV-1)** — 프레임명에 들어가는 화면명·상태명은 스토리/AC에서 온 말만 쓴다. 없으면 `[기획 확인 필요]`.
> - **플랜 정직(INV-4)** — 팀이 못 쓰는 기능을 전제한 요구를 강요하지 않고 항상 대체 경로를 병기한다.
>
> 근거 등급 표기: `[GOLD]` 공식 문서 · `[SILVER]` 벤더 공식 블로그 · `[BRONZE]` 3자 블로그 · `[관행]` 출처 없는 실무 관행.

## 1. 구조 계층 규약

| 계층 | 대응 | 명명 규칙 | 예 |
|------|------|-----------|-----|
| **페이지(Page)** | 에픽 / 기능 묶음 | `[{에픽ID}] {에픽명}` | `[EPIC-12] 주문 내역` |
| **섹션(Section)** | **유저스토리 1개** | `[{티켓ID}] {스토리 문장}` | `[US-123] 회원은 주문 내역을 필터링할 수 있다` |
| **프레임(Frame)** | **상태 1개** | `{티켓ID} / {화면} · {상태}` | `US-123 / 주문내역 · 필터결과 0건` |
| **레이어(Layer)** | 어노테이션 부착 지점 | 역할이 드러나는 이름(`btn-필터초기화`) | `Rectangle 12` 금지 |

**모든 명명 규칙과 티켓 ID 연계는 `[관행]`이다.** Figma 공식 문서는 sections를 "협업 영역 지정·파일 탐색 정리" 용도로 기술할 뿐, **티켓/이슈 트래커 연계에 대한 서술이 없다**. 팀에 이미 다른 규칙이 있으면 그 규칙을 우선하고, 이 문서의 형식을 강요하지 않는다.

### 왜 화면 단위가 아니라 스토리 단위인가

| | 화면 단위 묶음 | **스토리 단위 묶음(권장)** |
|---|---|---|
| 섹션 = | `주문내역` | `[US-123] 회원은 주문 내역을 필터링할 수 있다` |
| 티켓 → 디자인 | "주문내역 어디를 보라는 건지" 탐색 필요 | 티켓 ID로 섹션이 바로 특정됨 |
| 디자인 → 티켓 | 이 프레임이 어느 요구에서 왔는지 소실 | 프레임명 앞자리가 근거 티켓 |
| 변경 영향 | 화면에 여러 스토리가 섞여 무엇이 바뀐 건지 불명 | 스토리 단위로 변경·리뷰·마킹 |
| 빠진 상태 발견 | 안 드러남 | 섹션 안 프레임 수 = AC 상태 수 대조 가능 |

동일 화면이 여러 스토리에 등장하면 **프레임을 복제하지 말고**, 후속 스토리 섹션에서 `(재사용: US-100 / 주문내역 · 기본)`으로 참조를 명시한다. 재사용 여부는 명시되지 않으면 FE가 "새로 만들라는 것인지 기존 것을 쓰라는 것인지"를 추측하게 되는 항목이므로 프레임 목록의 `비고`에 반드시 남긴다.

## 2. 권장 / 지양 대조표

| 항목 | 지양 | 권장 | 이유 |
|------|------|------|------|
| 프레임명 | `Frame 24`, `주문내역2`, `최종_진짜최종`, `수정본_v3` | `US-123 / 주문내역 · 조회실패` | 이름이 곧 상태 식별자이자 검색 키 |
| 상태 표기 | 이름에 상태 없음(레이어를 숨겨 표현) | 상태를 이름에 명시, 상태당 프레임 1개 | 레이어 가시성으로만 표현하면 어느 조합이 그 상태의 정본인지 **이름에서 드러나지 않아** 대응 AC를 지목할 수 없다 |
| 섹션명 | `필터`, `2차 스프린트` | `[US-123] 회원은 주문 내역을 필터링할 수 있다` | 스토리 문장이 곧 검증 기준 |
| 티켓 연결 | 디자인 → 티켓 단방향(또는 없음) | 티켓 본문에 프레임 링크 + 프레임명에 티켓 ID(양방향) | 한쪽만 있으면 반대 방향 추적이 끊긴다 `[관행]` |
| 흐름 표현 | 프레임 옆 텍스트로 "여기서 저기로" | 프로토타입 연결로 표현 | 텍스트 설명은 해석 여지가 남는다 |
| 상태 전달 | 사각형에 직접 hex/px 입력(detach) | 라이브러리 컴포넌트 + Variables | Inspect 값의 신뢰성(§6) |
| 버전 | 파일 복제로 `_v2` 관리 | 한 파일 안에서 상태·마킹으로 관리 | 복제본은 어느 쪽이 정본인지 불명 |
| 미확정 값 | 그럴듯한 문구로 채움 | `[기획 확인 필요]` 유지 | INV-1 |

## 3. 프레임 목록 산출 형식

Phase 1 커버리지 매트릭스의 상태마다 **1행**. 표 스키마는 고정한다.

| 컬럼 | 내용 |
|------|------|
| **프레임명** | `{티켓ID} / {화면} · {상태}` 최종 문자열(디자이너가 그대로 입력) |
| **상태코드** | `S-DEFAULT` 등 Phase 1 코드 |
| **대응 AC** | AC 번호(복수 가능). AC 없이 카탈로그 호명으로 나온 것은 `(AC 없음)` |
| **신규/기존** | `신규` / `기존` / `기존-수정` / `미확인`(델타 진단 전) |
| **필요 이유** | 이 프레임이 없으면 FE가 무엇을 추측하게 되는지 한 줄 |
| **비고** | 미확인 값·재사용 관계·논의 필요 사항 |

### 예시 (도메인: 주문 목록 필터링)

| 프레임명 | 상태코드 | 대응 AC | 신규/기존 | 필요 이유 | 비고 |
|----------|----------|---------|-----------|-----------|------|
| `US-123 / 주문내역 · 기본` | `S-DEFAULT` | AC-1 | 기존 | 필터 적용 후 결과 목록의 기준 레이아웃 | 기존 `주문내역_최종` 프레임과 동일 추정 → 델타 확인 |
| `US-123 / 주문내역 · 조회중` | `S-LOADING` | AC-2 | 신규 | 로딩 표현이 없으면 스켈레톤/스피너/무표시를 FE가 임의 선택 | 형태·부분로딩 여부 `[기획 확인 필요]` |
| `US-123 / 주문내역 · 필터결과 0건` | `S-EMPTY` | AC-3 | 신규 | 최초 0건과 문구·행동이 다름 | 안내 문구 원문·CTA 라벨 `[기획 확인 필요]` |
| `US-123 / 주문내역 · 조회실패` | `S-ERROR` | AC-4 | 신규 | 재시도 UI 유무에 따라 API 재호출 설계가 달라짐 | 재시도 횟수·반복 실패 문구 `[기획 확인 필요]` |
| `US-123 / 주문내역 · 상품명 말줄임` | `S-OVERFLOW` | (AC 없음) | 신규 | 긴 상품명 처리 미정 시 줄수·툴팁을 FE가 임의 결정 | **되물음**: 최대 줄 수·툴팁 여부 |
| `US-123 / 주문내역 · 모바일 기본` | `S-BP-MOBILE` | AC-1 | 신규 | 필터가 인라인→바텀시트로 *재배치*됨(§9 기준 충족) | 태블릿 재배치 여부는 **근거 AC 없음 → 되물음 Q로**(동일 배치 여부를 임의 판단하지 않음) |

마지막 행처럼 **"만들지 않는 이유"도 기록한다.** 빠뜨린 것과 의도적으로 제외한 것을 구분하지 못하면 Phase 4에서 다시 캐물어야 한다.

## 4. 기존 Figma 파일 델타 진단 (읽기 전용)

기존 파일이 있을 때만 수행한다. 목적은 **"설계한 프레임 중 무엇이 이미 있고, 무엇이 없고, 무엇이 이름만 다른가"** 한 표를 만드는 것이다.

### 4.1 도구 로드와 호출 순서 (결정론적)

Figma MCP 도구는 기본 노출되지 않으므로 `ToolSearch`로 **읽기 도구만** 로드한다(도구 이름의 서버 접두사는 설치에 따라 다르다 — 관측된 예: `mcp__claude_ai_Figma__*`).

```
ToolSearch: select:mcp__claude_ai_Figma__get_metadata,
            mcp__claude_ai_Figma__get_design_context,
            mcp__claude_ai_Figma__get_variable_defs,
            mcp__claude_ai_Figma__get_screenshot,
            mcp__claude_ai_Figma__get_code_connect_map
```

| 순서 | 도구 | 범위 | 얻는 것 |
|------|------|------|---------|
| 1 | `get_metadata` | 파일/페이지 루트 1회 | 희소 XML 노드맵(이름·계층·id) `[GOLD]` — **이름 대조는 여기서 끝낸다** |
| 2 | `get_screenshot` | 판정 애매한 노드만 | 이름은 달라도 같은 화면인지 눈으로 확인 |
| 3 | `get_design_context` | 확정적으로 필요한 노드만 | 구조·값(기본 React+Tailwind 출력) `[GOLD]` |
| 4 | `get_variable_defs` | 토큰 확인이 필요한 노드만 | 변수 정의. **디자인이 실제 변수를 쓸 때만 토큰 반환, 하드코딩이면 hex 그대로** `[SILVER]` |

**금지·주의**
- **페이지를 통째로 `get_design_context`에 넣지 않는다.** 토큰이 폭주하고 델타 판정에 필요 없는 스타일 정보가 대부분이다. 1단계 노드맵으로 후보를 좁힌 뒤 노드 단위로만 호출한다.
- Figma MCP에는 **rate limit이 있다** `[GOLD]`. 노드 단위 호출을 무제한 반복하지 말고 필요한 것만 뽑는다.
- 선택(selection) 기반 프롬프트는 **데스크톱 서버만** 지원하고, remote는 **프레임 링크가 필요**하다 `[SILVER]`. 링크가 없으면 링크를 요청하는 것이 먼저다.
- **쓰기 계열 도구는 이 하네스에서 호출하지 않는다(INV-3)** — `use_figma`, `generate_figma_design`, `create_new_file`, `add_code_connect_map`, `upload_assets`(5개). 사용자가 "그냥 네가 만들어줘"라고 해도 범위 밖임을 밝히고 설계도 산출로 대신한다.
- MCP를 못 쓰는 환경이면 대체 경로: 디자이너에게 **페이지별 프레임 이름 목록**(또는 전체 캔버스 스크린샷)을 요청해 같은 대조표를 만든다. 추정으로 채우지 않는다.

### 4.2 델타 대조표

| 판정 | 의미 | 조치 |
|------|------|------|
| `Δ-MATCH` | 설계 프레임 = 기존 프레임(이름·의미 일치) | 없음 |
| `Δ-MISSING` | 설계에 있는데 파일에 없음 | **신규 생성 요청**(디자이너) |
| `Δ-RENAME` | 같은 화면인데 이름이 규약과 다름 | 개명 제안(강제 아님, 팀 규칙 우선) |
| `Δ-EXTRA` | 파일에 있는데 설계에 없음 | **되물음** — 폐기 대상인지 우리가 놓친 상태인지 |
| `Δ-UNKNOWN` | 스크린샷/컨텍스트로도 동일성 판단 불가 | 되물음 목록으로 이관(단정 금지) |

산출은 항상 세 묶음으로 요약한다 — **있는 것 / 없는 것 / 이름이 다른 것**. `Δ-EXTRA`를 "불필요한 잔재"로 단정하지 않는다.

## 5. 프로토타입 flow 설계

**원칙 — 흐름은 텍스트 설명이 아니라 연결로 표현한다.** "빈 상태에서 전체 보기를 누르면 기본으로 돌아온다"는 문장은 어느 레이어가 트리거인지, 어느 프레임으로 가는지를 여전히 추측하게 만든다. 연결은 그 두 가지를 강제로 확정시킨다.

| 컬럼 | 내용 |
|------|------|
| flow명 | `{티켓ID} / {시나리오 이름}` |
| 출발 프레임 | 프레임명 |
| 트리거 레이어 | **레이어 이름까지** 특정(`btn-전체보기`). "버튼" 같은 총칭 금지 |
| 인터랙션 | On click / On drag 등 + 조건 |
| 도착 프레임 | 프레임명 |
| 대응 AC | AC 번호 |

예시:

| flow명 | 출발 프레임 | 트리거 레이어 | 인터랙션 | 도착 프레임 | 대응 AC |
|--------|-------------|---------------|----------|-------------|---------|
| `US-123 / 필터 적용` | `· 기본` | `chip-기간-3개월` | On click | `· 조회중` | AC-1, AC-2 |
| `US-123 / 결과 없음` | `· 조회중` | (자동 전이) | After delay | `· 필터결과 0건` | AC-3 |
| `US-123 / 필터 초기화` | `· 필터결과 0건` | `btn-전체보기` | On click | `· 기본` | AC-3 |
| `US-123 / 조회 실패 재시도` | `· 조회실패` | `btn-재시도` | On click | `· 조회중` | AC-4 |

- **flow 시작점에 스토리 이름을 붙이면** Present로 시나리오를 재생하며 AC와 나란히 대조할 수 있다 `[관행]`.
- **모션은 어노테이션 텍스트보다 표현물이 낫다.** `Figma Motion`이 GA되어 키프레임·이징이 Dev Mode에서 그대로 inspect되고 CSS/JSON/React로 export되며 MCP로도 전달된다 `[SILVER]`. duration·easing을 글로 받아쓰기 전에 프로토타입/Motion으로 표현 가능한지 먼저 확인한다. 표현이 불가능한 경우에만 어노테이션으로 남긴다.
- flow 표에 등장하지 않는 프레임은 **진입 경로가 없는 프레임**이다. 의도된 것인지 확인한다(되물음 후보).

## 6. Inspect 신뢰성 요구

FE가 Dev Mode에서 읽는 값이 정확해야 어노테이션 분량이 줄어든다. 아래는 디자이너에게 요청할 **구조 요건**이지 비주얼 결정이 아니다.

| 요건 | 왜 | 근거 | 안 지켰을 때 |
|------|-----|------|--------------|
| 색·간격·타이포에 **Variables** 사용 | Inspect에 **변수명 + 해석된 값이 함께** 표시된다 | `[GOLD]` | FE가 하드코딩 hex를 그대로 복사 → 토큰 체계 이탈 |
| 코드 스니펫 표기 | 스니펫에는 **Code syntax 설정대로** 출력된다 | `[GOLD]` | 코드베이스 변수명과 어긋난 스니펫 |
| **라이브러리 컴포넌트** 인스턴스 사용 | 재사용 판단과 Code Connect 매핑의 전제 | `[관행]` | "이거 새로 만들라는 건가?"가 반복 질문이 된다 |
| **Auto Layout** 적용 | 반응 규칙(늘어남/고정)이 구조로 드러난다 | `[관행]` | 절대 좌표만 남아 FE가 배치 의도를 추측 |
| **detach 금지** | detach된 요소는 변수·컴포넌트 연결이 끊긴 사본이다 | `[관행]` | Inspect 값이 정본과 달라도 티가 안 난다 |

`get_variable_defs`는 **디자인이 실제 변수를 쓸 때만 토큰을 반환하고, 하드코딩 hex면 hex가 그대로 나온다** `[SILVER]`. 즉 MCP로 토큰이 안 나오는 것은 도구 문제가 아니라 **디자인이 변수를 쓰지 않았다는 신호**다.

## 7. Code Connect

- **무엇** — 리포지토리 컴포넌트 ↔ Figma 컴포넌트를 매핑해, Dev Mode/MCP가 실제 코드 컴포넌트를 가리키게 한다 `[GOLD]`. MCP `get_code_connect_map`의 데이터 소스 `[GOLD]`.
- **지원** — React / React Native, HTML(Web Components·Angular·Vue), SwiftUI, Jetpack Compose, **프레임워크 무관 TS template 파일(권장)** `[GOLD]`.
- **셋업** — CLI publish 또는 Figma 내 UI(GitHub 연동, 1:N) `[GOLD]`.
- **필요 조건 — Dev 또는 Full seat + Organization/Enterprise 플랜** `[GOLD]`.

**플랜이 안 되는 팀의 대체 경로(INV-4)** — 아래는 모두 `[관행]`이며, Code Connect와 동등한 자동 동기화는 제공하지 않는다(수동 유지보수 부채가 생긴다는 점을 함께 알린다).

| 대체 | 방법 |
|------|------|
| 어노테이션에 명시 | 해당 레이어 어노테이션에 `코드 컴포넌트: <OrderFilterChip>` 한 줄 |
| 매핑 표 동봉 | `Figma 컴포넌트명 / 코드 컴포넌트 경로 / props 대응` 3열 표를 핸드오프 문서에 첨부 |
| 명명 일치 | Figma 컴포넌트명을 코드 컴포넌트명과 동일하게(대소문자까지) 맞춰 검색으로 잇기 |

> `Code Layers`는 2026-07부터 waitlist 롤아웃 단계다 `[SILVER]`. **쓸 수 있다고 전제하지 말고**, 팀이 접근 가능한지 확인된 경우에만 계획에 넣는다.

## 8. Ready for dev 마킹 계획

Dev status는 **Section / Frame / Component**에 붙는다 `[GOLD]`. UI 라벨은 `Mark as ready for dev` `[GOLD]`.

| 상태 | 의미 | 가용 범위 |
|------|------|-----------|
| `Ready for dev` | 개발 착수 가능 | **전 유료 플랜** `[GOLD]` |
| `Completed` | 개발 완료 | **Organization / Enterprise 전용** `[GOLD]` |
| `Changed` | 마킹 후 디자인이 수정됨 — **자동 부여** `[GOLD]` | 마킹된 대상 |

- **상태 변경 권한** — Full 또는 Dev seat `[GOLD]`.
- **알림** — 해당 파일을 Dev Mode로 본 Full/Dev seat 사용자에게 마킹 시 통지되며, **파일별로 끌 수 있다** `[GOLD]`.
- **`Ready for dev` view / focus view는 Organization·Enterprise 전용** `[GOLD]`. 이 뷰로 목록을 훑는 절차를 전 팀에 전제하지 않는다.

### 마킹 계획 표

| 대상 | 타입 | 마킹 시점 | 선행 조건 |
|------|------|-----------|-----------|
| `[US-123] …` | Section | 스토리의 모든 상태 프레임 + 어노테이션 완료 후 | 프레임 목록 `Δ-MISSING` 0건, `[기획 확인 필요]` 해소 또는 명시 |
| `US-123 / 주문내역 · 기본` | Frame | 개별 상태가 먼저 확정되면 프레임 단위 선행 마킹 가능 | 해당 프레임의 핀 작성 완료 |

- **`[기획 확인 필요]`가 남은 대상을 마킹하지 않는다.** 마킹은 "추측 없이 개발 가능"의 신호이므로, 빈칸이 있는 채로 마킹하면 신호가 무의미해진다.
- 마킹 후 디자인을 고치면 `Changed`가 자동으로 붙는다 `[GOLD]` — 변경 사실은 드러나지만 **무엇이 왜 바뀌었는지는 드러나지 않는다.** 변경 사유는 별도로 전달한다.

**대체 경로(플랜/시트 제약 시)** — 모두 `[관행]`:
① 섹션명 접두사(`[READY] [US-123] …`), ② 핸드오프 문서의 `상태` 컬럼(준비/작업중/보류), ③ 티켓 본문에 프레임 링크 + 상태 기재. 어느 경우든 **정본이 어디인지 한 곳으로 정한다**(두 곳에 상태를 두면 반드시 어긋난다).

## 9. 반응형 브레이크포인트 판단 기준

**레이아웃이 *재배치*되는 지점만 프레임으로 만든다.** 폭 목록을 다 그리는 것은 커버리지가 아니라 비용이다(볼륨 가점 금지).

| 판정 | 기준 | 프레임 |
|------|------|--------|
| **재배치** | 요소의 **순서·계층·표현 형태**가 바뀜 — 인라인 필터 → 바텀시트, 2열 → 1열, 테이블 → 카드, 표시되던 요소가 사라짐/접힘 | **필요** |
| 신축 | 같은 배치에서 폭만 늘고 줆(Auto Layout으로 표현 가능) | 불필요 |
| 값만 다름 | 폰트 크기·여백만 토큰 값으로 분기 | 불필요 — 어노테이션/Variables로 |
| 불명 | 재배치 여부를 판단할 정보가 없음 | **되물음**(임의 결정 금지) |

- 대상 폭(px)은 팀이 실제 쓰는 값을 확인해서만 적는다. **표준 브레이크포인트를 지어내지 않는다(INV-1).**
- 프레임을 만들지 않기로 한 폭도 프레임 목록 `비고`에 "동일 배치 → 프레임 없음"으로 남긴다.

## 10. Phase 2 종료 자가 점검 (게이트 C 전)

- [ ] 모든 상태 프레임에 **대응 AC 또는 `(AC 없음)+되물음`** 이 붙었는가
- [ ] 프레임명이 규약 문자열로 **그대로 복붙 가능**한가(`[기획 확인 필요]` 포함 여부 표시)
- [ ] 기존 파일이 있는데 델타 진단을 **건너뛰지 않았는가**(못 했으면 그 사실을 명시)
- [ ] 델타 산출이 **있는 것/없는 것/이름 다른 것** 세 묶음으로 정리됐는가
- [ ] flow 표의 트리거가 **레이어 이름 수준**으로 특정됐는가 / 진입 경로 없는 프레임을 확인했는가
- [ ] Code Connect·`Ready for dev` 제안에 **플랜 조건과 대체 경로**가 병기됐는가
- [ ] 브레이크포인트 프레임이 **재배치 근거**를 갖는가
- [ ] 쓰기 계열 MCP 도구를 **호출하지 않았는가**
- [ ] "이대로 하면 질문이 없어진다"류의 **효과 약속이 문서에 없는가**(INV-2)
