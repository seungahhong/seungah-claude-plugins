# 맥락과 지시 설계 — CARE 프롬프트·UX 맥락 팩

Phase 2(`context-curator`)가 L1·L2 단계마다 만드는 것. 근거 번호는 [evidence.md](./evidence.md).

> CARE는 **빠뜨리지 않게 돕는 체크리스트**다. 효과가 측정된 기법이 아니다(E3). 이 문서의 규칙도 NN/g 실무 권고이며, 하네스는 "이렇게 쓰면 결과가 N% 좋아진다"고 말하지 않는다.

## 1. CARE 골격

| 요소 | 넣을 것 | UX 작업에서 흔히 빠지는 것 |
|---|---|---|
| **C 맥락** | 역할·제품·조직·사용자·현재 작업·관련 리서치 결과·스크린샷 | **사용자에 대해 실제로 알려진 것**(리서치 결과). 없으면 지어내지 않고 `[확인 필요]`. **참가자 원 발언·개인정보는 넣지 않고** `<정제된 자료를 여기 붙임>` 자리표시자를 둔다(INV-8) |
| **A 요청** | AI의 역할 · 산출물 · **개수** · **단계** · 형식 | 단계. "계획 만들어줘" 대신 순서 있는 단계(E9) |
| **R 규칙** | 방법론 모범 사례 · 브랜드·톤 기준 · 글자 수·공간 제약 · 금지 사항 | **방법론 규칙**. NN/g는 AI가 웹의 나쁜 예시로 배웠다고 본다(E9) — 아래 §3의 규칙 묶음을 붙인다 |
| **E 예시** | 좋은 예 · 나쁜 예 · 기존 안과 그 문제점 | 기존 문안. 한 저자의 비공식 시도에서 톤은 형용사보다 예시가 나았다(E29) |

순서는 바꿔도 된다. 단순한 정보 탐색에는 이만큼 필요 없다(E3).

### 모든 프롬프트 끝에 붙이는 두 줄

```
이 작업에 필요한 정보가 더 있으면 시작하기 전에 물어봐 주세요. 없으면 단계를 진행하세요.
사실·수치·출처를 말할 때는 근거를 함께 적고, 모르면 모른다고 적어 주세요.
```
첫 줄은 E3의 예시 프롬프트가 쓰는 문장이다. 단 **"AI가 알아서 맞는 질문을 해 줄 거라 기대하지 말라"**(E9) — 이 줄은 보험이지 맥락을 대신하지 않는다.

## 2. 지시 설계 규칙

1. **쪼갠다.** 결과물 전체를 한 번에 요청하지 않는다(E9). 단계별로 받고 사람이 조립한다.
2. **필요한 것보다 많이 받고 사람이 고른다.** 생성 N개 → 기준으로 M개 선택 → 순위와 이유(E3). 발산이 목적이면 프롬프트당 15~20개(E34).
3. **고른 것만 들고 새 세션.** 버린 후보가 대화 기록에 남아 다음 단계를 오염시키지 않게(E9).
4. **템플릿을 준다.** 동의서·스크리너·계획서는 빈 양식부터 만들게 하지 말고 조직 템플릿을 주고 채우게 한다(E8).
5. **수치는 코드로.** 계산이 들어가면 코드 실행·계산 과정 표시·합계 검증을 지시한다(E26).
6. **출처를 요구하고 직접 연다.** 데스크 리서치에서 1차 출처 링크를 요구한다. 링크를 받은 것은 확인이 아니다 — 사람이 연다(E6·E8).
7. **분류와 평가를 나눈다.** "이 화면에 무엇이 있나"와 "그것이 좋은가"를 한 프롬프트에 섞지 않는다(E37).
8. **프롬프트는 자족적이어야 한다.** 하네스와의 대화를 못 본 새 AI 세션이 읽어도 이해되게 쓴다. Phase 3에서 새 컨텍스트로 돌려 이것을 실제로 확인할 수 있다.

## 3. 방법론 규칙 묶음 (R 칸에 붙인다)

해당 작업에 맞는 묶음만 붙인다. 묶음 전체를 매번 붙이면 프롬프트가 길어지고 우선순위가 흐려진다.

**사용성 과제**(E9·E21)
- 인터페이스에 있는 단어·링크 이름을 과제 지시에 쓰지 않는다. 같은 뜻의 일상어로 쓴다.
- 참가자에게 다른 사람이라고 상상하게 하지 않는다.
- 과제마다 목표나 행동 유도를 넣는다.
- 어디로 가서 무엇을 순서대로 하라고 지시하지 않는다. 주의를 줄 곳을 알려주지 않는다.

**스크리너·모집**(E9)
- 연구 주제와 찾는 사람을 숨길 수 있는 위장용 보기를 넣는다.
- 모집 문안은 중립적이고 간결하게. 과장된 마케팅 어조를 쓰지 않는다.

**설문**(E20)
- 그리드 문항을 쓰지 않는다. 다중선택 보기는 10개를 넘기지 않는다.
- 인구통계 문항은 (스크리너가 아니면) 끝에 둔다.
- 다중선택 지시를 일관되게 한다.
- 목록이 망라적이지 않으면 '기타'를 넣는다.
- 척도는 표준 형식(리커트·의미변별)을 쓰고, 양 끝을 의미상 대칭으로, 리커트 범주를 빠뜨리지 않는다.
- 상대적 우선순위가 목적이면 순위 문항을 검토한다.
- 목표 응답 시간을 적는다. 문항당 소요 기준을 사용자가 줬으면 그 기준으로 계산해 보이게 하고, 없으면 계산하지 말고 문항 수만 세게 한다.

**문안·톤**(E29)
- 톤 형용사 하나 대신 기존 문안 예시, 또는 미묘한 형용사 여러 개.
- 대안을 여러 개 요청.

**AI 프로토타이핑**(E27)
- "깔끔하고 모던하게" 대신 정확한 시각 스타일 이름.
- 무드보드·디자인 시스템 스크린샷 같은 가벼운 시각 참조. 정밀도가 필요하면 디자인 소스와 직접 연결.
- **목 데이터를 먼저 만들어** 함께 준다.
- 쓸 수 있는 코드 스니펫(자사·오픈소스, 라이선스 확인)을 준다.
- 특정 브랜드를 모방하라고 하지 않는다.

**목 데이터**(E26)
- 고유성·고정값·서식·범위·분포를 명시.
- **테스트 과제가 의존하는 값은 바꾸지 말라고 명시.**
- 계산은 코드로, 과정 표시, 합계 검증.

**코딩·군집**(E8)
- 연구 목표·연구 질문을 맥락으로 준다.
- 좋은 코드 예시를 준다.
- 각 코드에 근거가 된 발언 위치(세션·타임스탬프)를 붙이게 한다(E22).

## 4. UX 맥락 팩 (선택 — 반복 작업일 때만)

같은 종류의 AI 작업을 여러 번 할 때 매번 맥락을 다시 쓰지 않도록 한 파일에 모은다. 형식은 E23의 DESIGN.md(실재) / UX.md(**저자가 가설로 제안**)를 참고한다.

```
# <제품> UX 맥락 팩 — v<날짜>
> 이 파일은 사람이 고른 리서치 결과를 AI가 읽도록 정리한 것이다. 효과는 측정하지 않았다.

## 사용자 모델 — 리서치로 확인된 것만
- <발견 문장> (출처: <연구명·날짜·n>)
## 사용 맥락(세계 모델)
- <중단·스트레스·규정 등> (출처: …)
## 용어집 — 사용자가 쓰는 말
- <사용자 용어> = <정의> (내부 용어 <X>는 쓰지 않음)
## 인터랙션 표준
- <확인 vs 실행 취소 기준, 오류 문구 원칙 …>
## 시각 표준
- <디자인 시스템·DESIGN.md 위치>
## 아직 모르는 것
- <[확인 필요] 목록>
```

규칙:
- **모든 문장에 출처**를 단다. 출처 없는 문장은 넣지 않는다(INV-5).
- 합성 사용자·AI 요약에서 나온 문장은 `가설` 라벨을 달거나 넣지 않는다(INV-2).
- 원자료를 통째로 넣지 않는다 — 중요한 것이 묻힐 수 있다(E23). 사람이 고른다.
- 맥락이 너무 많을 수 있다는 것은 저자도 열어 둔 질문이다(E23). 짧게 시작한다.
- 참가자 원 발언·개인정보를 넣지 않는다(INV-8).

