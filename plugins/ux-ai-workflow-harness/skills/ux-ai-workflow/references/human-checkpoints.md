# 사람 체크포인트·출처 라벨·인계

Phase 4(`checkpoint-planner`)가 최종 작업 계획을 만들 때 쓰는 규칙. 근거 번호는 [evidence.md](./evidence.md).

## 1. 사람 단계 배정 (L3)

Phase 1의 L3 단계마다 **누가·언제·무엇을 남기는지**를 정한다. "사람이 검토"처럼 주어가 없는 문장을 쓰지 않는다.

```
| # | 단계 | 담당 | 시점 | 남길 것 | 팀 학습 장치 |
|---|------|------|------|---------|--------------|
| 4 | 인터뷰 진행 | <이름/역할> | <날짜> | 세션 노트 | 동료 실시간 참관(E10) — 인원은 팀이 정한다 |
| 7 | 해석 | <팀> | 디브리프 직후 | 테마와 근거 발언 연결 | 함께 하는 디브리프(E10) |
```

**팀 학습 장치**는 E10의 "지킬 것"에서 고른다 — 실시간 관찰, 함께 하는 디브리프, 해석을 팀이 같이 하기. 워크숍이면 프롬프트 같이 쓰기(E34), AI로 How Might We 질문을 만들어 사람 토론을 여는 용도(E5 Inclusion).

## 2. 검증 체크포인트

L2 단계의 산출물마다, Phase 3 점검과 **별개로** 사람이 하는 확인을 배정한다.

| 산출물 | 체크포인트 | 근거 |
|---|---|---|
| 설문 | **실제 사람 파일럿**(완료 시간 실측 포함 — P-SURVEY-1이 `미확인`이면 여기서 잰다) — AI 관여와 무관하게 하네스가 항상 올린다. 사용자가 생략하면 따르고 '알고 넘어간 위험'에 기록 | E20 |
| 사용성 과제·스크리너·가이드 | 지정된 검수자 검토 — 점검표 항목을 판정할 수 있다고 사용자가 정한 사람(본인 가능). 없으면 `검수자 미정` | E4·E8 |
| PII 정제 | 원본 대비 표본 대조(지워진 연구 내용·남은 PII) — 담당 지정 | E8 |
| 동의서 문안 | 법무·개인정보 담당 검토(조직 템플릿이 없을 때 특히) | E8·E18 |
| 페르소나·여정지도 초안 | 각 세부를 실제 리서치 결과와 사람이 대조(P-ARTIFACT) | E8 |
| UX 문안 | 기존 브랜드 문안과 나란히 놓고 사람이 선택·다듬기 | E29 |
| 데스크 리서치 | P-COMMON-2 출처 목록을 **사람이 직접 열기** | E6·E8 |
| 1차 코딩·요약 | 원자료 표본 대조 | E8 |
| 정량 분석·목 데이터 | 표본 재계산 | E8·E26 |
| 합성 사용자 결과 | 어떤 실제 리서치로 확인할지 계획 | E12 |
| AI UX 감사 결과 | 항목별 사람 판정 | E35·E36 |
| AI 프로토타입 | 실제 사용자 테스트 | E27 |
| AI 진행 구조화 인터뷰 | 소개 대본 사람 작성, 표본 녹취 사람 청취 | E19 |

## 3. 출처 라벨 (INV-2)

하네스가 만들거나 다듬는 모든 산출물 블록에 출처 라벨을 붙인다.

| 라벨 | 뜻 |
|---|---|
| `실제 사용자` | 실제 참가자 관찰·발언에서 사람이 도출 |
| `AI 초안 · 검수됨(<검수자>)` | AI가 쓰고 지정된 사람이 검수 |
| `AI 초안 · 검수 전` | 아직 검수 안 됨 |
| `AI 초안 · 검수자 미정` | 검수할 사람이 정해지지 않음(D7). 게이트 E에서 지정하거나 `검수 생략`으로 바꾼다 |
| `AI 산출 · 표본 대조(<누가>)` | 원래 L1인 산출물(전사·번역·대안 생성 등) — 지정된 사람이 표본을 대조함 |
| `AI 초안 · 검수 생략` | 사용자가 검수를 생략하기로 결정(레인 변경 기록 있음) |
| `합성 데이터` | 합성 사용자·디지털 트윈 응답. **가설** |
| `모델 추정` | 실제 응답자의 결측을 모델이 채운 값 |
| `목 데이터` | 테스트용으로 만든 가짜 데이터 |
| `트랜스크립트 기반` | 행동 관찰 없이 발화만으로 분석 |
| `AI 진행 세션` | AI 인터뷰어가 진행한 세션의 데이터 |

규칙:
- **`가설`은 라벨이 아니라 덧붙임**이다 — `합성 데이터 · 가설`, `모델 추정 · 가설`처럼 붙여 "실제 리서치로 갱신할 전제"임을 표시한다.
- 한 문서에 여러 출처가 섞이면 블록 단위로 붙인다. 문서 하나에 라벨 하나로 뭉뚱그리지 않는다.
- `합성 데이터`를 `실제 사용자`와 같은 표·같은 문장에 근거 구분 없이 합치지 않는다(E12 "unethical").
- 이해관계자용 보고에서는 **탐색 신호와 권고를 구분**하고 각 결론이 어떻게 도출됐는지 적는다(E40).

## 4. 재사용 자산 (선택)

D5 반복성 테스트가 "반복"으로 나온 단계에만 만든다(E5 Automation). 일회성 작업에 프롬프트 라이브러리를 만들라고 권하지 않는다.

- **프롬프트 라이브러리 항목**: Phase 2 프롬프트 + Phase 3에서 고친 점 + 다음에 붙일 규칙 묶음.
- **UX 맥락 팩**: [care-prompting.md](./care-prompting.md) §4. 효과는 가설이다(X6).
- **커스텀 AI(GPT·Gem·Project)**: 워크숍·반복 작업용. 페르소나 챗봇의 답을 사용자 근거로 쓰지 않는다(X13).

## 5. 데이터 보호 체크포인트 (INV-8)

참가자 원 데이터(녹취·영상·응답·이메일)를 외부 AI 도구에 넣는 단계가 있으면, 그 단계 **앞에** 아래를 확인하는 사람 단계를 둔다.
- 동의서가 그 처리(외부 AI 서비스 전송·디지털 트윈 생성)를 포함하는가?(E18)
- 조직의 AI 사용 정책이 허용하는가?(E25)
- PII 정제를 **외부 AI에 넣기 전에**, 허용된 도구나 수작업으로 했고 표본 대조했는가?(E8) 정제 자체를 외부 AI로 하면 이 확인을 그 앞에 둔다.

확인할 수 없으면 `미확인`으로 적고 Phase 4 '알고 넘어간 위험'에 올린다. 하네스는 이 확인을 대신 판정하지 않는다.

## 6. AI 아이디에이션 워크숍 진행안 (I-WORKSHOP일 때)

```
준비  : 같은 LLM 지정 · 워밍업 활동 · 맥락 파일(텍스트, 미리 업로드해 읽히는지 확인) · CARE 예시 프롬프트(E33)
발산  : 개인 또는 2~4인이 프롬프트를 같이 써서 15~20개씩 · 시간은 AI 없을 때보다 길게(E34)
추리기: 기준(예: 실현 가능성·바람직함·사업성)으로 AI가 상위 안 추림 — 점수는 토론 입력
수렴  : 사람이 묶고 토론하고 우선순위 — 실행할 사람이 참여
기록  : 공유 문서(AI 출력은 길어서 포스트잇에 안 맞음)
금지  : 워크숍 중 사용자 데이터 정식 분석(E33)
```
근거: 사람 2명 + AI가 최상위 아이디어 비율을 높였다(E32, 하루짜리 사내 과제·전문가 평정). 개인+AI는 최상위에서 유의하지 않았다.

## 7. AI UX 도구 도입 검토안 (T-TOOL일 때)

```
벤더 질문 : 정확도를 사람 결과와 비교해 어떻게 쟀나 / 어디서 깨지나 / 가드레일과 생성형 AI의 정확한 역할(E37)
            AI 기능의 설계·학습 데이터·사용자가 통제할 수 있는 범위(E21)
주장 대조 : "분석 다 해 줌"·"편향 없음"·"모든 방법 지원"·"트랜스크립트로 사용성 분석"(E21·E22)
파일럿    : 훈련된 리서처가 실제 연구로 — 데모 아님(E21)
가드레일  : 리서치 경험 없는 사용자가 결함 있는 연구를 모르고 내지 않도록
판정      : 이 하네스는 '도입하라/말라'를 정하지 않는다. 질문별 답 유무와 파일럿 결과만 정리한다
```

## 8. 서비스 디자인 관점 (SD-SERVICE일 때)

블루프린트에 사용자 대리 AI 비서와 조직 AI 에이전트 행위자 줄을 추가하고, 지표 후보(AI 간 호환·AI↔직원 호환·데이터 품질·자동화 완료율·신뢰)를 목록으로만 붙인다. 전망이지 측정이 아니다(E31). 직원 인터뷰·현장 관찰은 L3.

## 9. 최종 보고 형식

```
[Phase 4 작업 계획 — <작업명>]

1. 단계별 레인 (최종)
   | # | 단계 | 레인 | 담당 | 출처 라벨 |

2. 사람이 하는 단계와 팀 학습 장치
3. 검증 체크포인트 (누가·언제) — `검수자 미정`·`[담당 미정]` 해소 결과(지정 / 검수 생략 / 미정 유지) 포함
4. 데이터 보호 체크포인트
5. 점검하지 않은 단계 — 레인 · 실행 시 쓸 점검표 ID (게이트 C에서 뒤로 미룬 단계, '다음 묶음' 밖 단계)
6. Phase 3 `미확인` 항목과 넘길 사람
7. 알고 넘어간 위험
   - <레인 변경 기록에서 옮긴 것: 단계 · 원래 레인 · 바꾼 레인 · 잃는 것>
   - <생략한 단계와 그것이 E7 조건에 맞는지>
8. 이 하네스가 확인하지 않은 것
   - <점검표 밖 영역, 출처 실재 여부, 시각 산출물, 실제 효과 …>
9. 재사용 자산 (해당 시)

이 계획이 주장하는 것 (실제 숫자로 채운다):
  ① 각 단계를 누가 할지와 왜 그런지를 판정 근거와 함께 적었다
  ② 점검한 초안 <n>개에서 알려진 실패 패턴을 확인했다 — 점검하지 않은 L1·L2 단계 <n>개, 담당 미정으로 남은 확인 <n>건
이 계획이 주장하지 않는 것: 리서치·디자인 품질이나 속도가 얼마나 좋아지는지
```
