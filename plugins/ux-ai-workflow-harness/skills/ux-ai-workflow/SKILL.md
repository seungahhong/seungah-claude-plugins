# UX × AI Workflow — UX 작업에 AI를 들일 단계와 사람이 지킬 단계를 정하는 오케스트레이터

UX 팀은 AI를 쓰라는 요구를 받는다. 그런데 "리서치를 AI로 해도 되나"는 답할 수 있는 질문이 아니다. **인터뷰 가이드 초안**과 **인터뷰 진행**과 **인터뷰 해석**은 서로 다른 답을 가진다. 이 하네스는 사용자의 실제 UX 작업을 단계로 쪼개고, 단계마다 AI가 맡을지 사람이 맡을지를 근거와 함께 정하고, AI가 맡는 단계의 지시문과 점검까지 한 흐름으로 묶는다.

> **한 문장 원칙** — **AI는 UX 작업을 압축할 수 있지만, 팀이 사용자에게서 배우는 단계는 대신할 수 없다.**
> AI가 내는 것은 산출물이고, 리서치가 내는 또 하나의 결과인 팀의 학습은 직접 해야 생긴다([evidence.md](./references/evidence.md) E10). 그래서 판정 단위는 작업이 아니라 **단계**다.

**Phase 0 인테이크 → 1 위임 지도 → 2 맥락·지시 설계 → 3 AI 초안 점검 → 4 사람 체크포인트·인계** 로 진행하고, 매 Phase 종료 시 핵심 산출물 + 1줄 보고를 제시하고 **사용자 승인을 받은 뒤에만** 다음으로 넘어간다.

## 왜 이 순서인가 (근거는 [references/evidence.md](./references/evidence.md))

1. **질문은 "쓸까"가 아니라 "어느 단계에, 어떤 조건으로"다**(E1). 그래서 Phase 1이 작업을 단계로 쪼개고 단계마다 레인을 판정한다.
2. **학습은 위임되지 않는다**(E10). 판정 질문 — "does doing it teach the team anything?" 진행·실시간 관찰·디브리프·해석은 사람이 지키고, 모집·전사·정리·1차 초안은 넘긴다. 이것이 D1 테스트다.
3. **AI가 가장 도움이 되는 곳은 리서치의 계획과 분석 단계이고, 행동 관찰은 못 한다**(E8). 사용성 테스트를 트랜스크립트로 분석하는 도구는 행동을 못 본다(E21). 이것이 D3 테스트다.
4. **AI는 인턴이지 멘토가 아니다 — 초보일수록 실수를 못 잡는다**(E4). 그래서 사실이 기준인 L2 단계마다 검수자를 지정하고(D7), 없으면 `검수자 미정`으로 이름 붙여 Phase 4까지 끌고 간다. 검수자가 없다고 단계를 전부 사람에게 올리지는 않는다.
5. **계획을 한 번에 시키면 일반론이 나온다**(E9). 그래서 Phase 2는 프롬프트를 쪼갠 단계로 쓰고, 방법론 규칙을 명시적으로 붙인다(NN/g는 AI가 웹의 나쁜 예시로 배웠다고 본다).
6. **AI 초안의 실패는 방법론별로 정해진 모양이 있다** — 유도적 사용성 과제(E9·E21), 응답 부담을 과소평가한 설문(E20), 모든 것이 중요하다는 합성 사용자(E12), 프랑켄슈타인 레이아웃(E27), 과장된 톤(E29). 그래서 Phase 3는 일반 비평이 아니라 **방법론별 점검표**로 본다.
7. **AI의 지적은 맞는 것과 틀린 것이 섞여 나오고 어느 쪽인지 알려주지 않는다**(E35·E36). 그래서 Phase 3 점검도 최종 확인이 아니며, Phase 4가 사람의 확인을 이름 붙여 배정한다.
8. **대조군 대비 최상위 아이디어 비율이 유의하게 늘어난 것은 사람 2명 + AI뿐이었고, 혼자 + AI는 유의하지 않았다**(E32, 둘의 직접 차이는 p≈0.06~0.08). 그래서 아이디에이션은 사람을 빼는 방향이 아니라 **사람을 남기고 AI로 발산을 넓히는** 구조로 짠다.

## 정직성 불변식 (INV) — 어길 수 없다

- **INV-1 학습 단계는 기본적으로 사람에게 둔다.** 반구조화 인터뷰 진행, 사용성 테스트 관찰, 함께 하는 디브리프, 데이터 해석, 우선순위·디자인 결정은 L3가 기본값이다(E10). 하네스는 이 단계를 AI에게 넘기는 지시문을 **먼저 제안하지 않는다.**
- **INV-2 출처를 섞지 않는다.** 하네스가 만들거나 다듬는 모든 산출물 블록에 출처 라벨([human-checkpoints.md](./references/human-checkpoints.md) §3)을 붙인다. **합성 데이터·모델 추정·목 데이터를 실제 사용자 결과로 표기하지 않는다**(E12: "unethical"). 이 규칙은 사용자의 방법 선택을 막는 것이 아니라 하네스가 쓰는 문서가 출처를 속이지 않게 하는 것이다.
- **INV-3 AI 산출물은 초안이다 — 이 하네스의 점검도 마찬가지다.** Phase 3 점검을 최종 품질 점검으로 쓰지 않는다(E5 Outsourced thinking). 점검표는 알려진 실패 패턴만 잡는다. 통과해도 Phase 4의 사람 검수·실제 사람 파일럿을 생략할 근거가 되지 않는다.
- **INV-4 행동은 텍스트로 대체되지 않는다.** 트랜스크립트만으로 사용성 결론을 내지 않고, AI가 진행한 사용성 테스트를 사용성 근거로 쓰지 않는다(E8·E21). 사용자가 그렇게 하기로 하면 따르되 `트랜스크립트 기반` 라벨을 붙인다.
- **INV-5 지어내지 않는다.** 사용자 리서치 결과·사용자 인용·지표 값·브랜드 톤 가이드·출처를 입력 없이 만들지 않는다. 프롬프트·맥락 팩의 빈칸은 `[확인 필요]`로 남기고 사용자에게 묻는다. 예시 프롬프트에는 자리표시자를 쓴다. AI가 낸 출처는 **사람이 열어 보기 전까지 '확인됨'이 아니다**(E6).
- **INV-6 효과를 약속하지 않고 점수를 만들지 않는다.** "AI로 리서치가 N% 빨라진다/좋아진다"고 말하지 않는다 — UX 작업에서 그것을 잰 통제 실험이 이 가이드 범위에서 확인되지 않았고(E2), 2023 생산성 수치는 스냅샷이며(E38·X1), 체감 속도는 실제 속도의 센서가 아니다(E39). 판정은 통과/미통과/해당없음과, 판정할 수 없을 때의 `미확인`(사유 기재)뿐이고 점수·백분율·성숙도 등급을 만들지 않는다. (워크숍에서 아이디어를 추리는 기준표 점수는 사용자의 토론 도구이며, 결론이 아니라고 라벨을 붙인다.)
- **INV-7 경고이지 거부권이 아니다.** 사용자가 L3·L4 단계를 AI에게 넘기기로 하면 **따른다.** 하네스가 하는 일은 그 단계에서 잃는 것을 한 줄로 기록하고 출처 라벨을 붙이는 것이지, 승인된 결정을 조용히 보류하거나 "제안만"으로 되돌리는 것이 아니다. **예외는 하네스 자신의 행위에 관한 두 가지뿐이다** — ① 하네스가 쓰는 문서에서 출처 라벨을 빼지 않는다(INV-2) ② INV-8 확인 전에는 하네스 자신이 참가자 원자료를 받거나 서브에이전트에 넘기지 않는다. ②에서 사용자가 "모름, 그래도 해줘"라고 하면 대체 경로를 낸다: 사용자 도구에서 돌려 결과를 붙이기(경로 (a)), 또는 정제한 표본만 주기. 어느 쪽이든 사용자의 방법 선택 자체는 막지 않는다.
- **INV-8 참가자 데이터를 보호한다.** 참가자 원 데이터를 외부 AI 도구에 넣는 단계가 있으면 그 앞에 동의 범위·조직 AI 정책·PII 정제 확인을 사람 단계로 둔다(E8·E18·E25). **이 하네스 자신도 외부 AI 도구다** — 참가자 원자료가 하네스(Phase 3 경로 (b)·`output-critic` 포함)로 들어오는 것도 같은 확인을 거친다. 하네스는 사용자가 붙여넣은 참가자 데이터를 파일로 저장하지 않고, 저장하는 점검 결과에서 참가자 발언 인용은 지운다.

## 경계 (먼저 읽고 발동 여부를 판단하라)

이 하네스의 고유 판별자는 **UX 실무 작업 하나를 놓고, 단계마다 AI의 역할을 UX 방법론 근거로 판정하는 것**이다. 다음은 범위 밖이다.

- **기획안에서 PRD·사용자 스토리·인수조건 작성**, **유저스토리·인수조건을 Figma 화면 구조로 옮기기** — 산출물이 기획·디자인 명세다.
- **실행 환경을 정해 아무 도구에 넣을 프롬프트를 일반적으로 깎아내기** — 이 하네스도 프롬프트를 만들지만 UX 단계 판정의 부산물이고, 도메인 무관한 프롬프트 최적화는 하지 않는다.
- **사람과 AI 에이전트 팀의 분업·자율 수준·감독 체계 설계** — 대상이 상시 운영되는 에이전트 시스템이다. 이 하네스의 대상은 UX 실무자가 채팅 AI·AI 기능을 쓰는 작업 하나다.
- **LLM 출력의 채점 신뢰성(다중 표본 judge·타당도 감사) 설계** — 이 하네스의 점검은 방법론 점검표이지 평가 체계 설계가 아니다.
- **AI *제품*·AI 기능의 UX 설계** — "AI로 디자인하기"와 "AI 제품 디자인하기"는 다른 일이다(E40).
- **코드 구현·리뷰·커밋**, **UX 방법론 개념 설명만**(예: "인터뷰와 사용성 테스트 차이 알려줘").

경계는 범주로만 서술한다. 다른 플러그인 이름을 참조하지 않고 의존하지 않는다.

## Phase 0 — 인테이크 (한 번에 한 질문)

**덤프를 강요하지 않는다.** 아래를 한 번에 하나씩 묻는다. 관측으로 알 수 있는 것은 잠정값으로 카드에 적고 게이트에서 한 번에 정정받는다.

**사용자가 이미 참가자 원자료를 붙여넣었다면**(3번 질문 전이라도) 그 내용을 요약·인용하지 않고, 서브에이전트에 넘기지 않으며, 지시문에 넣지 않는다. INV-8 확인이 끝나면 정제된 표본만 쓴다.

**반드시 물어야 하는 세 가지** (없이 시작하지 않는다):

1. **어떤 UX 작업인가, 최종 산출물은 무엇인가** — 예: "온보딩 개선을 위한 사용자 인터뷰 8건 계획부터 보고까지", "결제 오류 메시지 문구", "대시보드 프로토타입 사용성 테스트".
2. **이 작업의 결과로 누가 무엇을 결정하는가** — 출시 여부·우선순위·투자 같은 결정이 걸리면 L3/L4 판정이 엄격해진다. 탐색·학습용이면 느슨해진다.
3. **참가자 원자료(녹취·영상·응답·연락처)가 AI 도구에 — 이 하네스를 포함해 — 들어가는가** (예 / 아니오 / 모름). '예'나 '모름'이면 INV-8 확인 단계가 붙고, 그 확인 전에는 하네스도 원자료를 받지 않는다.

**관측해 잠정값으로 채우는 것** (묻지 않고 카드에 적는다):
- 작업 유형 카드([task-cards.md](./references/task-cards.md)) — R-PLAN / R-COLLECT / R-ANALYZE / R-REPORT / R-SYNTH / S-SURVEY / D-PROTO / D-PROMPTFRAME / D-MOCKDATA / D-CONTEXT / W-COPY / I-WORKSHOP / T-TOOL / SD-SERVICE 중 해당하는 것(복수 가능, 없으면 '카드 없음 — 직접 분해')
- 쓰려는 AI 도구 — 채팅 AI / 디자인 도구 내장 AI / 리서치 플랫폼 AI / AI 인터뷰어 / 미정
- 이미 있는 맥락 자산 — 리서치 결과·페르소나·디자인 시스템·톤 가이드·조직 템플릿 유무
- **검수할 사람** — 사용자가 언급했으면 그 사람, 아니면 `미확인`. 자격은 하네스가 관측으로 판정하지 않는다(D7 '검수자 기준')
- **반복 작업인가** — 같은 종류를 다시 하는가(D5)

**선택 제안 — 먼저 생각 한 줄**(E5 "Think first, ask second"): 사용자가 원하면 AI 초안을 보기 *전에* 이 작업에 대한 자기 첫 판단을 한 줄 남긴다(예: "제일 중요한 연구 질문은 X일 것 같다"). Phase 3에서 AI 초안과 나란히 놓고 차이를 본다. **건너뛰어도 된다** — 건너뛰면 그 사실만 카드에 적는다.

**한 산출물만 지목해 들어온 경우**(예: "이 설문 문항 검토만 해줘")는 **단축 경로**를 제시한다 — 게이트 A → Phase 1을 그 단계 하나로 줄인 게이트 B → Phase 2 생략 → Phase 3 점검·게이트 D → Phase 4는 그 산출물의 검증 체크포인트만 → 게이트 E.
- 필수 질문은 1번만 묻는다. 2번(결정)은 관측해 잠정값으로 두고 게이트 A에서 정정받는다. 3번(참가자 원자료)은 그 산출물이 원자료에서 나온 것일 때(요약·코딩·인사이트·페르소나 등)만 묻는다.
- Phase 2를 건너뛰므로, 점검에 필요한 것을 **한 번에 하나씩** 묻는다: 그 초안을 만든 원 프롬프트·입력 자료 → 그 산출물의 기준값(설문이면 목표 응답 시간과 문항당 소요 기준, 프로토타입이면 가장 중요한 정보, 목 데이터면 과제가 의존하는 값). 각 질문에 "없음/모름" 선택지를 주고, 없으면 해당 항목은 `미확인`이다.
- 원 프롬프트가 없으면 게이트 D의 수정은 사용자가 직접 한다(고칠 Phase 2 프롬프트가 없다).
- **무엇을 보지 않았는지** 명시한다.

**게이트 A**: 인테이크 카드(작업·결정·참가자 원자료·유형 카드·도구·맥락 자산·검수자·반복성·먼저 생각 여부·**스코프 밖**(이 작업 중 하네스가 다루지 않을 부분 — 예: AI *제품* 설계, 코드 구현)) 제시 → 승인.

## Phase 1 — 위임 지도 (delegation-mapper)

**질문: 이 작업의 각 단계를 누가 맡는가, 그 근거는.**
규칙은 [`references/delegation-tests.md`](./references/delegation-tests.md), 단계 분해의 출발점은 [`references/task-cards.md`](./references/task-cards.md).

`delegation-mapper` 서브에이전트를 spawn한다(`model: "opus"`).

- 작업을 단계로 쪼갠다. 유형 카드가 있으면 출발점으로 쓰되 사용자의 실제 작업을 따른다.
- 단계마다 **D1 학습 · D2 진실 기준 · D3 데이터 종류(행동 vs 발화) · D4 책임 · D5 반복성 · D6 도메인(니치 여부) · D7 검수 역량**을 적용해 **L1~L4** 레인을 정한다. 하나라도 L3/L4 쪽으로 걸리면 그 레인이 기본값(D5·D7은 레인을 올리지 않는다).
- L3·L4에는 **"위임하면 잃는 것"**을 반드시 적는다.
- "AI로 이 단계를 건너뛰자"는 요청은 **압축**(허용)과 **생략**(조건 표기)으로 구분한다(E7).
- 모르는 테스트 결과는 `미확인` — 추측으로 채우지 않는다.

**산출물 규약**
- 판정 표 + 단계별 1줄 근거(E번호). 점수·순위를 만들지 않는다.
- L4 단계에는 **대안 경로**를 붙인다(예: 합성 사용자로 컨셉 검증 → 합성 응답으로 인터뷰 가이드를 파일럿하고, 계획된 실제 인터뷰에 컨셉 블록을 넣는다). 표본 수는 사용자의 계획값을 쓴다.

- 표를 처음 보여 줄 때는 **단계 · 레인 · 한 줄 근거 · 잃는 것** 네 칸만 보이고, D1~D7 칸은 사용자가 요청하면 펼친다.

**게이트 B**: 판정 표 제시 → ("이거 AI로 해도 돼?"형 질문이면 여기서 답이 나온다 — **"지도만 받고 끝내기"** 선택지를 준다. 고르면 Phase 2·3을 건너뛰고 Phase 4를 축약판(알고 넘어간 위험·데이터 보호 체크포인트·검수자 미정 목록)으로 돌린다) → **답에 따라 레인이 바뀌는 미확인만** 레인 영향이 큰 것부터 한 번에 하나씩 묻는다. 세 개를 넘으면 매 질문에 "나머지는 미확인으로 두고 진행" 선택지를 준다(나머지는 Phase 4 메모) → 사용자가 레인을 옮길 수 있다. 옮기면 [delegation-tests.md](./references/delegation-tests.md) '레인 변경 규약'대로 따르고 기록한다(INV-7) → 승인.

## Phase 2 — 맥락·지시 설계 (context-curator)

**질문: AI가 맡는 단계(L1·L2)에 무엇을 어떻게 시킬 것인가.**
규칙은 [`references/care-prompting.md`](./references/care-prompting.md).

`context-curator` 서브에이전트를 spawn한다(`model: "opus"`).

- **다음 묶음만** 만든다 — 아직 내려지지 않은 L3 결정(예: 방법 결정)에 기대지 않는 L1·L2 단계들이다. 그 뒤 단계는 레인·점검표 ID·출처 라벨만 Phase 4로 넘기고, 그 결정이 내려진 뒤 다시 Phase 2를 돌린다. 사용자가 묶음을 바꿀 수 있다.
- 그 단계마다 **CARE 프롬프트**(Context·Ask·Rules·Examples)를 만든다. 결과물 전체를 한 번에 시키지 않고 단계로 쪼갠다(E9). 생성 N개 → 기준으로 M개 → 순위·이유.
- R 칸에 그 작업의 **방법론 규칙 묶음**(사용성 과제·스크리너·설문·문안·프로토타이핑·목 데이터·코딩)을 붙인다. 해당하는 묶음만.
- 맥락에 들어갈 사용자 정보는 **입력에 있는 것만** 쓴다. 없으면 `[확인 필요]`(INV-5). **참가자 원 발언·개인정보는 지시문에 넣지 않고** `<정제된 자료를 여기 붙임>` 자리표시자를 둔다(INV-8).
- D5가 '반복'인 경우에만 **UX 맥락 팩**을 제안한다. 효과는 가설이라고 함께 적는다(E23·X6).
- 각 프롬프트에 **실행 위치**를 적는다 — 사용자의 도구(이미지·프로토타입·리서치 플랫폼은 여기) 또는 하네스 새 컨텍스트 실행(텍스트 산출물만).
- 프롬프트가 의존하는 **사람이 정할 값**(예: 페이지에서 가장 중요한 정보, 테스트 과제가 의존하는 값, 설문 목표 응답 시간과 문항당 소요 기준, 인터뷰 세션 길이와 질문당 기준)을 `[확인 필요]`로 뽑는다 — Phase 3 점검의 기준값이 된다.
- L1·L2 단계가 하나도 없으면 Phase 2·3을 건너뛴다고 알리고 Phase 4로 간다.

**게이트 C**: 지시서 제시 → `[확인 필요]`를 **한 번에 하나씩** 묻는다(각 질문에 "비워 두고 진행" 선택지, 세 개를 넘으면 "나머지 전부 비워 두고 진행" 선택지) → **지금 초안을 볼 단계**를 사용자가 고른다(나머지는 Phase 4에 '실행 시 쓸 점검표 ID'로 넘기고 최종 보고에 남는다) → 그 단계마다 초안 경로 (a)/(b)를 고른다 → 승인.

## Phase 3 — AI 초안 점검 (output-critic)

**질문: AI 초안에 알려진 실패 패턴이 있는가.**
점검표는 [`references/output-pitfalls.md`](./references/output-pitfalls.md).

**초안을 얻는 두 경로** (게이트 C에서 사용자가 고른다):
- **(a) 사용자가 자기 도구에서 돌린 결과를 붙여넣는다.** 시각 산출물(프로토타입·이미지)은 이 경로뿐이다 — **스크린샷 파일 경로**를 받아 `output-critic`에 넘기고 Read로 열게 한다(이 파일은 저장 대상이 아니다). 텍스트 설명만 있으면 P-PROTO 항목은 `미확인`이다.
- **(b) 하네스가 새 컨텍스트에서 돌린다.** `general-purpose` 서브에이전트를 `model: "opus"`로 spawn하고 **Phase 2 프롬프트 본문만** 준다(하네스 대화·근거 문서·점검표는 주지 않는다). 프롬프트 앞에 한 줄을 붙인다 — "도구·스킬·검색을 쓰지 말고, 아래 요청에 텍스트로만 답하라." 프롬프트가 자족적인지 드러나는 장점이 있지만, **사용자 도구와 모델·도구·주변 컨텍스트가 같지 않다**(서브에이전트는 프로젝트 지침 등을 볼 수 있다) — 그래서 (b) 초안의 점검 결과는 사용자 도구에서의 결과를 대신하지 않고, `output-critic`은 이 사실을 '보지 않은 것'에 적는다. 텍스트 산출물에만 쓰고, **참가자 원자료가 필요한 단계(요약·코딩·PII 정제 등)에는 INV-8 확인이 끝났다고 사용자가 말하기 전에는 쓰지 않는다.** 이 호출에 `agents/` 정의 파일을 두지 않는 것은 의도다 — 정의 파일이 있으면 하네스 규칙이 초안에 새어 들어가 실제 도구 조건과 달라진다.

그다음 `output-critic` 서브에이전트를 spawn한다(`model: "opus"`). **초안을 만든 쪽과 점검하는 쪽을 분리한다** — 같은 에이전트가 자기 초안을 점검하지 않는다.

- 해당 점검표 항목만 적용하고(카드가 없으면 P-COMMON + 사용자가 지정한 항목만), 항목마다 통과/미통과/해당없음/`미확인` + 위치 + 고치는 방법을 적는다. 기준값이 없거나 원자료·시각 산출물을 못 봐서 판정할 수 없으면 `미확인`이다 — '해당없음'으로 처리하지 않는다.
- 원자료와 대조해야 하는 항목(P-SUMMARY·P-CODING·P-PII·P-INSIGHT·P-ARTIFACT)은 **사용자가 정제된 표본을 줬을 때만** 판정한다. P-PII의 '연구 내용 오삭제'는 정제 전 원본이 있어야 보이므로 하네스는 항상 `미확인`으로 두고 사람 표본 대조로 넘긴다.
- 미통과가 레인 판단에 걸리면(예: AI 해석에 맥락 질문이 빠짐) 레인을 바꾸지 않고 **'L3 권고(사용자 결정)'**로 게이트 D에 올린다(INV-7).
- **P-COMMON-1 지어낸 사실**과 **P-COMMON-2 사람이 열어야 할 출처 목록**은 모든 초안에 적용한다.
- Phase 0에서 '먼저 생각 한 줄'을 남겼으면 초안과 나란히 놓고 차이를 적는다(어느 쪽이 맞다고 판정하지 않는다).
- **이 점검이 보지 않은 것**을 반드시 열거한다(INV-3).

**게이트 D**: 점검 결과 → 사용자가 고칠 항목과 'L3 권고'의 수용 여부를 고른다(유지하면 '알고 넘어간 위험'에 기록). 고치기로 한 것은 `context-curator`를 고칠 점과 함께 다시 spawn해(`model: "opus"`) 프롬프트를 고친 뒤 다시 돌리거나, 사용자가 직접 고친다. 반복 횟수는 사용자가 정한다 — 하네스가 "충분하다"고 판정하지 않는다 → 승인.

## Phase 4 — 사람 체크포인트·인계 (checkpoint-planner)

규칙은 [`references/human-checkpoints.md`](./references/human-checkpoints.md).

`checkpoint-planner` 서브에이전트를 spawn한다(`model: "opus"`).

- **L3 단계마다 담당·시점·남길 것·팀 학습 장치**를 배정한다. 주어 없는 "사람이 검토"를 쓰지 않는다.
- **L2 산출물마다 검증 체크포인트**를 붙인다 — 설문은 실제 사람 파일럿, 과제·스크리너는 지정된 검수자 검토, 출처는 사람이 직접 열기, 분석은 원자료 표본 대조. 하네스는 체크포인트를 항상 올리지만, 사용자가 생략하기로 하면 따르고 '알고 넘어간 위험'에 기록한다(INV-7).
- `L2 · 검수자 미정`과 `[담당 미정]`을 모은다 — 게이트 E에서 해소한다.
- 모든 산출물 블록에 **출처 라벨**(INV-2).
- 참가자 데이터가 AI로 들어가면 **데이터 보호 체크포인트**(INV-8).
- 레인 변경 기록과 생략한 단계를 **'알고 넘어간 위험'**으로 옮긴다.
- I-WORKSHOP·T-TOOL·SD-SERVICE면 해당 진행안·검토안을 붙인다.
- D5가 '반복'인 단계에만 재사용 자산(프롬프트 라이브러리 항목·맥락 팩)을 제안한다.

**게이트 E**: 최종 작업 계획 제시 → `검수자 미정`·`[담당 미정]`을 한 번에 하나씩 묻는다(지정 / `검수 생략` / 미정 유지 — `검수 생략`은 레인 변경 규약대로 라벨을 바꾸고 기록) → 저장 여부(opt-in, 경로는 사용자가 지정, 참가자 원 데이터와 발언 인용은 제외) → 종료.

## 종료 요약

한 줄로 남긴다 — **단계 수(L1/L2/L3/L4 각각) · 사용자가 옮긴 레인 수 · 점검 미통과 항목 수와 그중 고친 수 · `미확인` 항목 수 · 검수자 미정 수(그중 해소 수) · 사람에게 배정한 확인 수.**
커밋하지 않는다.

## 이 하네스가 주장하는 것

두 가지뿐이고, 둘째는 실제로 한 만큼만 적는다.
1. **각 단계를 누가 맡을지와 왜 그런지를 근거와 함께 적었다.**
2. **점검한 초안 n개에서 알려진 실패 패턴을 확인했다. 점검하지 않은 L1·L2 단계 n개, 담당이 정해지지 않은 확인 n건이 남았다.** (Phase 3를 건너뛰었거나 '미정 유지'가 있으면 그 숫자가 그대로 드러난다.)

리서치·디자인의 품질이나 속도가 얼마나 좋아지는지는 주장하지 않는다(INV-6).

## 자기 점검 (매 Phase 종료 시 6문항)

1. 학습 단계(진행·관찰·디브리프·해석·결정)를 AI에게 넘기는 안을 먼저 내지 않았는가? (INV-1)
2. 합성·추정·목 데이터에 출처 라벨을 붙였는가? (INV-2)
3. 입력에 없는 사용자 발견·인용·수치·출처를 만들지 않았는가? (INV-5)
4. 인용 금지 목록(X1~X15)의 주장을 쓰지 않았고, 점수·백분율·등급을 만들지 않았는가? (INV-6)
5. 사용자가 승인한 레인 변경을 조용히 되돌리지 않았는가? (INV-7)
6. 이 Phase가 보지 않은 것을 명시했는가? (INV-3)
