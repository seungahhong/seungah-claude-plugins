# product-spec-harness

기획자(PM)가 요구·문제(또는 **기획안 초안**)로부터 **제품 기획문서(PRD)·사용자 스토리·인수조건**을 7단계 인터랙티브로 작성·검증하는 도메인 무관 멀티 에이전트 하네스 (개발 착수 *전* 단계). 기획안이 주어지면 **생성 전에 원본 기획안의 기획 완성도 점검(DoR)을 먼저 평가**(Phase 1)해 보강점을 PRD·스토리에 반영한다. **PRD(Phase 2)는 계획 → 설계 → 비평 세 서브에이전트를 한 회차로 돌려 그 피드백을 반영한 뒤 사용자가 확정을 선택할 때 기록한다.** 스토리 이후 **인수조건(Phase 5)** 을 조건·행동·결과(Given-When-Then)로 전개해 `acceptance-criteria.md`(최종 산출물)를 만들고 **2차 적대적 검증(Phase 6)** 으로 스토리↔인수조건을 검증한다.

사용자용 개요·사용법은 [README.md](README.md) 참조.

## 7단계 Phase 요약

| Phase | 이름 | 호출 에이전트 | 핵심 산출물 | 게이트 |
|-------|------|---------------|-------------|--------|
| 0 | 요구/문제 정의 (Discovery) | requirements-analyst | 문제 정의 카드 (problem / target_users / goals / constraints / success_metrics) | 기획안 있으면 추출, 없으면 한 번에 1질문 인터뷰 → 승인 |
| 1 | 기획 완성도 점검(DoR) (모드 A·진입질문 필수·생성 전 선행) | dor-evaluator | `# 기획 완성도 점검 결과(DoR Review)` (완성도 게이트 · 좋은 스토리 6가지 기준(INVEST) · 조건·행동·결과(Given-When-Then) 완결성 · 모호성 점검 · 의존성) + **보완할 점 점검표(보강 체크리스트)** — **채팅 제시, 즉시 저장 안 함** | 모드 A에서 진입질문 **필수 제시**(생략 금지)·평가 실행만 예/아니오, 결과를 PRD/스토리에 반영 |
| 2 | 기획문서(PRD) 작성·확정 (**계획 → 설계 → 비평 루프**) | prd-planner → prd-designer → prd-critic | PRD (배경·문제 / 목표·성공지표 / 범위 In·Out / 핵심 요구사항(FR·NFR) / 가정·리스크 / 마일스톤) + 비평 보고서 — Phase 1 보강점 반영, 부록 A 루프 이력·부록 B 알려진 제한사항 | **회차당 게이트 1개**(① 확정 / ② 한 번 더 / ③ 지정 항목만) → 확정 시 쓰기 전 미리보기 승인 |
| 3 | 사용자 스토리 도출 | story-writer | 스토리("…로서 …하고 싶다, 왜냐하면 …") + 좋은 스토리 6가지 기준(INVEST) 자가점검 + 요구 커버 표 + `[인수조건 인계]` 메모 — **조건·행동·결과 문장은 쓰지 않음**(Phase 5 단독 소유) | 승인 |
| 4 | **1차** 적대적 검증 (PRD ↔ 스토리) | spec-reviewer | 검증 리포트 (요구↔스토리 추적 매트릭스 / INVEST / 목표↔요구↔스토리 일관성 / 모호·판정불가 색출) — **채팅 제시만**(파일 없음) | 리포트 + 승인 (보완 시 additive-first) |
| 5 | **인수조건 작성** | acceptance-writer | `acceptance-criteria.md`(**최종 산출물**) — 스토리별 조건·행동·결과(Given-When-Then) 시나리오 + 흐름 커버 1줄(정상+경계·에러·빈 상태·권한·상태 전이) + 스토리↔인수조건 추적 표 | 쓰기 전 미리보기 승인 |
| 6 | **2차** 적대적 검증 (스토리 ↔ 인수조건) | spec-reviewer (2차) | 2차 리포트 (스토리↔인수조건 추적 빠짐·고아 / 인수조건 관찰성 / 단일 관심사 / 흐름 커버리지 / 누락 시나리오 마이닝) — **채팅 제시만**(파일 없음) | 리포트 + 승인 |
| 마무리 | 기획 완성도 점검(DoR) 결과 저장 (opt-in) | (오케스트레이터) | Phase 1 평가 결과 → `.claude/_docs/<슬러그>/product-spec-review.md` | **PRD·스토리 생성 후 사용자가 저장을 선택할 때만** 저장 |

매 Phase 종료 시 보고 형식: `[Phase N] {핵심결정} — 다음: {다음}. 진행할까요?`

> **입력 모드** — 시작 시 1회 판별하고 **결과를 채팅에 1줄로 선언**한다(이 라벨이 모든 Phase 전이의 기준). 경계가 모호하면 **모드 A로 안전 디폴트**(모드 미정인 채 PRD 직행 금지). (A) 기획안 입력: 기획안에서 문제 정의를 추출(Phase 0) → 생성 전 원본 기획안의 기획 완성도 점검(DoR)(Phase 1; 모드 A에선 **진입 질문 제시 필수**, 평가 실행만 동의 시) → 보강점 반영해 PRD·스토리 반드시 생성 → 적대적 검증. (B) 인터뷰: 기획안이 없으면 Phase 1을 건너뛴다(0→2는 모드 B 사양상 정상). 생성 산출물 완성도 점검은 **기본으로 제안하지 않고**, 사용자가 명시적으로 요청할 때만 마무리에서 수행·저장 선택.
> **네 번의 점검은 대상·축이 다르다(중복 금지)** — Phase 1은 *사용자가 준 원본 기획안*이 착수 가능한가(생성 전), Phase 2.3은 *이번 회차 PRD 초안 §1~§6*이 스스로 옳은가(확정 전, 스토리 없음 → 스토리·INVEST·커버리지 축 금지), Phase 4(1차)는 *PRD + 스토리 사이*가 맞는가(인수조건 아직 없음 → 완료 판정 축 금지), Phase 6(2차)은 *스토리 + 인수조건 사이*로 완료 판정이 서는가. Phase 4는 Phase 2에서 **사용자에게 제시된 항목**(비평 지적 목록·반영 대장·부록 B)을 스토리 증거 없이 재지적하지 않되, **제시된 적 없는 §1~§6 문장(절단·미점검분)은 정당한 대상이다**.
> **저장 정책** — 산출물은 `.claude/_docs/<기획서 슬러그>/`에 모으고 **파일은 정확히 4개다** — `PRD.md`·`user-stories.md`·`acceptance-criteria.md`(미리보기 승인 후 저장) + `product-spec-review.md`(마무리에서 저장 선택 시). **1차·2차 적대적 검증 리포트는 채팅 제시만 하고 파일로 만들지 않는다.**

## Conventions

- **승인 게이트**: 매 Phase 종료 시 핵심 산출물 + 1줄 보고를 제시하고, 파일을 쓰기 전 미리보기로 사용자 승인을 받은 뒤에만 진행한다.
- **산출 파일은 정확히 4개**: `.claude/_docs/<기획서 슬러그>/`에 `PRD.md`·`user-stories.md`·`acceptance-criteria.md`(미리보기 승인 시 저장) + `product-spec-review.md`(마무리에서 저장 선택 시). **이 넷 외의 파일(검증 리포트·중간 산출물·문제 정의 카드 등)은 만들지 않는다.**
- **관찰형 인수조건**: 인수조건(`acceptance-criteria.md`)과 success_metrics는 제3자가 관찰로 판정 가능해야 한다. 인수조건은 조건·행동·결과(Given/When/Then)로 작성한다. "좋다/만족" 같은 판정불가 문장 금지.
- **완전성·추적**: 모든 PRD 핵심 요구가 ≥1개 스토리로 커버되는지 요구↔스토리 매트릭스로 추적한다.
- **적대적 검증(2회)**: Phase 4(1차 PRD↔스토리)·Phase 6(2차 스토리↔인수조건) 모두 칭찬형 금지. **리포트는 채팅으로만 제시하고 파일로 만들지 않는다** — 결함은 additive-first로 해당 산출물에 흡수한다. **1차는 인수조건 축을 다루지 않는다**(그 시점엔 대상이 없다).
- **기획 완성도 점검(DoR) 내재화**: Phase 1(생성 전 선행)은 원본 기획안을 기획 완성도 점검(DoR) 관점에서 평가해 `# 기획 완성도 점검 결과(DoR Review)` + 보완할 점 점검표(보강 체크리스트)를 **채팅으로 제시**하고 그 보강점을 PRD·스토리 생성에 반영한다. 방법론은 외부 플러그인을 참조하지 않고 `references/dor-review-rubric.md`에 **내재화**한다(외부 의존 없음 — 이 플러그인만 설치해도 독립 동작). 모드 A에선 **진입 질문 제시가 필수**(생략·자동 스킵 금지)이고 평가 *실행*만 사용자 동의(예/아니오) 조건이다(모호한 응답은 '예'로 해석). 모드 판별이 모호하면 A로 안전 디폴트하고 모드를 사용자에게 1줄로 선언한다. **파일 저장(`product-spec-review.md`)은 PRD·스토리 생성 후 마무리에서 사용자가 저장을 선택할 때만** 수행(평가 시점 즉시 저장 금지). Honesty Guardrail(검증된 등급·출처 수치만, '개선 N%' 약속 금지)을 따른다.
- **인수조건 단일 원본**: 조건·행동·결과(Given-When-Then) 문장은 `acceptance-criteria.md`에만 존재한다. `user-stories.md`는 스토리(누가·무엇을·왜)·INVEST·커버 요구까지만 담고, 예외 흐름은 `[인수조건 인계]` 메모로 Phase 5에 넘긴다. 두 곳에 두면 한쪽만 고쳐진 채 완료 기준이 두 개가 된다.
- **인수조건 작성 규약**: 1개 = 단일 관심사 1개(서로 다른 관심사·트리거는 시나리오를 쪼갠다) · 스토리마다 정상 + 해당 예외 흐름(경계·에러·빈 상태·권한·상태 전이)을 덮고 해당 없으면 `해당 없음 — (사유)`로 **누락과 의도된 제외를 구분** · Then은 관찰 가능 · `AC-<스토리번호>.<일련번호>` ID와 출처 US ID 연결 · **예외 흐름 정책·수치를 발명하지 않고 `[확인필요]`로 되돌린다**(빈 곳 지적은 하네스 일, 정책 결정은 기획자 일).
- **PRD 확정 루프(계획 → 설계 → 비평)**: Phase 2는 PRD를 한 번에 쓰지 않고 세 서브에이전트를 한 회차로 돌린 뒤 사용자가 확정을 선택할 때 기록한다. **섹션 소유권 분리**(계획 §1~§3 / 설계 §4~§6 / 비평 쓰기 권한 0), **본문 단일 소유권**(오케스트레이터가 보유, 에이전트는 섹션 패치만 반환), **게이트 총량 불변식**(회차당 승인 게이트 정확히 1개 + 확인 질문 최대 1개), **루프 중 파일 생성 금지**(기록은 확정 후 미리보기 승인 1회), **차단 사유 닫힌 4종**(Out 공백·판정불가 지표·요구 ID 누락중복/미전개·출처 없는 수치), **처리분류 A/B/C**(B를 A로 처리하면 발명), **정체 가드 G1~G3**. 방법론은 `references/prd-design-checklist.md`·`references/prd-critique-lenses.md`에 **내재화**한다(외부 의존 없음).
- **비평에 거부권 없음**: 차단 지적이 남아 있어도 사용자가 확정을 선택하면 즉시 확정하고 잔존은 부록 B `[미해소 지적]`으로 기록한다. 위험은 알리되 감수는 사용자가 정한다(승인된 진행의 조용한 보류·재확인 반복 금지).
- **효과를 약속하지 않음**: 루프가 산출물 품질을 얼마나 높이는지 이 하네스는 측정하지 않는다. 주장 가능한 것은 *지적과 그 처리 결과가 문서에 남는다*뿐이고, 루프 이력은 변화의 기록이지 개선의 증거가 아니다. 점수·백분율·성숙도 등급을 산출하지 않는다(`n건` 카운트만). 예외는 Phase 1의 좋은 스토리 6가지 기준(INVEST) 점수표와 그 총점에서 나오는 3단 착수 판정(착수가능/보완 후/보류) 하나뿐으로, 입력 기획안의 착수 준비도 신호이지 산출물 품질 등급이 아니다. 여기서 금지하는 것은 **하네스가 산출물에 매기는 평가 점수·등급**이며, **PRD 본문의 성공지표 수치(예: 전환율 42% → 60%)는 해당하지 않는다** — 관찰형 지표는 이 하네스의 1급 요건이다.
- **기획 설계 ≠ 기술 설계**: Phase 2.2의 '설계'는 요구의 구조화(여정·상황·예외 제품 규칙·정책·권한·정보 항목·의존성)이며, API·데이터 모델·컴포넌트 트리·상태관리·캐싱 등은 산출하지 않는다. 스토리 문장(Phase 3 소유)·인수조건 문장(Phase 5 소유)도 쓰지 않는다.
- **기획안 입력 모드**: 기획안(초안)을 인자/대화로 주면 Phase 0에서 카드를 추출하고 PRD·스토리를 **반드시 생성**한다(생성 생략 금지).
- **additive-first(기존 것 보존·추가 우선)**: 합의된 PRD/스토리를 보완할 때 기존 항목을 뒤엎기 전에 비파괴 추가·완화를 먼저 제안한다.
- **인터뷰성**: 한 번에 한 질문. 어려운 용어(좋은 스토리 6가지 기준(INVEST)·조건·행동·결과(Gherkin)·기획 완성도 점검(DoR))는 쉬운 말 1줄 정의를 곁들인다.
- **경계**: 이 하네스는 '기획자의 제품 기획(도메인 무관, 개발 전)'이다. 프론트엔드 화면 구현·기술 설계용 PRD·구현 요구사항·코드 작성, 코드/하네스/커밋 작업, 그리고 *이미 완성된* 상류 산출물을 핸드오프 게이트로 검수만 하는 작업은 범위 밖이다.
- **독립성**: 이 플러그인은 단독 설치로 동작하며, 다른 마켓플레이스 플러그인을 참조·의존하지 않는다(기획 완성도 점검(DoR) 방법론은 `references/dor-review-rubric.md`에 내재화).
- 8개 에이전트 협업 하네스이므로 오케스트레이터 SKILL.md의 모든 Agent 호출에 `model: "opus"`를 명시한다.
