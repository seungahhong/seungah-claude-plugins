# product-spec-harness

기획자(PM)가 요구·문제(또는 **기획안 초안**)로부터 **제품 기획문서(PRD)·사용자 스토리·인수조건**을 단계별로 작성·검증하도록 돕는 도메인 무관 인터랙티브 멀티 에이전트 하네스입니다. 개발 착수 *전* 단계의 제품 기획 산출물에 특화합니다.

매 Phase 산출물을 보여주고 사용자 승인을 받은 뒤에만 다음 단계로 넘어갑니다. 한 번에 한 가지씩 인터뷰하듯 질문하며, 어려운 용어에는 쉬운 말 1줄 정의를 곁들입니다.

## 입력 모드

- **기획안 입력 모드** — 기획안(초안)을 인자/대화로 주면, 그 내용에서 문제 정의를 **추출**합니다. 이어 **생성 *전*에 원본 기획안의 기획 완성도 점검(DoR)을 먼저 평가**(동의 시)해 `# 기획 완성도 점검 결과(DoR Review)` + 보완할 점 점검표(보강 체크리스트)로 무엇을 고치면 좋을지 알려주고, 그 보강점을 반영해 PRD·사용자 스토리를 **반드시 생성**합니다(초안을 줬다고 생성을 건너뛰지 않습니다). 마지막에 산출물을 적대적 검증합니다. **평가 결과 파일(`product-spec-review.md`)은 PRD·스토리를 만든 뒤 저장할지 물어, 저장을 선택한 경우에만** `.claude/_docs/<기획서 슬러그>/`에 기록합니다.
- **대화형 인터뷰 모드** — 기획안이 없으면 한 번에 한 질문으로 문제를 정의한 뒤 PRD·스토리를 만듭니다(입력 기획안이 없어 완성도 점검은 건너뛰고, 필요 시 마무리에서 생성 산출물 대상으로 선택 적용).

## 설치

이 저장소를 Claude Code 플러그인 마켓플레이스로 추가한 뒤 `product-spec-harness` 플러그인을 활성화하면, `product-spec` 스킬이 자동으로 트리거되거나 직접 호출할 수 있습니다.

## 스킬

| 스킬 | 역할 |
|------|------|
| `product-spec` | 오케스트레이터(진입점). 문제 정의 → 기획 완성도 점검(DoR) → **PRD 작성·확정(계획 → 설계 → 비평 루프)** → 사용자 스토리 → 1차 적대적 검증 → **인수조건 작성** → 2차 적대적 검증의 7단계를 인터랙티브로 진행하며, 각 단계에서 전용 에이전트(requirements-analyst / dor-evaluator / **prd-planner · prd-designer · prd-critic** / story-writer / **acceptance-writer** / spec-reviewer)를 호출한다. |

## 언제 쓰나 / 언제 다른 도구를 쓰나

**이 하네스를 쓰세요**
- 새 제품·기능의 문제와 요구를 정리해 **기획문서(PRD)**를 만들고 싶을 때
- **기획안(초안)을 주고** 거기서 PRD·사용자 스토리를 뽑고 싶을 때
- PRD에서 **사용자 스토리**를 도출하고, 다시 **인수조건(조건·행동·결과 Given/When/Then)** 으로 전개해 "다 됐다"의 판정 기준까지 만들고 싶을 때
- 기획 산출물의 누락·모호·비일관을 **적대적으로 검증**하고 싶을 때
- PRD를 **계획 → 설계 → 비평 루프로 다듬어 확정**하고 싶을 때 (초안을 그대로 받는 게 아니라, 비평 지적을 반영한 뒤 확정)
- 생성 전에 **원본 기획안의 기획 완성도 점검(DoR)을 평가**해 무엇을 보강할지 점검표로 받고, 그 피드백을 PRD·스토리에 반영하고 싶을 때
- 개발 착수 *전*, 도메인 무관한 제품 기획 단계일 때

**이 하네스가 다루지 않는 것 (범위 밖)**
- 프론트엔드 화면 구현·컴포넌트·기술 설계용 PRD·구현 요구사항·코드 작성
- 코드 리뷰·커밋 메시지·PR 리뷰
- 하네스(에이전트팀·스킬·오케스트레이터) 자체를 생성·진단·개선하는 작업
- **이미 완성된** PRD/유저스토리/디자인/계약/인수조건을 (작성이 아니라) 핸드오프 시점에 독립 게이트로 검수만 하는 작업

이 하네스는 개발 착수 *전* 제품 기획문서·사용자 스토리 **작성**과 입력 기획안의 **기획 완성도 점검(DoR)**에 한정합니다(위 작업은 수행하지 않음). 트리거 충돌을 막기 위해 이 경계는 plugin.json description과 `evals/trigger-eval.json`에 명시되어 있습니다.

> **독립 플러그인**: 기획 완성도 점검(DoR)과 PRD 확정 루프(계획·설계·비평)는 외부 플러그인에 의존하지 않습니다. 방법론(기획 완성도 게이트(DoR 게이트)·좋은 스토리 6가지 기준 점수표(INVEST 스코어카드)·조건·행동·결과(Given-When-Then) 완결성·모호성 점검·의존성 참조 + Honesty Guardrail·근거)을 이 플러그인 안(`skills/product-spec/references/dor-review-rubric.md`)에 **내재화**했고, 확정 루프의 기획 설계 점검표(D1~D12)와 비평 렌즈(C-1~C-7)도 같은 폴더(`prd-design-checklist.md`·`prd-critique-lenses.md`)에 내재화해, 이 플러그인만 설치해도 단독으로 동작합니다. 여기서는 *작성 흐름의 생성 전 선행 평가*로 입력 기획안을 평가해 PRD·스토리에 반영합니다.

## 진행 방식 (인터랙티브 7단계)

| Phase | 단계 | 핵심 산출물 |
|-------|------|-------------|
| 0 | 요구/문제 정의 (Discovery) | 문제 정의 카드 (problem / target_users / goals / constraints / success_metrics) — 기획안 있으면 추출 |
| 1 | 기획 완성도 점검(DoR) (생성 전·모드 A 진입질문 필수) | 원본 기획안의 `# 기획 완성도 점검 결과(DoR Review)` (완성도 게이트 · 좋은 스토리 6가지 기준(INVEST) · 조건·행동·결과 완결성 · 모호성 점검 · 의존성) + **보완할 점 점검표(보강 체크리스트)** — **채팅 제시**, 보강점을 이후 PRD·스토리에 반영 |
| 2 | 기획문서(PRD) 작성·확정 (**계획 → 설계 → 비평 루프**) | 배경·문제 / 목표·성공지표 / 범위(In·Out) / 핵심 요구사항(FR·NFR) / 가정·리스크 / 마일스톤 (Phase 1 보강점 반영) + 비평 보고서 + 부록 A 루프 이력·부록 B 알려진 제한사항 |
| 3 | 사용자 스토리 도출 | "…로서 …하고 싶다, 왜냐하면 …" 스토리 + INVEST 자가점검 + 요구 커버 표 (조건·행동·결과 문장은 Phase 5 소유) |
| 4 | **1차** 적대적 검증 (PRD ↔ 스토리) | 요구↔스토리 추적 매트릭스 / INVEST 통과 / 일관성 / 모호·판정불가 색출 (**채팅 제시만** — 결함은 PRD·스토리에 흡수) |
| 5 | **인수조건 작성** | `acceptance-criteria.md`(**최종 산출물**) — 스토리별 조건·행동·결과 시나리오 + 흐름 커버(정상·경계·에러·빈 상태·권한·상태 전이) + 스토리↔인수조건 추적 표 |
| 6 | **2차** 적대적 검증 (스토리 ↔ 인수조건) | 추적 빠짐·고아 / 인수조건 관찰성 / 단일 관심사 / 흐름 커버리지 / 누락 시나리오 마이닝 (**채팅 제시만** — 결함은 인수조건에 흡수) |
| 마무리 | 기획 완성도 점검(DoR) 결과 저장 (opt-in) | Phase 1 평가 결과 → `product-spec-review.md` (**PRD·스토리 생성 후 사용자가 저장을 선택할 때만**) |

각 Phase 종료 시 `[Phase N] {핵심결정} — 다음: {다음}. 진행할까요?` 형식으로 1줄 보고하고, 파일을 쓰기 전 미리보기로 승인을 받습니다. 시작 시 입력 모드(A 기획안 / B 인터뷰)를 판별해 채팅에 선언하며, 경계가 모호하면 모드 A로 둡니다. **모드 A에서는 Phase 1 진입 질문("기획 완성도 점검(DoR)을 먼저 할까요?")을 반드시 제시**하고(생략 없이), 평가 *실행* 여부만 사용자 동의(예/아니오)로 정합니다 — 동의해야 평가가 돌아가고, 그 결과의 파일 저장도 PRD·스토리 생성 후 별도 동의가 있을 때만 합니다. (모드 B는 입력 기획안이 없어 Phase 1을 건너뜁니다.)

## 사용 예시 (기획안 입력 모드)

거친 기획 초안을 인자로 주고 PRD·사용자 스토리를 만드는 전형적인 흐름입니다. **기획 완성도 점검(DoR)(Phase 1)이 입력의 빈틈을 생성 *전*에 먼저 잡아, 그 보강점이 PRD·스토리에 반영되는 점**에 주목하세요. (아래는 진행 예시를 요약한 것입니다.)

**입력** — 초안을 붙여넣어 호출:

> "신규 사용자가 이메일로 가입하게 해줘. 가입이 **빠르고 쉬웠으면** 좋겠고, 가입 후 바로 서비스를 둘러볼 수 있게. 이걸로 PRD랑 사용자 스토리 만들어줘."

**Phase 0 — 요구/문제 정의 (초안에서 카드 추출)**

```
## 문제 정의 카드
- problem: 가입 절차가 번거로워 신규 사용자가 첫 경험 전에 이탈
- target_users: 결제 전 제품을 둘러보려는 신규 방문자
- goals: (비즈니스) 가입 전환율 향상 / (사용자) 부담 없는 빠른 가입
- constraints: (미정 — 확인 필요)
- success_metrics: (미정 — 관찰형으로 확인 필요)
❓ 성공을 어떻게 측정할까요? 예: "가입 시작→완료 전환율"
```
`[입력 모드] A(기획안 입력) — 다음: 카드 추출 → 기획 완성도 점검(DoR)(Phase 1)`
`[Phase 0] 문제·대상·목표·성공지표 합의 — 다음: 기획 완성도 점검(DoR)(Phase 1). 진행할까요?`

**Phase 1 — 기획 완성도 점검(DoR) ("예" 선택 · 채팅 제시, 이 시점엔 저장 안 함 — 저장은 마무리 opt-in)**

원본 초안을 기획 완성도 점검(DoR)으로 진단해 무엇이 빠졌는지 점검표로 공유합니다(이 보강점을 다음 단계에서 채웁니다). 충족 항목은 `[O]`, 미충족 항목은 `[ ]` 아래에 "어떻게 보강할지" 예시를 붙입니다.

```
# 기획 완성도 점검 결과(DoR Review)
## 1. 기획 완성도 게이트(DoR 게이트)
| 항목 | 결과 | 근거(인용) |
| 인수조건 측정 가능 | ❌ | "빠르고 쉽게" → 제3자 판정 불가 |
| 예외·에러·권한 흐름  | ❌ | 중복 이메일·형식 오류·네트워크 실패 흐름 없음 |
## 8. 보완할 점 점검표(보강 체크리스트)
- [O] 표준 포맷(누가·무엇을·왜)을 갖췄다
- [ ] 정상 흐름 외 경계(edge)·에러·빈 화면·권한 흐름이 기술됐다
  ↳ 이렇게 보강: 정상 가입만 적힘 → "이미 가입된 이메일 / 형식 오류 / 네트워크 실패" 시 각각 무엇을 보여줄지 1줄씩 추가
- [ ] 약한 단어("빠르게/쉽게")에 관찰형 기준이 달렸다
  ↳ 이렇게 보강: "빠르고 쉽게" → 관찰 가능한 기준으로 환산 필요 (입력 단계 수·전환율 등 **임계값은 기획이 지정**)
- [ ] 관찰형 성공지표가 있다
  ↳ 이렇게 보강: 지표 없음 → "가입 시작→완료 전환율 [기준선] → [목표값] (측정 시점·퍼널 기준 지정 필요)" — **수치는 기획이 정한다**(평가가 지어내지 않는다)
```
`[Phase 1] 기획 완성도 점검(DoR)(보완 후 / 보강 3건, 채팅 제시) — 다음: PRD 계획(Phase 2.1) → 설계 → 비평(보강점 반영). 진행할까요?`

**Phase 2 — PRD 작성·확정 (계획 → 설계 → 비평 루프 · Phase 1 보강점 반영)**

PRD를 한 번에 쓰지 않습니다. **계획**이 방향(§1~§3)을, **설계**가 요구(§4~§6)를 맡고, **비평**이 확정 전에 읽기 전용으로 약점을 캡니다. 세 결과를 보고 **확정할지 한 번 더 다듬을지는 사용자가 고릅니다.**

*① 계획 — 배경·목표·범위(In/Out)*

```
## 2. 목표·성공지표(관찰형)
- 가입 시작→완료 전환율 [확인필요] 기준선·목표값·측정 시점   ← "빠르게/쉽게"를 관찰형으로 환산하되 값은 발명하지 않음
## 3. 범위
- In: 이메일+비밀번호 가입, 가입 직후 온보딩 진입
- Out: 소셜 로그인(차기), 비밀번호 없는 매직링크          ← In과 헷갈릴 인접 항목을 박아 둠
```

*② 설계 — 요구사항·가정·리스크·마일스톤*

```
## 4. 핵심 요구사항
- FR-1 이메일+비밀번호로 가입할 수 있다                    ← §3 In-1
- FR-2 이미 가입된 이메일·형식 오류 시 안내한다            ← 완성도 점검 에러 흐름 반영
- NFR-1 가입 응답 지연 임계값                              [확인필요] 값을 얼마로 볼까요? (발명하지 않음)
## 5. 가정·리스크
- 가정: 이메일 인증 발송 채널이 이미 있다 — 깨지면 영향: FR-1
```

*③ 비평 — 확정 전 지적 (문서를 직접 고치지 않습니다)*

```
[차단][C-3] §2 — "전환율 [확인필요] 기준선·목표값" — B — 관찰형 판정에 필요한 값이 비어 있음. 사용자만 답할 수 있으므로 질문 큐로(회차를 더 돌려도 해소되지 않음)
[수정권고][C-5] §4 — "형식 오류 시 안내한다" — A — 네트워크 실패·중복 요청 시의 제품 규칙이 없음. FR-5로 추가 제안
차단 1건 / 수정권고 1건 / 참고 0건 — 후보: 확정(차단이 전부 B분류라 회차로 해소 불가)
```

`[Phase 2 · 1회차] PRD 초안(§1~§6) — 지적 {차단 1건 / 수정권고 1건 / 참고 0건}`
`계획 변경 요청 0건 · 확인 필요 1건 · 미전개 섹션 없음 · 미적용 렌즈 0개`
`최우선 권고: 전환율 기준선·목표값을 정해야 §2가 관찰형이 된다`
`권장: (1) — 남은 차단이 전부 B분류(사용자만 아는 값)라 회차를 더 돌려도 해소되지 않는다`
`선택 비용: (2) = 계획·설계·비평 3개 재호출 / (3) = 지정 항목 + 인접 섹션 소유 단계만`
`(1) 이대로 확정  (2) 한 번 더 다듬기  (3) 특정 항목만 지정해 수정`

→ "(2) 한 번 더"를 고르면 채택된 지적을 반영해 한 회차를 더 돌고, "(1)"을 고르면 잔존 지적을 **부록 B(확정 시점 미해소)** 에 남긴 채 즉시 확정합니다(비평에 거부권은 없습니다). 위 예시처럼 **차단이 남아도 그것이 '사용자만 아는 값' 때문이면 회차 대신 질문으로 해소**하거나, 모르는 채로 확정하고 그 사실을 부록 B에 남깁니다. 확정 후 전체 미리보기 승인을 거쳐 `PRD.md`에 기록합니다.

`[Phase 2] PRD 확정(범위 In/Out·핵심 요구 FR-1…FR-n·루프 1회차·부록 B 1건: 미해소 지적 1·계획 변경 요청 미반영 0·미반영 점검표 0·미점검 0·범위 밖 0) — 다음: 사용자 스토리 도출. 진행할까요?`

**Phase 3 — 사용자 스토리 (인수조건 문장 없음 · 인계 메모만)**

```
### US-1 (covers FR-1, FR-2)
신규 가입자로서 이메일로 가입하고 싶다, 왜냐하면 결제 전 부담 없이 둘러보고 싶기 때문이다.
- INVEST 자가점검: I○ N○ V○ E○ S○ T○(관찰 가능한 행동이라 인수조건으로 전개 가능)
- [인수조건 인계]: 중복 이메일 · 형식 오류 · 네트워크 실패 흐름 필요   ← 완성도 점검 반영
```
`[Phase 3] 스토리 2개 + 요구 커버 표 + 인계 메모 — 다음: 1차 적대적 검증(Phase 4). 진행할까요?`

→ 조건·행동·결과 문장은 여기 쓰지 않습니다. 예외 흐름은 **후보 메모로만** 남겨 Phase 5로 넘깁니다(단일 원본).

**Phase 4 — 1차 적대적 검증 (PRD ↔ 스토리)**

```
요구↔스토리 추적: FR-1 ✅US-1 / FR-2 ✅US-1 / NFR-1 ❌(미커버)
결함: NFR-1(응답 임계값)을 커버하는 스토리 없음 → additive로 US-3 추가 제안
```
`[Phase 4] 1차 적대적 검증 완료(결함 1건 / 전체 요구 3건 중 미커버 1건 / 재지적 제외한 수용 항목 0건)`
`— 이 단계는 완료 판정 기준(인수조건)을 검증하지 않았습니다(Phase 6 소유). 다음: 인수조건 작성(Phase 5). 진행할까요?`

→ 승인하면 `story-writer`를 다시 불러 **US-3을 additive로 추가**하고 미리보기 승인 후 `user-stories.md`를 갱신합니다. 리포트 자체는 파일로 남기지 않습니다.

**Phase 5 — 인수조건 작성 (최종 산출물)**

```
## US-1 — 이메일로 가입  (출처 요구: FR-1, FR-2)

### AC-1.1 유효한 이메일로 가입 성공 (정상)
  Given 로그인하지 않은 방문자가 가입 화면에 있고
  When  미사용 이메일과 8자 이상 비밀번호를 입력하고 '가입'을 누르면
  Then  온보딩 화면으로 이동하고, 해당 이메일로 인증 메일이 1통 발송된다.

### AC-1.2 이미 가입된 이메일 (에러)
  Given 이미 가입된 이메일이 존재하고
  When  같은 이메일로 가입을 시도하면
  Then  '이미 가입된 이메일입니다' 메시지가 표시되고, 가입은 진행되지 않으며, 입력값은 초기화되지 않는다.

(흐름 커버: 정상 · 에러(중복 이메일·네트워크 실패) — 경계/빈 상태/권한/상태 전이 해당 없음 — 가입 전 화면이라 목록·세션·경계값이 없음)
```
`[확인필요] 네트워크 실패 시 재시도 버튼을 보여줄까요, 자동 재시도할까요? — AC-1.3의 Then에 필요`
`[Phase 5] 인수조건 5건 / 스토리 3개 커버(빠짐 0건·고아 0건) · [확인필요]만으로 덮인 스토리 0건 — 다음: 2차 적대적 검증. 진행할까요?`

→ 위 `빠짐·고아` 건수는 **작성자 자기보고**입니다. 독립 판정은 Phase 6이 합니다.

**Phase 6 — 2차 적대적 검증 (스토리 ↔ 인수조건)**

```
스토리↔인수조건 추적: US-1 ✅AC-1.1~1.3 / US-2 ✅AC-2.1 / US-3 ❌(미커버)
결함: US-3(응답 임계값)의 인수조건이 [확인필요]뿐 → 스토리 재판정(INVEST Testable) 대상
누락 마이닝: (경계) 중복 클릭 시 가입이 2번 처리되는지 미정의 → [확인필요]
```
`[Phase 6] 2차 적대적 검증 완료(결함 2건 / 스토리 3개 중 인수조건 미커버 1건) — 마무리할까요?`

**마무리 — 기획 완성도 점검(DoR) 결과 저장 (PRD·스토리 생성 후 · opt-in)**

`[저장 확인] Phase 1의 기획 완성도 점검(DoR) 결과(# 기획 완성도 점검 결과(DoR Review) + 보완할 점 점검표)를 product-spec-review.md로 저장할까요? (예/아니오)`

"예"를 선택한 경우에만 저장합니다. 최종 산출물:

```
.claude/_docs/email-signup/
  PRD.md
  user-stories.md
  acceptance-criteria.md   # 최종 산출물
  product-spec-review.md   # 저장을 선택한 경우에만
```

> **대화형 인터뷰 모드(B)** 는 입력 기획안이 없으므로 Phase 1을 건너뛰고, 한 번에 한 질문으로 카드를 채운 뒤 PRD·스토리를 만듭니다. 마무리에서 요청하시면 *생성된* PRD·스토리를 대상으로 기획 완성도 점검(DoR)·저장을 수행합니다(자동으로 제안하지는 않습니다).

## 산출물

산출물은 `.claude/_docs/<기획서 슬러그>/` 폴더(기획서별 폴더)에 모입니다.

- **제품 기획문서(PRD)** — 배경·목표·범위·요구사항·리스크·마일스톤을 담은 한국어 문서 (`PRD.md`)
- **사용자 스토리 세트** — 좋은 스토리 6가지 기준(INVEST) 점검과 요구 커버 표를 포함 (`user-stories.md`). 조건·행동·결과 문장은 여기 두지 않습니다(단일 원본).
- **인수조건(최종 산출물)** — 스토리별 조건·행동·결과(Given-When-Then) 시나리오, 흐름 커버(정상·경계·에러·빈 상태·권한·상태 전이), 스토리↔인수조건 추적 표 (`acceptance-criteria.md`)
- **기획 완성도 점검(DoR) 리포트** — `# 기획 완성도 점검 결과(DoR Review)` + 보완할 점 점검표(`[O]`=충족, `[ ]`+예시=보완 대상). Phase 1 평가를 진행하고 **마무리에서 저장을 선택한 경우에만** `product-spec-review.md`로 저장 (그 전엔 채팅 제시).
- **비평 보고서(Phase 2)** — 확정 *전* PRD 초안에 대한 지적·최우선 권고 3가지. **채팅으로만 제시**하고 파일을 만들지 않으며, 반영 결과는 `PRD.md` 본문과 부록 A(루프 이력)·부록 B(알려진 제한사항)에 남습니다.
> **파일은 위 목록 중 앞의 네 개가 전부입니다**(마지막 항목인 비평 보고서는 파일이 아닙니다). 1차(요구↔스토리)·2차(스토리↔인수조건) 적대적 검증 결과는 **채팅으로만 제시**하고 파일로 남기지 않습니다 — 그 지적은 additive-first로 PRD·스토리·인수조건에 반영됩니다.

## evals

`evals/trigger-eval.json`은 이 하네스가 발동해야 하는 경우(should-trigger)와 발동하면 안 되는 경우(should-not-trigger, 예: 프론트엔드 개발 PRD·코드·커밋)를 정의해 트리거 정확도를 점검합니다.
