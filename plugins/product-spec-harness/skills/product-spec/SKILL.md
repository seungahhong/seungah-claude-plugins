# Product Spec Harness — 제품 기획 인터랙티브 오케스트레이터

기획자(PM)의 요구·문제(또는 **기획안 초안**)를 입력으로 받아 **요구 정의 → 기획 완성도 점검(DoR) → 기획문서(PRD) 작성·확정(계획→설계→비평 루프) → 사용자 스토리 → 1차 적대적 검증 → 인수조건 → 2차 적대적 검증**의 7 Phase를 인터랙티브하게 진행한다. 특정 기술 스택이나 도구에 종속되지 않은, **개발 착수 전** 제품 기획 산출물에 특화한 공통 절차다.

두 가지 입력 모드를 지원한다.

- **(A) 기획안 입력 모드** — 사용자가 기획안(초안)을 인자/대화로 제공하면, 그 내용에서 문제 정의를 **추출**한다. 이어 **생성 *전*에 원본 기획안의 기획 완성도 점검(DoR)을 먼저 평가**(Phase 1, 사용자 승인 시)해 보강점을 도출하고, 그 피드백을 반영해 PRD·사용자 스토리를 **반드시 생성**한다(초안을 받았다고 PRD·스토리 생성을 건너뛰지 않는다). 마지막에 산출물을 적대적 검증한다. **평가 결과 파일(`product-spec-review.md`)은 PRD·스토리 생성 후 마무리에서 사용자가 저장을 선택할 때만** `.claude/_docs/<기획서 슬러그>/`에 기록한다.
- **(B) 대화형 인터뷰 모드** — 기획안이 없으면 한 번에 한 질문으로 문제를 정의(Phase 0)한 뒤 PRD·스토리를 만든다. 평가할 입력 기획안이 없으므로 Phase 1(기획 완성도 점검(DoR))은 건너뛴다. *생성 산출물*을 대상으로 한 완성도 점검은 **기본으로 제안하지 않으며**, 사용자가 명시적으로 요청할 때만 마무리에서 수행한다.

## 경계 (먼저 읽고 발동 여부를 판단하라)

이 하네스는 **'기획자의 제품 기획(도메인 무관, 개발 전)'** 이다. 다음은 명시적으로 범위 밖이다.

- **프론트엔드 개발용 PRD·구현 요구사항·코드 작성** — 화면 구현·컴포넌트·기술 설계(설계 → 코드)로 들어가는 요청이면 이 하네스를 발동하지 말라. 이 하네스는 개발 전 *제품 기획문서*만 다룬다.
- **코드/하네스/커밋 작업** — 하네스 자체를 생성·진단·개선하는 작업, 코드 리뷰, 커밋 메시지 작성은 이 하네스가 다루지 않는다.
- **완성 산출물의 핸드오프 게이트 검수** — *이미 완성된* PRD/유저스토리/디자인/계약/인수조건을 (작성이 아니라) 착수 게이트로 검수만 하는 작업은 범위 밖이다(이 하네스는 *작성*과 입력 기획안 평가에 한정).

경계가 모호하면 한 질문으로 의도를 확인한다 — "개발 전 *제품 기획문서*를 만드는 건가요, 아니면 *구현/코드*로 들어가는 건가요?"

## 왜 단계별·인터랙티브인가

제품 기획은 한 번에 정답이 나오지 않는다. 잘못된 문제 정의 위에 쌓은 PRD·스토리는 상당 부분이 다시 쓰인다. 그래서 이 하네스는 **매 Phase 종료 시 핵심 산출물을 보여주고 사용자 승인을 받은 뒤에만** 다음으로 넘어간다. 승인 게이트는 비용이 가장 싼 시점(아직 한 Phase 산출물만 있을 때)에 방향 오류를 잡는 장치다.

## 내재화 원칙 (모든 Phase가 따른다)

- **승인 게이트** — 매 Phase 종료 시 핵심 산출물 + 1줄 보고를 제시하고 사용자 승인을 받는다. 보고 형식:
  `[Phase N] {핵심결정} — 다음: {다음}. 진행할까요?`
- **파일 쓰기 전 미리보기 승인** — 파일을 쓰기 전 전체 내용을 미리보기로 보여주고 승인받은 뒤에만 기록한다. 승인 없이 파일을 만들지 않는다.
- **산출 파일은 정확히 4개** — 산출물은 `.claude/_docs/<기획서 슬러그>/`에 모으고, **`PRD.md` · `user-stories.md` · `acceptance-criteria.md` · `product-spec-review.md` 넷만 만든다.** 앞의 셋은 미리보기 승인 시 저장하고, `product-spec-review.md`(Phase 1 결과)는 마무리에서 "저장할까요?(예/아니오)"를 물어 동의할 때만 저장한다. **이 넷 외의 파일(검증 리포트·중간 산출물·메모)은 만들지 않는다** — 검증 결과는 채팅으로 제시하고 그 지적은 위 네 문서에 흡수한다.
- **인수조건 단일 원본** — 조건·행동·결과(Given-When-Then) 문장은 **`acceptance-criteria.md`에만** 존재한다. `user-stories.md`는 스토리(누가·무엇을·왜)와 커버 요구까지만 담는다. 두 곳에 같은 문장을 두면 한쪽만 고쳐진 채 완료 기준이 두 개가 된다.
- **관찰형 인수조건** — 인수조건과 성공지표는 제3자가 관찰로 판정 가능해야 한다. 조건·행동·결과(Given/When/Then)로 적고, "좋다 / 만족스럽다 / 직관적이다" 같은 판정 불가 문장은 금지한다.
- **완전성·추적** — 모든 PRD 핵심 요구가 ≥1개 스토리로 커버되는지 요구↔스토리 매트릭스로 추적한다.
- **적대적 검증** — 검증 단계는 칭찬형 금지. 누락·모호·비일관을 능동적으로 캔다.
- **PRD 확정 루프(계획 → 설계 → 비평)** — Phase 2는 PRD를 한 번에 쓰지 않고 **계획 → 설계 → 비평**을 한 회차로 돌린 뒤 사용자가 확정을 선택할 때 기록한다. 세 역할은 **섹션 소유권으로 분리**한다(계획 §1~§3 / 설계 §4~§6 / 비평 쓰기 권한 0). 본문은 오케스트레이터가 단독 보유하고 에이전트는 **섹션 패치만** 반환한다. **게이트 총량 불변식** — Phase 2가 추가하는 승인 게이트는 회차당 정확히 1개다. **비평에 거부권 없음** — 사용자가 확정을 선택하면 잔존 지적을 기록만 하고 즉시 따른다. 방법론은 외부 플러그인을 참조하지 않고 [references/prd-design-checklist.md](./references/prd-design-checklist.md)·[references/prd-critique-lenses.md](./references/prd-critique-lenses.md)에 **내재화**돼 있다.
- **효과를 약속하지 않는다** — 이 하네스는 루프가 산출물 품질을 얼마나 높이는지 측정하지 않는다. 정직하게 주장할 수 있는 것은 **지적과 그 처리 결과(반영/질문/수용)가 문서에 남는다**는 것뿐이며, 회차 이력은 *변화의 기록*이지 *개선의 증거*가 아니다. **점수·백분율·성숙도 등급을 산출하지 않는다** — 쓸 수 있는 것은 `n건` 카운트뿐이다. **예외는 Phase 1의 좋은 스토리 6가지 기준(INVEST) 점수표와 그 총점에서 나오는 3단 착수 판정(착수가능/보완 후/보류)** 하나뿐으로, 이는 입력 기획안의 착수 준비도를 재는 기존 루브릭 신호이지 이 하네스 산출물의 품질 등급이 아니다. 여기서 금지하는 것은 **하네스가 산출물에 매기는 평가 점수·등급**이며, **PRD 본문의 성공지표 수치(예: 전환율 42% → 60%)는 해당하지 않는다** — 관찰형 지표는 이 하네스의 1급 요건이다.
- **기획 완성도 점검(DoR) 내재화** — 모드 A에서 PRD·스토리 생성 **전(Phase 1)**, **진입 질문(평가할까요?)을 반드시 먼저 제시하고**(생략·자동 스킵 금지) 사용자가 동의(예/모호한 긍정)하면 원본 기획안을 기획 완성도 점검(DoR) 관점에서 평가해 `# 기획 완성도 점검 결과(DoR Review)` + 보완할 점 점검표(보강 체크리스트)를 채팅으로 공유하고, 그 보강점을 PRD·스토리 생성에 **반영**한다. 평가 결과의 **파일 저장(`product-spec-review.md`)은 PRD·스토리 생성 후 마무리에서 사용자가 저장을 선택할 때만** 수행한다(평가 시점엔 채팅 제시만, 즉시 저장 금지). 평가 방법론은 외부 플러그인을 참조하지 않고 [references/dor-review-rubric.md](./references/dor-review-rubric.md)에 **내재화**돼 있다.
- **additive-first(기존 것 보존·추가 우선)** — 이미 합의된 PRD/스토리를 보완할 때, 기존 항목을 뒤엎기 전에 비파괴 추가·완화를 먼저 제안한다.
- **한 번에 한 질문** — 인터뷰하듯 질문은 한 번에 하나만. 어려운 용어(예: 좋은 스토리 6가지 기준(INVEST), 조건·행동·결과(Given-When-Then/Gherkin), 기획 완성도 점검(DoR))는 처음 등장 시 쉬운 말 1줄 정의를 곁들인다.

## 에이전트 팀

| Phase | 에이전트 | 책임 |
|-------|----------|------|
| 0 | `requirements-analyst` | 요구/문제/사용자 정의 (Discovery) — 기획안 있으면 카드 추출 |
| 1 | `dor-evaluator` | **원본 기획안** 기획 완성도 점검(DoR) 평가 (모드 A에서 **진입 질문 제시 필수** · 평가 실행만 예/아니오 · 생성 전 선행, 채팅 제시·즉시 저장 안 함) |
| 2.1 | `prd-planner` | **계획** — PRD §1 배경·문제 / §2 목표·성공지표(관찰형) / §3 범위(In·Out) 소유 (Phase 1 보강점 반영) |
| 2.2 | `prd-designer` | **설계** — PRD §4 핵심 요구사항(FR·NFR) / §5 가정·리스크 / §6 마일스톤 소유 (기획 설계이지 기술 설계가 아님) |
| 2.3 | `prd-critic` | **비평** — 확정 전 PRD 초안(§1~§6)을 읽기 전용으로 비평 (쓰기 권한 0 · 확정 거부권 없음) |
| 3 | `story-writer` | 사용자 스토리 도출 + `[인수조건 인계]` 메모 (인수조건 문장 없음 — Phase 5 소유) |
| 4 | `spec-reviewer` | **1차** 적대적 검증 — PRD ↔ 스토리 (**채팅 제시만** · 결함은 PRD·스토리에 흡수) |
| 5 | `acceptance-writer` | **인수조건 작성** — 스토리를 조건·행동·결과(Given-When-Then)로 전개 → `acceptance-criteria.md` (미리보기 승인 후 저장) |
| 6 | `spec-reviewer` (2차) | **2차** 적대적 검증 — 스토리 ↔ 인수조건 (**채팅 제시만** · 결함은 인수조건에 흡수) |

각 에이전트 정의는 `../../agents/{name}.md`에 있다. **모든 Agent 호출은 `model: "opus"`를 명시한다** — 추론 품질이 기획 산출물 품질을 좌우한다.

### 네 번의 점검은 대상과 축이 서로 다르다 (중복 금지)

이 하네스에는 점검하는 단계가 넷 있다. **넷이 같은 일을 하면 실패한 설계다.** 대상·시점·축이 모두 다르다.

| 단계 | 대상 (무엇을 읽는가) | 시점 | 고유 축 | 산출 |
|------|---------------------|------|---------|------|
| **Phase 1** `dor-evaluator` | **사용자가 준 원본 기획안** (하네스가 만들지 않은 것) | 생성 **전** | 착수 준비도 — 완성도 게이트 · 좋은 스토리 6가지 기준(INVEST) 점수표 · 조건·행동·결과 완결성 · 모호성 Before→After · 의존성/계약 참조 | `# 기획 완성도 점검 결과(DoR Review)` + 보완할 점 점검표 (채팅 제시) |
| **Phase 2.3** `prd-critic` | **이번 회차 PRD 초안 §1~§6** (스토리는 아직 없음) | 생성 **중** (확정 전, 회차마다) | 계획의 내적 강건성 — 문제–목표 정합 · 범위 경계 · 지표 관찰성 · 요구 완결성·원자성 · 예외 공백 · **근거 추적·발명 감사** · 보강점 반영 감사 | 비평 보고서 → PRD에 흡수 (파일 안 만듦) |
| **Phase 4** `spec-reviewer` (1차) | **확정 PRD + 사용자 스토리** (두 산출물 **사이**) | 스토리 생성 **후** | 요구↔스토리 추적·정합 — 요구↔스토리 매트릭스 · INVEST 위반 · 목표↔요구↔스토리 일관성 · 모호·판정불가 문장 | 1차 검증 리포트 (**채팅 제시만**) |
| **Phase 6** `spec-reviewer` (2차) | **사용자 스토리 + 인수조건** (두 산출물 **사이**) | 인수조건 생성 **후** | 스토리↔인수조건 추적·완료 판정 — 빠짐·고아 · **인수조건 관찰성** · 단일 관심사 · 흐름 커버리지(정상+5흐름) · 누락 시나리오 마이닝 | 2차 검증 리포트 (**채팅 제시만**) |

한 줄 요약: **Phase 1은 "받은 것이 착수 가능한가", Phase 2.3은 "쓴 계획이 스스로 옳은가", Phase 4는 "요구와 스토리가 맞는가", Phase 6은 "스토리를 다 됐다고 판정할 수 있는가."**

**2.2의 `[D 점검 결과]`는 자기보고다** — 차단 판정의 근거는 비평 지적뿐이고, 설계의 자기 점검 결과는 차단을 만들지도 풀지도 않는다(둘이 상충하면 비평 지적이 기준).

중복 억제 규칙 — ① `prd-critic`은 **스토리·인수조건·요구↔스토리 커버리지·INVEST를 다루지 않는다**(대상이 아직 존재하지 않는다). ② `prd-critic`은 원본 기획안을 재평가하지 않는다(Phase 1 축). 모드 A에서 Phase 1이 이미 지적한 문장은 새 지적이 아니라 **보강점 반영 감사**로만 다룬다. ③ `spec-reviewer`(1차)는 Phase 2에서 **사용자에게 제시된 항목**(비평 지적 목록·반영 대장·부록 B로 화면에 나온 것)을 **스토리 증거 없이 재지적하지 않는다**(사용자가 이미 마주한 항목을 결함 목록에서 다시 만나게 하지 않는다). **제시된 적 없는 §1~§6 문장(절단·미점검으로 화면에 나오지 않은 것)은 이 단계의 정당한 대상이다** — 비평은 회차당 12건 상한과 닫힌 렌즈를 가지므로 제시되지 않은 문장이 구조적으로 남는다. 스토리와의 정합이 새로 깨진 경우도 보고한다. ④ `spec-reviewer`(2차)는 Phase 4에서 이미 제시된 PRD↔스토리 항목을 **인수조건 증거 없이 재지적하지 않는다** — 2차의 대상은 스토리↔인수조건이다.

## 산출물 배치

별도 지정이 없으면 **`.claude/_docs/<기획서 슬러그>/`** 폴더에 다음을 만든다(기획서별로 폴더 하나). 슬러그는 기획서/제품명에서 영문 소문자로 만들고(예: `email-signup`), 시작 시 한 번 확인한다. 모든 문서 언어는 **한국어**.

```
.claude/_docs/<기획서 슬러그>/        # 예: .claude/_docs/email-signup/
  PRD.md                   # Phase 2 산출 — 미리보기 승인 후 저장
  user-stories.md          # Phase 3 산출 — 미리보기 승인 후 저장 (인수조건 문장은 담지 않음)
  acceptance-criteria.md   # Phase 5 산출(최종) — 미리보기 승인 후 저장
  product-spec-review.md   # Phase 1 기획 완성도 점검(DoR) 결과 — 마무리에서 저장을 선택할 때만 기록
```

- **이 네 파일이 전부다** — 파일을 쓰기 전 전체 내용을 미리보기로 보여준다. `PRD.md`·`user-stories.md`·`acceptance-criteria.md`는 미리보기 승인 시 기록하고, `product-spec-review.md`는 마무리에서 "저장할까요?(예/아니오)"를 물어 **사용자가 저장을 선택한 경우에만** 기록한다.
- **검증 리포트는 파일로 만들지 않는다** — Phase 4(1차)·Phase 6(2차) 적대적 검증 결과는 **채팅으로만** 제시하고, 발견된 결함은 additive-first로 위 네 문서에 흡수한다. 리포트를 따로 남기면 문서가 늘어나는 만큼 어느 것이 합의된 산출물인지 흐려진다.
- **`product-spec-review.md`(Phase 1 기획 완성도 점검 결과)는 PRD·스토리 생성 후 마무리에서** 저장을 묻는다 — Phase 1 평가 시점에는 채팅으로만 제시하고 파일을 만들지 않는다.
- Phase 0의 문제 정의 카드는 채팅에서 합의한 뒤 `PRD.md`의 도입부로 반영한다(**별도 파일로 만들지 않는다**).

# 인터랙티브 플로우

시작 시 두 가지를 정한다 — (1) 산출물 위치를 한 번 확인하고(기본 `.claude/_docs/<기획서 슬러그>/`, 슬러그는 기획서/제품명에서 영문 소문자로 생성), (2) **입력 모드를 판별**한다.

## 입력 모드 판별 (시작 시 1회 · 판별 결과를 사용자에게 명시 선언)

- 사용자가 **기획안(초안)** 을 인자/대화로 제공했거나 파일 경로를 가리키면 → **기획안 입력 모드(A)**. 원본 기획안 전문을 보존하고(파일이면 경로 기록), Phase 0은 인터뷰가 아니라 **카드 추출**로 시작한다. 이어 Phase 1(기획 완성도 점검(DoR), 생성 전 선행)을 거치고, 기획안을 받았다는 이유로 PRD·스토리 생성을 건너뛰지 않는다 — **PRD·스토리(Phase 2·3)는 반드시 수행**한다.
- 기획안이 없으면 → **대화형 인터뷰 모드(B)**. Phase 0을 한 번에 한 질문 인터뷰로 진행하고, 입력 기획안이 없으므로 Phase 1은 건너뛴다.

> **무엇이 '기획안'인가(모드 A 임계)** — 문제·목표·기능·대상·제약 중 **둘 이상을 서술한 사용자 제공 텍스트/파일**이면 분량·형식과 무관하게 기획안(초안)으로 간주한다(자유서술 문단·메모·붙여넣기 포함). 한 줄짜리 단순 요구만 있으면 모드 B다.
> **모호하면 A로 안전 디폴트** — 기획안인지 단순 요구인지 경계가 모호하면 **모드 A로 간주**하고 모드 B로 떨어뜨리지 않는다(평가는 어차피 Phase 1 진입 질문에서 사용자가 거절할 수 있으므로 A쪽이 안전하다). **모드를 못 정한 채 Phase 2(PRD)로 직행하지 않는다.**
> **모드 선언(사용자 가시)** — 판별 결과를 채팅에 1줄로 **명시**한다: `[입력 모드] A(기획안 입력) — 다음: 카드 추출 → 기획 완성도 점검(DoR)(Phase 1)` 또는 `[입력 모드] B(인터뷰) — 다음: 카드 인터뷰 → PRD 계획·설계·비평(Phase 2); 입력 기획안 없어 Phase 1 완성도 점검은 건너뜀`. 이 모드 라벨이 이후 **모든 Phase 전이의 기준**이며, **Phase 1 진입 시 한 번 더 확인**한다.

이후 Phase 0부터 순차 진행하며, 각 Phase는 **반드시 승인 게이트를 통과한 뒤에만** 다음으로 넘어간다. 사용자가 보완을 요청하면 additive-first(기존 것 보존·추가 우선)로 같은 Phase 안에서 보완한다.

## Phase 0 — 요구/문제 정의 (Discovery)

`requirements-analyst`를 호출해 문제를 정의한다. 산출은 다음 고정 필드를 채운 **문제 정의 카드**다.

- **모드 A(기획안 입력)**: 기획안 전문을 입력으로 넘겨 카드를 **추출**한다. 기획안에서 도출되는 필드는 채우고(근거 1줄), 추출 불가하거나 모호·판정불가한 필드만 **한 번에 한 질문**으로 보강한다. 처음부터 다시 인터뷰하지 않는다.
- **모드 B(인터뷰)**: **한 번에 한 질문**으로 인터뷰하며 카드를 채운다(직전 답이 다음 질문을 결정한다).

| 필드 | 내용 |
|------|------|
| `problem` | 풀려는 문제(현상·페인포인트) |
| `target_users` | 대상 사용자(세그먼트·맥락) |
| `goals` | 목표 — 비즈니스 목표 / 사용자 목표 구분 |
| `constraints` | 제약(범위·일정·정책·기술 전제 등) |
| `success_metrics` | 성공지표 — **관찰형**(제3자가 측정·관찰 가능) |

호출:

```
Agent(
  subagent_type="requirements-analyst", model="opus",
  prompt="""
  [역할] 문제 정의 카드를 채운다. 기획안이 있으면 추출 우선, 없으면 한 번에 한 질문 인터뷰.
  [입력] 입력 모드: {A 기획안 입력 / B 인터뷰}
         기획안(있으면 전문 또는 경로): {기획안}
         사용자 초기 요구: {사용자 발화}
  [규칙] 모드 A면 기획안에서 5필드를 추출하고 근거를 1줄씩 남긴다. 추출 불가·모호 필드만 한 번에 한 질문으로 보강(처음부터 재인터뷰 금지).
         모드 B면 한 번에 한 질문으로 채운다. 공통: 어려운 용어는 쉬운 말 1줄 정의, success_metrics는 관찰형, 기획안에 없는 사실 발명 금지.
  [출력] 고정 필드(problem/target_users/goals{비즈니스·사용자}/constraints/success_metrics) 채운 문제 정의 카드.
          아직 비어 있거나 모호한 필드는 다음 질문 1개로 표시.
  """
)
```

카드가 모두 채워지면 사용자에게 보여주고 승인 게이트를 띄운다. **이때 '다음'은 위에서 선언한 모드 하나의 행선지만 적는다**(두 모드를 슬래시로 병기하지 않는다 — 병기는 모드 혼선·스킵의 원인이다).

- **모드 A** → `[Phase 0] 문제·대상·목표·성공지표 합의 — 다음: 기획 완성도 점검(DoR)(Phase 1). 진행할까요?`
- **모드 B** → `[Phase 0] 문제·대상·목표·성공지표 합의 — 다음: PRD 계획(Phase 2.1) → 설계 → 비평; 입력 기획안 없어 완성도 점검 건너뜀. 진행할까요?`

승인 전에는 다음 Phase로 넘어가지 않는다. **모드 A에서 Phase 0이 승인되면 다음 행동은 반드시 Phase 1 진입 질문 제시다 — Phase 2(PRD)로 직행하지 않는다.**

## Phase 1 — 기획안 평가 (기획 완성도 점검(DoR), 내재화 · 모드 A 진입 질문 **필수** · 생성 전 선행)

PRD·스토리를 만들기 **전에**, 입력으로 받은 **원본 기획안을 기획 완성도 점검(DoR) 관점에서 평가**해 보강점을 도출하고 그 피드백을 이후 생성(PRD·스토리)에 반영한다. 사용자에게 **평가 진행 여부를 먼저 묻고, 승인할 때만** 진행한다(별도 승인 게이트).

> **'조건부'의 의미를 혼동하지 말 것** — 조건부는 **평가 실행 여부**(예/아니오)에만 걸린다. **진입 질문을 던지는 것 자체는 모드 A에서 필수이며 생략할 수 없다.** 모드 A에서 Phase 1을 건너뛰는 합법 경로는 단 둘뿐이다 — ① 모드 B(입력 기획안 없음), ② 모드 A에서 사용자가 진입 질문에 **명시적으로 "아니오"**라고 답함. **진입 질문을 띄우지 않은 채 Phase 2로 직행하는 것은 금지**(보고된 0→2 스킵 결함의 직접 원인).

> 쉬운 말 1줄 정의: **기획 완성도 점검(DoR, Definition of Ready)** = 산출물이 개발·QA가 추측 없이 착수할 수 있는 상태인지 판정하는 착수 게이트.

진입 질문(승인 게이트 · 모드 A에서 **반드시 제시**):

`[Phase 1] 원본 기획안을 기획 완성도 점검(DoR)으로 먼저 평가해서, 보강점을 PRD·스토리에 반영할까요? (예/아니오 — 모호하면 '예'로 진행)`

- **예 (또는 '진행해/알아서 해' 등 모호한 긍정)** → `dor-evaluator`를 호출해 평가한다. **모호한 응답은 거절이 아니라 '예'로 해석**한다(평가는 채팅 전용·비파괴라 기본값으로 안전). 결과는 **채팅으로만** 제시한다 — **이 시점에는 파일로 저장하지 않는다**(저장은 PRD·스토리 생성 후 마무리에서 별도로 묻는다).
- **아니오 (명시적 거절일 때만)** → 평가를 건너뛰고 바로 Phase 2(PRD)로 간다.
- **모드 B(입력 기획안 없음)** → 이 Phase는 건너뛴다(평가할 입력 기획안이 없음). 생성 산출물 완성도 점검은 **기본으로 제안하지 않으며**, 사용자가 명시적으로 요청할 때만 마무리에서 수행한다(마무리 §1 참조).

평가는 [references/dor-review-rubric.md](./references/dor-review-rubric.md)에 **내재화**된 루브릭(기획 완성도 게이트(DoR 게이트) · 좋은 스토리 6가지 기준 점수표(INVEST 스코어카드) · 조건·행동·결과(Given-When-Then) 완결성 · 모호성 점검 · 의존성/계약 참조)을 따른다. 외부 플러그인을 참조하지 않는다.

## Phase 2 — 기획문서(PRD) 작성·확정 (계획 → 설계 → 비평 루프)

PRD는 한 번에 완성되지 않는다. 방향을 정하면(계획) 요구로 전개하는 과정에서 빈틈이 드러나고(설계), 그 결과를 적대적으로 읽으면 계획의 전제가 흔들리기도 한다(비평). 그래서 Phase 2는 **계획 → 설계 → 비평**을 한 회차로 묶어 돌린 뒤, 사용자가 확정을 선택할 때 PRD를 기록한다.

```
 2.0 준비
      ↓
 ┌─ 2.1 계획 ──→ 2.2 설계 ──→ 2.3 비평 ──→ 2.4 판정·질문 ─┐
 │                                                        │
 └──── (2) 한 번 더 / (3) 지정 항목만 ◀── 2.5 게이트 ─────┘
                                          │ (1) 확정
                                          ▼
                                    2.6 확정·기록
```

**이 루프가 정직하게 주장하는 것** — 초안을 만드는 쪽과 비평하는 쪽은 같은 컨텍스트를 읽는다. 그래서 "루프를 돌리면 PRD 품질이 올라간다"고 주장하지 않는다. 주장할 수 있는 것은 하나다 — **지적과 그 처리 결과(반영/질문/수용)가 문서에 남는다.** 회차 이력은 *변화의 기록*이지 *개선의 증거*가 아니다.

### 이 루프의 불변식 (깨지 않는다)

- **섹션 소유권 분할** — 계획은 **§1 배경·문제 / §2 목표·성공지표 / §3 범위 In·Out**, 설계는 **§4 핵심 요구사항 / §5 가정·리스크 / §6 마일스톤**만 소유한다. 비평은 **쓰기 권한이 없다**. 이 분할이 세 역할이 같은 일을 하는 것을 막는다.
- **본문 단일 소유권** — PRD 본문은 **오케스트레이터가 보유**한다. 2.1·2.2는 자기 소유 섹션의 **패치만** 반환하고, PRD 전문을 매 회차 다시 쓰지 않는다.
- **게이트 총량 불변식** — Phase 2가 추가하는 승인 게이트는 **회차당 정확히 1개**(2.5)다. 2.1·2.2·2.3 사이에는 게이트를 두지 않는다. 게이트가 많아지면 사용자는 읽지 않고 넘기고, 그 순간 게이트의 본래 기능(싼 시점에 방향 오류 잡기)이 죽는다.
- **파일은 루프 종료 후 1회만** — 루프 도중에는 파일을 만들지 않는다(중간 초안·비평 리포트를 `.claude/_docs/<슬러그>/`에 떨어뜨리지 않는다). 전체 미리보기 승인과 기록은 2.6에서 한 번만 한다.
- **비평에 거부권 없음** — 차단 지적이 남아 있어도 사용자가 확정을 선택하면 **즉시 확정한다.** 잔존 지적은 PRD **부록 B(알려진 제한사항)** 에 `[미해소 지적]`으로 기록하되, 그것을 이유로 진행을 막거나 조용히 보류하거나 재확인을 반복하지 않는다.

### 2.0 준비 (오케스트레이터)

승인된 문제 정의 카드와, 모드 A라면 Phase 1 보완할 점 점검표를 **작업 세트**로 묶는다. 점검표가 있으면 항목별 **반영 대장**을 만든다 — `항목 / 출처 / 상태(미반영·반영·질문대기·범위밖) / 흡수 위치`. 이 대장을 매 회차 비평 입력에 다시 넣어, 회차가 돌면서 초기 보강점이 컨텍스트에서 밀려 유실되는 것을 막는다.

### 2.4 판정·질문 (오케스트레이터)

0. **선행 점검 — 산출이 비어 돌아왔는가** — 설계가 `[계획 변경 요청]`만 반환했거나 비평이 섹션 부재로 보고서를 못 낸 경우에도 **회차를 중단하지 않는다.** 지적 3필드와 최우선 권고를 `(비평 미산출 — {사유})`로 채우고, `미전개 섹션 {목록}`을 게이트에 명시한 뒤 아래 단계 중 입력이 있는 것만 수행한다. 흐름이 여기서 멈추면 사용자는 아무 선택지도 받지 못한다.
1. **차단 판정** — 비평의 차단 지적(닫힌 4종)이 남아 있는지 센다.
2. **채택 기준(고정)** — 다음 회차로 넘길 지적을 여기서 확정한다. 회차마다 기준이 흔들리면 정체 판정 자체가 무의미해지므로 기준을 고정한다.
   - **넘긴다**: 차단 전부 + 최우선 권고 3가지 + 처리분류 **A**(문서 내부 해소 가능).
   - **단 처리분류 B는 등급이 차단이라도 넘기지 않는다** — 질문 큐가 우선한다. B를 델타로 넘기면 소유 단계가 빈칸을 그럴듯한 값으로 메우게 되고, 그것이 곧 이 하네스가 막으려는 발명이다.
   - **안 넘긴다**(회차를 새로 도는 사유가 아니다): 처리분류 **B**(사용자만 아는 사실)는 질문 큐로, **C**(범위 밖)는 **§5 가정·리스크 이관 대상**으로 설계에 넘긴다(회차가 돌면 설계가 §5에 반영한다). 확정 시점까지 §5에 반영되지 않은 C 항목만 부록 B에 `[범위 밖 이관]`으로 기록한다.
   - 참고 등급 지적은 사용자가 (3)으로 지정하지 않는 한 넘기지 않는다(이미 사용자가 본 문장을 소리 없이 바꾸지 않는다 — additive-first).
3. **`[계획 변경 요청]`·`[D 점검 결과]` 처리** — 설계가 반환한 `[계획 변경 요청]`을 조용히 버리지 않는다. 게이트 요약에 **`계획 변경 요청 {r}건`을 별도 표기**하고, (2)·(3) 선택 시 2.1 입력 델타에 포함하며, (1) 확정 시 **부록 B로 이관**한다. `[D 점검 결과]` 중 **`미점검` 항목만** 확정 시 부록 B에 `[미점검]`으로 남긴다 — `해당 없음`은 정상 판정이므로 §4 본문에만 두고 부록 B에 넣지 않는다(넣으면 `부록 B {k}건`이 위험을 과대 표기한다).
4. **반영 대장 갱신** — 비평의 '반영 대장 감사'를 받아 각 항목의 상태(미반영·반영·질문대기·범위밖)와 흡수 위치를 갱신한다. 대장은 파일로 만들지 않으므로 **매 회차 게이트 직전 채팅에 표로 다시 출력해** 유지한다(컨텍스트에서 밀려 유실되면 막으려던 실패 모드가 그대로 재현된다). 확정 시 미반영으로 남은 항목은 부록 B로 옮긴다.
5. **정체 가드** — 가드마다 처리가 다르다.
   - **G1 반복**(새 회차 지적의 렌즈 × 위치가 직전 회차와 같고 처리분류도 그대로): 회차를 **더 권하지 않고** 사용자 판단을 구한다. **단 사용자가 그래도 (2)를 선택하면 정체 경고 1줄만 병기하고 즉시 회차를 돈다**(거부·재확인 반복 금지).
   - **G2 증식**(**렌즈를 지정하지 않은 지적이 있다**): 그 지적만 드롭하고 건수를 보고한다. **건수 증가 자체는 가드가 아니다** — 직전 회차에 적용 못 한 렌즈가 있었다면 이번 회차의 증가는 정상이다.
   - **G3 무근거**(원문 인용이 없다): 그 지적을 세지 않고 드롭한 뒤 사실을 보고한다.
   - **G2·G3은 회차 판단에 쓰지 않는다.** 인용 없는 지적 1건을 드롭한 것은 정체 신호가 아니라 정상 동작이다.
6. **질문 1개** — `[확인필요]` 큐가 비어 있지 않으면 **가장 결정적인 질문 하나만** 던진다(한 번에 한 질문 원칙 유지). 나머지는 초안에 `[확인필요]`로 남긴다.
   **답을 받으면 그 항목을 소유한 단계를 해당 항목만 지정해 재호출해 초안에 반영한 뒤** 게이트로 간다(오케스트레이터가 남의 섹션에 직접 쓰지 않는다 — 섹션 소유권 불변식 유지). **이 재호출은 회차로 세지 않는다.** 반영 후에는 해소된 항목에 `(답변으로 해소)`를 표기한다 — **비평 지적 건수 자체는 원본을 유지한다**(차단 판정의 근거는 비평 지적뿐이므로, 오케스트레이터가 비평이 낸 적 없는 '차단 해소' 판정을 만들지 않는다).

`[확인필요]` 중 **처리분류 B**(사용자만 아는 사실)는 루프로 해소되지 않는다 — 회차를 더 돌려도 답이 나오지 않으므로 질문으로만 해소하고, 답이 없으면 마커를 남긴 채 확정한다.

### 2.5 게이트 (회차당 정확히 1개)

게이트를 띄우기 전에 **비평 보고서의 지적 목록 전문**(등급·렌즈·위치·인용·처리분류), 갱신된 반영 대장 표, **'이번 회차에 보지 못한 것'(미적용 렌즈·미점검 섹션)**, 그리고 **비평 이후 변경분**(2.4-6 답변 반영으로 바뀐 섹션 — *이 부분은 이번 회차 비평을 거치지 않았다*)을 채팅에 제시한다. 건수만 요약한 채 확정을 받으면, 사용자가 본 적 없는 지적이 부록 B에 '미해소'로 남고 Phase 4가 그것을 이미 판정된 항목으로 취급한다.

```
[Phase 2 · {n}회차] PRD 초안(§1~§6) — 지적 {차단 a건 / 수정권고 b건 / 참고 c건}
계획 변경 요청 {r}건 · 확인 필요 {q}건 · 미전개 섹션 {목록 또는 없음} · 미적용 렌즈 {m}개
최우선 권고: {1줄}
권장: ({1|2}) — {사유 1줄}
선택 비용: (2) = 계획·설계·비평 3개 재호출 / (3) = 지정 항목 + 인접 섹션 소유 단계만
(1) 이대로 확정   (2) 한 번 더 다듬기   (3) 특정 항목만 지정해 수정
(1)~(3) 중 번호로 답해 주세요. (3)이면 고칠 지적의 항목 번호(#n)를 함께 적어 주세요.
```

- **미적용 렌즈는 0이어도 항상 표기한다** — 부분 재비평(3)을 전수 통과로 읽지 않게 하기 위해서다.
- **게이트 총량** — Phase 2가 추가하는 **승인 게이트는 회차당 정확히 1개**(2.5)이고, 그 앞에 **확인 질문이 최대 1개** 붙을 수 있다(질문은 게이트가 아니다). 2.1·2.2·2.3 사이에는 아무것도 두지 않는다.
- **기본 추천 표기** — 차단이 1건 이상이면 `(2)`를, 차단이 0건이면 `(1)`을 권장으로 표기한다. **단 남은 차단이 전부 처리분류 B(사용자만 아는 사실)면 `(2)` 대신 `(1)`+질문을 권장하고 '이 차단은 회차를 더 돌려도 해소되지 않는다'를 1줄 병기한다** — 값이 없어서 막힌 것을 '다듬으면 해결된다'로 암시하지 않는다. 추천은 추천일 뿐 선택은 사용자가 한다.
- **선택지의 비용** — `(2)`는 계획·설계·비평 **3개를 다시 호출**하고, `(3)`은 지정 항목 소유 단계(+인접 섹션 소유 단계)만 호출한다. 위 게이트 블록의 `선택 비용` 줄이 이 차이를 사용자에게 알린다.
- **(3) 지정 항목만 수정** — 지정 항목을 소유한 단계 **+ 그 변경이 건드리는 인접 섹션 소유 단계**를 함께 재호출한다(예: §3 범위를 고치면 §4 요구가 In을 넘어설 수 있으므로 설계도 함께 호출). 비평은 **지정 항목 + C-2(범위 경계)·C-4(요구 완결성)** 를 재점검한다(전면 재비평은 하지 않되, 부분 수정이 만든 정합 파괴는 놓치지 않는다). **(3)에서는 '렌즈 7개 전수' 원칙의 예외가 적용되며, 보지 않은 렌즈를 보고서의 '이번 회차에 보지 못한 것'에 기재한다.** **(3) 회차는 정체 가드 비교 대상에서 제외한다**(부분 비평 결과를 전체 비평과 비교하면 판정이 오작동한다).
- **회차 상한** — 하네스가 스스로 도는 회차는 **1회차**다. 그 이상은 사용자가 게이트에서 선택할 때만 돈다. **권고 상한은 3회차**이며, 사용자가 명시적으로 더 원하면 상한과 무관하게 따르되 정체 경고를 1줄 병기한다.
- **조기 종료** — 사용자가 "이 정도면 충분 / 그만 / 이대로 확정" 취지를 표시하면 **어느 하위 단계에서든 즉시 2.6**으로 간다. 잔존 지적은 부록 B에 `[미해소 지적] {렌즈} — {한 줄}`로 기록하고, 재확인 질문이나 보류를 하지 않는다.
- **루프 생략 요청** — 사용자가 처음부터 "루프 없이 한 번만"을 요청하면 2.1 → 2.2 → 2.3 → **2.4까지 수행하고**(차단 판정·대장 갱신·확인 질문은 그대로 한다) 회차를 추가로 돌지 않은 채 게이트로 간다. 비평 자체를 건너뛰지는 않는다.

### 2.6 확정·기록

오케스트레이터는 보유한 본문에 2.1·2.2가 마지막으로 반환한 **섹션 패치를 합치기만 한다** — 남의 섹션 문장을 직접 쓰지 않는다. **미전개 섹션은 `(미전개 — 확인 필요: {질문})` 자리표시자 한 줄만** 넣는다(내용을 대신 작성하지 않으면서 빈 섹션도 남기지 않는 유일한 방법이다). 확정 시점에 남아 있던 지적(채택됐으나 아직 반영 전인 것 포함)은 반영하지 않고 **부록 B로 넘긴다**(반영을 원하면 사용자가 게이트에서 (2)·(3)을 고른다). 확정된 §1~§6을 [references/prd-template.md](./references/prd-template.md)의 표준 구조로 합치고, 부록에 **루프 이력**(회차별 변경 1줄씩)과 **알려진 제한사항**(`[미해소 지적]`·처리분류 C 이관 항목)을 남긴다.

**파일 쓰기 전 전체 미리보기**를 보여주고 승인받은 뒤 `.claude/_docs/<기획서 슬러그>/PRD.md`에 기록한다.

승인 게이트:

`[Phase 2] PRD 확정(범위 In/Out·핵심 요구 FR-1…FR-n·루프 {n}회차·부록 B {k}건: 미해소 지적 a·계획 변경 요청 미반영 b·미반영 점검표 c·미점검 d·범위 밖 e) — 다음: 사용자 스토리 도출. 진행할까요?`

## Phase 3 — 사용자 스토리 도출

**확정 PRD의 §4에 요구가 0개면** Phase 3 진입 전에 §4 전개를 먼저 제안하고, 사용자가 그대로 진행을 고르면 스토리에 `(요구 미전개 — 추적 불가)`를 표기한다(요구 없이 스토리를 지어내지 않는다).

승인된 PRD의 핵심 요구사항(`FR-1`…`FR-n` / `NFR-1`…`NFR-n`)을 입력으로 `story-writer`를 호출한다. **Phase 2.2 설계가 남긴 §4.1 사용자 여정 · §4.2 상황(상태)·전이 · §4.3 권한·역할 · §4.4 필요 정보 항목(과 §4의 예외 경계 제품 규칙)**이 시나리오와 예외 흐름의 1차 재료다(설계도 이 단계도 목록·메모까지만 만들고, 문장화는 Phase 5다). **Phase 1 보완할 점 점검표가 있으면** 예외 흐름(경계/에러/빈/권한) 등 식별된 누락을 **어느 스토리가 안는지 배정하고 `[인수조건 인계]` 메모로 Phase 5에 넘긴다**(여기서 문장화하지 않는다). 작성 규약은 [references/user-story-guide.md](./references/user-story-guide.md)를 따른다.

각 스토리는:

- **형식** — "…로서 …하고 싶다, 왜냐하면 …" (As a / I want / so that)
- **인수조건은 여기서 쓰지 않는다** — 조건·행동·결과(Given/When/Then) 문장은 Phase 5의 `acceptance-criteria.md`가 단독 소유한다(단일 원본).
- **`[인수조건 인계]` 메모** — 스토리별로 Phase 5가 덮어야 할 예외 흐름 후보를 문장화하지 않고 목록으로 남긴다. **이 메모는 `user-stories.md`에 함께 기록해** Phase 5 입력으로 전달한다 — 채팅에만 남기면 저장 시 사라져 그 누락을 이후 어느 단계도 잡지 못한다.
- **좋은 스토리 6가지 기준(INVEST) 자가점검** — Independent(독립적) / Negotiable(협상가능) / Valuable(가치있음) / Estimable(추정가능) / Small(작음) / Testable(검증가능) (각 항목 쉬운 말 1줄 정의 곁들임)
- **추적** — 각 스토리가 커버하는 요구 식별자(`FR-n`/`NFR-n`)를 명시

호출:

```
Agent(
  subagent_type="story-writer", model="opus",
  prompt="""
  [역할] PRD 핵심 요구 → 사용자 스토리 + `[인수조건 인계]` 메모. **조건·행동·결과 문장은 쓰지 않는다**(Phase 5 단독 소유). Phase 1 보강점(예외 흐름 등)은 메모로 인계.
  [입력] PRD 핵심 요구사항(FR-1…FR-n / NFR-1…NFR-n): {PRD 요구 목록}
         Phase 2.2 설계 산출(§4.1 여정 · §4.2 상황·전이 · §4.3 권한·역할 · §4.4 필요 정보 항목 · 예외 제품 규칙): {설계 §4~§6 근거}
         Phase 1 보완할 점 점검표(있으면): {미충족 항목·누락 흐름}
  [참조] references/user-story-guide.md (As a/I want/so that + 좋은 스토리 6가지 기준(INVEST)). 인수조건 문장 규약은 참조하지 않는다(Phase 5 소유).
  [규칙] **인수조건(Given/When/Then) 문장은 쓰지 않는다** — Phase 5가 단독 소유한다(단일 원본). 각 스토리에 커버 요구(FR-n/NFR-n) 표기. INVEST 자가점검 결과 포함.
         완성도 점검이 지적한 경계/에러/빈/권한 흐름은 **어느 스토리에서 다뤄야 하는지 메모로만** 남겨 Phase 5에 넘긴다(문장화는 Phase 5).
  [출력] 스토리 목록 + 요구↔스토리 커버 표(어떤 FR-n/NFR-n이 어떤 스토리로 커버되는지) + [인수조건 인계] 메모(스토리별로 Phase 5가 덮어야 할 예외 흐름 후보).
  """
)
```

스토리 초안이 완성되면 **파일 쓰기 전 미리보기**를 보여주고 승인받은 뒤 `.claude/_docs/<기획서 슬러그>/user-stories.md`에 기록한다.

승인 게이트:

`[Phase 3] 스토리 N개 + 요구 커버 표 — 다음: 1차 적대적 검증(Phase 4). 진행할까요?`

## Phase 4 — 1차 적대적 검증 (PRD ↔ 스토리)

`spec-reviewer`를 호출해 **칭찬 금지·결함 색출** 모드로 PRD와 스토리를 교차 검증한다. 인수조건은 아직 없으므로 **완료 판정 기준은 이 단계의 축이 아니다**(Phase 6 소유). 점검 축:

1. **완전성** — 요구↔스토리 추적 매트릭스를 만들어 커버 안 된 요구(`FR-n`/`NFR-n`)를 찾는다.
2. **좋은 스토리 6가지 기준(INVEST) 통과** — 각 스토리가 INVEST를 만족하는지, 위반 항목을 지목한다.
3. **일관성** — 목표 ↔ 요구 ↔ 스토리 사슬의 불일치(목표에 없는 요구, 요구 없는 스토리 등).
4. **모호/판정불가 문장** — PRD·스토리 전반의 애매어·미정의 용어를 캔다.

호출:

```
Agent(
  subagent_type="spec-reviewer", model="opus",
  prompt="""
  [역할] 적대적 검증 — 칭찬 금지, 누락·모호·비일관을 능동적으로 캔다.
  [입력] PRD: {PRD.md}, 스토리: {user-stories.md}, 문제 정의 카드: {Phase 0 카드}
         Phase 2에서 **사용자에게 제시된 항목 목록**(회차별 지적 목록 전문 + 부록 B 전문): {목록} — 이 목록에 있는 것만 재지적 금지 대상이고, 여기 없는 §1~§6 문장은 정당한 대상이다.
  [점검] 1) 완전성(요구↔스토리 추적 매트릭스로 미커버 요구 색출)
         2) 좋은 스토리 6가지 기준(INVEST) 통과/위반
         3) 일관성(목표↔요구↔스토리)
         4) 모호/미정의 용어
         (인수조건 관찰성·흐름 커버리지는 대상이 아직 없으므로 다루지 않는다 — Phase 6 소유)
  [규칙] Phase 2에서 **사용자에게 제시된 항목**(비평 지적 목록·반영 대장·부록 B로 화면에 나온 것)을 **스토리 증거 없이 재지적하지 않는다**. 다만 **제시된 적 없는 문장(절단·미점검분)은 대상이며**, 스토리와의 정합이 새로 깨진 것도 보고한다.
  [출력] 검증 리포트 — 추적 매트릭스 + 발견 결함 목록(심각도·위치·근거·수정 제안). 결함 0건이면 그 근거를 명시.
  """
)
```

검증 리포트는 **채팅으로만 제시한다 — 파일로 저장하지 않는다.** 적대적 검증은 그 자체가 최종 산출물이 아니라 PRD·스토리를 다듬기 위한 피드백이므로, 결함은 `PRD.md`·`user-stories.md` 보완으로 흡수한다.

**결함이 있으면 additive-first(기존 것 보존·추가 우선)로 보완한다** — 합의된 PRD/스토리를 뒤엎기 전에 비파괴 추가(누락 스토리 추가, 커버 요구 보강)·완화를 먼저 제안하고, 사용자 승인 후 해당 Phase(2 또는 3)로 돌아가 반영한다(반영 결과는 `PRD.md`·`user-stories.md`에 기록). 구조적 뒤집기는 사용자가 명시적으로 승인할 때만 한다.

승인 게이트:

`[Phase 4] 1차 적대적 검증 완료(결함 {n}건 / 전체 요구 {t}건 중 미커버 {k}건 / 재지적 제외한 수용 항목 {j}건)`
`— 이 단계는 완료 판정 기준(인수조건)을 검증하지 않았습니다(Phase 6 소유). 다음: 인수조건 작성(Phase 5). 진행할까요?`

## Phase 5 — 인수조건 작성 (`acceptance-criteria.md`)

확정된 사용자 스토리를 **"이 스토리가 다 됐다고 어떻게 판정하는가"**의 검증 기준으로 쪼갠다. `acceptance-writer`를 호출해 각 스토리를 조건·행동·결과(Given-When-Then) 시나리오로 전개하고 `acceptance-criteria.md`를 만든다. 이것이 이 하네스의 **마지막 산출물**이다.

> 쉬운 말 1줄 정의: **인수조건(Acceptance Criteria)** = 스토리가 "다 됐다"고 판정할 수 있는, 제3자가 관찰로 참/거짓을 가릴 수 있는 완료 기준.

**스토리가 부모, 인수조건이 자식이다** — 스토리는 누가·무엇을·왜(의도와 범위), 인수조건은 완료 판정. 스토리 1개에 인수조건이 여러 개 붙는다.

**단일 원본** — 조건·행동·결과 문장은 **`acceptance-criteria.md`에만** 둔다. `user-stories.md`는 스토리와 커버 요구까지만 담고 같은 문장을 중복해 싣지 않는다(두 곳에 두면 한쪽만 고쳐진 채 완료 기준이 두 개가 된다).

작성 규약은 [references/acceptance-criteria-guide.md](./references/acceptance-criteria-guide.md)를 따른다.

호출:

```
Agent(
  subagent_type="acceptance-writer", model="opus",
  prompt="""
  [역할] 확정 사용자 스토리를 인수조건(조건·행동·결과)으로 전개해 acceptance-criteria.md를 작성한다.
  [입력] 사용자 스토리(US ID·커버 요구·`[인수조건 인계]` 메모): {user-stories.md}
         PRD §4 핵심 요구사항과 §4.1~§4.4(여정·상황·전이·권한·정보 항목): {PRD 근거}
         Phase 1 보완할 점 점검표(있으면): {예외 흐름 누락 지적}
         Phase 4 1차 검증 리포트(있으면): {남은 결함}
         원본 기획안(모드 A): {전문/경로} — **출처 대조 전용**(어떤 정책이 실제로 입력에 있었는지 확인). 재평가 금지.
  [참조] references/acceptance-criteria-guide.md (형식·단일 관심사·흐름 커버리지·판정 체크·추적).
  [규칙] 인수조건 1개 = 단일 관심사 1개. 서로 다른 관심사·트리거는 '그리고'로 묶지 말고 시나리오를 쪼갠다.
         스토리마다 정상 + 해당되는 예외 흐름(경계/에러/빈 상태/권한/상태 전이)을 덮고, 해당 없으면 '해당 없음 — (사유)'로 명시한다.
         **예외 흐름 정책·수치를 발명하지 않는다** — 입력에 없으면 [확인필요]. '이 흐름이 비었다'를 지적하는 것이 이 단계의 일이고, 정책을 정하는 것은 기획자의 일이다.
         Then은 관찰 가능해야 한다("좋다/적절히/잘 된다" 금지). 각 인수조건에 AC-<스토리번호>.<일련번호> ID와 출처 US ID를 연결한다.
         조건·행동·결과 문장을 user-stories.md에 중복하지 않는다. 사용자에게 직접 질문하지 않고 [확인필요]로 반환한다.
  [출력] acceptance-criteria.md 초안(스토리별 인수조건 + 흐름 커버 1줄 + 스토리↔인수조건 추적 표) + [확인필요] + [빠짐·고아 점검].
  """
)
```

`[확인필요]`가 있으면 **한 번에 한 질문**으로 해소한 뒤 반영한다. 초안이 완성되면 **파일 쓰기 전 전체 미리보기**를 보여주고 승인받은 뒤 `.claude/_docs/<기획서 슬러그>/acceptance-criteria.md`에 기록한다.

승인 게이트:

`[Phase 5] 인수조건 {n}건 / 스토리 {m}개 커버(빠짐 {a}건·고아 {b}건) · [확인필요]만으로 덮인 스토리 {c}건 — 다음: 2차 적대적 검증. 진행할까요?`

> **`빠짐·고아` 건수는 작성자 자기보고다** — 독립 판정은 Phase 6이 한다(Phase 2.2의 `[D 점검 결과]`와 같은 취급). 이 수치를 검증된 결과로 읽지 않는다.

## Phase 6 — 2차 적대적 검증 (스토리 ↔ 인수조건)

`spec-reviewer`를 **2차로** 호출해 이번에는 **스토리와 인수조건 사이**를 검증한다. Phase 4(1차)가 *PRD↔스토리*를 봤다면, 여기서는 *스토리↔인수조건*을 본다 — 대상이 다르므로 같은 점검을 반복하지 않는다.

점검 축:

1. **스토리↔인수조건 추적** — 모든 스토리가 ≥1개 인수조건으로 덮였는가(빠짐), 출처 스토리 없는 인수조건이 있는가(고아).
2. **인수조건 관찰성** — 각 Then이 제3자 관찰로 통과/실패를 판정 가능한가. 판정 불가 문장을 색출한다.
3. **단일 관심사** — 서로 다른 관심사·트리거가 `그리고`로 묶여 통과/실패가 뭉개지지 않았는가.
4. **흐름 커버리지** — 정상 외 5흐름(경계·에러·빈 상태·권한·상태 전이)을 덮었는가. `해당 없음`이 **사유와 함께** 적혔는가(누락과 의도된 제외의 구분).
5. **누락 시나리오 마이닝** — 이 인수조건만 보고 만들면 빠지는 것을 5흐름 축으로 능동적으로 캔다. 발견은 조건·행동·결과로 옮길 수 있는 제안 형태로 적되, **정책을 지어내지 않는다**(빈 곳을 지적하고 `[확인필요]`로 돌린다).
6. **스토리 재판정** — 인수조건이 **전부 `[확인필요]`이거나 `(전개 불가)`인 스토리**는 좋은 스토리 6가지 기준(INVEST)의 Testable(검증가능) 위반으로 되돌린다. Phase 3·4는 인수조건이 없는 시점에 T를 *예측*으로 판정했으므로, 실제로 전개해 본 지금이 그 예측을 반증할 수 있는 유일한 지점이다.

호출:

```
Agent(
  subagent_type="spec-reviewer", model="opus",
  prompt="""
  [역할] 2차 적대적 검증 — 대상은 **스토리와 인수조건 사이**다. 칭찬 금지.
  [입력] 사용자 스토리: {user-stories.md}, 인수조건: {acceptance-criteria.md}, PRD: {PRD.md}
         Phase 4 1차 검증에서 이미 판정된 항목 목록: {목록}
  [참조] references/acceptance-criteria-guide.md (§3 흐름 커버리지 · §4 판정 체크 · §5 추적 · §6 누락 마이닝).
  [점검] 1) 스토리↔인수조건 추적 매트릭스(빠짐·고아)
         2) 인수조건 관찰성(판정 불가 Then 색출)
         3) 단일 관심사 위반(서로 다른 관심사가 '그리고'로 묶임)
         4) 흐름 커버리지(정상 + 5흐름, '해당 없음'에 사유가 있는가)
         5) 누락 시나리오 마이닝(5흐름 축)
         6) 스토리 재판정 — 인수조건이 전부 [확인필요]/(전개 불가)인 스토리는 INVEST Testable 위반으로 Phase 3 보완 제안
  [규칙] Phase 4에서 이미 제시된 PRD↔스토리 항목을 **인수조건 증거 없이 재지적하지 않는다**(대상이 다르다).
         누락을 지적하되 **정책·수치를 지어내지 않는다** — 빈 곳은 [확인필요]로 돌린다.
  [출력] 2차 검증 리포트 — 스토리↔인수조건 추적 매트릭스 + 결함 목록(심각도·위치·근거·수정 제안) + 누락 시나리오 제안. 결함 0건이면 그 근거를 명시.
  """
)
```

리포트는 **채팅으로만 제시한다 — 파일로 저장하지 않는다.** 결함은 additive-first로 `acceptance-criteria.md`에 흡수한다(필요하면 **Phase 5로**, 스토리 자체가 검증 불가로 판정되면 **Phase 3으로** 돌아가 반영).

승인 게이트:

`[Phase 6] 2차 적대적 검증 완료(결함 {n}건 / 스토리 {m}개 중 인수조건 미커버 {k}건) — 마무리할까요?`

# 마무리

## 1. 기획 완성도 점검(DoR) 결과 저장 (PRD·스토리 생성 후 · opt-in)

PRD·스토리가 만들어진 **뒤에만**, Phase 1에서 수행한 기획 완성도 점검(DoR) 결과를 파일로 남길지 묻는다. **사용자가 저장을 선택한 경우에만** 저장한다(요청·평가 시점에 자동 저장 금지).

`[저장 확인] Phase 1의 기획 완성도 점검(DoR) 결과(# 기획 완성도 점검 결과(DoR Review) + 보완할 점 점검표)를 product-spec-review.md로 저장할까요? (예/아니오)`

- **예** → 평가 결과 전체를 **파일 쓰기 전 미리보기**로 다시 보여주고, 승인 후 `.claude/_docs/<기획서 슬러그>/product-spec-review.md`에 기록한다.
- **아니오** → 저장하지 않는다(채팅 제시로만 남긴다).
- **Phase 1을 건너뛴 경우(모드 B 등 입력 기획안 없음·평가 미실시)** → 저장할 평가 결과가 없다. Phase 4가 같은 대상을 이미 검증했으므로 **기본은 제안하지 않는다.** 사용자가 명시적으로 요청할 때만 수행하되, **총점 밴드·착수가능 등급 없이 항목·건수로만** 제시한다(하네스 산출물에 성숙도 등급을 매기지 않는다). 수행했다면 동일하게 저장 여부를 묻는다(보고서에 대상이 "생성 산출물"임을 명시). **단 모드 A에서 Phase 1 *평가만* 거절한 경우 대상은 여전히 원본 기획안이므로**, 뒤늦게 요청하면 Phase 1과 동일한 루브릭(INVEST 점수표·3단 착수 판정 포함)을 적용하고 대상도 "원본 기획안"으로 적는다.

## 2. 산출물 요약

만들어진 산출물의 위치를 요약해 보고한다 — `.claude/_docs/<기획서 슬러그>/` 하위의 `PRD.md` / `user-stories.md` / **`acceptance-criteria.md`(최종 산출물)**, 그리고 저장을 선택했다면 `product-spec-review.md`(기획 완성도 점검(DoR) 결과 + 보완할 점 점검표). **이 넷이 이 하네스가 만드는 파일의 전부다** — 1차·2차 적대적 검증 리포트는 채팅으로만 제시했고, 그 피드백은 **사용자가 반영을 선택한 범위에서만** 위 문서들에 흡수됐다(반영하지 않기로 한 지적은 이 세션의 문서에 남지 않는다). 추가 보완 요청은 항상 additive-first(기존 것 보존·추가 우선)로, 해당 Phase에서 한 번에 한 질문으로 진행한다.
