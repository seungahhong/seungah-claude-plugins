# 사용자 스토리 작성 가이드

PRD의 요구사항(기능 요구사항(FR)/비기능 요구사항(NFR))을 사용자 관점의 **스토리**로 전개하는 가이드다. Phase 3(`story-writer`)가 이 가이드를 따르고, Phase 4(`spec-reviewer` 1차)가 이 기준으로 검증한다. 모든 산출 문서는 한국어로 작성한다.

> **인수조건은 이 문서의 범위가 아니다(단일 원본).** 조건·행동·결과(Given/When/Then) 문장은 Phase 5가 [`acceptance-criteria.md`](./acceptance-criteria-guide.md)에서 **단독 소유**한다. `user-stories.md`는 스토리(누가·무엇을·왜)·좋은 스토리 6가지 기준(INVEST)·커버 요구까지만 담는다. 아래 §2·§4의 조건·행동·결과 설명은 **스토리가 인수조건으로 전개 가능한지(INVEST의 Testable) 판단하기 위한 참고**이지, 여기에 문장을 쓰라는 지시가 아니다. **스토리가 부모, 인수조건이 자식이다.**

> 쉬운 말 1줄 정의: **사용자 스토리(User Story)** = 기능을 "누가·무엇을·왜"의 사용자 관점 한 문장으로 표현한 작업 단위.

> **문서 머리 표기** — `user-stories.md`는 제목 바로 아래에 `> 기준 입력: v{N}` 1줄을 둔다(원본 기획안·문제 정의 카드가 `v0`, 보완이 반영되면 `v1`…). 이 문서가 어느 버전의 입력에서 나왔는지 가리키는 **식별자이지 등급·점수가 아니다.** 재갱신에서 이 문서가 갱신되지 않았으면 `> 기준 입력: v{N} (미반영: v{M})`으로 적는다. **단 그 문서를 실제로 쓰는 회차의 미리보기 안에서만 붙인다** — '변경 없음'으로 승인된 파일을 라벨만 고치려고 열지 않는다(그 배치의 미반영 사실은 R7 종료 보고의 `미갱신 문서와 기준 입력` 줄이 남긴다).

## 1. 사용자 스토리 형식

```
[역할]로서 [목표/행동]하고 싶다, 왜냐하면 [이유/가치]이기 때문이다.
```

- **[역할]**: 구체적 사용자 유형. ("사용자" 같은 뭉뚱그림보다 "신규 가입자", "관리자"처럼 구체화.)
- **[목표/행동]**: 사용자가 하고 싶은 일. *해결책(UI·구현)이 아니라 의도*를 적는다.
- **[이유/가치]**: 왜 그것이 가치 있는지. 이유가 약하면 스토리의 필요성(Valuable)을 재검토한다.

**예시**
- 좋음: "신규 가입자로서 이메일만으로 빠르게 가입하고 싶다, 왜냐하면 결제 전 부담 없이 제품을 둘러보고 싶기 때문이다."
- 나쁨: "가입 폼에 이메일 input 박스를 추가한다." (역할·이유 없음 — 작업 지시이지 스토리가 아님.)

각 스토리에는 고유 ID(예: `US-1`)와, 출처가 된 PRD 요구사항 ID(예: `FR-1`)를 함께 기록한다. → [§5 추적 연결](#5-prd-요구와의-추적-연결) 참조.

---

## 2. 인수조건은 이 문서가 다루지 않는다 (단일 원본)

조건·행동·결과(Given/When/Then) 문장의 **형식·작성법·좋은/나쁜 예는 전부 [`acceptance-criteria-guide.md`](./acceptance-criteria-guide.md)** 에 있고, 문장 자체는 Phase 5가 `acceptance-criteria.md`에 **단독으로** 쓴다.

이 문서(Phase 3)가 하는 일은 그 전 단계다 — **스토리가 인수조건으로 전개 *가능한가*** 를 판단하는 것(좋은 스토리 6가지 기준(INVEST)의 Testable). 전개 가능성은 아래로 가늠한다.

- 스토리의 목표가 **관찰 가능한 행동**인가? ("가입한다" ○ / "만족한다" ✕)
- 성공/실패를 가를 **트리거가 하나로 특정**되는가?
- 예외 흐름 후보가 떠오르는가? → 문장으로 쓰지 말고 **`[인수조건 인계]` 메모**로 남긴다.

전개 가능성이 의심되면 스토리를 **관찰 가능한 목표로 다시 쓴다**(인수조건 문장을 여기서 손보는 것이 아니다).

---

## 3. 좋은 스토리 6가지 기준(INVEST)

좋은 사용자 스토리의 6가지 속성. 각 스토리는 작성 후 아래 점검질문으로 자가점검한다.

| 기준 | 1줄 설명 | 점검질문 |
|------|----------|----------|
| **I** — Independent (독립적) | 다른 스토리에 묶이지 않고 따로 다룰 수 있다 | 이 스토리를 단독으로 진행/검증할 수 있는가? 다른 스토리가 끝나야만 의미가 생기지 않는가? |
| **N** — Negotiable (협상가능) | 세부 구현이 아니라 의도를 담아 조정 여지가 있다 | UI·구현 방식을 못박지 않고 "무엇을·왜"만 담았는가? |
| **V** — Valuable (가치있음) | 사용자/비즈니스에 분명한 가치가 있다 | '왜냐하면' 절이 실제 가치를 설명하는가? 가치가 없으면 왜 만드는가? |
| **E** — Estimable (추정가능) | 규모를 가늠할 만큼 충분히 명확하다 | 모호함 때문에 크기를 추정 못 할 부분은 없는가? |
| **S** — Small (작음) | 한 반복 주기에 들어갈 만큼 작다 | 'and/또는'로 여러 기능이 뭉쳐 있지 않은가? 쪼갤 수 있는가? |
| **T** — Testable (검증가능) | 인수조건으로 전개해 통과/실패를 판정할 수 있다 | Phase 5에서 조건·행동·결과로 전개 *가능한가*(문장은 거기서 쓴다) |

**S와 T가 가장 자주 깨진다**: 접속사로 여러 기능을 묶었으면(S 위반) 분리하고, 전개 가능성이 의심되면(T 위반) **스토리를 관찰 가능한 목표로 다시 쓴다**(인수조건 문장은 Phase 5 소유).

---

## 4. 판정 가능성 — 기준은 인수조건 가이드에 있다

"좋다/만족/잘 된다" 같은 판정 불가 문장을 금지하는 기준과 좋은/나쁜 예 표는 [`acceptance-criteria-guide.md` §4](./acceptance-criteria-guide.md)에 **한 벌만** 둔다(여기 같은 표를 두면 두 교재가 서로 다른 것을 가르치게 된다 — 실제로 임계값 발명 여부에서 갈렸다).

이 단계에서 쓸 것은 한 문장이다 — **스토리의 목표를 읽고 "이걸 통과/실패로 가를 관찰 가능한 결과를 적을 수 있는가?"가 'No'면 스토리를 다시 쓴다.**

## 5. PRD 요구와의 추적 연결

모든 스토리는 **출처 PRD 요구사항(FR/NFR ID)을 명시**한다. 이것이 Phase 4의 **요구↔스토리 추적 매트릭스**의 근간이다.

- 한 PRD 요구사항은 1개 이상의 스토리로 커버된다(완전성: 커버되지 않은 요구가 있으면 누락).
- 한 스토리는 보통 하나의 핵심 요구를 출처로 가진다(여러 요구를 묶으면 INVEST의 S/I 위반 의심).
- 추적 표기 예:

| 스토리 ID | 스토리 요약 | 출처 요구(PRD) | 인수조건 인계 메모 |
|-----------|-------------|----------------|-------------|
| US-1 | 이메일로 가입 | FR-1 | 정상1 / 예외2 |
| US-2 | 가입 응답 속도 | NFR-1 | 1 |

- **빠짐 점검**: PRD의 모든 FR/NFR ID가 이 표의 '출처 요구' 열에 최소 1회 등장하는지 확인한다. 등장하지 않는 요구 = 스토리 누락(또는 PRD에서 Out으로 명시되었어야 함).
- **고아 점검**: 어떤 PRD 요구에도 연결되지 않은 스토리 = 출처 불명. PRD에 요구를 추가하거나 스토리를 제거한다.
- **재갱신에서 `US-n`을 재번호하지 않는다**: 인수조건(`AC-n.m`)이 이 번호를 **주소**로 참조하므로, 스토리가 늘거나 분할·삭제돼도 기존 번호를 다시 매기지 않는다(신설은 최대 번호 뒤에 이어붙이고, 삭제 번호는 재사용하지 않는다).

- [ ] 조건·행동·결과 문장을 `user-stories.md`에 쓰지 않았는가(단일 원본 — Phase 5 소유)?
- [ ] 각 스토리가 INVEST 6기준을 통과하는가(특히 S·T)?
- [ ] 모든 스토리에 출처 PRD 요구 ID가 연결되었는가?
- [ ] PRD의 모든 요구가 최소 1개 스토리로 커버되는가(빠짐 점검)?
