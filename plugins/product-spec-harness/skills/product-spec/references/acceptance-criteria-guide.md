# 인수조건(acceptance-criteria.md) 작성 가이드 — 조건·행동·결과(Given-When-Then)

`user-stories.md`의 각 사용자 스토리를 **"완성을 어떻게 판정하는가"**의 검증 기준으로 쪼개 `acceptance-criteria.md`로 작성하는 가이드다. Phase 5(`acceptance-writer`)가 이 가이드를 따르고, Phase 6(`spec-reviewer` 2차 적대적 검증)이 이 기준으로 검증한다. 모든 산출 문서는 한국어.

> 쉬운 말 1줄 정의: **인수조건(Acceptance Criteria)** = 스토리가 "다 됐다"고 판정할 수 있는, 제3자가 관찰로 참/거짓을 가릴 수 있는 완료 기준.

> **사용자 스토리가 부모, 인수조건이 자식이다.** 스토리는 "누가·무엇을·왜"(의도와 범위)를, 인수조건은 그 스토리를 "어떻게 완성으로 판정하는가"를 담는다. 스토리 1개에 인수조건이 여러 개 붙는다. → 스토리 형식·좋은 스토리 6가지 기준(INVEST)은 [user-story-guide.md](./user-story-guide.md)를 따른다.

> **단일 원본 원칙**: 조건·행동·결과(Given-When-Then) 문장은 **`acceptance-criteria.md`에만** 존재한다. `user-stories.md`는 스토리(누가·무엇을·왜)와 커버 요구까지만 담고 인수조건 문장을 중복해 싣지 않는다. 두 곳에 같은 문장을 두면 한쪽만 고쳐진 채 서로 다른 완료 기준이 두 개가 된다.

> **쉬운 말 우선**: 비개발 기획자가 추가 검색 없이 읽을 수 있어야 한다. 조건·행동·결과(Given/When/Then)·예외 흐름 같은 용어는 처음 등장 시 괄호로 쉬운 한 줄 풀이를 붙이고, 약어보다 풀어 쓴 우리말을 본문에 둔다. 한 번 풀면 반복하지 않는다.

---

## 1. 왜 인수조건이 최종 산출물인가

인수조건은 이 하네스의 **마지막 산출물**이자, 개발·QA가 "무엇을 만들고 무엇을 통과시켜야 하는가"를 추측 없이 판정하는 기준이다.

- **스토리 없이 인수조건만** 있으면 → "왜 만드는지"가 사라진다.
- **인수조건 없이 스토리만** 있으면 → "다 됐다"의 기준이 모호해져 적대적 검증에서 바로 깨진다.
- **착수 전에 쓴다(Shift-Left)** — 인수조건은 코드를 짠 뒤 검사하는 체크리스트가 아니라, 코드를 짜기 *전에* 합의하는 실행 가능한 명세다. 조건·행동·결과(Given-When-Then)로 쓰면 그대로 기획서 + 테스트 시나리오 + 회귀 검증 자산이 된다.

## 2. 인수조건 형식 — 조건·행동·결과(Given / When / Then)

인수조건은 **제3자가 관찰로 참/거짓을 판정**할 수 있어야 한다. 표준 형식은 조건·행동·결과(Given-When-Then)다.

```gherkin
시나리오: <단일 관심사 한 줄 제목>
  Given <전제 상황 / 초기 상태>
  When  <사용자의 행동 / 트리거>
  Then  <관찰 가능한 결과 / 시스템 반응>
```

- **Given**: 시나리오의 출발 상태. ("로그인하지 않은 신규 방문자가 가입 화면에 있다.")
- **When**: 검증 대상이 되는 단일 행동/트리거. ("유효한 이메일과 비밀번호를 입력하고 '가입'을 누른다.")
- **Then**: 관찰 가능한 결과. ("온보딩 화면으로 이동하고, 환영 이메일이 1통 발송된다.")

> 쉬운 말 1줄 정의: **조건·행동·결과(Given-When-Then)** = "어떤 상황에서 / 무엇을 하면 / 무엇이 보인다"로 끊어 적는 검사 기준. Gherkin 문법이라고도 부른다.

**단일 관심사(single concern) 원칙**: 인수조건 1개 = 검증 대상(관심사) 1개. 하나의 트리거(When)가 일으키는 **한 관심사**를 검증하되, 같은 관심사의 **분리 불가한 다중 관찰점**은 한 Then에 둘 수 있다(예: "이미 가입된 이메일 거부" 관심사 = 메시지 표시 + 가입 미진행 + 입력값 미초기화 — 모두 한 거부 동작의 관찰점). 단, **서로 다른 관심사·트리거**(예: 정상 가입 성공 vs 이미 가입된 이메일 거부)는 `그리고(And)`로 묶지 말고 시나리오를 쪼갠다 — 통과/실패가 한 관심사 단위로 갈리게.

**예시 (스토리 US-1 "이메일로 가입", 출처 FR-1)**

```gherkin
시나리오: 유효한 이메일로 가입 성공 (정상)
  Given 로그인하지 않은 방문자가 가입 화면에 있고
  When  미사용 이메일과 8자 이상 비밀번호를 입력하고 '가입'을 누르면
  Then  온보딩 화면으로 이동하고, 해당 이메일로 인증 메일이 1통 발송된다.

시나리오: 이미 가입된 이메일 (예외)
  Given 이미 가입된 이메일이 존재하고
  When  같은 이메일로 가입을 시도하면
  Then  '이미 가입된 이메일입니다' 메시지가 표시되고, 가입은 진행되지 않으며, 입력값은 초기화되지 않는다.
```

## 3. 흐름 커버리지 — 정상 경로만으로는 미완성

정상 흐름(happy path)만 있는 인수조건은 **미완성**으로 본다. 스토리마다 아래 흐름 중 해당되는 것을 빠짐없이 시나리오로 덮는다.

| 흐름 | 쉬운 말 | 점검 질문 |
| --- | --- | --- |
| 정상(happy) | 기대대로 동작 | 기대 입력 → 기대 결과가 명시됐는가? |
| 경계(edge) | 끝값·한계 | 최소/최대, 0개/1개/N개, 동시 요청, 중복 제출은? |
| 에러(error) | 실패 반응 | 외부 연동 실패·검증 실패·응답 지연 시 사용자에게 무엇을 보여주나? |
| 빈 상태(empty) | 데이터 없음 | 목록 0건일 때 화면·문구·다음 행동(CTA)은? |
| 권한(authz) | 누가 보나 | 비로그인·권한 없음·세션 만료 시 차단인가 리다이렉트인가? |
| 상태 전이(state) | 이미 끝난 일 다시 | 완료된 항목 재처리, 취소 후 재신청, 중복 클릭은? |

> 쉬운 말 1줄 정의: **예외 흐름(negative path)** = 정상 흐름이 아닌 모든 흐름(경계·에러·빈·권한·상태 전이). 버그는 대부분 여기서 샌다.

각 스토리의 인수조건 묶음 끝에 어떤 흐름을 덮었는지 1줄로 표기한다. 예: `(흐름 커버: 정상 · 경계(중복 제출) · 에러(네트워크) — 빈/권한/상태 전이 해당 없음)`. 해당 없으면 "해당 없음 — (사유)"로 명시해 *의도된 제외*임을 드러낸다(누락과 구분).

**흐름을 채우려고 정책을 지어내지 않는다.** 예외 흐름은 원본 기획안에 거의 없다. 규칙이 입력에 없으면 그럴듯한 문장으로 메우지 말고 `[확인필요]`로 남긴다 — 지어낸 "중복 시 로그인 화면으로 유도한다" 같은 문장은 합의된 적 없는 제품 정책이 되어 개발까지 그대로 내려간다.

## 4. 좋은 vs 나쁜 인수조건 (관찰 가능 vs 판정 불가)

인수조건은 "좋다 / 만족 / 잘 된다 / 직관적이다" 같은 **판정 불가 문장을 금지**한다. 서로 다른 두 사람이 같은 화면·로그를 보면 통과/실패에 동일하게 합의해야 한다.

| 나쁜 예 (모호·판정 불가) | 좋은 예 (관찰 가능) |
| --- | --- |
| "가입이 잘 된다" | "Then 가입 완료 후 온보딩 화면으로 이동한다" |
| "에러를 적절히 처리한다" | "Then '이미 가입된 이메일입니다' 메시지가 표시되고, 폼은 초기화되지 않는다" |
| "성능이 충분하다" | "Then 가입 요청 응답이 p95 기준 [확인필요]ms 이내로 반환된다" |
| "사용자가 만족한다" | "Then 가입 완료 화면에 사용자 이름이 표시된다" |
| "보안이 안전하다" | "Then 비밀번호는 응답·로그·화면 어디에도 평문으로 노출되지 않는다" |

**판정 체크**: Then을 읽고 "두 사람이 같은 화면/로그를 보면 통과/실패에 동일하게 합의하는가?"가 'No'면 다시 쓴다. 수치 임계값을 모르면 임의로 지어내지 말고 `[확인필요]`로 표시해 기획자 확인 항목으로 돌린다.

## 5. 스토리 ↔ 인수조건 추적

인수조건은 반드시 **출처 스토리(US ID)를 명시**한다. 이것이 Phase 6(2차 적대적 검증)의 **스토리↔인수조건 추적 표**의 근간이다.

- 한 스토리는 **1개 이상**의 인수조건으로 덮인다(인수조건 없는 스토리 = 완료 판정 불가 = 미완성).
- 한 인수조건은 정확히 하나의 스토리를 출처로 가진다(여러 스토리에 걸치면 스토리 분리를 의심).

추적 표기 예:

| 스토리 ID | 인수조건 ID | 흐름 | 출처 요구(PRD.md) |
| --- | --- | --- | --- |
| US-1 | AC-1.1 / AC-1.2 / AC-1.3 | 정상 / 예외 / 에러 | FR-1 |
| US-2 | AC-2.1 | 정상(성능) | NFR-1 |

- **빠짐 점검**: `user-stories.md`의 모든 스토리 ID가 이 표에 최소 1회 등장하는가? 등장하지 않는 스토리 = 인수조건 누락.
- **고아 점검**: 어떤 스토리에도 연결되지 않은 인수조건 = 출처 불명. 스토리를 추가하거나 인수조건을 제거한다.

> **범위 NOTE**: 인수조건은 이후 테스트 시나리오의 출처가 되지만(인수조건 1개 → 테스트 1개 이상), 테스트 작성·실행은 이 하네스의 범위 밖이다. 이 절의 추적은 스토리↔인수조건 한 층위만 다룬다.

## 6. 누락 시나리오 마이닝 (2차 적대적 검증용 체크리스트)

작성을 마친 뒤(그리고 Phase 6 검증에서) "이 인수조건만 보고 만들면 빠지는 게 없나?"를 **정상 외 5흐름**으로 능동적으로 캔다(§3 흐름 커버리지와 동일한 축). 발견한 누락은 조건·행동·결과(Given-When-Then)로 바로 옮길 수 있는 제안 형태로 적는다.

- **경계(edge)** — 최소/최대값, 0개 / 1개 / N개, 동시 요청, 중복 제출.
- **에러(error)** — 외부 연동 실패·응답 지연·부분 실패·재시도 실패, 검증 실패 시 사용자 피드백.
- **빈 상태(empty)** — 데이터 0건일 때 화면·문구·다음 행동(CTA).
- **권한(authz)** — 비로그인·권한 없음·세션 만료, 역할별 노출 차이, 내 자원 vs 남의 자원 접근.
- **상태 전이(state)** — 완료 항목 재처리, 취소 후 재신청, 뒤로 가기 후 재제출, 중복 클릭.

> 이 5흐름은 §3 흐름 커버리지 표(정상 + 5흐름)에서 정상을 뺀 예외 흐름과 같고, Phase 6 `spec-reviewer`(2차)·`acceptance-writer` 추적 표가 쓰는 동일한 축이다(권한 없음·세션 만료는 권한, 검증 실패는 에러, 중복 요청은 경계/상태 전이로 분류). 작성 단계에서 미리 자가 점검하면 2차에서 깨질 일이 줄어든다.

**마이닝으로 찾은 누락도 발명 금지가 우선한다.** "이 흐름이 비어 있다"를 지적하는 것과 "이 흐름의 정책은 이것이다"를 써넣는 것은 다르다. 전자는 이 단계의 일이고, 후자는 기획자가 답할 일이다.

- [ ] 각 인수조건이 단일 관심사인가(`그리고`로 서로 다른 관심사가 묶이지 않았는가)?
- [ ] 각 스토리가 정상 + 해당되는 예외(경계/에러/빈/권한/상태 전이) 흐름을 덮는가(§3)? 해당 없는 흐름은 사유와 함께 명시했는가?
- [ ] 모든 인수조건에 출처 스토리(US ID)가 연결됐는가?
- [ ] `user-stories.md`의 모든 스토리가 최소 1개 인수조건으로 덮였는가(빠짐 점검)?
- [ ] 수치 임계값·정책을 임의로 지어내지 않고, 미정은 `[확인필요]`로 표시했는가?
- [ ] 조건·행동·결과 문장이 `acceptance-criteria.md`에만 있고 `user-stories.md`에 중복되지 않았는가(단일 원본)?
