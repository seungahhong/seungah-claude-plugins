# 기획 설계 점검표 (PRD §4~§6 전개 기준)

Phase 2의 **설계** 단계(`prd-designer`)가 따르는 점검표다. 여기서 말하는 **설계는 기술 설계가 아니라 '기획 설계'** — 합의된 범위(§1~§3)를 **추측 없이 다음 단계로 넘길 수 있는 요구사항 구조**로 전개하는 일이다. 모든 산출 문서는 한국어로 작성한다.

> 쉬운 말 1줄 정의: **기획 설계** = "무엇이 필요한가"를 빠짐없이·중복 없이 적는 일. **기술 설계** = "그것을 어떻게 만드나"를 정하는 일. 이 하네스는 앞의 것만 한다.

---

## 경계 — 이 점검표가 다루지 않는 것

이 하네스는 개발 착수 **전** 제품 기획 산출물에 한정된다. 아래는 **산출 금지**이며, 필요해 보이면 *그것을 필요로 하는 기획 요구*만 적고 `[구현 방법은 개발 단계 결정]`으로 표기한다.

**금지 어휘(등장하면 그 항목은 기술 설계로 넘어간 것이다)** — API 엔드포인트·HTTP 메서드·요청/응답 스키마 / DB 테이블·컬럼·타입·인덱스·마이그레이션 / 컴포넌트 트리·Props·상태관리 라이브러리 / 캐싱·TTL·트랜잭션·락·큐·백오프 / 프레임워크·라이브러리 고유명 / 파일 경로·코드·의사코드 / 배포·CI·브랜치 전략.

경계선 한 줄: **"무엇을, 누구에게, 어떤 조건에서, 얼마나"까지가 기획이고, "그것을 어떻게 구현하나"부터가 기술이다.**

또한 이 단계는 **사용자 스토리·인수조건 문장을 쓰지 않는다**. 설계는 *무엇이 필요한가 목록*이고, `…로서 …하고 싶다` 문장은 Phase 3, `Given-When-Then` 문장은 Phase 5의 몫이다. 설계가 스토리를 미리 써버리면 Phase 3은 형식 변환기로 전락한다.

## 점검 항목 D1~D12

각 항목은 **기획 영역(적을 것)** 과 **기술 영역(적지 않을 것)** 을 대조로 둔다. 해당 없는 항목은 비워두지 말고 `해당 없음 — (사유)`로 명시한다.

| # | 점검 항목 | 기획 영역 — 적을 것 | 기술 영역 — 적지 않을 것 |
| --- | --- | --- | --- |
| **D1** | **요구 원자성·식별자** | 한 문장 = 한 요구. 접속사로 묶인 복합 요구는 분리한다. 각 요구에 `FR-n`/`NFR-n`을 유일하게 부여한다(Phase 3 스토리와 Phase 4 추적이 참조하는 **주소**) | 코드 심볼명·티켓 시스템 ID |
| **D2** | **기능/비기능 분리** | FR = "사용자가 무엇을 할 수 있다". NFR = "얼마나 잘"의 **관찰 가능한 임계값**(응답·가용·접근성·보안 요구 수준) | 그 임계값을 *어떻게* 달성할지(캐시·인덱스·비동기 처리) |
| **D3** | **범위↔요구 쌍방 매핑** | §3 In의 각 항목이 ≥1개 요구로 전개됐는가(공백), 어떤 요구가 In에 없는 범위를 넘어섰는가(이탈). 양방향으로 훑는다 | — |
| **D4** | **사용자 여정 단계 커버** | 진입 → 정상 완료 → 중단/재시도 → 재방문. 각 단계에 대응 요구가 있는가. 단계는 **화면 이름이 아니라 사용자 행동 단위**로 적는다 | 화면 전환·라우팅·네비게이션 구현 |
| **D5** | **상황(상태) 목록과 전이** | 대상(신청·주문·계정 등)이 가질 수 있는 상태 목록, 허용되는 전이, 되돌리기 가능 여부. 각 상태에서 **사용자에게 무엇이 참인가** | 상태관리 라이브러리·리듀서·상태 머신 구현 |
| **D6** | **예외·경계의 제품 규칙** | 최소 5종 — 중복 입력 / 자격 미달 / 권한 없음 / 데이터 없음(빈 상태) / 외부 지연·실패. 각각 **사용자에게 무엇이 보이고 무엇이 허용되는가**. **입력에 규칙이 없으면 지어내지 말고 `해당 없음 — 기획 확인 필요` + `[확인필요]`로 남긴다**(예외 흐름은 원본에 거의 없으므로 여기가 발명이 가장 쉽게 일어나는 자리다) | 에러 코드 체계·재시도 백오프·타임아웃 값 |
| **D7** | **업무 규칙·정책** | 계산식·자격 조건·한도·유효기간·중복 처리·취소/환불·규칙 간 우선순위를 `조건 → 결과` 문장으로. **값이 미정이면 지어내지 말고 `[확인필요]`** | 검증 로직·정규식·알고리즘·연산 복잡도 |
| **D8** | **필요 정보 항목** | 사용자에게 **무엇을 받고 무엇을 보여주는가** — 항목명, 필수/선택, 왜 필요한가, 없으면 어떻게 되는가 | 테이블·컬럼·타입·정규화·저장 방식 |
| **D9** | **권한·역할** | 역할 목록 × 허용 행위(가능/불가/조건부) 표 | 인증 방식·토큰·세션 저장소 |
| **D10** | **의존·선행조건** | 타 팀·외부 계약·법규·운영 준비물을 **담당·완료 기준**과 함께. 언제까지 필요한지 마일스톤과 연결 | 패키지 의존성·빌드 순서 |
| **D11** | **가정↔요구 연결** | §5의 각 가정이 깨졌을 때 흔들리는 `FR-n`/`NFR-n`을 ID로 명시한다. 연결되지 않은 가정은 리스크로 승격하거나 제거한다 | — |
| **D12** | **마일스톤·우선순위 완료 판정** | 각 마일스톤 = 포함 요구 ID + **관찰형 완료 기준**. 무엇을 먼저 내고 무엇을 미루는지, 미룬 것은 §3 Out과 연결 | 스프린트 공수·릴리스 브랜치·배포 파이프라인 |

## 소유 경계 — §1~§3은 고치지 않는다

설계 단계는 **§4~§6만 소유**한다. §1 배경·문제 / §2 목표·성공지표 / §3 범위 In·Out은 계획 단계의 소유이므로 직접 고쳐 쓰지 않는다.

전개 중 "범위를 바꿔야 요구가 성립한다"고 판단되면 **`[계획 변경 요청]` 목록으로 반환**한다(무엇을·왜·어느 요구가 걸리는지 1줄씩). 오케스트레이터가 이를 게이트 요약에 `계획 변경 요청 {r}건`으로 표기하고, 다음 회차의 계획 입력으로 넘기거나(한 번 더) 확정 시 부록 B로 이관한다(조용히 버려지지 않는다). 같은 회차 안에서 계획과 설계가 서로를 고치며 왕복하지 않는다(핑퐁 방지).

## 발명 금지

문제 정의 카드·기획안·사용자 답변에 **없는 수치·임계값·비율·사용자군·정책·기한을 만들어내지 않는다.** 빈칸은 `[확인필요]` 마커로 남기고 질문 후보로 반환한다(직접 질문하지 않는다 — 질문은 오케스트레이터가 한 번에 하나씩 던진다).

빈칸을 그럴듯한 숫자로 메우면 그 숫자가 **합의된 적 없는 스펙**이 되어 이후 단계 전부가 그것을 참으로 취급한다. 빈칸이 있는 정직한 문서가 채워진 추측보다 낫다.

## 산출 형식

- §4·§5·§6 각 섹션의 **패치**(교체할 내용)만 반환하고, PRD 전문을 다시 쓰지 않는다.
- D4·D5·D8·D9의 산출은 §4 하위 블록(**4.1 여정 / 4.2 상황·전이 / 4.3 권한·역할 / 4.4 필요 정보 항목**)에 실어 PRD에 남긴다 — 점검만 하고 문서에 남기지 않으면 Phase 3이 그 재료를 받지 못한다.
- 각 요구 문장 끝에 근거 역참조를 단다 — `← 카드.constraints`, `← §3 In-2`, `← 점검표 #3` 등.
- `[확인필요]` 목록과 `[계획 변경 요청]` 목록을 각각 분리해 첨부한다.
- D1~D12 중 이번 회차에 **점검하지 못한 항목**이 있으면 그 사실을 숨기지 않고 적는다.
