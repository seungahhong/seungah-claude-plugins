# 리스크 티어링 — 어디에 리뷰 주의를 얼마나 쓸 것인가

리뷰 자원은 유한하다. 티어링은 **모든 줄을 똑같이 읽지 않기 위한 배분 장치**다. 품질 점수가 아니다.

> **핵심 규약** — 티어는 **저자가 아니라 리스크**로 정한다(INV-5). "에이전트가 썼다"는 티어를 올리는 근거가 아니다. 다만 [agent-failure-signatures.md](./agent-failure-signatures.md)의 결함 서명 스캔은 **저자와 무관하게 항상** 돌린다.

---

## 1. 3축 관측 (추측 금지 · 모르면 미확인)

각 파일군마다 세 축을 **관측값**으로 적는다. 모르면 `미확인`으로 남기고 되묻는다. 지어낸 값으로 티어를 정하는 것이 이 하네스의 최악 실패다.

### 축 1 · Blast radius — 터지면 무엇이 무너지나

| 등급 | 관측 기준 | 전형 |
|------|-----------|------|
| `없음` | 실패해도 사용자·데이터·매출에 도달하지 않음 | 로컬 스크립트, 실험 코드, 문서 |
| `국소` | 한 화면·한 배치 잡이 깨짐. 사용자가 재시도로 우회 가능 | 내부 도구, 단일 뷰 |
| `광범위` | 다수 사용자 경로가 막힘. 롤백으로 회복 가능 | 공통 컴포넌트, 핵심 API 핸들러 |
| `비가역` | 데이터 손상·유출·금전 이동. 롤백해도 되돌아오지 않음 | 결제, 인증/권한, 개인정보, 파괴적 마이그레이션 |

> 판정 질문: **"이 코드가 조용히 틀린 값을 내면, 사흘 뒤 무엇이 남는가?"** 이 질문에 "아무 일도 없다"라고 답할 수 있으면 `없음`이다.

### 축 2 · Longevity — 얼마나 오래 살 코드인가

| 등급 | 관측 기준 |
|------|-----------|
| `일회성` | 이번에 쓰고 버림. 다음 사람이 읽을 일이 없음 |
| `단기` | 몇 주~몇 달. 곧 대체될 예정이 있음 |
| `장기` | 기한 없이 유지. 다른 코드가 여기에 기대게 됨 |

> 판정 질문: **"6개월 뒤 이 코드를 누가 고치게 되는가?"** "아무도 안 고친다(사라짐)"면 `일회성`이다.
> 관측 힌트 — 같은 파일이 최근 자주 바뀌었다면 앞으로도 바뀔 가능성이 있다(`git log --oneline -20 -- <path>`). 이건 **관측 신호**이지 결함 예측이 아니다.

### 축 3 · Comprehension distribution — 누가 이걸 이해해야 하나

| 등급 | 관측 기준 |
|------|-----------|
| `혼자` | 작성자만 이해하면 됨. 남이 손댈 일이 없음 |
| `팀` | 팀원이 읽고 고칠 수 있어야 함 |
| `조직` | 다른 팀·외부가 의존. 계약이 공개됨 |

> 판정 질문: **"이걸 이해 못 하는 사람이 여기 손대면 무슨 일이 벌어지는가?"**
> 이 축이 높을수록 *정확성*보다 **읽고 이해할 수 있는가·계약이 명시적인가**가 중요해진다.

## 2. 표면 감지 (결정론적 · 후보 제시일 뿐 판정 아님)

경로·파일명 패턴으로 위험 표면을 **후보 감지**한다. 감지 결과는 반드시 사용자 확인을 받는다 — 프로젝트마다 규약이 다르므로 패턴은 틀릴 수 있다.

| 표면 | 감지 힌트(예시 · 프로젝트마다 다름) | 자동 하한 |
|------|--------------------------------------|-----------|
| 인증·권한·세션 | `auth`, `login`, `session`, `token`, `permission`, `role`, `guard`, `middleware` | ≥ T2 |
| 결제·정산 | `payment`, `billing`, `checkout`, `order`, `refund`, `price`, `invoice` | ≥ T3 |
| 개인정보·민감정보 | `user`, `profile`, `pii`, `email`, `phone`, `address`, `ssn`, 암·복호화 모듈 | ≥ T2 |
| 데이터 스키마 변경 | `migration`, `schema`, `alembic`, `prisma/migrations`, `*.sql` | ≥ T3 (비가역이면 T3 고정) |
| 인프라·배포·CI | `Dockerfile`, `*.tf`, `k8s/`, `.github/workflows`, `Jenkinsfile`, 배포 스크립트 | ≥ T2 |
| 의존성 | `package.json`, `lock` 파일, `requirements*.txt`, `go.mod`, `Cargo.toml`, `pom.xml` | ≥ T2 |
| 공개 인터페이스 | `api/`, `routes/`, `handlers/`, `*.proto`, `openapi*`, 패키지 export 진입점 | ≥ T2 |
| LLM 프롬프트 조립 | `prompt`, `llm`, `agent`, `completion`, `chat`, 시스템 프롬프트 문자열 | ≥ T2 (외부 입력이 섞이면 T3) |
| 테스트·품질 게이트 | 테스트 파일, `jest.config`, `.eslintrc`, `tsconfig`, 커버리지 설정, pre-commit 훅 | 티어와 별개로 **항상 정독** |

> **주의** — 표면 감지는 *어디를 더 볼지*를 정하는 데만 쓴다. 감지되지 않았다고 안전한 것이 아니고, 감지됐다고 결함이 있는 것도 아니다.

## 3. 티어 정의

각 축의 관측값과 표면 하한 중 **가장 높은 것**이 그 파일군의 티어다.

| 티어 | 성립 조건 | 뜻 |
|------|-----------|-----|
| **T0** | blast=없음 · longevity=일회성 · 표면 없음 | 자동 검사(린트·타입·테스트)로 충분. 사람은 훑기만 |
| **T1** | blast=국소 이하 · longevity=단기 이하 · 표면 없음 | 렌즈 소수 + 사람 훑기 |
| **T2** | blast=광범위 또는 longevity=장기 또는 comprehension=조직 또는 T2 표면 | 직교 렌즈 다수 + 오라클 감사 + 사람이 diff를 읽음 |
| **T3** | blast=비가역 또는 T3 표면(결제·비가역 마이그레이션·외부 입력이 프롬프트/셸/SQL로 유입) | 위 전부 + **소유자 사람 게이트** + 롤백 계획 확인 |

**규약**
- **한 PR 안에 티어가 섞이는 것이 정상이다.** 파일군별로 티어를 적고, **최고 티어가 그 변경의 사람 게이트를 결정**한다.
- 티어가 섞였는데 최고 티어 파일이 소수라면, **분할(split) 후보**로 표기한다. 낮은 티어 변경이 높은 티어 변경에 묶여 함께 느려지거나, 반대로 함께 대충 통과한다.
- 사용자가 티어를 **낮출 수 있다.** 낮추면 그 결정을 기록하고, **무엇을 안 보게 되는지 한 줄로 경고**한 뒤 따른다. 경고는 하되 수용은 사용자 결정이다.

## 4. 티어별 리뷰 예산 배분

렌즈 코드는 [review-lenses.md](./review-lenses.md) 참조.

| 티어 | 렌즈(기본) | 오라클 감사 | 결정적 센서 | 사람 게이트 | 오탐 예산(보고 상한) |
|------|-----------|-------------|-------------|-------------|----------------------|
| T0 | — | 존재 여부만 | 린트·타입 | 없음 | 3건 |
| T1 | L1, L7 | 강/약/없음 판정 | 린트·타입·해당 테스트 | 없음 | 5건 |
| T2 | L1, L2, L5, L6 + 표면별 1개 | 전수 판정 + 약화 diff 정독 | 전체 테스트·빌드 | **사람이 diff를 읽음** | 8건 |
| T3 | L1~L8 전부 | 전수 판정 + 약화 diff 정독 | 전체 + 마이그레이션 dry-run 가능하면 | **소유자 승인 + 롤백 계획 확인** | 12건 |

**예산 규약**
- 예산 상한을 넘으면 **무엇을 포기했는지 명시**한다. 조용한 절단은 "다 봤다"로 읽힌다.
- 상한은 **보고 상한**이지 탐색 상한이 아니다. 더 찾았으면 "상한 초과 {N}건은 보고하지 않음"이라고 적는다.
- **T3에서 센서를 못 돌리면** 그것 자체를 최상단 UNVERIFIED로 올린다. 못 돌린 채 통과 판정을 내지 않는다.

| src/billing/*.ts | 비가역 | 장기 | 조직 | 결제 | **T3** | 금액 계산 경로 · 롤백해도 청구는 되돌지 않음 |

| # | 무엇을 모르나 | 왜 필요한가 | 누구에게 |
|---|---------------|-------------|----------|
| U1 | scripts/oneoff.py가 실제로 1회용인지 | 맞으면 T0, 아니면 T2 | 저자 |

## 리뷰 예산 배분
| 티어 | 대상 | 렌즈 | 센서 | 사람 게이트 |
|------|------|------|------|-------------|
| T3 | src/billing/*.ts | L1 L2 L3 L4 L5 L6 L7 L8 | 전체 테스트·빌드 | 소유자 승인 |
| T2 | src/api/routes.ts | L1 L2 L5 L6 | 전체 테스트 | diff 정독 |
| T1/T0 | 나머지 | L1 L7 | 린트·타입 | 없음 |

## 6. 안티패턴

- **저자로 티어를 정한다** — INV-5 위반. 리스크로만 정한다.
- **관측하지 않고 티어를 찍는다** — 3축을 적지 않고 "T2 같다"고 하면 그건 인상이다. 축마다 근거 한 줄이 있어야 한다.
- **모르는 축을 그럴듯하게 채운다** — `미확인` + 되물음이 정답이다.
- **PR 전체에 단일 티어를 붙인다** — 파일군마다 다르다. 단일 티어는 과잉 리뷰나 과소 리뷰 둘 중 하나를 낳는다.
- **티어를 품질 점수로 읽는다** — 티어는 "얼마나 위험한 자리인가"이지 "코드가 얼마나 나쁜가"가 아니다. T3 코드가 훌륭할 수 있고 T0 코드가 엉망일 수 있다.
- **예산을 조용히 줄인다** — 포기한 항목을 적지 않으면 리포트가 커버리지를 과장한다.
