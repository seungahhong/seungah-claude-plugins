# 리뷰 렌즈 카탈로그 — 겹치지 않게 나눠 보기

한 리뷰어가 전부를 보면 실제로는 **한 가지 관점으로만** 본다. 렌즈는 주의를 강제로 분산시키는 장치다.

> **왜 나누는가** — 실측상 서로 다른 리뷰어의 발견은 거의 겹치지 않는다. 같은 모델을 여러 번 돌려도 공통 발견은 소수다([evidence.md](./evidence.md) §2). 즉 **한 번 훑은 결과는 표본 하나**이지 리뷰가 아니다.
>
> **동시에 정직해야 할 것** — 다중 표본·다중 렌즈는 재현율을 올리지만 **정밀도 문제를 해결하지 못한다**(evidence.md §2). 그래서 렌즈 뒤에는 반드시 반증 단계가 붙는다.

---

## 사용 규약

- **한 `lens-reviewer` 호출 = 한 렌즈.** 맡은 렌즈 밖의 발견을 내지 않는다. 다른 렌즈의 영역이 보이면 "L{n} 영역" 한 줄로만 남긴다.
- 렌즈 배정은 [risk-tiering.md](./risk-tiering.md) §4의 티어별 표를 따른다.
- 각 발견은 **파일:라인 · 무엇이 잘못됐나 · 어떤 조건에서 드러나나** 셋을 모두 포함한다. 하나라도 못 쓰면 **발견을 내지 않는다**.
- 각 렌즈는 마지막에 **"이 렌즈가 못 보는 것"** 을 보고한다. 이게 Phase 4의 잔여 위험이 된다.

## L1 · 정확성·로직

| | |
|---|---|
| **무엇을 보나** | 이 코드가 의도한 값을 내는가. 경계·예외 입력에서 무너지지 않는가 |
| **전형 결함** | off-by-one, 경계값(0·빈·최대), null/undefined 경로, 부호·단위 혼동, 부동소수 비교, 타임존·DST, 조건 우선순위, 에러를 삼키는 catch, 조기 반환 누락, 반복 중 변형 |
| **확인 방법** | 입력 공간을 경계로 나눠 각 구획에서 결과를 따라간다. "이 값이 0이면?" "빈 배열이면?" "실패하면?"을 각 분기에 묻는다 |
| **못 보는 것** | 여러 요청·여러 프로세스에 걸친 문제(L3), 계약 호환성(L2), 성능(L6) |

## L2 · 계약·호환

| | |
|---|---|
| **무엇을 보나** | 밖에서 이 코드에 기대던 것이 여전히 성립하는가 |
| **전형 결함** | 공개 시그니처 변경(파라미터·반환·예외), 직렬화/응답 스키마 변경, 이벤트 페이로드 변경, 기본값 변경, 열거값 추가/제거, 마이그레이션과 코드의 배포 순서 의존, 옵셔널→필수 전환 |
| **확인 방법** | 변경된 공개 지점마다 **호출자를 찾는다**. 저장소 안 호출자와 저장소 밖 소비자(다른 서비스·클라이언트)를 구분한다. 구버전과 신버전이 **동시에** 떠 있는 순간을 상상한다 |
| **못 보는 것** | 내부 구현의 정확성(L1), 런타임 자원(L3) |

## L3 · 상태·동시성·자원

| | |
|---|---|
| **무엇을 보나** | 시간·순서·공유 상태가 개입할 때 무너지는가 |
| **전형 결함** | 경합(read-modify-write), 재진입, 트랜잭션 경계 밖 부작용, 커넥션/파일/리스너 누수, 무한 재시도, 멱등성 없는 재시도, 캐시 무효화 누락, 전역·모듈 수준 가변 상태, 순서 의존 초기화 |
| **확인 방법** | "두 번 동시에 실행되면?" "중간에 실패하면?" "같은 요청이 두 번 오면?"을 각 부작용 지점에 묻는다 |
| **못 보는 것** | 단일 실행 경로의 값 오류(L1), 보안 경계(L4) |

## L4 · 보안·신뢰 경계

| | |
|---|---|
| **무엇을 보나** | 신뢰할 수 없는 입력이 어디까지 들어오고 무엇을 할 수 있는가 |
| **전형 결함** | 인증/인가 누락·우회, 권한 검사 위치 오류(클라이언트에만), 주입(SQL·셸·경로·템플릿·**LLM 프롬프트**), 역직렬화, SSRF, 시크릿 노출·로그 유출, 과도한 권한 부여, 검증을 신뢰 경계 안쪽에서만 수행 |
| **확인 방법** | 외부 입력의 **출발점부터 종착점까지** 따라간다. 종착점이 인터프리터(셸·SQL·템플릿·LLM)면 그 경로를 전부 적는다. "이 값을 공격자가 정한다면?"을 묻는다 |
| **못 보는 것** | 논리 오류(L1), 성능(L6). 그리고 **정적 읽기로는 실제 악용 가능성을 증명할 수 없다** — 재현 경로를 쓸 수 없으면 PLAUSIBLE에 머문다 |

## L5 · 테스트 오라클

| | |
|---|---|
| **무엇을 보나** | 이 테스트들이 **무엇을 고정하는가**. 초록인데 버그가 통과할 수 있는가 |
| **전형 결함** | 단언 없는 실행, 구현을 되뇌는 기대값, 스냅샷 맹신, 모킹한 값을 다시 단언(순환), 행복 경로만, 에러 경로 미검증, 플래키를 재시도로 덮음, 커버리지는 높으나 단언은 없음 |
| **확인 방법** | 각 테스트에 **"구현을 일부러 틀리게 바꾸면 빨개지는가"** 를 묻는다. 아니오면 그 테스트는 통과를 보증하지 않는다 |
| **못 보는 것** | 테스트가 아예 없는 영역의 결함(그건 "오라클 없음"으로 보고), **가시 테스트를 전부 통과시키는 국소 구현**(evidence.md §3 — 조합·end-to-end 관점이 필요하며 이 렌즈만으로는 부족하다) |

## L6 · 통합·운영

| | |
|---|---|
| **무엇을 보나** | 실제 환경에 나갔을 때 무슨 일이 벌어지는가 |
| **전형 결함** | 설정·환경변수 누락, 마이그레이션 순서·롤백 불가, 실패 시 사용자에게 보이는 것, 관측성 부재(무슨 일이 났는지 알 방법 없음), 타임아웃·재시도·백오프 부재, N+1·불필요한 라운드트립, 대용량에서 메모리 급증, 외부 의존 장애 시 동작 |
| **확인 방법** | "이게 새벽 3시에 실패하면 누가 무엇을 보고 무엇을 하는가"를 따라간다. 배포 순간(구/신 공존)과 롤백 순간을 상상한다 |
| **못 보는 것** | 코드 내부 정확성(L1), 계약 세부(L2) |

## L7 · 응집·중복·규약

| | |
|---|---|
| **무엇을 보나** | 이 변경이 저장소의 기존 자산·관용구와 어긋나는가 |
| **전형 결함** | 이미 있는 유틸의 재구현, 프로젝트 관용구 이탈, 레이어 경계 위반(UI가 DB를 직접), 죽은 코드·미사용 export, 이름과 동작 불일치, 한 함수가 서로 다른 이유로 바뀌게 됨, 무관한 변경 혼입 |
| **확인 방법** | 새로 추가된 것마다 **"이미 있는가"** 를 저장소에서 검색한다. 주변 파일 2~3개를 열어 관용구를 확인한다 |
| **못 보는 것** | 동작 오류(L1). **이 렌즈의 발견은 대체로 `수정 권고` 이하다** — 스타일 선호를 차단으로 올리지 않는다 |

## L8 · 요구 정합

| | |
|---|---|
| **무엇을 보나** | 이 변경이 **요청된 것을 하는가**. 요청되지 않은 것을 하지는 않는가 |
| **전형 결함** | 요구의 일부만 구현하고 나머지 조용히 누락, 요청 없는 동작·의존성·설정 추가, 문제를 우회(원인 대신 증상 처리), 명세와 다른 해석, 범위를 넘어선 리팩터 |
| **확인 방법** | Phase 0의 목적 진술과 diff를 **양방향**으로 대조한다. 요구 → 구현(빠진 것), 구현 → 요구(왜 있는지 설명 안 되는 것) |
| **못 보는 것** | 목적 진술이 없으면 **이 렌즈는 판정 불가**다. 그 사실 자체를 발견으로 보고한다 |

## 렌즈 산출 형식

```markdown
## L{n} · {렌즈명} — 후보 발견
| # | 파일:라인 | 무엇이 잘못됐나 | 어떤 조건에서 드러나나 | 근거(코드 인용) |
|---|-----------|-----------------|------------------------|------------------|
| L1-1 | src/billing/discount.ts:44 | 할인율 합산 시 상한을 적용하지 않음 | 쿠폰 2개 이상이 겹치고 합이 100%를 넘을 때 | `total * (1 - sum)` — sum 클램프 없음 |

## 이 렌즈가 못 본 것
- 동시 요청 시 할인 중복 적용 여부는 L3 영역 — 여기서는 판정하지 않음
- 실제 쿠폰 정책 문서를 확인하지 못함 → 상한 100%가 맞는지 UNVERIFIED
```

## 안티패턴

- **렌즈를 넘나든다** — 다양성이 사라진다. 다른 렌즈 영역은 한 줄 언급만.
- **"개선하면 좋을 것 같다"로 발견을 만든다** — 조건 없이 쓴 발견은 반증 단계에서 전량 탈락한다. 세 요소(위치·무엇·조건)를 못 쓰면 내지 않는다.
- **발견 개수를 늘리려 한다** — 재현율을 올리면 노이즈가 더 빨리 는다(evidence.md §2). "이 렌즈에서 발견 없음"은 정상 결과다.
- **코드를 고친다** — 렌즈 리뷰어는 읽기만 한다(INV-1).
- **PR 본문의 설명을 근거로 인용한다** — 근거는 코드다(INV-2·INV-3).
- **못 보는 것을 적지 않는다** — 그러면 리포트가 커버리지를 과장한다.
