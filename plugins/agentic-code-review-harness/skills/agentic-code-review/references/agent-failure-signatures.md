# 결함 서명 · 증거 감사 — 저자의 주장이 아니라 diff를 본다

이 문서는 Phase 2 `evidence-auditor`의 절차서다. 핵심 태도는 하나다.

> **"통과했습니다"는 근거가 아니다.** 직접 돌린 센서와 직접 읽은 diff만 확인이다(INV-3).

**서명 스캔은 저자와 무관하게 항상 돌린다.** 사람도 붙여넣는다. 아래 목록은 *에이전트가 흔히 남기는 흔적*이지 *에이전트만 남기는 흔적*이 아니다.

---

## 1. 읽는 순서 (규약)

```
① 테스트 diff  →  ② 품질 게이트 설정 diff  →  ③ 코드 diff  →  ④ 의존성·인프라 diff
```

**왜 테스트가 먼저인가** — 뒤에 오는 모든 판단이 "테스트가 지켜준다"는 가정에 기대기 때문이다. 그 가정이 깨져 있으면 코드를 읽는 방식 자체가 달라져야 한다. 실측상 에이전트가 쓴 테스트 패치의 대다수는 **동작을 단언하지 않는다**([evidence.md](./evidence.md) §3). 그래서 "테스트가 추가됨"은 신뢰 신호로 쓸 수 없다.

---

## 2. 오라클 강도 판정 (Phase 2의 1급 산출물)

**오라클** = "무엇이 옳은가"를 결정하는 기준. 테스트가 실행만 하고 옳음을 결정하지 않으면 통과는 의미가 없다.

| 강도 | 판정 기준 | 예 |
|------|-----------|-----|
| **강** | 기대 동작을 **독립적으로** 단언한다. 구현을 바꾸면 실패한다 | 명세에서 나온 기대값, 불변식, 성질(property), 왕복(round-trip), 골든 파일 |
| **약** | 단언은 있으나 구현을 그대로 되뇐다. 구현이 틀려도 통과한다 | 구현 결과를 그대로 기대값에 박아둠, `toBeDefined`/`not.toThrow`만, 스냅샷 자동 갱신, 모킹한 값을 다시 단언 |
| **없음** | 실행만 하고 단언이 없다 | 호출만 하고 끝, `expect(true).toBe(true)`, try/catch로 삼킴 |

### 판정 절차

1. 추가·수정된 테스트마다 **어떤 단언이 무엇을 고정하는지** 한 줄로 쓴다. 못 쓰면 `약` 이하다.
2. **"구현을 일부러 틀리게 바꾸면 이 테스트가 빨개지는가?"** 를 각 테스트에 묻는다. 아니오면 `약`이다.
3. **기대값의 출처**를 확인한다. 명세·요구사항에서 왔으면 `강`, 실행 결과를 복사했으면 `약`.
4. 코드 변경이 있는데 대응 테스트가 없으면 `없음`으로 기록한다(테스트 추가 요구는 티어에 따라).

### 오라클 약화 diff 서명

| 서명 | 무엇을 본다 | 탐지 힌트 |
|------|-------------|-----------|
| 테스트 삭제 | 삭제된 테스트 파일·케이스 | `git diff --diff-filter=D --name-only <base>...HEAD`, diff에서 `-` 로 시작하는 `it(`/`test(`/`def test_` |
| 비활성화 | 건너뛰기·집중 실행 마커 추가 | `skip`, `xit`, `xdescribe`, `test.only`, `describe.only`, `@Ignore`, `@pytest.mark.skip`, `t.Skip()` |
| 단언 삭제 | 케이스는 남고 단언만 빠짐 | 테스트 블록 안 `-` 라인에 `expect`/`assert` 포함 |
| 기대값 조정 | 기대값을 실제 출력에 맞춤 | 단언 라인의 리터럴만 바뀐 diff. **이게 가장 위험한 서명이다** — 초록으로 보이지만 버그가 고정됐을 수 있다 |
| 스냅샷 일괄 갱신 | 스냅샷 파일이 대량 변경 | `__snapshots__`, `.snap`, `.approved.` 파일의 대량 diff |
| 관용도 상향 | 실패해도 통과하게 만듦 | 타임아웃 증가, 재시도 추가, 부동소수 허용오차 확대, `toBeCloseTo` 정밀도 하향 |
| 커버리지 임계 하향 | 게이트 자체를 낮춤 | 커버리지 설정의 임계 숫자 감소 |

> **판정 규칙** — 위 서명이 있으면 **자동으로 결함은 아니다.** 정당한 경우(요구사항이 실제로 바뀜, 잘못된 테스트를 고침)가 있다. 판정은 **"변경 근거가 diff나 PR에 있는가"** 로 한다. 근거가 없으면 `되돌림 사유 후보`로 올린다.

## 3. 게이트 완화 서명

| 서명 | 탐지 힌트 |
|------|-----------|
| 린트 규칙 비활성 | `eslint-disable`, `// noqa`, `# type: ignore`, `#pragma warning disable`, 설정 파일의 규칙 off |
| 타입 억제 | `@ts-ignore`, `@ts-nocheck`, `as any`, `any` 도입, `strict` 옵션 하향, `Object` 캐스팅 |
| CI 단계 제거·완화 | 워크플로 파일에서 job/step 삭제, `continue-on-error: true`, 필수 체크 해제, 매트릭스 축소 |
| 훅 우회 | `--no-verify`, pre-commit 설정 삭제, husky 훅 제거 |
| 빌드 경고 무시 | `--force`, `--legacy-peer-deps`, 경고를 에러로 올리던 플래그 제거 |

> 게이트 완화는 **변경의 본문이 아니라 변경의 조건**을 바꾼다. 본문 리뷰에서 놓치기 쉬우므로 별도 스캔한다.

## 4. 결함 서명 카탈로그

### S1 · 의존성

- 새로 추가된 패키지가 **실제로 존재하는지·이름이 정확한지** 확인한다. 존재하지 않거나 유사한 이름의 패키지를 지목하는 사례가 보고된다.
- lock 파일이 함께 갱신되지 않은 추가, 버전 핀 제거(`^`/`*`로 완화), 스크립트(`postinstall`) 추가.
- **확인 방법** — 패키지 레지스트리에서 이름·최근 릴리스·다운로드를 직접 확인. 확인 못 하면 UNVERIFIED로 남기고 되돌림 사유 후보로 올린다.

### S2 · 비밀·설정

- 하드코딩된 키·토큰·비밀번호·엔드포인트, `.env` 커밋, 테스트 픽스처에 실제 자격증명.
- 환경 분기 제거(개발 전용 우회가 프로덕션에도 적용), 디버그 로그·`console`·`print` 잔여, 임시 백도어(`if (userId === 'test')`).

### S3 · 신뢰 경계 유입

- **사용자·외부 입력이 어디로 흘러가는가**를 추적한다: LLM 프롬프트 조립 / 셸 명령 / SQL / 파일 경로 / 역직렬화 / 템플릿 렌더.
- 프롬프트 조립 지점에 외부 텍스트가 들어가면 **그 자체가 T3 표면**이다. 값이 지시문으로 해석될 수 있고, 그 결과는 diff에 보이지 않는다.
- 새 외부 호출·네트워크 송신 추가(무엇이 어디로 나가는지).

### S4 · 되돌리기 어려움

- 비가역 마이그레이션(컬럼/테이블 삭제, 타입 변경, 백필), 데이터 삭제·덮어쓰기.
- 공개 시그니처 변경(파라미터 제거·순서 변경·반환 타입 변경), 직렬화 포맷 변경, 이벤트 스키마 변경.
- **롤백 계획이 있는가**를 확인한다. 없으면 T3에서는 되돌림 사유다.

### S5 · 유령 코드

- 호출되지 않는 새 함수·클래스·파일(추가만 되고 참조 없음).
- 도달 불가 분기, 항상 참/거짓인 조건, `TODO`/`NotImplemented`/`pass` 스텁이 실제 경로에 남음.
- 설정만 추가되고 읽는 곳이 없음, 플래그만 추가되고 분기가 없음.

### S6 · 중복 재구현

- 프로젝트에 **이미 있는** 유틸·헬퍼·클라이언트를 새로 만든 흔적. 이름은 다르고 하는 일은 같다.
- **확인 방법** — 새 함수의 핵심 동작을 키워드로 저장소 전체에서 검색한다. 있으면 "왜 기존 것을 안 썼는지"가 되돌림 질문이다.
- 프로젝트 관용구 이탈(다른 곳은 전부 A 방식인데 여기만 B 방식).

### S7 · 응집도·범위 이탈

- 요청과 무관한 변경 혼입(포맷 대량 변경, 무관한 리팩터, 버전 범프).
- 한 PR이 서로 다른 티어의 변경을 묶고 있음 → **분할 후보**.

### S8 · 명세 이탈

- 변경이 요청된 것을 **하지 않거나**, 요청되지 않은 동작을 **추가**함.
- 요청된 것 중 **일부만** 하고 나머지를 조용히 남김.
- Phase 0에서 목적을 "모름"으로 답했다면 이 항목은 판정 불가이며, **그 사실 자체가 발견**이다.

## 5. 인테이크 바 (되돌릴지 판단하는 최소 조건)

리뷰를 시작하기 전에 저자에게 요구할 수 있는 항목이다. **비어 있으면 되돌림 사유 후보**로 올리되, **충족이 품질을 보증한다고 말하지 않는다**([evidence.md](./evidence.md) §5 — 이 항목들의 효과는 측정된 근거가 없는 실무 관행이다).

| 항목 | 무엇을 요구하나 | 비었을 때의 비용 |
|------|-----------------|------------------|
| 목적 진술 | 이 변경이 무엇을 하기로 되어 있는가 | "요청한 것을 하는가"를 판정할 수 없다(S8 판정 불가) |
| 변경 근거 | 왜 이 방식인가, 무엇을 고려하다 버렸는가 | 리뷰어가 대안 검토를 처음부터 다시 한다 |
| 실행 증거 | 무엇을 어떻게 돌렸고 출력이 무엇인가 | 자기보고만 남는다 → 전부 UNVERIFIED |
| 응집도 | 무관한 변경이 섞이지 않았는가 | 리뷰 주의가 분산되고 티어가 섞인다 |
| 크기 | 한 번에 읽을 수 있는 크기인가 | 큰 diff일수록 후반부가 덜 읽힌다(관행 · 정량 근거는 evidence.md §5) |

## 6. 결정적 센서 실행

가능하면 **직접 돌리고 출력을 인용**한다. 못 돌리면 이유와 함께 UNVERIFIED로 남긴다.

| 센서 | 무엇을 확인하나 | 못 돌릴 때 |
|------|-----------------|------------|
| 테스트 | 현재 오라클 기준으로 깨지는 게 있는가 | "테스트 미실행 — 통과 여부 UNVERIFIED" |
| 타입체크 | 타입 계약이 성립하는가 | 동일 |
| 린트 | 규약 이탈·억제 주석이 있는가 | 동일 |
| 빌드 | 산출물이 만들어지는가 | 동일 |

**규약**
- 센서 출력은 **인용**한다(요약하지 않는다). 요약하면 무엇이 확인됐는지가 뭉개진다.
- **테스트 통과는 "이 테스트들이 잡는 결함이 없다"는 뜻**이다. 오라클이 `약`/`없음`이면 통과의 정보량은 거의 0이다.
- 센서를 돌리는 것과 **코드를 수정하는 것은 다르다.** 센서 실행 중에도 코드를 고치지 않는다(INV-1).

```markdown

| billing.spec.ts:12 `계산 결과` | 세율 적용 후 총액이 명세의 예시값과 일치 | **강** | 기대값이 요구사항 문서에서 옴 · 구현 바꾸면 실패 |

| # | 분류 | 위치 | 관측 | 확인 상태 |
```

## 8. 안티패턴

- **"테스트 추가됨"을 통과 신호로 쓴다** — 무엇을 단언하는지를 봐야 한다.
- **저자의 "전부 통과" 주장을 표에 옮긴다** — 직접 돌린 것만 확인이다(INV-3).
- **서명이 있으면 자동으로 결함이라고 단정한다** — 정당한 경우가 있다. 판정 기준은 **근거의 유무**다.
- **코드 diff부터 읽는다** — 테스트가 먼저다. 순서가 판단을 바꾼다.
- **센서 출력을 요약한다** — 인용해야 무엇이 확인됐는지가 남는다.
- **PR 본문의 설명을 사실로 옮긴다** — 본문은 리뷰 대상이지 근거가 아니다(INV-2).
